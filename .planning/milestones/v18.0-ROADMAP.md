# Milestone v18.0: Projection-Native Frontend Substrate

**Status:** ✅ SHIPPED in-tree (Phase 263 verified 15/15; UAT complete); publish operator-gated
**Phases:** 263 (single-phase milestone)
**Total Plans:** 5

## Overview

`ferro-inertia` was projection-blind — an Inertia page hand-authored its props, so it did not
receive the projection's data, its field schema/meanings/validations, or the set of actions
currently permitted for a record (all of which the visual and MCP surfaces already compute from
the same `ServiceDef`/`ActionDef` declaration and guards). This milestone closes those three
missing derivations once and delivers them Inertia-first: a pure `schema_contract` derivation, a
tenant-scoped data query shaped by the field set, and a `permitted_actions` evaluation — attached
to an Inertia page in one `Inertia::from_projection` call. Writes reuse the existing
`dispatch_write` kernel unchanged. These are missing derivations, not new coupling: the
operability layer is already renderer-independent.

**Anchor spec:** `docs/superpowers/specs/2026-07-27-headless-projection-substrate-design.md`.

**Architectural constraints:** one structural change only (after the refactor, guards are
evaluated in exactly ONE place — `ferro-mcp-server` and `ferro-inertia` both call `framework`'s
`permitted_actions(...)`, no duplicate control surface); no new write path (Inertia forms route
through `dispatch_write(channel="web")`); `SchemaContract` is schema-level and dependency-free
(leaning `ferro-projections`); no new auth model (same-origin session/cookie + CSRF); JSON-UI's
role unchanged (velocity path; this substrate is the customization path). Generic JSON delivery
mode and projection-native JSX component derivation are out of scope (later, separate specs).

## Phases

### Phase 263: Projection-native Inertia substrate

**Goal:** From one `ServiceDef`, derive a custom (Inertia) frontend's
props = `{ schema, data, permitted_actions }` and deliver them to an Inertia page in one
`Inertia::from_projection` call; route that frontend's writes through the existing
channel-agnostic `dispatch_write` kernel; and lift guard-visibility (`permitted_actions`) out of
`ferro-mcp-server` into `framework` so the MCP `tools/list` filter and the Inertia substrate
evaluate guards in exactly one place. **Requirements:** SUBST-01..05. **Plans:** 5/5.

- [x] 263-01: `schema_contract(&ServiceDef)` pure derivation in ferro-projections (SUBST-01)
- [x] 263-02: lift `permitted_actions` into framework; refactor MCP `tools/list` to call it (SUBST-02)
- [x] 263-03: relocate the tenant-scoped data query into `framework::projection_read` (SUBST-03 data core)
- [x] 263-04: `Inertia::from_projection` delivery helper + write reuse via `dispatch_write(channel="web")` (SUBST-03/04)
- [x] 263-05: single-source parity + tenant-scoping + write-parity tests (SUBST-05)

**Success Criteria (all met):**

1. ✅ `schema_contract(&ServiceDef) -> SchemaContract` returns field set / meanings / validations
   / action definitions; snapshot-tested; pure, dependency-free, in `ferro-projections`.
2. ✅ `permitted_actions(service, record, tenant, ctx)` lives in `framework`, called by BOTH
   `ferro-mcp-server` (`tools/list`) and `ferro-inertia` — one guard-evaluation site.
3. ✅ Permitted-actions parity: `permitted_actions(...)` equals the guard-filtered set MCP
   `tools/list` returns for the same record/tenant; a state change changes both identically.
4. ✅ `Inertia::from_projection(...)` loads tenant-scoped data, attaches `SchemaContract` +
   per-record `permitted_actions` as props; helper on the framework-side Inertia facade
   (`framework/src/inertia/projection.rs`) — the operator-approved cycle-safe placement (framework
   already depends on ferro-inertia, mirroring Phase 261's `ferro-bundle`).
5. ✅ Data reads tenant-scoped (cross-tenant ids not found); filter/limit shaping matches the field set.
6. ✅ Write parity: an Inertia `POST /{service}/{action}` reaches the same
   `dispatch_write(channel="web")` kernel MCP reaches — no new write path, no new failure semantics.

## Milestone Summary

**Key Decisions:**

- **One guard-evaluation site**: `permitted_actions` lifted from `ferro-mcp-server` into
  `framework`; MCP `tools/list` and Inertia both call it — no duplicate control surface.
- **`Inertia::from_projection` on the framework-side Inertia facade**, not the pure
  `ferro-projections` crate (cycle-safe; renderer-location intent preserved).
- **No new write path** — Inertia forms reuse `dispatch_write(channel="web")`.
- Generic JSON delivery and projection-native JSX derivation deferred to later specs.

**Technical Debt / Deferred:** generic JSON delivery mode (decoupled SPA / native);
projection-native JSX/React component derivation + design-lint on generated frontends.

**Publish status:** shipped in-tree, not yet published (operator-gated).
