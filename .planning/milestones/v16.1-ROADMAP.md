# Milestone v16.1: ferro-payments — Polymorphic Billable Layer

**Status:** ✅ SHIPPED 2026-06-21

**Total Plans:** 18 (3 + 3 + 5 + 7)
**Consumer-paired with:** gestiscilo Phases 218–223 (tenant booking upfront payment)

## Overview

A new project-agnostic workspace crate `ferro-payments` providing a polymorphic
`PaymentIntent` entity and a `Billable` trait, so consumer apps can take Stripe
payments for any first-class entity without re-implementing the wiring. Reuses the
existing `ferro-stripe` `SyncDispatcher`, `ProcessedEventLog`, `CheckoutBuilder`, and
Connect destination-charge support — no new ferro-stripe surface. Published as
`ferro-payments 0.1.0` (later 0.1.6, independently versioned).

**Source spec:** `docs/superpowers/specs/2026-06-17-ferro-payments-crate-design.md`.
**Consumer companion:** `gestiscilo-it/app:docs/superpowers/specs/2026-06-17-tenant-booking-upfront-payment-design.md`.

## Milestone Summary

**Key Decisions:**

- New crate on the capability axis, project-agnostic (reads `APP_NAME`/`APP_URL`
  conventions), parallel to `ferro-stripe`; no new ferro-stripe surface — reuses
  `SyncDispatcher`, `ProcessedEventLog`, `CheckoutBuilder`, Connect destination charges.
- Polymorphic `(billable_kind, billable_id)` keying with a partial unique index over
  the active statuses, so at most one live intent exists per billable.
- Stripe abstracted behind a local `StripeGateway` seam because `ferro-stripe` exposes
  no injectable client (static facade) — enables offline unit tests with a mock.
- `is_transient` money-safety boundary: `Db`/`Stripe` errors propagate (Stripe retries
  the webhook); all other variants absorb — a transient error inside a consumer's
  `on_paid` must never cause an irreversible refund.
- Auto-refund on loader-None / side-state, deduped by `refund_amount_cents IS NULL`;
  refunds by `payment_intent` (a `checkout.session.completed` carries no charge id).

**Issues Resolved:**

- `stripe::Currency::parse()` lowercase requirement — uppercase `"EUR"` from
  `Billable::currency()` was rejected; fixed by `.to_lowercase()` in
  `ferro-stripe/src/checkout.rs` (surfaced by the live e2e).

**Technical Debt (deferred to 0.1.1):**

- CR-01: `charge_id` never persisted in the production lifecycle, so the public
  `request_refund` manual-refund API is structurally unreachable. Does not affect the
  milestone goal — the reaper auto-refund/reconcile path refunds by
  `payment_intent_id`, which IS persisted.
- WR-01..05 / IN-01..04: webhook idempotency-before-side-effect window, opaque
  unique-violation mapping, reconcile trusting Stripe amount over snapshot,
  vanished-loader stranding a refunded row, `refunds.first()` selection ambiguity,
  discarded Stripe idempotency key, coarse `is_transient`, missing `charge_id` index,
  hardcoded 1h age anchor.

**Deferred-closed sign-offs:** live-webhook auto-refund reach and stuck-refund
recovery — covered by 17 webhook unit tests and in production at gestiscilo; a full
live exercise needs a running consumer HTTP endpoint (out of scope for this library).

**Stats:** `ferro-payments` ≈ 5,963 LOC (src). First commit `44e6d232` (233-01,
2026-06-17); published `ferro-payments 0.1.0`.
