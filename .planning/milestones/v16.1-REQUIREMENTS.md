# Requirements — v16.1 ferro-payments (Polymorphic Billable Layer) [ARCHIVED]

> **Archive note.** Reconstructed at milestone close (2026-08-12) from the ROADMAP
> inline phase details and the phase VERIFICATION reports. v16.1 shipped before the
> milestone-close discipline was applied, and its requirements never lived in the
> working `.planning/REQUIREMENTS.md` (which held v16.3) — they were tracked inline
> in ROADMAP. This file is the milestone-scoped record of that requirement set.

**Milestone goal:** Ship a new project-agnostic workspace crate `ferro-payments`
providing a polymorphic `PaymentIntent` entity and a `Billable` trait, so consumer
apps can take Stripe payments for any first-class entity without re-implementing the
wiring. Reuses the existing `ferro-stripe` `SyncDispatcher`, `ProcessedEventLog`,
`CheckoutBuilder`, and Connect destination-charge support — no new ferro-stripe
surface. First consumer: gestiscilo Phases 218–223 (tenant booking upfront payment),
unblocked by publishing `ferro-payments 0.1.0`.

**Source spec:** `docs/superpowers/specs/2026-06-17-ferro-payments-crate-design.md`.

## Requirements

### Data Model (Phase 233)

- [x] **PAY-POLY-DM-01**: `payment_intents` SeaORM entity keyed on a polymorphic
  `(billable_kind, billable_id)` pair, with a cross-backend migration
  (`m20260617_create_payment_intents`) portable across Postgres + SQLite + MySQL and
  a partial unique index `(billable_kind, billable_id) WHERE status IN ('reserved','paid')`.
- [x] **PAY-POLY-DM-02**: `BillableKind` and `PaymentIntentStatus` enums; crate scaffold
  registered in the workspace and the publish pipeline (Wave 1b).
- [x] **PAY-POLY-DM-03**: lifecycle methods on the model (`create_reserved`, `mark_paid`,
  `mark_released`, `mark_refunded`, `find_active_for`, `find_by_stripe_session`) with
  `GuardedUpdate` no-op semantics, unit-tested against in-memory SQLite.
- [x] **PAY-POLY-DM-04**: supporting indexes for the query paths.

### Service Core (Phase 234)

- [x] **PAY-POLY-SVC-01**: `Billable` trait (kind/id/tenant/amount/currency/description
  + `on_paid`/`on_released`/`on_refunded` hooks).
- [x] **PAY-POLY-SVC-02**: `BillableLoader` trait resolving `(kind, id)` back to a `Billable`.
- [x] **PAY-POLY-SVC-03**: `PaymentService<L: BillableLoader>` with `start_checkout`
  (mints a Stripe Checkout session via `ferro_stripe::CheckoutBuilder`, snapshots
  `application_fee_cents`, attaches the session id).
- [x] **PAY-POLY-SVC-04**: `PaymentService::request_refund` (calls Stripe refund API,
  snapshots `refund_amount_cents`); `PaymentError` enum extended
  (`Stripe`/`Loader`/`AutoRefundTriggered`).
- [x] **PAY-POLY-SVC-05**: local `StripeGateway` trait seam so unit tests inject a
  `MockStripeGateway` and a mocked `BillableLoader` with no `Stripe::init`.

### Webhook Integration (Phase 235)

- [x] **PAY-POLY-WH-01**: `wire_dispatcher` registers exactly three typed-event handlers
  (`OnCheckoutCompleted`, `OnCheckoutExpired`, `OnChargeRefunded`) on the caller's
  `SyncDispatcher`.
- [x] **PAY-POLY-WH-02**: `handle_session_completed` marks paid, attaches
  `payment_intent_id`, dispatches `on_paid`; replay is a no-op (idempotency via
  `ProcessedEventLog`).
- [x] **PAY-POLY-WH-03**: `handle_session_expired` marks released, dispatches
  `on_released`; already-released is a no-op.
- [x] **PAY-POLY-WH-04**: `handle_charge_refunded` finds by `payment_intent`
  (fallback `charge_id`), marks refunded, dispatches `on_refunded`.
- [x] **PAY-POLY-WH-05**: auto-refund fallback for the loader-None and
  billable-already-in-side-state cases, exactly once, via payment-intent refund.
- [x] **PAY-POLY-WH-06**: webhook + reaper interleaved produce exactly one side-effect;
  `GuardedUpdate` prevents double-honor. `is_transient` money-safety boundary:
  `Db`/`Stripe` propagate (Stripe retries), all other variants absorb.

### Reapers + Publish (Phase 236)

- [x] **PAY-POLY-REAP-01**: `ReleaseExpiredPaymentIntents` — single SQL pass over
  `payment_intents WHERE status='reserved' AND expires_at < now()`, dispatches
  `on_released` per row in a transaction.
- [x] **PAY-POLY-REAP-02**: `ReconcileRefundsInFlight` — polls Stripe for
  refund-in-flight intents (> 1h) and reconciles.
- [x] **PAY-POLY-REAP-03**: both as ferro-queue–compatible `Job` structs consumers
  schedule via cron.
- [x] **PAY-POLY-REAP-04**: workspace test bin driving an end-to-end
  (`start_checkout → release_expired`) against ferro-stripe test mode
  (`#[ignore]`-gated); version-bump + publish `ferro-payments 0.1.0` to crates.io.

## Outcomes

- **Validated:** the polymorphic `Billable` layer shipped as published
  `ferro-payments 0.1.0` (later 0.1.6) and is in production use at the first consumer
  (gestiscilo booking upfront payment).
- **Deferred to 0.1.1 (tech debt, non-blocking):** CR-01 (`charge_id` never persisted →
  the public `request_refund` manual path is structurally unreachable; the reaper
  auto-refund/reconcile path refunds by `payment_intent_id`, which IS persisted) plus
  the WR-01..05 / IN-01..04 code-review findings.
- **Deferred-closed:** the two live-webhook sign-offs (live auto-refund reach,
  stuck-refund recovery) — covered by 17 webhook unit tests and in production; a full
  live-webhook exercise needs a running consumer HTTP endpoint, out of scope for this
  library crate.
