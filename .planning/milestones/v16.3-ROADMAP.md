# Milestone v16.3: MCP CRUD Data Surface (Track A)

**Status:** ✅ SHIPPED 2026-06-24 (0.2.80)
**Phases:** 239–243 + 243.1
**Total Plans:** 18 (3 + 4 + 3 + 4 + 3 + 1)

## Overview

A projection that opts in derives a complete, safe, tenant-scoped CRUD interface —
create / read+query / update / soft-delete — as MCP tools with zero hand-written tool
code. Foundational track (highest compression) of the four-track MCP capability program
(A–D).

**Anchor spec:** `docs/superpowers/specs/2026-06-23-projection-crud-data-surface-design.md`.

**Builds on shipped work:**
- v16.0 (231/232) — `derive_transition_plan` + the channel-agnostic `framework::write`
  kernel (`dispatch_write`, `ExecutorFn`, `OverrideFn`, `WriteDispatcher`, idempotency,
  channel-parameterized audit, confirmation, guard re-eval, tenant isolation).
- Phase 212 — `TenantScoped` + `find_for_tenant(id, tenant_id)`.
- Phase 205 — the `tools/call` `CallToolResult::structured` `content[]` envelope.

**Architectural constraint (encoded in every phase goal):** CRUD dispatch **extends** the
`framework::write` kernel via a new `derive_crud_plan` (the CRUD analog of
`derive_transition_plan`). It MUST NOT rebuild the `WriteDispatcher` / override-hook /
idempotency / audit / confirmation machinery — those already exist. Update/delete targeting
reuses `TenantScoped` + `find_for_tenant`. Rebuilding the dispatcher would create the
duplicate write-control surface ferro's conventions forbid.

**Already shipped before the milestone (not re-planned):** CRUD-07 and the CRUD-01
*declaration surface* (`.creatable`/`.updatable`/`.deletable`/`.mcp_write_ability`/`.table`/
`.soft_delete_column` builders + the `ServiceDef::validate()` write-ability fail-fast rule)
landed in `5cb17d60`.

## Phases

### Phase 239: Soft-delete data model + `deleted_at` migration

**Goal:** Establish the soft-delete data substrate every CRUD read/update/delete path
depends on — a nullable `deleted_at` column plus the `field→column` binding — so a deleted
row becomes invisible by construction. `created_at`-on-create and the
tenant-column-as-server-injected contract are fixed at the data layer.
**Requirements:** foundation phase (substrate for CRUD-03 + CRUD-05). **Plans:** 3/3.

- [x] 239-01: additive `deleted_at` migration + orders entity sync
- [x] 239-02: `ServiceDef` resolver accessors + `is_server_injected_field` classifier
- [x] 239-03: dispatch `resolved_table` wiring + `deleted_at IS NULL` predicate + exclusion test

### Phase 240: CRUD input-schema derivation + `list_` query polish

**Goal:** Derive correct, safe MCP input schemas for `create_`/`update_`/`delete_<svc>` from
the existing `field()` declarations (single source of truth) and extend the derived
`list_<svc>` equality filters with range/comparison ops, sort, and pagination.
**Requirements:** CRUD-01, CRUD-02, CRUD-04. **Plans:** 4/4.

- [x] 240-01: `ServiceDef::is_write_excluded_field` shared predicate
- [x] 240-02: `is_range_filter_field` + create/update/delete schema builders + `list_` range/sort schema
- [x] 240-03: CRUD tool emission + NTI envelope + Phase 205 guard extension
- [x] 240-04: `list_` dispatch `__op` filters + sort read execution

### Phase 241: `derive_crud_plan` + wire CRUD verbs into `framework::write`

**Goal:** Add `derive_crud_plan(svc, verb, inputs)` in `ferro-projections` producing a pure,
serializable INSERT/UPDATE/soft-delete plan, and teach the existing `framework::write` kernel
a CRUD verb alongside the transition path — so create/update/soft-delete execute through the
same dispatcher, override registry, idempotency, audit, and confirmation transitions use. The
kernel is extended, never forked.
**Requirements:** CRUD-06, CRUD-03. **Plans:** 3/3.

- [x] 241-01: `CrudPlan`/`CrudVerb`/`TenantColumn` + pure `derive_crud_plan` + 6 tests (ferro-projections)
- [x] 241-02: `execute_crud_plan` + `dispatch_write` CRUD param + confirmation-seam + 8 dispatch tests (framework::write)
- [x] 241-03: replace NTI block with derive→dispatch + structured envelope + delete confirm tools + framing tests (ferro-mcp-server)

### Phase 242: Write authorization, tenant injection & non-disclosure

**Goal:** Make every CRUD write require `read_write` key scope and pass the
`.mcp_write_ability` policy Gate, inject `tenant_id` from context (never an agent input), and
ensure cross-tenant or soft-deleted targets are indistinguishable from "not found". The
shipped `validate()` write-ability fail-fast rule (CRUD-07) is verified here.
**Requirements:** CRUD-05, CRUD-07 (verified). **Plans:** 4/4.

and the visual surface, extend the structured-envelope regression guard to each verb, update
`ferro-mcp` `json_ui_catalog`/`code_templates` and docs.
**Requirements:** integration phase (exercises CRUD-01..07 end-to-end). **Plans:** 3/3.

- [x] 243-01: flip app order projection to CRUD + boot-validate
- [x] 243-02: in-process MCP e2e (create→list→update→delete) + per-verb envelope guard + MCP↔visual parity + confirmation flow
- [x] 243-03: `ferro-mcp` code_templates + generation_context + docs/src CRUD opt-in; full blocking workspace gate

### Phase 243.1: Projection computed/derived fields (decimal insert)

**Goal:** Honor the `writable` flag in CRUD write-input derivation (Gate F: read-only fields
excluded from `create_`/`update_`), and orchestrate server-side recomputation of a derived

`order.total = SUM(line_items.amount)`, recomputed on every line-item write. Surfaced by the
Phase 243 live `:8090/mcp` field test. **Plans:** 1/1.

## Milestone Summary

**Key Decisions:**

- CRUD dispatch **extends** the `framework::write` kernel via `derive_crud_plan` — no second
  dispatcher, no re-encoded transition `match`; the same derived plan drives MCP and the
  visual/form surface (channel the only divergence).
- Soft-delete by `deleted_at` enforced at the data layer (`deleted_at IS NULL` predicate),
  not per-tool; a deleted row is invisible by construction.
- `tenant_id` server-injected and excluded from every write schema; cross-tenant / soft-deleted
  targets are non-disclosing ("not found / denied").
- Write schemas auto-derived from the existing `field()` declarations (single source of truth):
  Identifier/CreatedAt/tenant/Sensitive excluded; `Status` server-set to the SM initial state.

**Technical Debt / Deferred:** dedicated `get_<svc>` single-record tool; per-field
`immutable()`/`read_only()` overrides. (Both listed as Future Requirements.)

**Track context:** Track A of the four-track MCP capability program (B/C/D are future
milestones). Phase 243.1 was a decimal insert (after 243, extending the CRUD integration it
built on; no renumbering of 244–249).
