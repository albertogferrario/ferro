# Scaffolder gap: multi-bin, copy_dirs, runtime_apt

**Source:** gestiscilo-it Phase 75 field test, 2026-04-09
**Reporter:** Field deployment of ferro 0.1.72 against a real multi-bin project
**Related:** Phase 127 (Generated artifact polish), Phase 130 (Invert dep convention)
**Status:** Backlog — propose as new phase

## Summary

`ferro docker:init` and `ferro do:init` in 0.1.72 produce deployment artifacts that are unusable for projects with any of the following characteristics:

1. **Multiple binaries** (e.g. a web server `[[bin]]` plus a background worker `[[bin]]`)
2. **Runtime resource directories** that must be copied into the final image (e.g. `themes/`, `templates/`, `migrations/`)
3. **Non-trivial runtime apt dependencies** (e.g. headless Chromium, image processing libraries, fonts)

Phase 127 made the single-binary case functional end-to-end. This note captures the gap that remains for non-trivial projects.

## Observed behavior (gestiscilo-it on ferro 0.1.72)

Running `ferro docker:init --force` in a project with:
- `[[bin]] gestiscilo` (web server)
- `[[bin]] screenshot-worker` (background worker using headless Chromium)
- `themes/` directory loaded at runtime by `ferro-json-ui`
- Runtime dependency on Chromium + fonts for screenshot generation

produced a Dockerfile with:

1. A **Node.js frontend build stage** — the project has no JS/TS frontend (it's server-rendered via `ferro-json-ui`). The stage is dead code that bloats the image and slows the build.
2. A **single hardcoded binary path** — `/usr/local/bin/gestiscilo-it` (wrong name too — the binary is `gestiscilo`). No detection of additional `[[bin]]` entries; the `screenshot-worker` binary is never built or copied into the runtime image.
3. **No `COPY themes themes`** (or equivalent mechanism for runtime resource directories). The server boots but crashes at first request because `themes/` is missing.
4. **No runtime apt packages** for Chromium / fonts. Even if the worker binary were copied, it would fail at launch because `chromium` is not in the final image.

Running `ferro do:init --force` produced an `.do/app.yaml` with:

1. **Wrong region** — defaults to `nyc` instead of reading the existing file's `region:` value or taking a CLI/env hint.
2. **No workers block** — no `ferro.toml` / `[[bin]]` introspection to emit background workers as DigitalOcean worker services.
3. **Unwanted `health_check`** block added unconditionally.
4. **Empty envs block** — Phase 127's `.env.example`-driven envs logic didn't activate in this case (separate bug to verify).

## Impact

Any project beyond the "single web binary, no runtime assets, no system deps" case must hand-maintain `Dockerfile` and `.do/app.yaml`. This defeats the purpose of the scaffolder — which is to keep deployment artifacts aligned with upstream templates — and creates silent drift risk because the files still carry `# Generated by ferro docker:init` headers.

gestiscilo Phase 75 documented this with a functional-pass / intent-miss verdict and replaced the misleading headers with honest hand-maintained notices (gestiscilo commit `6f6d397`).

## Proposed scope for a ferro phase

A new phase should make the scaffolders project-aware enough to handle the three gaps above. Suggested decomposition:

### 1. Multi-bin detection

- Extend `bin_detect` (introduced in Phase 127-01) to return **all** `[[bin]]` entries, not just the primary.
- Dockerfile template: emit `cargo build --release` once (already done in 127) and then `COPY --from=builder /app/target/release/{bin_name} /usr/local/bin/{bin_name}` for each detected bin.
- `.do/app.yaml` template: emit a `services` entry for the first `[[bin]]` (web) and a `workers` entry for every additional `[[bin]]`, with `run_command: /usr/local/bin/{bin_name}` wired through.
- Optional: allow `[package.metadata.ferro.bins]` in `Cargo.toml` to override the default web/worker classification (e.g., mark a bin as `kind = "cron"` → DO Functions job).

### 2. Runtime resource directories (`copy_dirs`)

- Read a `[package.metadata.ferro.docker]` table from `Cargo.toml`:
  ```toml
  [package.metadata.ferro.docker]
  copy_dirs = ["themes", "templates", "migrations"]
  runtime_apt = ["chromium", "fonts-liberation"]
  ```
- Dockerfile template: emit `COPY {dir} {dir}` for each `copy_dirs` entry in the runtime stage.
- `.dockerignore` template: ensure `copy_dirs` entries are NOT excluded (whitelist style like the `!README.md` pattern from Phase 127).

### 3. Runtime apt packages (`runtime_apt`)

- Same metadata table as above.
- Dockerfile template: emit an `apt-get install` layer in the runtime stage (separate from the builder stage's build-time deps) when `runtime_apt` is non-empty. Use `--no-install-recommends` and clean lists to keep image size down.

### 4. `.do/app.yaml` region and envs robustness

- Read the existing `.do/app.yaml` (if present) and preserve `region`, `name`, and repo binding when running `--force`. Treat them as identity, not scaffolder-owned content.
- Fix the Phase 127 envs-from-`.env.example` path so it actually fires when the file exists. Investigate why gestiscilo saw an empty envs block.
- Drop the unconditional `health_check` block. Make it opt-in via metadata or detect it from the existence of a `/health` route.

### 5. Drift detection

- Once the scaffolder is expressive enough to regenerate real projects byte-identically, add `ferro doctor` check `docker_template_drift` that re-runs the scaffolder in-memory and diffs against the committed Dockerfile / `.do/app.yaml`. Phase 128 was going this direction; this closes the loop.

## Non-goals

- This is NOT about making the scaffolder handle every possible project shape. A handful of extension points (`copy_dirs`, `runtime_apt`, multi-bin) is enough to cover 90% of non-trivial Rust services without inventing a YAML-in-TOML config DSL.
- This is NOT about deprecating hand-maintenance. Projects should always be free to edit the generated files; the goal is to make the initial generation good enough that hand-edits are rare and localized.

## Test case

Use gestiscilo-it as the field test bed. Target state: running `ferro docker:init --force` and `ferro do:init --force` against the current gestiscilo repo produces Dockerfile and `.do/app.yaml` files that are byte-identical to the hand-maintained ones (commit `6f6d397` on gestiscilo `master`). When that holds, gestiscilo Phase 75 can reopen and adopt the scaffolder output for real, and the "Hand-maintained" warning headers can be replaced with honest `# Generated by` headers.
