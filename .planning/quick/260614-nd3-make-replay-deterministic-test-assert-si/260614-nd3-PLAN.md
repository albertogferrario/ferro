# Quick Task 260614-nd3: Strengthen `replay_deterministic` test

## Problem

`ferro-mcp-server/tests/intent_loop.rs::replay_deterministic` (lines 842–916) runs each
fixture through `process_nl_turn` twice and asserts `structuredContent` is byte-identical.
The executor is a **constant** closure (`Ok(json!({ "status": "approved" }))`), so the
equality holds trivially — two constant returns are equal whether or not idempotency replay
actually fires. The test proves nothing about single-execution / replay.

## Fix

Convert the constant executor into a **counting** executor (shared `AtomicUsize`, mirroring
`write_turn` at line 579) and inject an `idempotency_key` into the write fixture's arguments
so run 2 replays the stored result instead of re-executing. Then assert the executor fired
exactly once on the write path.

### Mechanism (verified during research)
- `intent.rs:180-182` builds `call_params` with `"arguments": sel.arguments` (the fixture's
  `recorded_selection.arguments`), which flows into `handle_write_call` → `dispatch_write`.
- `write_dispatch.rs:302-334` reads `inputs.get("idempotency_key")`: on a hit it returns the
  stored result (no executor call); on a miss it executes then stores. An unknown extra key is
  tolerated (length-capped at 128, not schema-rejected).
- Both runs share the same `db` (created per fixture-iteration), so the `mcp_idempotency_keys`
  row persists between run 1 and run 2.
- Read fixture (`list_order`) never reaches the write path → executor count stays 0. Inject the
  key only for the write fixture to avoid passing an unknown filter to the read handler.

## Tasks

### Task 1: Rewrite `replay_deterministic` to assert single-execution

- **files:** `ferro-mcp-server/tests/intent_loop.rs`
- **action:**
  1. Add `Clone` to the `IntentTurnFixture` derive (line ~20) so the fixture can be cloned and
     mutated per iteration.
  2. In `replay_deterministic`, inside the `for fixture in [&f_list, &f_approve]` loop:
     - Clone the fixture to a local `mut fixture`.
     - For the write fixture only (`fixture.expected_tool != "list_order"`), insert
       `"idempotency_key": "replay-determinism-key"` into
       `fixture.recorded_selection["arguments"]` (via `as_object_mut`).
     - Create `let exec_count = Arc::new(AtomicUsize::new(0));` per iteration.
     - Change `make_dispatcher`'s executor from the constant closure to a counting one that
       `count.fetch_add(1, Ordering::SeqCst)` before returning `Ok(json!({ "status": "approved" }))`
       (clone `exec_count` into the closure, as in `write_turn`).
     - Build `provider1`/`provider2` from the mutated `&fixture`.
  3. After the existing `assert_eq!(sc1, sc2, ...)`, add a single-execution assertion:
     `let expected = if fixture.expected_tool == "list_order" { 0 } else { 1 };`
     then `assert_eq!(exec_count.load(Ordering::SeqCst), expected, ...)` with a message stating
     the write path must execute exactly once across two runs (idempotency replay) and the read
     path must never invoke the executor.
- **verify:** `cargo test -p ferro-mcp-server --all-features replay_deterministic`
- **done:** `replay_deterministic` passes; the executor-count assertion is non-trivial (would
  fail if idempotency replay were removed, i.e. count would be 2 on the write path).
