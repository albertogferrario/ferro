DO NOT author a per-name CRUD SQL dispatcher (a `make_crud_dispatcher` with a
`match action_name { "create_order" => INSERT ... }` body). RESEARCH.md Pattern 3 and

VERIFIED FACT (framework/src/write/mod.rs dispatch_write step 4, ~line 765):
```rust
let result = if let Some(plan) = crud_plan {
    execute_crud_plan(plan, tenant_id, db).await?   // framework SQL — app executor BYPASSED
} else {
    (dispatcher.executor)(&action.name, inputs, tenant_id, db).await?  // transition path only

```
When `crud_plan` is `Some(...)`, the framework's generic `execute_crud_plan` does the SQL;
the dispatcher's `executor` closure is NEVER invoked for CRUD verbs. A per-name CRUD SQL
dispatcher would duplicate `execute_crud_plan` and re-create the exact duplicate
write-control surface that Phases 241/242 were built to eliminate (CLAUDE.md conceptual
coherence; milestone single-source principle).

THE CORRECT PATH — reuse the EXISTING dispatcher:
- MCP surface: call `handle_tools_call(...)` with a `create_order`/`update_order`/`delete_order`
  tool call. Internally it routes to the CRUD branch → `derive_crud_plan(svc, verb, args)` →
  `dispatch_write(.., "mcp", .., Some(&plan))` → `execute_crud_plan`. Pass the EXISTING
  `make_test_write_dispatcher(db)` from `mcp_write_dispatch.rs` (it supplies the
  guard_evaluator + a transition executor that is simply unused for CRUD).
- Visual surface: call `dispatch_write(&ActionDef::new("create_order"), &args, tid, db,
  &dispatcher, None /*transition_guard*/, "web", #[cfg(confirmation)] false, Some(&plan))`
  where `plan = derive_crud_plan(svc, CrudVerb::Create, &args)`. Same shipped
  `execute_crud_plan` under the hood — that IS the single-source proof (one derived plan,
  two callers).

If a task appears to need per-name CRUD SQL in the harness, the design is wrong — re-route
through handle_tools_call / dispatch_write(Some(plan)).
