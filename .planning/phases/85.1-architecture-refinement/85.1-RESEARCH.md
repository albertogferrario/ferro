# Phase 85.1: Architecture Refinement - Research

**Researched:** 2026-02-28
**Domain:** schemars JSON Schema + prior art critical analysis + intent derivation architecture
**Confidence:** MIXED (see breakdown)

<research_summary>
## Summary

Three research threads, in order of architectural impact:

**1. The actual innovation: structural intent derivation.** No existing system computes UI intent from structural analysis of a pre-existing data schema. A2UI relies on LLM choice. AG-UI defers to the agent. SAP Fiori requires manual OData annotations. Refine.dev hardcodes CRUD. The W3C MBUI line stalled in 2014. Ferro's IntentGraph — where the intent is DERIVED from ServiceDef structure (field meanings, state machine shape, relationship cardinality) — occupies genuinely unexplored territory. This is the core architectural insight that should drive Phase 87-89 design.

**2. FieldMeaning schema has a real problem.** schemars generates `anyOf` with `const` strings for known variants plus bare `{"type": "string"}` for `Custom(String)`. The catch-all completely shadows the named variants — any string validates. JSON Schema has no concept of ordered evaluation. This is inherent to JSON Schema's set-based semantics (schemars issues #222, #388). Three options: accept it (informational schema), fix it with `schema_with` (maintenance burden), or accept it now and fix later if consumers need strict validation.

**3. SAP Fiori floorplans are a flawed basis for Intent taxonomy.** They assume enterprise ERP patterns (transactional workflows, data-dense screens, OData backends). SAP's own documentation concedes ~30-40% of real requirements escape the taxonomy. Missing from SAP: analytical-first dashboards, timeline/feed views, map-based views, comparison views. The 7-intent mapping from the previous research was mechanical translation without examining fitness for Ferro's agent-driven, general-purpose context.

**Primary recommendation:** Treat Phase 85.1 as the pivot point where v9.0 shifts from "map prior art" to "derive intent from structure." schemars is straightforward to add. The real architectural work is defining the structural heuristics for Phase 89 intent graph generation.
</research_summary>

<architecture_patterns>
## Architecture Patterns

### Pattern 1: Schema as Protocol Contract (not just "nice to have")
**What:** JSON Schema generated from Rust types IS the protocol. Agents read it to understand ServiceDef structure, discover available operations, and generate appropriate UIs.
**Why this matters:** Schema-driven discovery is the established pattern. MCP uses JSON Schema for tool inputs. Google ADK auto-creates tools from OpenAPI schemas. MCP-Zero (June 2025) achieves 98% token reduction via on-demand schema-based tool discovery. Ferro's schema should serve the same role — an agent reads the ServiceDef schema and knows what the service can do.
**Implication:** Schema quality matters. The `FieldMeaning` schema problem (see Pitfall 1) directly impacts agent comprehension.

### Pattern 2: Structural Intent Derivation (the innovation)
**What:** Instead of manually mapping ServiceDef → Intent, DERIVE the appropriate intent from structural analysis of the ServiceDef.
**Why this is novel:** Every existing system punts this decision to either the LLM, the developer, or manual annotations:

| System | Source of UI Intent |
|--------|-------------------|
| A2UI | LLM decides from conversational context |
| AG-UI / CopilotKit | Agent or developer specifies |
| SAP Fiori Elements | OData annotation author specifies |
| Refine.dev Inferencer | Hardcoded CRUD (list/show/create/edit) |
| CHI 2025 paper | User prompt drives LLM to generate schema first |
| MCP Apps | Tool author attaches UI to specific tool |
| W3C MBUI (2012-2014) | Design-time manual specification (research stalled) |

**Ferro's approach:** The ServiceDef schema contains enough structural signals to select intent automatically:

```
Structural Signal                           → Derived Intent
──────────────────────────────────────────────────────────────
Has state machine + approval transitions    → Process (kanban/workflow)
Has state machine + linear progression      → Track (status timeline)
Has Money/Percentage/Score fields           → Summarize (dashboard/KPIs)
Has >5 writable fields                      → Collect (form/wizard)
Has collection operation + filterable       → Browse (list/table)
Has single entity + detail fields           → Focus (detail view)
Has geolocation fields                      → Locate (map view)
Has time-series numeric data                → Analyze (charts)
Default (no strong signal)                  → Focus (safest default)
```

This is the core of Phase 89 — not graph traversal, but heuristic intent selection from schema shape.

### Pattern 3: schemars Derive (mechanical addition)
**What:** Add `JsonSchema` to derive lists on public types. schemars respects all serde attributes.
**Scope:** 7 types: `ServiceDef`, `FieldDef`, `FieldMeaning`, `DataType`, `StateMachine`, `StateDef`, `Transition`. Skip `Error`, `Warning` (internal types).
```rust
#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum DataType {
    String, Integer, Float, Boolean, DateTime, Date, Json, Binary, Uuid, Enum,
}
// Schema: {"enum": ["string", "integer", "float", ...]}
```

### Pattern 4: CAMELEON Mapping — Where Ferro Diverges
**What:** Ferro's pipeline maps to CAMELEON's 4-level model, but diverges in two critical ways:

```
CAMELEON                          Ferro v9.0
──────────────────────────────────────────────
Task & Domain Model          →    ServiceDef (Phase 84-85)
Abstract UI (AUI)            →    IntentGraph (Phase 87-89)
Concrete UI (CUI)            →    Renderer (Phase 90)
Final UI (FUI)               →    RenderOutput (Phase 90)
```

**Divergence 1: Runtime generation.** CAMELEON assumes AUI is designed at design-time by a human. Ferro generates IntentGraph at runtime from ServiceDef structure + current state context. This is the innovation.

**Divergence 2: Agent as consumer.** CAMELEON assumes a human user navigates the FUI. Ferro's primary consumer may be an agent that reads the IntentGraph to decide what to show. The IntentGraph serves both human renderers and agent reasoning.

### Anti-Patterns to Avoid
- **Treating schemars as the main deliverable.** Adding JSON Schema is 2 hours of work. The real Phase 85.1 work is refining the architectural direction for Phases 86-93.
- **Copying SAP vocabulary.** SAP names carry enterprise baggage. Ferro needs its own taxonomy grounded in structural analysis.
- **Static intent mapping tables.** The Phase 87 Intent enum should not be a 1:1 translation of SAP floorplans. It should emerge from the structural signals ServiceDefs actually contain.
- **Over-deriving JsonSchema.** Only on types that are part of the schema contract.
</architecture_patterns>

<critical_analysis>
## Critical Analysis: Why the Previous Research Was Weak

### Problem 1: Treated schemars as the entire phase
The v1 research spent 60% of content on "add derive, it works." That's a mechanical task, not architecture refinement. The research should have been 20% schemars (confirmed it works, noted the FieldMeaning issue) and 80% "how does prior art change our architectural approach."

### Problem 2: Mechanical SAP mapping without fitness analysis
The v1 research mapped SAP floorplans → Ferro intents without asking: "Is this mapping appropriate?" SAP Fiori Elements has known limitations:

- **Transactional bias.** Every floorplan presupposes create/approve/post workflows. Consumer and agent-driven apps have different intents: explore, discover, compare, monitor.
- **Data density over usability.** Fiori optimizes for ERP clerks processing high-volume data. Ferro's targets are more varied.
- **OData coupling.** Fiori's intent selection requires manual OData annotations (`@UI.LineItem`, `@UI.Identification`). This is the opposite of what Ferro needs — Ferro should DERIVE intent, not require it as input.
- **SAP's own escape hatch.** SAP documentation recommends "freestyle SAPUI5" for requirements that don't fit floorplans (~30-40% of real cases).

### Problem 3: Uncritical confidence levels
Everything was marked HIGH confidence. But:
- The 7-intent taxonomy is untested and based on enterprise patterns → should be MEDIUM
- Whether `anyOf` schema for FieldMeaning is acceptable for agent consumption → should be MEDIUM
- The prior art → phase mapping was vocabulary translation, not validated architecture → should be LOW

### Problem 4: Missed the actual innovation
The research validated that Ferro's pipeline "maps to CAMELEON" without identifying WHERE Ferro does something no one else does. The structural intent derivation — computing what UI to show from schema shape — is genuinely novel. Every other system requires manual specification or defers to LLM reasoning. This should have been the centerpiece of the research.
</critical_analysis>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: FieldMeaning Schema Produces Useless Validation (CONFIRMED)
**What goes wrong:** schemars generates this for FieldMeaning:
```json
{
  "anyOf": [
    { "type": "string", "const": "identifier" },
    { "type": "string", "const": "email" },
    { "type": "string", "const": "money" },
    ...
    { "type": "string" }
  ]
}
```
The bare `{"type": "string"}` matches EVERYTHING, including known variants. The const constraints are informational only — completely shadowed by the catch-all. JSON Schema's `anyOf` has no precedence (unlike serde's ordered evaluation).

**This is a known limitation:** schemars issues #222 and #388. The fundamental `anyOf` overlap is inherent to JSON Schema's set-based semantics.

**Impact:** An agent reading this schema can't distinguish known variants from arbitrary custom strings via validation alone. The enum values in the const branches serve as documentation, not constraints.

**Options:**
1. **Accept it (recommended for now).** The schema documents known variants as `const` values. Agents can read these as "preferred values." Strict validation isn't needed at the schema level — serde handles correctness at deserialization time.
2. **`schema_with` override.** Replace the `Custom` branch with `{"type": "string", "not": {"enum": [...]}}`. Maintenance burden — must keep the exclusion list in sync with the enum.
3. **`#[schemars(description = "...")]` on enum.** Add a description documenting that known variants are preferred. Low cost, decent agent comprehension.

**Recommendation:** Option 1 + Option 3. Accept the broad schema, add a description. Revisit only if agent consumers actually mishandle it.

### Pitfall 2: SAP-Derived Intent Taxonomy Doesn't Fit
**What goes wrong:** Blindly mapping SAP floorplans to Ferro intents produces a taxonomy biased toward enterprise ERP patterns.
**Why it happens:** SAP is the most comprehensive prior art, so it's tempting to adopt wholesale.
**How to avoid:** Derive the intent taxonomy from structural signals in ServiceDef, not from SAP vocabulary. Use SAP as ONE input, not THE input. Validate each proposed intent against: "Can a structural signal in ServiceDef trigger this?"
**Warning signs:** An Intent variant that no structural heuristic can select automatically (e.g., `Navigate` — what ServiceDef structure triggers a navigation intent?).

### Pitfall 3: schemars Version Confusion (0.8 vs 1.x)
**What goes wrong:** Using 0.8 API patterns with 1.x crate.
**How to avoid:** `schemars = { version = "1", features = ["derive"] }`. `Schema` is now a wrapper around `serde_json::Value`. `Visitor` replaced with `Transform`.
**Warning signs:** Compilation errors about missing `SchemaObject` or `Visitor` types.

### Pitfall 4: Confusing Schema Contract with Implementation
**What goes wrong:** Adding JsonSchema to internal types (Error, Warning) that aren't part of the protocol.
**How to avoid:** Only derive on data transfer types: ServiceDef, FieldDef, FieldMeaning, DataType, StateMachine, StateDef, Transition. Skip Error, Warning.

### Pitfall 5: Premature Intent Taxonomy Lock-in
**What goes wrong:** Defining the Intent enum in Phase 88 before Phase 89 validates that structural derivation actually works for those intents.
**Why it happens:** Waterfall thinking — define types before testing them.
**How to avoid:** Phase 88 should propose CANDIDATE intents. Phase 89 should validate each candidate against actual ServiceDef structures. Intents that can't be structurally derived should be questioned.
**Warning signs:** An Intent variant that requires manual annotation to select.
</common_pitfalls>

<intent_taxonomy>
## Intent Taxonomy: Proposed Revision

The previous research proposed 7 SAP-derived intents. Here's a revised taxonomy grounded in structural derivation:

### Structurally Derivable Intents

| Intent | Structural Signal | Prior Art Analog |
|--------|-------------------|-----------------|
| `Browse` | Collection operations, filterable fields, list semantics | SAP List Report, Refine list |
| `Focus` | Single entity access, multiple detail fields | SAP Object Page, Refine show |
| `Collect` | Writable fields, form semantics (>3 inputs) | SAP Wizard, Refine create/edit |
| `Process` | State machine with approval/review transitions | SAP Worklist |
| `Summarize` | Money/Percentage/Score fields, aggregatable data | SAP Overview Page, Metabase dashboard |
| `Analyze` | Time-series data, numeric fields with temporal dimension | SAP Analytical List Page |
| `Track` | State machine with linear progression, status field | (no SAP analog — timeline view) |

### Dropped from SAP Mapping

| SAP Floorplan | Why Dropped |
|---------------|------------|
| `Navigate` (Initial Page) | No structural signal can trigger this. It's an app-level concern, not a service-level intent. If needed, it belongs in the router, not in IntentGraph. |

### Candidates Needing Validation (Phase 89)

| Candidate | Structural Signal | Concern |
|-----------|-------------------|---------|
| `Locate` | Geolocation fields (Latitude, Longitude) | Requires FieldMeaning::Latitude/Longitude (not yet in enum). Validate if common enough. |
| `Compare` | Multiple entities of same type with comparable fields | May be a Browse variant rather than a separate intent. |
| `Edit` | Single entity + writable fields | May be a Focus variant with edit mode, not a separate intent. |

### Design Principle
**Every intent must be derivable from structural analysis.** If an intent can't be selected without manual annotation, it doesn't belong in the enum. Manual override should exist (ServiceDef metadata or explicit intent hints), but the default path must be automatic.

This is the principle that separates Ferro from every prior system. SAP requires annotations. A2UI requires agent LLM reasoning. Ferro's IntentGraph computes it from schema shape.
</intent_taxonomy>

<phase_refinement>
## Phase 86-93 Refinement

Based on this research, the phases should be adjusted:

### Phase 86: ActionDef & Relationships (mostly unchanged)
- **Siren actions** → ActionDef structure: name, display_name, inputs[], preconditions, side_effects
- **ActionInput should reuse existing types:** `ActionInput { name: String, data_type: DataType, meaning: Option<FieldMeaning>, required: bool }` — reuse DataType and FieldMeaning, don't invent parallel types
- **FieldDef additions:** `readable: bool`, `writable: bool` (from Hydra SupportedProperty) — needed for Collect vs Focus intent derivation
- **Relationships:** Cardinality (one-to-one, one-to-many, many-to-many) enables cross-service intent derivation

### Phase 87: Relationships (RENAMED from "Service Relationships")
- **Concern:** Original roadmap has Phase 87 as "Service Relationships" separate from Phase 86 "Actions & Preconditions." But the current Phase 86 description says "Actions & Preconditions" only, while the roadmap Phase 87 says "Declare how services relate to each other."
- **Recommendation:** Keep Phase 87 focused on relationships. Relationship cardinality is a structural signal for intent derivation (one-to-many → Browse sub-list, one-to-one → embedded detail).

### Phase 88: Intent Layer (SIGNIFICANT CHANGE)
- **Old approach:** Define Intent enum from SAP mapping
- **New approach:** Define Intent enum from structural derivation analysis
- Intent variants must pass the test: "What structural signal triggers this?"
- Start with the 7 structurally-derivable intents above
- Include `Custom(String)` escape hatch (same pattern as FieldMeaning)
- Add `IntentHint` — optional per-ServiceDef override for when automatic derivation is wrong

### Phase 89: Intent Graph Generation (THE CORE PHASE)
- **Old approach:** Graph generation algorithm connecting ServiceDef to intents
- **New approach:** Structural analysis engine
  - Input: ServiceDef (fields, meanings, state machine, actions, relationships)
  - Analysis: Pattern matching on structural signals
  - Output: Ranked list of applicable intents with confidence scores
  - The "graph" is the set of intents with their derivation rationale
- This is where Ferro's novelty lives. Every other system requires manual specification or LLM reasoning. Ferro computes it.
- **Risk:** Heuristics may not generalize. Phase 93 field test is the validation gate.

### Phase 90: Renderer Trait & JSON-UI Renderer (unchanged)
- Renderer trait maps Intent + ServiceDef → component tree
- A2UI widget catalog vocabulary for component names
- If mapping feels forced, the intent taxonomy needs revision (this is the canary)

### Phase 91: Framework Integration (unchanged)
### Phase 92: MCP Introspection & CLI (unchanged)

### Phase 93: Field Test (ELEVATED IMPORTANCE)
- Must validate structural intent derivation against real ServiceDefs
- Build Order Management, User Management, Analytics Dashboard services
- Test: does the system derive the right intent for each without manual hints?
- If >30% of cases need manual `IntentHint` overrides, the heuristics need rework

### Phase 94: Protocol Documentation (descoped, unchanged)
- Post-93 protocol documentation only, patent dropped

### Structural Intent Derivation (conceptual Phase 89)
```rust
/// Analyze a ServiceDef and return applicable intents ranked by confidence.
fn derive_intents(service: &ServiceDef) -> Vec<(Intent, f32)> {
    let mut intents = Vec::new();

    // State machine signals
    if let Some(sm) = &service.state_machine {
        let has_approval = sm.transitions.iter()
            .any(|t| t.guard.as_deref().map_or(false, |g| g.contains("approv")));
        if has_approval {
            intents.push((Intent::Process, 0.9));
        }
        let is_linear = sm.states.iter().filter(|s| !s.is_final).count() > 2;
        if is_linear && !has_approval {
            intents.push((Intent::Track, 0.8));
        }
    }

    // Field meaning signals
    let meanings: Vec<&FieldMeaning> = service.fields.iter()
        .map(|f| &f.meaning)
        .collect();

    let has_money = meanings.iter().any(|m| matches!(m, FieldMeaning::Money));
    let has_percentage = meanings.iter().any(|m| matches!(m, FieldMeaning::Percentage));
    if has_money || has_percentage {
        intents.push((Intent::Summarize, 0.7));
    }

    // Always offer Browse and Focus as baseline
    intents.push((Intent::Browse, 0.5));
    intents.push((Intent::Focus, 0.5));

    // Writable fields → Collect
    let writable_count = service.fields.iter().filter(|f| f.writable).count();
    if writable_count > 3 {
        intents.push((Intent::Collect, 0.6));
    }

    intents.sort_by(|a, b| b.1.partial_cmp(&a.1).unwrap());
    intents
}
```

<open_questions>
## Open Questions

1. **How accurate can structural intent derivation be?**
   - What we know: Structural signals exist (Money→Summarize, StateMachine→Process). Refine.dev proves field-type inference works for CRUD.
   - What's unclear: Whether the heuristics generalize beyond obvious cases. What's the false-positive rate?
   - Recommendation: Phase 89 must include a validation suite — run derivation against 10+ representative ServiceDefs and measure accuracy. If <70% correct without hints, the approach needs rethinking.
   - Confidence: MEDIUM

2. **Should Intent use confidence scores or hard selection?**
   - What we know: A ServiceDef may match multiple intents (an order service is both Browse-able and Process-able).
   - What's unclear: Whether the consumer wants ranked options or a single recommendation.
   - Recommendation: Return ranked list with scores. Let the consumer (renderer or agent) pick. This avoids the trap of making a wrong binary choice.
   - Confidence: HIGH (ranked > binary is almost always better)

3. **Accept or fix the FieldMeaning schema problem?**
   - What we know: `anyOf` with string catch-all shadows all const constraints. Known schemars limitation.
   - What's unclear: Whether agent consumers actually mishandle this in practice.
   - Recommendation: Accept it for Phase 85.1. Add `#[schemars(description)]` documenting known variants. Revisit if agents demonstrate confusion in Phase 93 field test.
   - Confidence: HIGH (defer to field test)

4. **Should ActionDef inputs reuse FieldDef or introduce a new type?**
   - What we know: Siren uses separate field definitions for actions. Ferro already has FieldDef with DataType+FieldMeaning.
   - What's unclear: Whether action inputs need different metadata than entity fields (e.g., default values, input constraints).
   - Recommendation: Start with reuse (`ActionInput` wrapping or extending `FieldDef`). Split only if a concrete need emerges in Phase 86.
   - Confidence: MEDIUM

5. **Should `readable`/`writable` be booleans or something richer?**
   - What we know: Hydra uses simple booleans. But "writable" might depend on state (e.g., status writable in draft, read-only after submission).
   - What's unclear: Whether state-dependent field visibility belongs in FieldDef or in the state machine.
   - Recommendation: Start with simple booleans. State-dependent visibility is a Phase 89 IntentGraph concern (the graph already has access to current state).
   - Confidence: MEDIUM
</open_questions>
