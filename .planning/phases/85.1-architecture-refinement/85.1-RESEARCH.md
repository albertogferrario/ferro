# Phase 85.1: Architecture Refinement - Research

**Researched:** 2026-02-28
**Domain:** schemars JSON Schema generation + prior art integration for service projection architecture
**Confidence:** HIGH

<research_summary>
## Summary

Researched two domains: (1) the schemars crate for adding JSON Schema generation to ferro-projections types, and (2) how prior art discovered in Phase 94 research maps to upcoming v9.0 phases (86-93).

schemars v1.2.1 is the current stable release. The v0.8→v1.0 rewrite simplified the `Schema` type to a wrapper around `serde_json::Value` (instead of a complex struct hierarchy). All existing serde attributes in ferro-projections (`rename_all`, `skip_serializing_if`, `default`, per-variant `untagged`) are fully compatible with `#[derive(JsonSchema)]`. The `serde_json::Value` type used in `StateDef.metadata` implements `JsonSchema` with an open/any schema (no type constraint), which is correct behavior.

Prior art maps cleanly to v9.0 phases: SAP Fiori floorplans inform Intent taxonomy (Phases 87-88), Siren action format informs ActionDef inputs (Phase 86), Hydra SupportedProperty informs FieldDef rendering hints (Phase 86), A2UI widget catalog informs Renderer component targets (Phases 89-91), and CAMELEON's 4-level abstraction validates the ServiceDef→IntentGraph→Renderer→Output pipeline.

**Primary recommendation:** Add `schemars = { version = "1", features = ["derive"] }` and derive `JsonSchema` on all public types. No code changes needed beyond adding the derive — all existing serde attributes are respected automatically.
</research_summary>

<architecture_patterns>
## Architecture Patterns

### Pattern 1: Derive JsonSchema alongside Serialize/Deserialize
**What:** Add `JsonSchema` to existing derive lists. schemars respects all serde attributes.
**When to use:** All public types in ferro-projections.
**Example:**
```rust
use schemars::JsonSchema;

#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum DataType {
    String,
    Integer,
    // ... schemars generates {"enum": ["string", "integer", ...]}
}
```

### Pattern 2: Untagged enum variant with JsonSchema
**What:** `#[serde(untagged)]` on individual variants works in schemars v1.
**When to use:** `FieldMeaning::Custom(String)` — the untagged fallback variant.
**Example:**
```rust
#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum FieldMeaning {
    Identifier,
    Email,
    Money,
    // ...
    #[serde(untagged)]
    Custom(String),
    // schemars generates: { "anyOf": [{"enum": [...]}, {"type": "string"}] }
}
```

### Pattern 3: Open schema for serde_json::Value
**What:** `serde_json::Value` implements `JsonSchema` with an open/any schema (accepts anything).
**When to use:** `StateDef.metadata: Option<serde_json::Value>` — intentionally untyped.
**Example:**
```rust
// StateDef.metadata schema output:
// { "metadata": {} }  (open schema, any JSON value accepted)
// Combined with skip_serializing_if, it's also removed from "required"
```

### Pattern 4: skip_serializing_if removes from required
**What:** Fields with `#[serde(skip_serializing_if = "Option::is_none")]` are not included in the JSON Schema `required` array.
**When to use:** All `Option<T>` fields in ferro-projections (display_name, description, guard, metadata, etc.)
**Schema effect:**
```json
{
  "properties": { "display_name": {"type": "string"} },
  "required": ["name", "initial_state", "states", "transitions"]
  // display_name NOT in required — correct behavior
}
```

### Pattern 5: Prior Art → Phase Mapping (CAMELEON 4-Level)
**What:** CAMELEON Reference Framework's 4-level abstraction maps to Ferro's pipeline.
**Mapping:**
```
CAMELEON                          Ferro v9.0
─────────────────────────────────────────────
Task & Domain Model          →    ServiceDef (Phase 84-85)
Abstract UI (AUI)            →    IntentGraph (Phase 87-88)
Concrete UI (CUI)            →    Renderer (Phase 89-91)
Final UI (FUI)               →    RenderOutput (Phase 92)
```
**Validation:** Ferro's pipeline follows a well-researched UI generation abstraction model.

### Anti-Patterns to Avoid
- **Hand-writing JSON Schema:** Derive it. Manual schemas drift from types.
- **Using schemars 0.8 patterns:** v1.0 changed `Schema` type and removed `Visitor`. Use `Transform` if custom schema modification is needed.
- **Deriving JsonSchema on Error types:** The `Error` enum uses `thiserror` and is not a data transfer type. Skip it.
- **Deriving JsonSchema on Warning:** Internal validation type, not part of the schema contract. Skip it.
</architecture_patterns>

<dont_hand_roll>
## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON Schema from Rust types | Manual JSON schema construction | schemars `#[derive(JsonSchema)]` | Auto-syncs with struct changes, handles serde attributes |
| Schema validation | Custom validators | Downstream consumers use JSON Schema validators | JSON Schema is a standard; many validators exist |
| Intent taxonomy | Invent categories from scratch | Map from SAP Fiori floorplans + A2UI patterns | 20+ years of UI pattern research exists |
| Action field definitions | Design from scratch | Adapt Siren action field format | Standardized hypermedia action format |

**Key insight:** The prior art research (Phase 94) revealed that Ferro's pipeline maps to CAMELEON, SAP Fiori, Siren, and A2UI — all mature systems. Don't reinvent their taxonomies; adapt them.
</dont_hand_roll>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: schemars version confusion (0.8 vs 1.x)
**What goes wrong:** Using 0.8 API patterns with 1.x crate.
**Why it happens:** Most existing blog posts and examples target 0.8.
**How to avoid:** Use `schemars = { version = "1", features = ["derive"] }`. The `Schema` type in v1 is a wrapper around `serde_json::Value`, not the complex struct from 0.8. `Visitor` was replaced with `Transform`.
**Warning signs:** Compilation errors about missing `SchemaObject` or `Visitor` types.

### Pitfall 2: Untagged variant ordering
**What goes wrong:** serde tries untagged variants in order. If `Custom(String)` is not last, it matches before known variants.
**Why it happens:** `#[serde(untagged)]` on a variant means "try this if nothing else matches."
**How to avoid:** Already handled — `Custom(String)` is the last variant in `FieldMeaning`. Keep it last.
**Warning signs:** Known variants like `Money` deserialize as `Custom("money")` instead.

### Pitfall 3: Over-deriving JsonSchema
**What goes wrong:** Deriving on internal types (Error, Warning) pollutes the schema with implementation details.
**Why it happens:** Mechanical "add derive to everything" approach.
**How to avoid:** Only derive on types that are part of the schema contract: `ServiceDef`, `FieldDef`, `FieldMeaning`, `DataType`, `StateMachine`, `StateDef`, `Transition`. Skip `Error`, `Warning`.
**Warning signs:** Schema output includes error variant descriptions.

### Pitfall 4: Copying prior art too literally
**What goes wrong:** Importing SAP/Siren/Hydra nomenclature directly into Ferro types.
**Why it happens:** Research shows how others solved it; tempting to use their exact terms.
**How to avoid:** Extract the structural patterns, not the names. Ferro has its own vocabulary (ServiceDef, FieldMeaning, Intent). Map concepts, don't copy identifiers.
**Warning signs:** Types named `Floorplan` or `SupportedProperty` in a Ferro crate.
</common_pitfalls>

## State of the Art (2025-2026)

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| schemars 0.8 (SchemaObject struct) | schemars 1.x (Schema wraps serde_json::Value) | 2024 | Simpler API, better serde compat |

## Prior Art → Phase Mapping

Critical output of this research: how Phase 94 discoveries refine Phases 86-93.

### Phase 86: ActionDef & Relationships
- **Siren actions** → ActionDef structure: `name`, `title`, `inputs[]` (typed fields), `preconditions`, `side_effects`
- **Hydra SupportedProperty** → FieldDef hints: `readable`, `writable` booleans for intent resolution
- **Action:** Add `ActionInput { name, data_type, required }` to ActionDef. Add `readable`/`writable` to FieldDef.

### Phase 87: Intent Enum
- **SAP Fiori floorplans** → Intent taxonomy categories:
  - Overview Page → `Dashboard` (KPI aggregation, multi-entity summary)
  - List Report → `Browse` (filterable entity list with search)
  - Worklist → `Process` (action-oriented list, status-driven)
  - Object Page → `Focus` (single entity detail with sections)
  - Wizard → `Create` (multi-step guided entity creation)
  - Analytical List Page → `Analyze` (data visualization, charts)
  - Initial Page → `Navigate` (entry point, routing)
- **Action:** Define Intent enum with these 7 variants (not the SAP names, the Ferro names).

### Phase 88: IntentGraph
- **CAMELEON AUI layer** → IntentGraph is the abstract UI model
- **A2UI adaptive patterns** → Graph edges represent context-dependent intent selection
- **Action:** IntentGraph connects ServiceDef fields/actions/states to Intent variants via edges with conditions.

### Phases 89-91: Renderers
- **A2UI widget catalog** → Renderer component vocabulary:
  - Text, Image, Row, Column, List, Card, Tabs, Modal, TextField, Button, Badge, Table, Form
- **SAP Fiori components** → Layout patterns per intent type
- **CAMELEON CUI→FUI** → Renderer is CUI, output format is FUI
- **Action:** Renderer trait maps Intent+ServiceDef → component tree. Components are data structures, not runtime widgets.

### Phase 92: JSON-UI Renderer
- **Existing ferro JSON-UI** → First concrete renderer implementation
- **Action:** Implement Renderer trait that produces JSON-UI output from IntentGraph.

### Phase 93: Integration
- **Full pipeline validation** → ServiceDef→IntentGraph→Renderer→Output
- **Action:** End-to-end tests, CLI integration, MCP tool for schema introspection.

### Phase 94: Protocol (descoped)
- **Original scope:** Protocol standardization + patent preparation
- **Descoped to:** Post-93 protocol documentation only. Patent dropped per Phase 94 research recommendation (prior art too dense for broad claims).
- **Action:** Update roadmap to reflect descope.

<open_questions>
## Open Questions

1. **Should `preserve_order` feature be enabled?**
   - What we know: Without it, JSON Schema property order is non-deterministic (HashMap). With it, order matches struct field order (IndexMap).
   - What's unclear: Whether schema consumers care about property ordering.
   - Recommendation: Skip for now. Add later if schema diffing or snapshot testing needs it.

2. **Should `readable`/`writable` be added to FieldDef in Phase 85.1 or deferred to Phase 86?**
   - What we know: Hydra SupportedProperty uses these. They inform intent resolution.
   - What's unclear: Whether adding them now (before ActionDef exists) is premature.
   - Recommendation: Defer to Phase 86. Phase 85.1 is about schemars + architecture refinement, not new fields.

3. **How should schemars interact with future `schemars::Transform` needs?**
   - What we know: v1.0 replaced `Visitor` with `Transform` for custom schema modification.
   - What's unclear: Whether any ferro-projections types will need custom schema transforms.
   - Recommendation: Don't add Transform impls now. Derive-only is sufficient. Add transforms only when a concrete need arises.
</open_questions>
