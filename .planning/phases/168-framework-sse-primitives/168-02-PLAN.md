<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application handler → SseEvent serialization | Handler-supplied `event`/`id`/`data` field values are serialized into the SSE wire stream. `event`/`id` are single-line fields; a CR/LF could inject extra SSE fields/events. |
| SseStream (bounded mpsc) → client connection | A held-open streaming connection backed by a bounded channel; a slow client backpressures the sender. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-168-SEC-01 | Tampering (SSE field injection) | `SseEvent::event` / `SseEvent::id` setters | mitigate | Strip `\n`/`\r` from `event` and `id` in the builder setters (`s.replace(['\n','\r'], "")`) so a value cannot inject an extra SSE field/event line. `data` is safe by construction (split into repeated `data:` lines). `retry` is `u64`. A `#[test]` asserts a newline-bearing `event`/`id` yields exactly one field line. Documented in rustdoc. |
| T-168-SEC-02 | Denial of Service (unbounded buffering) | `SseStream` mpsc channel | mitigate | Bounded mpsc channel (default buffer ≈16, D-04). A slow consumer backpressures the sender's `send().await`. Documented: connection-count limits are the application's concern (L1 note). |
| T-168-SEC-03 | Availability (reverse-proxy idle timeout / buffering) | SSE response headers + keep-alive | mitigate | `X-Accel-Buffering: no` header defeats nginx buffering (D-04); 15s `:ping` keep-alive prevents idle-timeout disconnects (D-05). |
| T-168-SEC-04 | Information Disclosure | SSE `data` payload | accept | `data` payload content is the application's responsibility; the primitive does not inspect or redact it. |
</threat_model>
