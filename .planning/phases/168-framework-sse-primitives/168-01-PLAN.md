<objective>
Generalize the framework's response body from the concrete `hyper::Response<Full<Bytes>>`
to `hyper::Response<FerroBody>`, where `FerroBody` is a zero-cost enum admitting both the
existing buffered path (`Full(Full<Bytes>)`) and a future streaming variant
(`Stream(SseStream)`). This is the load-bearing structural change of Phase 168 (D-03).

Purpose: A streaming body type is incapable of whole-body buffering — this is the structural
guarantee that SC#3 ("excluded from CompressionLayer") was meant to protect, reinterpreted for
the real raw-hyper stack (CONTEXT Scope Premise Correction). The SSE types (Plan 02) build on
top of this; without `FerroBody::Stream` there is nowhere for a streaming body to live.

Output: `FerroBody` enum + `http_body::Body` impl, the 17-site `Full<Bytes>` → `FerroBody`
refactor across 6 files, and the buffered-path regression proven green.
</objective>

    ```rust
    use http_body_util::Full;
    use bytes::Bytes;
    use http_body::{Body, Frame, SizeHint};
    use std::pin::Pin;
    use std::task::{Context, Poll};

    pub enum FerroBody {
        Full(Full<Bytes>),
        Stream(crate::http::sse::SseStream),
    }

    impl Body for FerroBody {
        type Data = Bytes;
        type Error = std::convert::Infallible;
        fn poll_frame(mut self: Pin<&mut Self>, cx: &mut Context<'_>)
            -> Poll<Option<Result<Frame<Bytes>, Self::Error>>> {
            match &mut *self {
                FerroBody::Full(b) => Pin::new(b).poll_frame(cx).map_err(|e| match e {}),
                FerroBody::Stream(s) => Pin::new(s).poll_frame(cx),
            }
        }
        fn is_end_stream(&self) -> bool {
            match self { FerroBody::Full(b) => b.is_end_stream(), FerroBody::Stream(s) => s.is_end_stream() }
        }
        fn size_hint(&self) -> SizeHint {
            match self { FerroBody::Full(b) => b.size_hint(), FerroBody::Stream(s) => s.size_hint() }
        }
    }

    impl From<Full<Bytes>> for FerroBody {
        fn from(b: Full<Bytes>) -> Self { FerroBody::Full(b) }
    }
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application handler → framework response pipeline | Handler-constructed response bodies cross into the hyper serve loop. All response bytes here are server-originated (no external input is reflected by FerroBody itself). |
| framework serve loop → TCP/network | The hyper connection writes frames to the client. A streaming body holds the connection open. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-168-01 | Tampering | `FerroBody` response path | accept | FerroBody carries server-originated bytes only; no external/user input is serialized at the body level in this plan. SSE field-injection is handled in Plan 02 where SseEvent serialization lives. |
| T-168-02 | Denial of Service | `FerroBody::Stream` (held-open connection) | accept | The streaming variant keeps a connection open by design (this is the SSE feature). Connection-count limits are the application's concern (documented). Buffer bounding is enforced in Plan 02 (bounded mpsc, buffer ≈16). |
| T-168-03 | Denial of Service | buffered path (`FerroBody::Full`) | accept | No regression: `Full<Bytes>` is the unchanged buffered body; the enum adds no allocation or vtable on the hot path (zero-cost vs BoxBody — RESEARCH anti-pattern note). |
</threat_model>
