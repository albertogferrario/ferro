<objective>
Install the permanent two-layer CI guard (D-08) so a non-compiling scaffold can never ship
silently again. Layer 1 (SCAF-05): a fast, non-ignored, no-network per-PR test that scaffolds and
`cargo build`s against the workspace `ferro` via a `[patch.crates-io]` override, wired into
`ci.yml`. Layer 2 (SCAF-04): the existing cold-cache Dockerfile parameterized by `ARG
FERRO_VERSION`, wired into `publish.yml` as a post-publish gate against the just-published
`ferro-rs`. The local proof of Plan 01 (SCAF-03) is the new test passing.

Purpose: Plan 01 fixed the drift; this plan keeps it fixed. The per-PR layer catches template↔
library API drift on every PR before publish; the release gate catches packaging/Cargo.toml drift
that only manifests after the crate is on crates.io.

Output: `scaffold_builds_against_workspace_ferro` test; parameterized Dockerfile; `scaffold-smoke`
ci.yml job; `post-publish-scaffold-smoke` publish.yml job.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| crates.io published ferro-rs → CI release-gate container | The post-publish job pulls and compiles a freshly published crate inside a Docker container on a CI runner |
| Dockerfile base image (debian:bookworm-slim) → CI build | The release gate builds on an upstream base image |
| generated app source → `cargo build` in CI | The per-PR job and the container compile generated Rust source |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-214-04 | Tampering / Supply chain | `cargo install ferro-cli --version ${FERRO_VERSION} --locked` in the release gate | mitigate | `--locked` pins the exact dependency graph from the published `Cargo.lock`; the version is the just-published one (passed from `check-version.outputs.new_version`), not "latest". The container only runs `cargo build` of a generated app under the CI runner's own privileges; no secrets are mounted into `docker run`. |
| T-214-05 | Tampering / Supply chain | Dockerfile `FROM debian:bookworm-slim` (tag, not digest) | accept | Inherited from the Phase 211 evidence apparatus; the Dockerfile comment already notes digest-pinning as a hardening follow-up (T-211-02). The release gate is a build-smoke check, not a distributed artifact — a compromised base would fail the build, not ship malware. Digest-pinning is tracked, out of scope for this parity phase. |
| T-214-06 | Denial of service | crates.io propagation lag causing the gate to flap/fail spuriously after publish (A4) | mitigate | The Dockerfile `cargo install` is wrapped in a 5×30s retry loop, absorbing the typical <60s propagation window before failing the release gate. |
| T-214-07 | Information disclosure | `docker run` output / CI logs from the generated app build | accept | The generated app build emits only compiler diagnostics; no secrets are injected into the container or the test environment. The per-PR test runs in a tempdir with no credentials. |
| T-214-08 | Elevation of privilege | `.github/workflows/*` edits | mitigate | The automated CI token lacks `workflow` scope, so it CANNOT push these edits — the developer pushes them manually after review (recorded in the SUMMARY). This is a structural guard against unreviewed workflow changes, not a defect. |

All threats are low severity (CI-internal, no untrusted network input, `--locked` supply-chain
pin). No high-severity threat blocks this plan.
</threat_model>
