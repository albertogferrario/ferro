Write the protocol introduction page covering:

1. **Protocol name and version:** "Ferro Projections Protocol, version 0.1.0-draft"

2. **Motivation:** The gap in the 2026 agent protocol stack. A2A handles agent coordination, MCP handles tools, AG-UI handles event transport, A2UI/Open-JSON-UI handle UI specification — but nothing formalizes "given a service definition, derive what user intents exist." This protocol fills that gap.

3. **What this protocol defines:**
   - A schema for describing service capabilities (ServiceDef)
   - Rules for deriving user intents from service structure (IntentGraph)
   - A trait for rendering intents into UI component trees (Renderer)
   - Validation rules for service definitions
   - An extension mechanism for vendor-specific data

4. **What this protocol does NOT define** (explicit non-goals):
   - Transport (use MCP, HTTP, WebSocket, etc.)
   - Authentication or authorization
   - Session management
   - Deployment or hosting
   - Specific UI component libraries (the Renderer is pluggable)

5. **Protocol positioning diagram:** Include the agent protocol stack diagram from the RESEARCH.md showing where Ferro sits between MCP and A2UI/AG-UI.

6. **Audience:** Protocol implementors, framework authors, agent developers, UI renderer authors.

7. **Notational conventions:** State that the spec uses RFC 2119 keywords (MUST, SHOULD, MAY) per BCP 14. Include the standard boilerplate paragraph.

Use scientific, clear language. No marketing. Reference RFC 2119 for conformance language.

**terminology.md** — Define all domain-specific terms used throughout the spec:

Key terms (alphabetical):
- **Action** — A named business operation a service can perform (ActionDef)
- **Confidence Score** — A floating-point value [0.0, 1.0] indicating how strongly a service matches an intent
- **Data Type** — Abstract category for field values (String, Integer, Float, Boolean, DateTime, Date, Json, Binary, Uuid, Enum)
- **Derivation** — The process of analyzing a ServiceDef's structure to produce ranked IntentScores
- **Field Meaning** — Semantic annotation on a field (e.g., Money, Status, Email) driving rendering decisions
- **Guard** — A named boolean precondition for transitions or actions
- **Intent** — A high-level user interaction pattern (Browse, Focus, Collect, Process, Summarize, Analyze, Track)
- **Intent Hint** — An optional manual override for intent derivation (Primary or Exclude)
- **Navigation Hint** — Presentation guidance for relationships (Inline, Link, Tab, Nested, Hidden)
- **Renderer** — A component that transforms a ServiceDef and IntentScores into a UI component tree
- **Render Context** — Runtime parameters for rendering (intent index, current state, display/input mode)
- **Service Definition** — A complete schema describing a business service's fields, actions, guards, relationships, state machine, and intent hints
- **Signal** — A structural feature of a ServiceDef that contributes to intent derivation
- **State Machine** — A lifecycle definition with states, transitions, guards, and effects
- **Transition** — A named event moving a state machine from one state to another

**architecture.md** — Describe the three-layer pipeline:

1. **Pipeline overview:** ServiceDef → derive_intents() → IntentScore[] → Renderer → UI Output

2. **Layer 1: Service Definition (Data Model)**
   - ServiceDef is the protocol's core input type
   - Composed of fields, actions, guards, relationships, state machine, intent hints
   - Schema-only constraint: no closures, no runtime logic, fully serializable
   - JSON Schema generated from Rust types (never hand-written)

3. **Layer 2: Intent Derivation (Analysis)**
   - Five analyzers examine structural signals in ServiceDef
   - Output: ranked list of IntentScores with confidence values
   - Always produces at least one result (default fallback: Focus at 0.5)
   - Signal types are normative (MUST consider). Exact weights are informative (implementation-specific).

4. **Layer 3: Rendering (Output)**
   - Renderer trait accepts ServiceDef + IntentScores + RenderContext
   - Produces framework-independent output (e.g., JSON-UI, A2UI, HTML)
   - RenderMode: Display (read-only) vs Input (form)
   - Pluggable — any output format can implement the Renderer trait

5. **CAMELEON correspondence:** Map the three layers to the W3C CAMELEON Reference Framework (Task/Domain → Abstract UI → Concrete UI → Final UI). Acknowledge prior art explicitly.

6. **Roles:**
   - **Service Author** — Creates ServiceDef definitions
   - **Protocol Consumer** — Reads ServiceDef, derives intents, renders UI
   - **Renderer Implementor** — Implements the Renderer trait for a target format

Include a pipeline diagram (ASCII art) showing data flow between layers.
