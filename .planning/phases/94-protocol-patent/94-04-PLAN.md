Write the intent derivation specification. Read ferro-projections/src/derive.rs for the complete implementation.

**Critical distinction:** Signal types (WHAT each analyzer considers) are NORMATIVE. Exact weights are INFORMATIVE (implementation-specific tuning). The spec defines the analyzers and their signal categories, not the numeric constants.

Structure:

1. **Overview:** derive_intents(service: &ServiceDef) → Vec<IntentScore>. Always returns >= 1 result. Default fallback: Focus at 0.5 if no signals detected.

2. **Analyzer pipeline:** Five analyzers run in sequence, each contributing signals:

   **2a. Field Meaning Analyzer** (MUST implement):
   - MUST examine FieldMeaning variants on non-system fields
   - MUST consider Money/Percentage/Quantity as Summarize signals
   - MUST consider EntityName as Focus/Browse signal
   - MUST consider Status as Track signal
   - MUST consider DateTime + numeric combination as Analyze signal
   - MUST consider Category as Browse signal
   - System fields (Identifier, CreatedAt, UpdatedAt) SHOULD be excluded from analysis
   - Document which FieldMeaning variants map to which intents (the signal mapping)

   **2b. Writability Analyzer** (MUST implement):
   - MUST examine readable/writable ratios across fields
   - Majority writable → Collect signal
   - Majority non-writable → Summarize/Focus signal
   - Write-only fields → strong Collect signal

   **2c. State Machine Analyzer** (MUST implement if StateMachine present):
   - MUST examine guard density (guarded transitions / total transitions) → Process signal
   - MUST examine branching states (states with >1 outgoing transition) → Process signal
   - MUST examine transition triggers → Process signal
   - MUST examine linear progression (each state has exactly 1 outgoing) → Track signal
   - MUST examine final states → Track signal

   **2d. Relationship Analyzer** (MUST implement if relationships present):
   - MUST examine OneToMany/ManyToMany relationships → Browse signal
   - MUST examine OneToOne with Inline navigation → Focus signal
   - MUST examine ManyToOne → Focus signal
   - Multiple relationships → Browse signal

   **2e. Action Analyzer** (MUST implement if actions present):
   - MUST examine transition triggers → Process signal
   - MUST examine input counts → Collect signal
   - MUST examine preconditions → Process signal
   - Simple CRUD actions → Browse signal

3. **Signal aggregation:** Signals from all analyzers are combined. Implementations MAY use any aggregation strategy (sum, weighted average, max, etc.). The reference implementation uses additive scoring.

4. **Baseline signals:** Browse and Focus SHOULD receive small baseline scores to ensure they appear in results when no strong signals override them.

5. **Tie-breaking:** When two intents have equal confidence, implementations MUST use stable ordering: Process(0) > Track(1) > Collect(2) > Browse(3) > Focus(4) > Summarize(5) > Analyze(6) > Custom(7).

6. **IntentHint override:** If ServiceDef includes IntentHint::Primary(intent), that intent MUST be boosted. If IntentHint::Exclude(intent), that intent MUST be removed from results.

Do NOT include exact numeric weights from the Rust implementation — those are tuning parameters, not protocol requirements.

**rendering.md** — Renderer trait and rendering specification:
- Read ferro-projections/src/render/mod.rs and ferro-projections/src/render/json_ui.rs

Structure:
1. **Renderer trait:** `render(service, intents, context) -> Result<Value, Error>`. The trait is the protocol's output contract.
2. **RenderContext:** intent_index (which intent to render), current_state (optional, for state-machine-aware rendering), mode (Display or Input)
3. **RenderMode:** Display (read-only presentation) vs Input (editable form). Every intent SHOULD support both modes.
4. **Output format:** Framework-independent JSON. The exact component vocabulary depends on the renderer implementation (e.g., JSON-UI, A2UI, HTML).
5. **Intent-to-layout mapping (informative):** Document the reference mapping for each intent:
   - Browse → Table/List layout with pagination
   - Focus → Card/Detail layout with description lists
   - Collect → Form layout with typed inputs
   - Process → State display with transition actions
   - Summarize → Metric cards with aggregations
   - Analyze → Table with sortable columns and summary stats
   - Track → Timeline/table with status and date columns
   - Custom → Falls back to Focus (Display) or Collect (Input)
6. **Field rendering (informative):** How FieldMeaning influences component selection (e.g., Money → formatted currency, Email → mailto link, Status → badge)
7. **Relationship rendering (informative):** How NavigationHint maps to UI patterns (Inline → embedded, Tab → tabbed sections, etc.)

Mark the intent-to-layout and field rendering sections as INFORMATIVE (not normative). Different renderers MAY map intents to different UI patterns.

**validation.md** — ServiceDef validation rules:
- Read ferro-projections/src/service.rs validate() method and ferro-projections/src/error.rs

Structure:
1. **Validation entry point:** `ServiceDef::validate() -> Result<Vec<Warning>, Error>`. Errors are fatal. Warnings are structural concerns.
2. **Error variants (MUST reject):**
   - Definition errors (e.g., duplicate field names)
   - Validation errors (e.g., undefined state/guard references)
   - Missing required fields
3. **Warning variants (SHOULD report):**
   - UnreachableState — state not reachable via BFS from initial state
   - DeadEndState — non-final state with no outgoing transitions
   - UnusedGuard — guard defined but never referenced
   - DuplicateRelationship — same target service defined twice
   - ManyToManyWithForeignKey — foreign_key on many-to-many (unusual)
   - ConflictingIntentHints — both Primary and Exclude for same intent
   - MultiplePrimaryIntentHints — more than one Primary hint
   - TransitionTriggerWithoutStateMachine — action has transition_trigger but no state machine defined
4. **BFS reachability:** Validation MUST check reachability from initial_state via BFS traversal
5. **Reference resolution:** All string references (guard names, state names, event names) MUST resolve to defined entities. Undefined references are hard errors.
6. **Cross-subsystem validation:** Validate that guards referenced from transitions exist in the guards pool. Validate that transition_trigger events match transition event names.
