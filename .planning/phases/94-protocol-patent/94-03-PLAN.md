- The data model defines the schema for service projections
- All types are JSON-serializable, transport-agnostic
- JSON Schema files generated from Rust source types (canonical definitions)
- Link to JSON Schema Reference appendix for machine-readable schemas
- Overview of type hierarchy: ServiceDef contains FieldDef[], ActionDef[], GuardDef[], RelationshipDef[], StateMachine?, IntentHint[]

**data-model/service-def.md** — ServiceDef type specification:
- Read ferro-projections/src/service.rs for the exact struct definition
- Document every field: name (required), display_name (optional), fields[], actions[], guards[], relationships[], state_machine (optional), intent_hints[]

- Builder API is implementation detail (informative, not normative)
- ServiceDef is the protocol's root type — all other types compose into it

**data-model/field-def.md** — FieldDef, DataType, and FieldMeaning:
- Read ferro-projections/src/field.rs for exact definitions
- **FieldDef**: name, data_type, meaning, required (default true), is_list (default false), readable (default true), writable (default true)
- **DataType enum**: 10 variants — String, Integer, Float, Boolean, DateTime, Date, Json, Binary, Uuid, Enum. Serialized as snake_case strings.
- **FieldMeaning enum**: 18 known variants + Custom(String) — Identifier, ForeignKey, CreatedAt, UpdatedAt, EntityName, Email, Phone, Url, ImageUrl, Money, Percentage, Quantity, Status, Category, Boolean, FreeText, DateTime, Sensitive. Custom uses untagged serde.
- Document the semantic meaning of each FieldMeaning variant and how it influences rendering (e.g., Money → currency display, Status → badge, Email → mailto link)
- Document infer_meaning() as informative (not normative) — one possible algorithm for auto-detecting meaning from field names
- Include JSON example showing a few fields with different meanings

**data-model/state-machine.md** — StateMachine, StateDef, Transition:
- Read ferro-projections/src/state.rs for exact definitions
- **StateMachine**: name, initial_state, states[], transitions[]. Optional on ServiceDef.
- **StateDef**: name, display_name (optional), is_final (default false), on_enter[] (effects), on_exit[] (effects), metadata (optional JSON value). Note: metadata prevents Eq derive.
- **Transition**: from (state name), event (trigger), to (state name), guard (optional guard name), actions[] (side effects)
- Schema-only constraint: guards are string references, not closures. This is critical for serialization and introspection.
- Document the initial_state MUST reference an existing state name
- Document that transitions reference states and guards by name (string references resolved externally)
- JSON example: order lifecycle with draft → submitted → completed states
- Note: StateMachine is a structural signal for Process and Track intent derivation

**data-model/actions.md** — ActionDef, InputDef, GuardDef:
- Read ferro-projections/src/action.rs for exact definitions
- **ActionDef**: name, display_name (optional), inputs[], preconditions[] (guard names), effects[] (side effect descriptions), transition_trigger (optional event name)
- **InputDef**: name, data_type (DataType), meaning (FieldMeaning), required (default true). Reuses DataType/FieldMeaning — single type vocabulary, no parallel systems.
- **GuardDef**: name, display_name (optional), description (optional). A named boolean condition referenced from transitions and action preconditions.
- Document that guards are a shared pool — same guard can be referenced from both transitions and action preconditions
- Document transition_trigger linking actions to state machine events
- JSON example: submit action with inputs, precondition, and transition trigger

For each type, include: definition, JSON example, normative rules, schema link.

**data-model/relationships.md** — RelationshipDef, Cardinality, NavigationHint:
- Read ferro-projections/src/relationship.rs for exact definitions
- **RelationshipDef**: name, target (service name), cardinality, navigation (NavigationHint), foreign_key (optional)
- **Cardinality enum**: OneToOne, OneToMany, ManyToOne, ManyToMany. Serialized as snake_case.
- **NavigationHint enum**: Inline, Link, Tab, Nested, Hidden. Serialized as snake_case.
- Document that NavigationHint has default values derived from Cardinality (default_navigation() method — informative, not normative)
- Document that cardinality is a structural signal for intent derivation (OneToMany → Browse signal)
- Document two-dimensional design: structural (Cardinality) + presentational (NavigationHint)
- JSON example: order with items (one_to_many, nested) and customer (many_to_one, link)

**data-model/intent.md** — Intent, IntentScore, IntentHint:
- Read ferro-projections/src/intent.rs for exact definitions
- **Intent enum**: 7 structurally-derivable variants + Custom(String):
  - Browse — Exploring collections of entities
  - Focus — Viewing a single entity in detail
  - Collect — Gathering data through forms
  - Process — Advancing entities through workflows
  - Summarize — Presenting aggregated/metric views
  - Analyze — Examining data patterns and trends
  - Track — Monitoring entity status over time
  - Custom(String) — Escape hatch for intents not covered by the standard set
- Custom uses `#[serde(untagged)]` — serialized as plain string, not `{"custom": "..."}`
- **IntentScore**: intent (Intent), confidence (f64 in [0.0, 1.0]), matching_signals (Vec<String>). NOT Eq (f64 confidence).
- **IntentHint**: Primary(Intent) or Exclude(Intent). Externally tagged serde. Optional manual override for derivation.
- Document that each standard intent MUST be derivable from structural signals alone (no manual annotation required)
- Document stable tie-breaking order for equal confidence: Process > Track > Collect > Browse > Focus > Summarize > Analyze > Custom
- JSON examples: IntentScore array from derivation, IntentHint configuration

For each type, include: definition, JSON example, normative rules, schema link.
