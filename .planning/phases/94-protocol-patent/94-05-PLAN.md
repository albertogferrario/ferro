**extensions.md** — Two-tier extension mechanism (modeled after JSON:API):

1. **Vendor extensions (x-* prefix):**
   - Any field prefixed with `x-` MAY appear on ServiceDef, FieldDef, ActionDef, RelationshipDef, StateDef
   - Implementations MUST ignore unrecognized `x-*` fields (forward compatibility)
   - Example: `"x-acme-priority": "high"`

2. **Protocol extensions (URI-namespaced):**
   - The optional `extensions` array on ServiceDef carries formal protocol extensions
   - Each extension has: `uri` (unique identifier), `critical` (boolean — MUST the consumer understand this?), `data` (arbitrary JSON)
   - If `critical: true` and consumer doesn't understand the extension URI, consumer MUST reject the ServiceDef
   - If `critical: false`, consumer MAY ignore the extension
   - Example with audit trail extension

3. **Extension registration:** No central registry. URI uniqueness is the author's responsibility (domain-based).

4. **Future-proofing:** New fields added to types in future protocol versions MUST be optional. Consumers MUST ignore unrecognized fields (beyond x-* handling).

**conformance.md** — Conformance levels:

1. **RFC 2119/BCP 14 reference:** Restate that MUST, SHOULD, MAY keywords are used per RFC 2119.

2. **Conformance levels:**
   - **Level 1 — Schema Conformant:** ServiceDef serialization/deserialization matches JSON Schema. Implementations MUST produce valid JSON per the schema.
   - **Level 2 — Derivation Conformant:** Intent derivation implements all 5 analyzers with the normative signal types. Implementations MUST consider the specified signal categories.
   - **Level 3 — Rendering Conformant:** Renderer implements the Renderer trait contract. Output MUST be valid JSON. Implementations SHOULD support all 7 standard intents + Custom.

3. **Partial conformance:** Implementations MAY be conformant at Level 1 only (e.g., a validation-only tool) or Levels 1+2 (e.g., a derivation engine without rendering).

4. **Test suite reference:** The ferro-projections test suite (309+ tests) serves as the reference implementation's conformance validation. Future protocol versions MAY include a formal conformance test suite.

**security.md** — Security considerations:

1. **Input validation:** Implementations accepting ServiceDef from untrusted sources MUST validate against the JSON Schema before processing. Malformed input MUST be rejected.

2. **String injection:** FieldMeaning::Custom(String) and guard/action names are user-provided strings. Implementations MUST NOT interpret these as code, SQL, HTML, or shell commands. Treat all string values as opaque labels.

3. **Resource consumption:** ServiceDef with very large field/action/state/relationship arrays could be used for resource exhaustion. Implementations SHOULD impose reasonable limits on array sizes.

4. **Sensitive data:** FieldMeaning::Sensitive indicates a field contains sensitive data (passwords, tokens). Renderers MUST NOT display Sensitive fields in plaintext. Implementations SHOULD exclude Sensitive fields from logs and debug output.

5. **Extension security:** Extensions with `critical: true` that are not understood MUST cause rejection, preventing silent bypass of security-relevant extensions.

6. **Transport security:** This protocol does not define transport. Transport security (TLS, authentication) is the responsibility of the transport layer (MCP, HTTP, etc.).

7. **No executable code:** The schema-only constraint (no closures, no runtime logic) is itself a security property. ServiceDef cannot execute arbitrary code — it is pure data.

**related-work.md** — Prior art and related protocols:

1. **W3C CAMELEON Reference Framework (2003):** Four-level abstraction chain (Task/Domain → AUI → CUI → FUI). Ferro's three layers map directly. Key difference: CAMELEON's AUI is tree-based and static; Ferro's IntentGraph is dynamically derived with confidence scores. Cite: Calvary et al., "A Unifying Reference Framework for Multi-Target User Interfaces."

2. **SAP Fiori Elements + OData Annotations:** Production-proven semantic UI generation at massive scale. OData annotations enrich service metadata — functionally identical to FieldMeaning driving renderer decisions. Validates the approach at enterprise scale.

3. **MECANO (Puerta & Eriksson, 1996):** Pioneered semantic enrichment of data models for automatic UI generation. FieldMeaning is this concept realized in a modern framework.

4. **Siren (2012):** Hypermedia type with entities, actions, and links. Inspired ActionDef design (actions with fields/inputs).

5. **A2UI (Google, 2025-2026):** Declarative UI specification for AI agents. Covers "what UI to render" but not "what UI does this service need." Complementary — A2UIRenderer could be an alternative Renderer implementation.

6. **AG-UI (CopilotKit, 2025-2026):** Event-based agent-frontend transport. Covers "how to deliver UI" but not "what to derive." Complementary transport layer.

7. **MCP (Anthropic/LF, 2024-2026):** Tool and context protocol for AI agents. ferro-mcp uses MCP for projection discovery. MCP is the natural introspection transport.

8. **Open-JSON-UI (OpenAI, 2025):** Token-efficient flat JSON for LLM-generated UI. Optimizes for generation; Ferro optimizes for derivation from structure.

9. **json-render (Vercel, 2025):** Catalog-constrained generative UI. Validates the approach of constraining generation to a known component catalog.

Acknowledge that generating UI from data models is not novel (MECANO, 1996). Multi-level abstraction is not novel (CAMELEON, 2003). What is novel is the specific combination of: schema-only constraints + confidence-scored intent derivation from 5 structural analyzers + pluggable rendering in a server-side framework context.
