<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → Pipeline::run | Untrusted tenant-supplied asset bytes (HTML/CSS/JS/images/JSON) enter the pipeline |
| Asset.path → consumer filesystem | `Asset.path` is a logical key; a future consumer might use it as a real path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-187-01 | Denial of Service | Pipeline::run on async executor | mitigate | run() is synchronous (CONTEXT D-08); lib.rs + run() doc-comment instruct callers to wrap in tokio::task::spawn_blocking so a long CPU job never stalls the async executor |
| T-187-02 | Tampering | Pipeline partial output on error | mitigate | run() returns Err on first transform failure and never returns a partial Vec<Asset> (D-17); SC-5 test in all_or_nothing.rs proves it — the consumer's two-phase upload relies on this atomicity |
| T-187-03 | Tampering / path traversal | Asset.path used as filesystem path by a consumer | accept | ferro-assets is in-memory and writes no files; documented in README (Plan 04) that Asset.path is a logical key and consumers MUST sanitize before using it as a real path. No high-severity surface in this crate. |
| T-187-04 | Repudiation | Error context lost | mitigate | Error::Transform carries transform + path + cause so the caller can report which file failed in which stage (D-17) |
</threat_model>
