<objective>
Thread the offload handle key from the caller through the enqueue→claim boundary to the
worker, mirroring the EXISTING `tenant_id: Option<i64>` propagation path EXACTLY (D-05,
246-PATTERNS.md maps every file:line). The key travels as job-execution metadata (a nullable
`jobs` table column), NEVER as a payload field — the serializable payload stays exactly the
method's parameters (preserves 244 D-11).

Changes (all within `ferro-queue`, no new dependency):
1. `Offloadable::offload()` — mint the `HandleKey` before dispatch and carry it via a new
   `PendingDispatch::with_handle_key()` (D-04). The caller's `OffloadHandle` holds the same key.
2. `PendingDispatch` — new `handle_key: Option<String>` field + `with_handle_key()` builder.
3. `jobs` table — nullable `handle_key TEXT` column, AMENDED into the existing
   `CreateJobsTable` migration (pre-production, no migration chain, per planning guidance).
4. `enqueue` — new `handle_key: Option<&str>` param; both INSERT arms write the column.
5. `claim` SELECT (both Postgres + SQLite arms) — add `handle_key` to the column list.
6. `JobRow` — new `handle_key: Option<String>` field; `parse_job_row` reads it back.

Purpose: SC#2 (retrieve-by-handle) requires the caller's key and the worker's write key to be
identical. This plan establishes that seam. Plan 04 consumes `job_row.handle_key` in the
worker to persist the result.

Output: the four `ferro-queue` files modified; the `tenant_id` propagation path fully
mirrored for `handle_key`. This plan is file-disjoint from Plans 01 and 02 (Wave 1 parallel).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| enqueue → jobs table → claim | The handle key is written to and read from an internal `jobs` table row. No external/untrusted input reaches this path — the key is a server-minted UUID v4. |
| claimed row → worker | `parse_job_row` deserializes the row (including `handle_key`) for the worker. The row is internal DB state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-246-tamper | Tampering | `parse_job_row` / enqueue SQL | mitigate | The `jobs` table is internal; `enqueue`/`claim` use `Statement::from_sql_and_values` (parameterized) — no string-concatenated SQL, no external input reaches `parse_job_row`. Existing mitigation preserved by mirroring the `tenant_id` binding idiom exactly. |
| T-246-01 | Elevation of privilege (V4) | handle key on the job row | accept | UUID v4 handle key is 122 bits of entropy, non-guessable. It is server-minted, never client-supplied. Not access-controlled in 246 (in-process); Phase 247 adds subscriber authz. |
| T-246-schema | Tampering / availability | amended `CreateJobsTable` migration | accept | Column is nullable — existing rows and non-offload jobs get NULL (backward-compatible). Pre-production, so amending the original migration is safe (no chain, no double-apply of an `up()`). |
