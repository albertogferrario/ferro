<objective>
Build the visual/form transition-write surface — the unbuilt half of EXEC-05. The projection renderer
already EMITS `POST /{service}/{action}` action-button URLs (`ferro-json-ui/src/projection/builder.rs:685,309`),
but NO handler receives them (verified: the visual write path does not exist — research §Q2). This plan
adds the HTTP handler that receives that POST, resolves the `ServiceDef`+`ActionDef` from the same
`exposed_services()` the MCP path uses, authenticates the tenant from auth context, derives the transition
plan, and calls the SAME `framework::write::dispatch_write` kernel relocated in Plan 01 — with the audit
channel set to `"web"`, not `"mcp"`.

CRITICAL: This is framing only, NOT a second executor. The handler does NOT re-derive a plan format, does
NOT run its own guard loop, does NOT re-audit — it calls the shared kernel. There is NO `match action_name`
(that would re-introduce the duplication Phase 231 deleted). `to_state` comes ONLY from
`derive_transition_plan(...).to_state` (`Transition.to`), never from the form. Tenant comes from
`ferro::current_tenant()`, never from `req.input()`.

Purpose: One declaration backs writes in the visual modality too — EXEC-05's "every modality, no per-channel
executor" (SC2). Output: a working `POST /{service}/{action}` handler routing through the shared kernel.
</objective>

MCP framing to mirror (`ferro-mcp-server/src/write_dispatch.rs:470-545`, `app/src/controllers/mcp.rs`):
