<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent → list_ query params | `<field>__<op>` keys, `__in` arrays, and `sort` are agent-supplied. Op suffix, base field name, and sort field name cross into SQL assembly and must be allowlisted, never interpolated. |
| read SQL → database | The assembled WHERE/ORDER BY is sent to the backend. Any unparameterized value or unvalidated identifier is an injection surface. |

No new authorization here. The tenant predicate and Phase 239 `deleted_at IS NULL` predicate
remain applied on every read after the user filters — query polish must not disturb them
(asserted by the unchanged-blocks acceptance criterion). Write authz is Phase 242.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-240-10 | Tampering (SQL injection via op suffix) | `__op` SQL operator mapping | mitigate | The op suffix is mapped to a fixed string constant (`>`, `>=`, `<`, `<=`, `!=`, `IN`) via an exhaustive match; an unknown suffix returns `InvalidFilter`, never reaching SQL. No suffix is interpolated. Covered by the range/`__in` tests + the unknown-op error path. |
| T-240-11 | Tampering (SQL injection via __in elements) | `__in` array expansion | mitigate | Each array element is bound via `json_to_sea_value` + `placeholder(backend, idx)`; the IN list is `(?,?,...)` placeholders only — no element is interpolated. Covered by `in_filter_returns_correct_rows`. |
| T-240-12 | Information Disclosure (filter/sort on excluded field) | base-field + sort allowlists | mitigate | Range/ne/in base fields are validated against `is_range_filter_field`/`is_filter_field`; the sort base against `is_filter_field`. A non-filterable/non-sortable field returns the same non-disclosing `InvalidFilter` used for equality keys — no field-existence oracle beyond the existing equality surface. |
| T-240-13 | Tampering (predicate stripping) | tenant + `deleted_at IS NULL` predicates | mitigate | Query polish adds clauses but leaves the always-on tenant and soft-delete predicates unchanged (verified by the unchanged-blocks acceptance criterion); a soft-deleted or cross-tenant row remains excluded after the extension. |
| T-240-14 | Denial of Service (malformed IN) | empty `__in` array | accept→mitigate | An empty `__in` array is rejected at the application layer with `InvalidFilter` (Pitfall 2) rather than emitting invalid/ambiguous `IN ()` SQL; covered by the empty-array case in `in_filter_returns_correct_rows`. |
</threat_model>
