## Summary

The core deliverable of this phase — `header()` replace semantics with case-insensitive matching via `retain` + `push`, paired with an `append_header()` escape hatch for multi-value headers — is implemented correctly. The `Set-Cookie` / `cookie()` path correctly uses `append_header`. The `Content-Type` double-emission bug in `JsonUi::build_response` is fixed correctly: `HttpResponse::text()` sets `text/plain` and the chained `.header("Content-Type", "text/html; charset=utf-8")` replaces it in one step.

Three warnings exist in pre-existing code that this phase did not introduce but that are directly adjacent to the changed API surface. Three info items round out the picture.

## Warnings

### WR-01: `ResponseExt::header` and `ResponseExt::status` silently no-op on `Err` responses

**File:** `framework/src/http/response.rs:194-200`

**Issue:** Both `ResponseExt` methods use `.map(|r| ...)`, which only applies the transformation to the `Ok` variant. When a handler or middleware chain calls `.header()` or `.status()` on a `Result<HttpResponse, HttpResponse>` that is already an `Err`, the operation is silently dropped. The caller has no indication the header was not set. This is particularly relevant now that `header()` has well-defined replace semantics — a caller may rely on the replace behaviour to override a security-relevant header (e.g., `Content-Security-Policy`), not knowing the `Err` branch bypasses it entirely.

**Fix:** Either document the limitation explicitly in the `ResponseExt` trait docs, or apply the transformation to both branches when the intent is to always set the header regardless of Ok/Err:

```rust
impl ResponseExt for Response {
    fn header(self, name: impl Into<String>, value: impl Into<String>) -> Self {
        let name = name.into();
        let value = value.into();
        self.map(|r| r.header(name.clone(), value.clone()))
            .map_err(|r| r.header(name, value))
    }
}
```

If the current "only apply to Ok" behaviour is intentional, add a doc comment:

```rust
/// Note: has no effect if the inner result is `Err`.
fn header(self, name: impl Into<String>, value: impl Into<String>) -> Self;
```

### WR-02: Query parameter values in `Redirect` and `RedirectRouteBuilder` are not percent-encoded

**File:** `framework/src/http/response.rs:248-253` and `299-306`

**Issue:** Both `build_url` implementations concatenate key-value pairs with raw `format!("{k}={v}")`. If a key or value contains `&`, `=`, `?`, `#`, or space, the resulting URL will be structurally malformed. For example, `.query("msg", "a&b=c")` produces `?msg=a&b=c`, which a server will parse as two separate query parameters.

This is a correctness bug for any caller passing values from user input or database fields. It also has mild injection potential (e.g., injecting a second query parameter that overrides a server-side check).

**Fix:** Apply percent-encoding before interpolation. Using the `urlencoding` crate (already common in Rust HTTP stacks) or a hand-rolled encoder for the query value:

```rust
fn encode_query_value(v: &str) -> String {
    v.chars().flat_map(|c| match c {
        'A'..='Z' | 'a'..='z' | '0'..='9' | '-' | '_' | '.' | '~' => vec![c],
        c => format!("%{:02X}", c as u32).chars().collect(),
    }).collect()
}

// Then in build_url:
.map(|(k, v)| format!("{}={}", encode_query_value(k), encode_query_value(v)))
```

Alternatively, add `urlencoding` to the framework's dependencies and use `urlencoding::encode(v)`.

### WR-03: `into_hyper()` calls `.unwrap()` and can panic on invalid header values

**File:** `framework/src/http/response.rs:168-176`

**Issue:** `builder.body(Full::new(self.body)).unwrap()` will panic if any accumulated header name or value is rejected by hyper's header parser (non-ASCII bytes, control characters, or an invalid status code). Because `HttpResponse` stores headers as raw `String` pairs with no validation at insertion time, the panic site is distant from the source of the bad value, making bugs hard to trace.

**Fix:** Return a `Result` from `into_hyper`, or validate header name/value at insertion time in `header()` and `append_header()`. A minimal guard in `into_hyper` that converts the panic to an error response:

```rust
pub fn into_hyper(self) -> hyper::Response<Full<Bytes>> {
    let mut builder = hyper::Response::builder().status(self.status);
    for (name, value) in self.headers {
        builder = builder.header(name, value);
    }
    builder.body(Full::new(self.body)).unwrap_or_else(|_| {
        hyper::Response::builder()
            .status(500)
            .body(Full::new(Bytes::from("internal error: invalid response headers")))
            .unwrap()
    })
}
```

### IN-01: `custom_head` is injected verbatim — no API-level warning about XSS risk

**File:** `framework/src/json_ui/mod.rs:116-118`

**Issue:** `config.custom_head` is appended to the HTML head string without escaping. This is intentional (it is raw HTML), but the neighbouring code (lines 100-109) explicitly calls out defense-in-depth for `stylesheet_urls`. An app that passes a user-controlled value into `.custom_head(...)` would introduce XSS. The API offers no warning.

**Fix:** Add a doc comment to `JsonUiConfig::custom_head` stating that the value is emitted verbatim and must be trusted/app-controlled content only. No code change needed.

### IN-02: Theme CSS injected without `</style>` escape guard

**File:** `framework/src/json_ui/mod.rs:125-127`

**Issue:** `head.push_str(&format!("<style>{}</style>", theme.css))` — if `theme.css` contains the literal string `</style>`, the tag closes prematurely and the remainder of the CSS leaks into the HTML document. Themes are app-controlled trusted content, so exploitation requires a misconfigured or malicious theme, but it is a latent correctness issue.

**Fix:** Strip or replace `</style>` occurrences before injection, or document that theme CSS must not contain that sequence:

```rust
let safe_css = theme.css.replace("</style>", "<\\/style>");
head.push_str(&format!("<style>{safe_css}</style>"));
```

### IN-03: `test_download_filename_sanitization` assertion logic is misleading

**File:** `framework/src/http/response.rs:535-548`

**Issue:** The assertion `!cd.contains('"') || cd.matches('"').count() == 2` passes vacuously when the filename contains no `"` at all, but also when it contains exactly two — both conditions satisfy `||`. The intent is to verify that the only `"` characters in the `Content-Disposition` value are the two enclosing the filename. The condition does not distinguish between those cases and would pass even if one injected `"` survived alongside the enclosing pair (total of 3, not 2).

The sanitization logic itself is correct and removes `"` from the input before it reaches the header. This is purely a test-assertion quality issue.

**Fix:** Tighten the assertion to exactly check the structural invariant:

```rust
// The filename portion sits between the two outer quotes.
// After sanitization, only those two outer quotes should remain.
assert_eq!(
    cd.matches('"').count(),
    2,
    "only the two enclosing quotes around the filename should remain"
);
assert!(!cd.contains('\n'), "filename must not contain newlines");
```
