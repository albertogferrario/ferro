# Phase 143.1 Plan 01: HttpResponse Header Replace Semantics Summary

**One-liner:** Replace-semantics for `HttpResponse::header()` via case-insensitive `retain+push`, eliminating the double `Content-Type` header that caused Cloudflare to emit `text/plain,text/html; charset=utf-8` and Safari to render raw HTML source.

## What Was Built

Fixed `HttpResponse::header()` to strip any existing header with a matching name (case-insensitive ASCII) before inserting the new value. Added `append_header()` as a public escape hatch for legitimately multi-value headers (`Set-Cookie`, `Vary`, `Link`). Rerouted `cookie()` through `append_header()` to preserve multi-cookie behaviour. Added a `headers()` accessor. Updated two stale docstrings. Bumped workspace version to `0.2.5`.

### Root Cause

`HttpResponse::text()` prepopulates `Content-Type: text/plain`. Every `JsonUi::render()` call then chains `.header("Content-Type", "text/html; charset=utf-8")`, which previously appended a second entry. Cloudflare comma-joined the two values into `text/plain,text/html; charset=utf-8`. Safari honoured the first value and rendered every ferro JSON-UI page as plain text. Chrome/Firefox honoured the last value — the bug was invisible in dev.

## Decisions Made

1. **retain+push pattern** — `self.headers.retain(|(n, _)| !n.eq_ignore_ascii_case(&name))` followed by `push`. Vec storage retained (D-06 honoured). No HashMap migration.
2. **append_header as pub** — callable from application code for `Set-Cookie`, `Vary`, `Link`, and similar multi-value headers.
3. **cookie() through append_header()** — the only correct path: `Set-Cookie` must not be stripped when multiple cookies are set per response.
4. **headers() accessor** — `pub fn headers(&self) -> &[(String, String)]` aligned with success criteria; enables external consumers without exposing the private field.
5. **Version 0.2.4 → 0.2.5** — one patch step from the verified current value (CONTEXT.md D-08 had a stale version reference `0.2.5 → 0.2.6`; corrected).
