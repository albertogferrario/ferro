## Summary

The bug is a double `Content-Type` header produced by `HttpResponse::text()` (sets `text/plain`) followed by `.header("Content-Type", "text/html; charset=utf-8")` (appends rather than replaces). Cloudflare comma-joins the two values into `text/plain,text/html; charset=utf-8`. Safari reads the first value and treats the response body as plain text. Chrome and Firefox use the second; the bug was invisible in non-Safari testing.

The fix is a single-file change to `framework/src/http/response.rs`. The `header()` method gains retain+push replace semantics. A new `append_header()` method provides the previous append behaviour as an explicit escape hatch. `cookie()` is rerouted through `append_header()` to preserve multi-cookie support.

**Primary recommendation:** Implement exactly as specified in CONTEXT.md decisions D-01 through D-08. No alternatives to evaluate.

## Common Pitfalls

### Pitfall 1: Existing json_ui test uses `get_all()` workaround

**What goes wrong:** `framework/src/json_ui/mod.rs:305-316` has a helper `has_content_type()` that calls `hyper.headers().get_all("Content-Type")` and checks if _any_ value matches the expected string. This was written to tolerate the double-header bug.

**After the fix:** `get_all()` will return only one value (the correct one). The helper still works — `any()` over a single-element iterator is fine. No change to the json_ui test is needed. But the planner should note that this helper is now exercising the "one header" path, and its comment ("Handles the case where multiple Content-Type headers exist") becomes stale.

**How to avoid:** Do not change the json_ui test logic. The helper remains correct. Optionally update its comment.

### Pitfall 2: ResponseExt::header() docstring says "Append"

**What goes wrong:** `framework/src/http/response.rs:167` — the `ResponseExt` trait declares `fn header` with docstring "Append a response header." After this fix the semantics are replace, not append. The docstring will be a lie.

**How to avoid:** Update the `ResponseExt::header()` docstring to match the new semantics. The implementation delegates to `HttpResponse::header()` and requires no code change, but the comment does.

### Pitfall 3: cookie() currently calls self.header(), not self.append_header()

**What goes wrong:** `response.rs:136` — `self.header("Set-Cookie", header_value)`. After D-01 lands, `header()` strips any existing `Set-Cookie` before pushing. A response with two cookies would silently drop the first.

**How to avoid:** Change `cookie()` to call `self.append_header(...)` per D-03. This is a required change, not optional.

### Pitfall 4: Version bump target

**What goes wrong:** D-08 says 0.2.5 → 0.2.6 but the workspace `Cargo.toml` currently reads 0.2.4. If the planner writes the bump task as "change 0.2.5 to 0.2.6" the task will fail because the string 0.2.5 is not present.

## HTTP Spec Context: Multi-Value Headers

Which headers are legitimately multi-value (justify `append_header()` use cases):

| Header | Multi-value? | Example use |
|--------|-------------|-------------|
| `Set-Cookie` | Yes — one header per cookie | `cookie()` method routes here |
| `Vary` | Yes — comma-separated or multiple | CDN / cache negotiation |
| `Link` | Yes — rel preload/prefetch chains | HTTP/2 push hints |
| `Accept-Encoding` | Yes in request, singular in response | N/A for responses |
| `Content-Type` | No — exactly one per response | This is the bug being fixed |
| `Location` | No — exactly one redirect target | Should use `header()` |
| `X-Inertia` | No | Should use `header()` |

**Key insight:** `Set-Cookie` is the only multi-value header the framework currently sets internally. `append_header()` is primarily an escape hatch for application code that needs `Vary: Accept-Language` + `Vary: Accept-Encoding` on the same response, or `Link: </font>; rel=preload` chains.

[ASSUMED] — HTTP spec claim from training knowledge. RFC 7230 Section 3.2.2 allows field values to be combined with commas for most headers; RFC 6265 Section 4.1 explicitly requires separate `Set-Cookie` lines. These are stable RFCs unlikely to have changed.

## Delegation Chain: ResponseExt

`ResponseExt` is defined at `response.rs:163-178`. Its `header()` implementation:

```rust
impl ResponseExt for Response {
    fn header(self, name: impl Into<String>, value: impl Into<String>) -> Self {
        self.map(|r| r.header(name, value))
    }
}
```

`self.map()` applies the closure to the `Ok` variant of `Result<HttpResponse, HttpResponse>`. It delegates directly to `HttpResponse::header()`. Once `HttpResponse::header()` gains replace semantics, `ResponseExt::header()` automatically inherits them — D-05 is confirmed. No code change needed.

The `Err` variant (error responses) is not touched by `map()` — error responses never go through `.header()` chains in practice.

   ```rust
   fn test_header_replaces_existing() {
       let resp = HttpResponse::text("x").header("Content-Type", "text/html");
       let headers = resp.headers();
       let ct: Vec<_> = headers.iter().filter(|(k, _)| k.eq_ignore_ascii_case("Content-Type")).collect();
       assert_eq!(ct.len(), 1);
       assert_eq!(ct[0].1, "text/html");
   }
   ```

2. **Multi-cookie test:**
   ```rust
   fn test_multi_cookie_preserved() {
       let resp = HttpResponse::new()
           .cookie(Cookie::new("a", "1"))
           .cookie(Cookie::new("b", "2"));
       let headers = resp.headers();
       let cookies: Vec<_> = headers.iter().filter(|(k, _)| k == "Set-Cookie").collect();
       assert_eq!(cookies.len(), 2);
   }
   ```

3. **Case-insensitive replace test:**
   ```rust
   fn test_header_case_insensitive_replace() {
       let resp = HttpResponse::new()
           .append_header("content-type", "text/plain")
           .header("Content-Type", "text/html");
       let headers = resp.headers();
       let ct: Vec<_> = headers.iter().filter(|(k, _)| k.eq_ignore_ascii_case("Content-Type")).collect();
       assert_eq!(ct.len(), 1);
       assert_eq!(ct[0].1, "text/html");
   }
   ```
