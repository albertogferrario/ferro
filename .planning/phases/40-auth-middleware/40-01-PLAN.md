  <files>framework/src/auth/extract.rs, framework/src/auth/mod.rs</files>
  <action>
Create `framework/src/auth/extract.rs` with two extractor types:

**AuthUser<T>** - Extracts the authenticated user, returns 401 if not authenticated:
```rust
pub struct AuthUser<T>(pub T);
```
- Implement `FromRequest` for `AuthUser<T>` where `T: Authenticatable + Clone + 'static`
- In `from_request`: call `Auth::user().await?`, if None return `FrameworkError::Unauthorized`, if Some downcast via `as_any().downcast_ref::<T>().cloned()`, if downcast fails return internal error
- Implement `Deref<Target = T>` so `user.email` works without `user.0.email`
- Do NOT consume the Request body (Auth uses session thread-locals, not request data)

**OptionalUser<T>** - Extracts the authenticated user as Option, never fails on auth:
```rust
pub struct OptionalUser<T>(pub Option<T>);
```
- Implement `FromRequest` for `OptionalUser<T>` where `T: Authenticatable + Clone + 'static`
- In `from_request`: call `Auth::user().await?`, if None return `Ok(OptionalUser(None))`, if Some downcast via `as_any().downcast_ref::<T>().cloned()` and wrap in Some
- Implement `Deref<Target = Option<T>>` for ergonomic access

IMPORTANT: The `FromRequest` trait takes `req: Request` but the extractors don't actually need to consume or use it. The Auth system reads from session thread-locals. The handler macro (`ferro-macros/src/handler.rs`) classifies non-primitive, non-Request, non-Model types as `FormRequest` which calls `FromRequest::from_request`. The blanket impl `impl<T: FormRequest> FromRequest for T` exists in form_request.rs, but since `AuthUser<T>` and `OptionalUser<T>` don't implement `FormRequest`, there's no conflict — we provide direct `FromRequest` impls for them.

There IS a problem: the handler macro generates code that moves `__ferro_req` into the `FromRequest::from_request` call. If a handler has both an `AuthUser` param AND a `Request` param (or form request), the request would be moved twice. But the handler macro already handles this: it allows exactly ONE request-consuming param. Auth extractors should still take `req: Request` in their signature (trait requirement) but simply ignore it. If a user needs both `AuthUser<User>` and `Request`, they must use `Auth::user_as::<User>()` manually in the handler body — same as Laravel's approach. Document this limitation.

Actually, re-examining the handler macro more carefully: for `FormRequest`-classified params, it generates `<Type as FromRequest>::from_request(__ferro_req).await?` which moves `__ferro_req`. So if there are two FormRequest-typed params, the second would fail to compile because `__ferro_req` was already moved. This is the existing behavior — the framework allows at most one body-consuming extractor per handler.

For AuthUser, since it doesn't actually need the request body, we could clone the request or take a reference. But the `FromRequest` trait signature requires `req: Request` (owned). The simplest approach: AuthUser's `from_request` receives the request, ignores it, calls `Auth::user()`. This means AuthUser counts as the "one FromRequest param" — users cannot combine AuthUser with FormRequest in the same handler. This is acceptable because:
1. If you need auth + form input, use `AuthUser<User>` and parse body manually, OR
2. Use `Request` param and call `Auth::user_as::<T>()` + `req.input()` manually

This matches the existing constraint. Document it.
