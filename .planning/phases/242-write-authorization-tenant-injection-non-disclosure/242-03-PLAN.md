<objective>
Close the write-ability half of SC#1 (the scope half already ships at jsonrpc.rs). Add a
DEDICATED fail-closed authorization signal — `write_authorized: Option<bool>` on `McpContext`
(D-01/D-02/D-03) — populated by the host running the real `Gate::authorize_for` against the
projection's `.mcp_write_ability` for write tools, and enforced inside `ferro-mcp-server`
`handle_write_call` BEFORE any CRUD/confirmation routing. A `None`/`Some(false)` denies.

Purpose: this is the policy-Gate enforcement point (SC#1 second half) for create/update/delete
(and the destructive confirm flow). It is deliberately SEPARATE from `evaluated_guards` —
renderer.rs:210 documents that the guard map is a *visibility* filter, NOT an authorization
gate (D-02). The host (`app/src/controllers/mcp.rs`) already runs `Gate::authorize_for(&user,
ability, None)` for READ tools (mcp.rs:306) and documents a deliberate skip-gap for WRITE tools
(mcp.rs:256-264); this plan closes that gap and feeds the result into the channel as a boolean
the kernel-facing dispatcher enforces fail-closed.

Output: `McpContext.write_authorized` field; a fail-closed early-deny in `handle_write_call`;
host wiring that resolves the write tool's owning service, fail-closed-reads its
`mcp_write_ability`, runs the Gate, and sets `write_authorized`; plus ferro-mcp-server framing
tests proving deny on `None`/`Some(false)` and proceed on `Some(true)`, and that the existing
read-key scope gate still rejects writes.

Coherence guard: do NOT route write authorization through `evaluated_guards`; do NOT rebuild
the scope gate (jsonrpc.rs:77) or the `dispatch_write` guard re-eval — this adds ONE new
boolean signal and ONE fail-closed check.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API key scope → write tools | The jsonrpc scope gate (already shipped) rejects a `read`-scope key on any non-`list_` tool before dispatch. |
| policy Gate → channel | The host runs `Gate::authorize_for(&user, mcp_write_ability, None)` and passes a single boolean (`write_authorized`) into the channel; the channel enforces it fail-closed. Authorization decisions stay in the host's policy layer; the channel only enforces the result. |
| evaluated_guards vs write_authorized | The visibility guard map and the write-authorization signal are SEPARATE fields — visibility filtering can never be mistaken for an authorization grant (renderer.rs:210). |

| T-242-01 | Spoofing / Authorization bypass | host write-tool branch | mitigate | The host resolves the owning service by stripping verb + confirmation prefixes and runs the same policy Gate the read path uses, with a full resolved `User` (not session state).
