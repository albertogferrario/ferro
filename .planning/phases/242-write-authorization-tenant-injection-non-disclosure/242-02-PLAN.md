<objective>
Bind the runtime `tenant_id` (currently the ignored `_tenant_id` parameter) into the SQL of
`execute_crud_plan` whenever the plan's `tenant_column` is `Some` (D-05). Create injects the
tenant column into the INSERT; Update and Delete add `AND <tenant_column> = ?` to the existing
`WHERE id=? AND <soft_delete_column> IS NULL` predicate. This is the ONLY place SQL changes;
no new dispatcher, no new error kind.

Purpose: This is the enforcement mechanism for tenant isolation (SC#2) and non-disclosure
(SC#3). The `AND <tenant_column> = ?` predicate makes a foreign-tenant row *unaddressable* at
the DB level — it falls through to 0 affected rows → the existing
`WriteError::RecordNotFound` path (D-08), so a cross-tenant row reads identically to a missing
row. No separate cross-tenant code path is added (that would itself be a disclosure vector).

Output: tenant-aware `execute_crud_plan` (Create/Update/Delete + post-update SELECT) plus
sqlite-in-memory dispatch tests covering injection, cross-tenant non-disclosure, soft-deleted
non-disclosure, and the same-tenant happy path.

⚠ HIGHEST-RISK DETAIL: `created_at` is a SQL *literal* (`now_expr`), NOT a bound parameter.
It does not consume a placeholder index. The tenant placeholder for Create is therefore
`placeholder(backend, columns.len() + 1)` — NOT `+ 2`. Getting this wrong silently binds
tenant_id into the wrong column. This arithmetic is stated verbatim in the action below.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| auth context → SQL kernel | `tenant_id` arrives as a function parameter sourced from auth (JWT `sub`), never from agent payload. The kernel binds it as a SQL parameter — it never reaches SQL via string interpolation. |
| agent input → write target | The agent supplies `id` for update/delete; the kernel scopes the WHERE by the auth tenant so a supplied foreign-tenant id is unaddressable. |
| DB row tenancy → response | A 0-affected-row outcome (foreign tenant / soft-deleted / genuinely missing) all collapse to one indistinguishable `RecordNotFound`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-242-02 | Elevation of Privilege | `execute_crud_plan` Create | mitigate | Tenant column is injected from the auth `tenant_id` parameter, bound (never interpolated). The column is write-excluded from agent schemas upstream (Phase 239), so an agent cannot set or override it (defense-in-depth, D-07). |
| T-242-03 | Information Disclosure | `execute_crud_plan` Update/Delete | mitigate | `AND <tenant_column> = ?` makes a foreign-tenant row produce 0 rows → existing `WriteError::RecordNotFound`. No distinct cross-tenant signal, error kind, or code path (D-08). Tests assert the seeded foreign row is also left untouched (no partial-write leak). |
| T-242-02 | Tampering | tenant_id binding | mitigate | tenant_id is bound as `sea_orm::Value::BigInt(Some(tenant_id))` through the dual-dialect `placeholder()` helper — never string-formatted into the SQL, so it cannot be used as an injection vector. |
| T-242-03 | Information Disclosure | post-update SELECT race (Pitfall 5) | mitigate | The post-update SELECT also carries `AND <tenant_column> = ?` + `AND <soft_delete_column> IS NULL`, so a concurrent cross-tenant/soft-delete reassignment between UPDATE and SELECT cannot return foreign data. |
</threat_model>
