# Phase 250: Code Review Report

**Reviewed:** 2026-07-03T04:12:02Z
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Reviewed the token vocabulary v2 expansion (23 → 30 slots) across the Rust constants, the Tailwind bridge, the default theme, the scaffold, the generated base CSS, and the docs.

**What checks out cleanly:**

- The 7 new token names (`--spacing`, `--motion-duration-fast/base/slow`, `--motion-ease`, `--color-ring`, `--font-display`) are spelled identically across `token.rs` constants, `ALL_TOKENS`, `input.css`, all three cascade blocks of `default.css`, the `make_theme.rs` scaffold, and `themes.md`.
- Fallback values in `input.css` match the spec and `default.css`: `120ms` / `220ms` / `320ms`, `cubic-bezier(0.2, 0, 0.38, 0.9)`, `var(--font-sans)` for the display font.
- `default.css` contains no Tailwind at-rules — only standard `@media` — so verbatim `<style>` injection is safe.
- Generated `ferro-base.css` reflects the current `input.css` (Tailwind v4.2.3 output): bridge variables with fallbacks (`--duration-fast:var(--motion-duration-fast,.12s)` etc.), the `prefers-reduced-motion` block with `.01ms` collapse, and generated `.ease-base`, `.font-display`, `.ring-ring` utilities are all present.
- `token.rs` asserts `ALL_TOKENS.len() == 30`; `make_theme.rs` tests assert all 30 slots plus the no-`@theme` plain-CSS constraint; `loader.rs` error-path tests (NotFound / Io / Json) are solid.

**Key concerns:** the three motion *duration* utility classes (`duration-fast/base/slow`) were silently not generated by Tailwind despite the safelist — the motion duration tokens cannot currently be consumed as utility classes; the reduced-motion collapse is defeated by cascade order once any theme is injected; `--color-ring` is the one new slot without a base-CSS default, breaking the documented v1-theme compatibility contract; and `themes.md` still documents the retired `@theme`/Tailwind-CLI authoring model, which produces fully broken themes under the verbatim-injection path.

## Warnings

### WR-01: `duration-fast/base/slow` utility classes are not generated — motion duration tokens are unconsumable via classes

**File:** `ferro-json-ui/assets/input.css:49-51,72`
**Issue:** The bridge declares `--duration-fast: var(--motion-duration-fast, 120ms)` (and base/slow) and the safelist requests `@source inline("duration-fast duration-base duration-slow ...")`, but the generated `ferro-base.css` contains **no** `.duration-fast`, `.duration-base`, or `.duration-slow` rules — the only duration utilities emitted are `.duration-150` and `.duration-300` (bare-value classes scanned from component source). Tailwind v4.2.3 does not resolve the `duration-*` utility against a `--duration-*` theme namespace the way it does for `--ease-*` (`.ease-base` **was** generated), so the safelisted candidates are silently dropped as unknown utilities. Consequences: (a) the phase's motion duration tokens cannot be consumed as utility classes at all, which blocks the follow-on component migration; (b) the `assets/mod.rs` drift guard passes for the wrong reason — `var(--motion-duration-fast,` matches the *unused* theme-layer variable emission `--duration-fast:var(--motion-duration-fast,.12s)`, not a working utility.
**Fix:** Define the utilities explicitly in `input.css` (Tailwind v4 `@utility` is processed by the CLI build, not injected at runtime), regenerate, and strengthen the drift guard to assert the class rules exist:
```css
@utility duration-fast {
  transition-duration: var(--motion-duration-fast, 120ms);
}
@utility duration-base {
  transition-duration: var(--motion-duration-base, 220ms);
}
@utility duration-slow {
  transition-duration: var(--motion-duration-slow, 320ms);
}
```
In `ferro-json-ui/src/assets/mod.rs`, assert `FERRO_BASE_CSS.contains(".duration-fast{")` (minified form) instead of only the `var(...)` substring.

### WR-02: Reduced-motion collapse is defeated by theme `<style>` cascade order

**File:** `ferro-json-ui/assets/input.css:76-82` (also `framework/src/json_ui/mod.rs:131-153`, `ferro-theme/assets/default.css:46-49`)
**Issue:** The head is assembled as: `ferro-base.css` `<link>` first (`mod.rs:131`), theme `<style>` after (`mod.rs:151`). The reduced-motion block in the base CSS declares `--motion-duration-*: .01ms` on `:root` (unlayered, specificity 0,1,0). Every theme surface — `default.css` `:root` block and the scaffold — unconditionally declares `--motion-duration-fast: 120ms` etc. on `:root` with the same specificity, **later in document order**. Media queries do not affect cascade priority, so for `prefers-reduced-motion: reduce` users the theme's `120ms` wins and the collapse never applies whenever ThemeMiddleware is active (the recommended setup — it always injects at least the default theme). Currently masked by WR-01 (no utility consumes these variables yet), but once WR-01 is fixed the accessibility guarantee is silently dead.
**Fix:** Add `!important` to the collapse declarations — `!important` is valid on custom-property declarations and important author declarations beat later normal ones regardless of source order:
```css
@media (prefers-reduced-motion: reduce) {
  :root {
    --motion-duration-fast: 0.01ms !important;
    --motion-duration-base: 0.01ms !important;
    --motion-duration-slow: 0.01ms !important;
  }
}
```
Then regenerate `ferro-base.css` and verify the `!important` survives minification.

### WR-03: `--color-ring` is the only new slot with no base-CSS default — v1-theme compatibility gap

**File:** `ferro-json-ui/assets/input.css:55`
**Issue:** Six of the seven new slots have defaults reachable without a v2 theme (three durations + ease via `var(..., fallback)`, `--font-display` via nested `var(--font-sans)`, `--spacing` via Tailwind's built-in layered `0.25rem` default). `--color-ring` is bridged with **no fallback**: `--color-ring: var(--color-ring);`. With a 23-slot v1 theme active, `--color-ring` is never defined at `:root`, so `.ring-ring{--tw-ring-color:var(--color-ring)}` resolves against an undefined/self-referential property and focus rings render broken. This directly contradicts `themes.md:59`: "Every valid v1 theme (23 slots) remains a valid v2 theme without changes — the 7 new slots ship with defaults in the base CSS."
**Fix:** Give the bridge the documented primary-family fallback and regenerate:
```css
--color-ring: var(--color-ring, var(--color-primary));
```
This inlines into `.ring-ring{--tw-ring-color:var(--color-ring,var(--color-primary))}` so a v1 theme's primary color is used at the use site. Verify against a 23-slot fixture theme, and add a drift-guard assertion for the fallback.

### WR-04: themes.md documents the retired `@theme`/Tailwind-CLI authoring model — following it produces a broken theme

**File:** `docs/src/features/themes.md:9,43-53,160-169,295-303`
**Issue:** The scaffold (`make_theme.rs`) generates plain-CSS `:root` tokens explicitly because "@theme syntax ... only works under the Tailwind browser runtime (dev-only)", and its tests assert `@theme {` is absent. `ThemeMiddleware` injects `tokens.css` **verbatim** into an inline `<style>` (`framework/src/json_ui/mod.rs:145-151`). But themes.md still teaches the old model: line 9 calls `tokens.css` a "Tailwind v4 `@theme` block"; the Quick Start example (43-47) uses `@theme { ... }` syntax; lines 49-53 and 295-303 instruct running `npx tailwindcss -i ... -o public/themes/myapp.css` (an output nothing ever serves); the dark-mode example (160-169) shows `@media { @theme { ... } }`, which the scaffold tests explicitly forbid. A theme creator following the Quick Start writes `@theme { ... }`, the browser ignores the unknown at-rule wholesale, and every color token in their theme is undefined.
**Fix:** Rewrite the affected sections to plain-CSS authoring: describe `tokens.css` as a plain `:root { ... }` variable block injected verbatim; change the Quick Start and dark-mode examples to `:root`; delete the Tailwind CLI processing step from Quick Start and "For Theme Creators" (or reframe it as a note explaining why no build step is needed).

### WR-05: themes.md "Default (light)" values are stale vs the refreshed default.css; scaffold palette not harmonized

**File:** `docs/src/features/themes.md:64-83` (also `ferro-cli/src/commands/make_theme.rs:84-96`)
**Issue:** The docs token tables show the pre-refresh palette — pure-gray surfaces (`--color-background: oklch(100% 0 0)`, `--color-text: oklch(15% 0 0)`, etc.) and accent `oklch(65% 0.15 200)` — but `default.css` now ships cool-tinted hue-250 neutrals (`oklch(99% 0.004 250)` background, `oklch(20% 0.02 250)` text) with accent harmonized to `oklch(70% 0.13 250)`. The docs match the `make_theme.rs` scaffold instead, which itself still carries the old palette (accent hue 200, untinted grays, `oklch(100% 0 0)` background) — so the phase's "accent harmonized from hue 200 to 250" refresh landed in `default.css` only. Two surfaces claiming to represent the default now disagree with the actual default theme.
**Fix:** Update the themes.md "Default (light)" columns to the refreshed `default.css` values. Decide deliberately whether the scaffold should mirror the refreshed palette (recommended, so `ferro make:theme` starts from the shipped default) or intentionally stay neutral — and if the latter, relabel the docs column so it does not claim to describe the default theme.

### WR-06: loader.rs drift guard checks 7 of 30 tokens despite its name

**File:** `ferro-theme/src/loader.rs:72-93`
**Issue:** `default_theme_returns_all_30_token_slots` asserts only 7 substrings (2 v1 + 5 v2 spot checks). Dropping e.g. `--radius-md` or `--color-warning` from `default.css` would not fail any test — the guard does not deliver what its name promises, and nothing cross-checks `token.rs` against `default.css`.
**Fix:** Iterate the vocabulary from the same crate:
```rust
use crate::token::ALL_TOKENS;

#[test]
fn default_theme_declares_every_token_slot() {
    let theme = Theme::default_theme();
    for token in ALL_TOKENS {
        assert!(
            theme.css.contains(&format!("{token}:")),
            "default.css missing declaration for {token}"
        );
    }
}
```
The `{token}:` suffix avoids prefix false-positives (`--color-text` matching `--color-text-muted`). This also closes token.rs ↔ default.css name drift permanently.

## Info

### IN-01: `--spacing` / `--font-sans` / `--font-mono` bridge omission is correct but undocumented

**File:** `ferro-json-ui/assets/input.css:18-59`
**Issue:** The `@theme inline` bridge intentionally omits `--spacing` and the two font tokens — Tailwind's built-in namespaces already provide `var()` indirection (verified in the generated output: `--spacing:.25rem` in the theme layer, `.p-4{padding:calc(var(--spacing) * 4)}`), so runtime theme overrides work and the `0.25rem` default is satisfied. But nothing in the file says so; a future maintainer auditing "30 slots vs 27 bridge entries" will either "fix" it or assume drift.
**Fix:** Add a comment in `input.css` noting that `--spacing`, `--font-sans`, and `--font-mono` are covered by Tailwind's built-in theme namespaces and deliberately not re-bridged.

### IN-02: default.css and scaffold dark blocks redundantly redeclare identical-value tokens

**File:** `ferro-theme/assets/default.css:75-89,108-122` (also `make_theme.rs:149-162`)
**Issue:** The dark `@media` and `[data-theme="dark"]` blocks redeclare `--spacing`, all four motion tokens, and `--font-display` with values identical to the `:root` block; custom properties inherit, so only `--color-ring` genuinely differs in dark. The duplication is harmless today but widens the surface that fights the reduced-motion collapse (WR-02) and invites value drift across three copies.
**Fix:** Keep only the tokens that actually change in the dark blocks (`--color-*` overrides including `--color-ring`); drop the duplicated spacing/motion/display declarations.

### IN-03: assets/mod.rs regeneration guard covers only 2 of the 6 new safelisted utilities

**File:** `ferro-json-ui/src/assets/mod.rs:33-45`
**Issue:** The guard checks the motion-fast fallback substring and `prefers-reduced-motion`, but not `.ease-base`, `.font-display`, or `.ring-ring` — a regeneration that lost those (e.g. a safelist edit) would pass tests.
**Fix:** Extend the test to assert `.ease-base{`, `.font-display{`, and `.ring-ring{` are present (and `.duration-fast{` etc. once WR-01 lands).
