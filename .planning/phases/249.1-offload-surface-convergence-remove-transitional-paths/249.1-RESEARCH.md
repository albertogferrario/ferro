## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01 — Single registration path via a framework-default broadcaster**
When bootstrap registered no `Broadcaster`, the framework provides a default in-process
`Broadcaster` so `App::get::<Broadcaster>()` is always `Some` by the time the offload hooks
register. `register_offload_hooks()` (the persist-only variant) is deleted;
`register_offload_hooks_with_broadcaster()` becomes the sole registration function.
Worker-only deployments get a default in-process hub that publishes to nobody.

**D-02 — Full linearization of `run_common_boot`**
Converge to one linear flow:
1. run `bootstrap_fn`; init the queue DB connection (unchanged guards)
2. ensure a `Broadcaster` (per D-01)
3. attach the shared transport if `transport_redis_url` is configured (feature-gated Redis attach;
   `with_transport` still runs before any WebSocket client connects — Pitfall WR-03)
4. register the offload result hook once
5. spawn the in-process worker once when `!no_worker && has_registered_jobs()`

Removes all duplicate registration/spawn calls and the early-`return`s. Preserves the WR-01
ordering constraints and the D-07 feature-off + URL-set `warn!`.

**D-03 — Narrow sweep boundary (244–249 introductions only)**
Remove only transitional / "for compatibility" / dual-path constructs introduced during 244–249.
Pre-existing legacy that predates offload is explicitly kept:
- `ferro-queue/src/dispatcher.rs` `#[deprecated(since = "0.2.0")]` dispatch alias — keep
- `ferro-queue/src/db.rs` legacy-row timestamp fallbacks — keep
- `ferro-broadcast` legacy signing / "ok" sentinel auth paths — keep

**D-04 — Cleanliness verification: one-time grep, comment neutralization**
SC#2 evidenced by a one-time grep; no permanent CI grep-guard added.
`OffloadResult::Pending` is a plain additive variant; keep the variant and the
`offload_result_pending_round_trip` test; reword "backward-compat" comments to neutral.

## Summary

Phase 249.1 is a pure deletion and linearization sweep over two files:
`framework/src/app.rs::run_common_boot` and `framework/src/offload.rs`. Every factual claim
below was verified by reading the actual source in this session; no claims rely on training
knowledge alone.

`run_common_boot` currently registers the offload result hook at **four** distinct call sites
and spawns the in-process worker at **three** of them, using early `return`s to escape the
`redis-transport` feature block before reaching the bottom `if/else`. The bottom `if/else`
contains the `None`-broadcaster fallback (`register_offload_hooks()`) that D-01 designates for
deletion. The linearization (D-02) removes the early returns and the duplicated spawn calls,
producing a single readable flow with one hook registration and one spawn.

The persist-only function `register_offload_hooks()` (offload.rs:278) is called in exactly one
production code site (`app.rs:500`) and in one integration test
(`framework/tests/offload_result_round_trip.rs:242`). The test must be updated alongside the
production deletion: it should call `register_offload_hooks_with_broadcaster` with a bare
in-process `Broadcaster::new()` (no transport) instead of the deleted function.

The `offload_result_pending_round_trip` test (offload.rs:579) contains a comment at line 577
reading `"backward-compat, A3 verification"` — this is the sole `backward-compat` comment in
the test. D-04 directs rewording it to neutral language (e.g., "serde additivity regression
guard: existing completed/failed envelopes still deserialize").

**Primary recommendation:** treat the sweep as three tightly-sequenced tasks — (1) install
framework-default `Broadcaster` + delete `register_offload_hooks()` + update
`offload_result_round_trip.rs`, (2) linearize `run_common_boot` + update `lib.rs` doc at
line 228, (3) run the SC#2 structural grep and neutralize the `Pending` test comment — with
the full regression guard (offload unit + integration suites) run once at the end.

## WR-01 / WR-03 Ordering Constraints

The linearized `run_common_boot` must preserve two ordering constraints, in both boot paths:

**WR-03 (from 248 D-06 / 248 Code Context):** `with_transport` discards existing WebSocket
clients. Therefore the Redis transport attach must run **before** `Server::from_config().run()`
starts accepting connections. The current structure already guarantees this: the `redis-transport`
block is inside `run_common_boot`, which is called at the start of both `run_server_internal`
(line 583) and `run_worker` (line 549), before the HTTP server is started in `run_server_internal`
(line 593: `Server::from_config(router).run()`). The linearized version preserves this because
`run_common_boot` returns before `run_server_internal` calls `Server`.

**WR-01 (from 248 D-06):** Transport attach must run after `bootstrap_fn` (so any app-registered
`Broadcaster` singleton is present) and before the offload hooks register (so hooks see the
transport-attached instance). This order is D-02 steps 1→3→4 and is explicit in the current
code comments at lines 437–441. The linearized flow preserves it by sequencing: bootstrap →
ensure Broadcaster → attach transport → register hook → spawn.

**`run_worker` path (248 decision):** `run_worker` calls `run_common_boot(bootstrap_fn, true)`,
passing `no_worker = true`, so the worker spawn (D-02 step 5) is skipped. The `WorkerLoop` is
then started explicitly in `run_worker` (lines 571–576). This path is unaffected by the
linearization; the only change it sees is that `run_common_boot` no longer has an early `return`
that might accidentally skip step 4 (hook registration) when the redis feature is enabled.

## Common Pitfalls

### Pitfall 1: `offload_result_round_trip.rs` still imports the deleted function

**What goes wrong:** Compilation fails with `unresolved import
ferro::offload::register_offload_hooks`.
**Why it happens:** `offload_result_round_trip.rs` was written when `register_offload_hooks()`
was the only function; it imports and calls it directly (lines 23 and 242).
**How to avoid:** Update the test in the same task that deletes the function. Replace with
`register_offload_hooks_with_broadcaster(Arc::new(Broadcaster::new()))`.
**Warning signs:** Compilation error on `cargo test --package ferro-rs --test
offload_result_round_trip`.

### Pitfall 2: Removing too much — touching out-of-scope `backward compatibility` strings

**What goes wrong:** The grep matches many `backward compat` strings across inertia, routing,
session, and http modules. These are load-bearing for pre-244 code. D-03 is explicit: do not
touch them.
**How to avoid:** The In/Out table above identifies every hit. Work only from the IN-SCOPE rows.
**Warning signs:** Diff showing changes to `framework/src/inertia/`, `framework/src/routing/`,
`framework/src/http/`, `framework/src/session/`, `ferro-queue/src/dispatcher.rs`,
`ferro-broadcast/src/broadcaster.rs`.

### Pitfall 3: Installing a default `Broadcaster` after the Redis check

**What goes wrong:** If the "ensure a Broadcaster" step (D-02 step 2) is placed after the Redis
attach block, then the Redis block's `App::get::<Broadcaster>()` call might still return `None`
for a worker-only process that registered no broadcaster. The early redis block then falls
through with no broadcaster.
**How to avoid:** D-02 is explicit: step 2 (ensure Broadcaster) precedes step 3 (attach
transport). With a guaranteed `Some` from `App::get`, the Redis block can be simplified to
always call `register_offload_hooks_with_broadcaster` without an `if let`.
**Warning signs:** `App::get::<Broadcaster>()` returning `None` inside the redis-transport
feature block after the linearization.

### Pitfall 4: `OnceLock` silently ignoring a duplicate `OFFLOAD_BROADCASTER` set

**What goes wrong:** If the default Broadcaster installation path calls
`register_offload_hooks_with_broadcaster` and then a different path also calls it (perhaps in a
test), the second `OFFLOAD_BROADCASTER.set()` is silently ignored (returns `Err`), leaving the
first broadcaster active. This is the intended behavior for production, but tests that need a
specific broadcaster must ensure it is the first registered one.
**How to avoid:** The linearization guarantees exactly one call site in production. Tests that
call `register_offload_hooks_with_broadcaster` must manage `OnceLock` semantics themselves —
which the existing integration tests already do via the single-test-function pattern.

### Linearized `run_common_boot` Structure (D-02 — sketch)

```rust
pub async fn run_common_boot(bootstrap_fn: Option<BootstrapFn>, no_worker: bool) {
    // Step 1: bootstrap
    if let Some(f) = bootstrap_fn { f().await; }
    if !ferro_queue::Queue::is_initialized() {
        let conn = Self::get_database_connection().await;
        let _ = ferro_queue::Queue::init(conn).await;
    }

    // Step 2: ensure a Broadcaster (D-01)
    if crate::App::get::<ferro_broadcast::Broadcaster>().is_none() {
        crate::App::singleton(ferro_broadcast::Broadcaster::new());
    }

    // Step 3: attach transport (WR-01, WR-03 — before any WebSocket clients)
    #[cfg(feature = "redis-transport")]
    {
        let bc = crate::App::get::<ferro_broadcast::Broadcaster>().unwrap();
        if let Some(ref url) = bc.config().transport_redis_url {
            match ferro_broadcast::transport::redis::RedisTransport::connect(url).await {
                Ok(t) => {
                    let bc2 = bc.with_transport(std::sync::Arc::new(t));
                    crate::App::singleton(bc2);
                }
                Err(e) => { tracing::warn!(error = %e, "Redis connect failed — in-process hub"); }
            }
        }
    }

    // D-07: feature-off + URL-set warn
    #[cfg(not(feature = "redis-transport"))]
    {
        let bc = crate::App::get::<ferro_broadcast::Broadcaster>().unwrap();
        if bc.config().transport_redis_url.is_some() {
            tracing::warn!("BROADCAST_REDIS_URL set but redis-transport feature disabled");
        }
    }

    // Step 4: register the offload result hook once (OnceLock — re-registration silently ignored)
    let bc = crate::App::get::<ferro_broadcast::Broadcaster>().unwrap();
    crate::offload::register_offload_hooks_with_broadcaster(std::sync::Arc::new(bc));

    // Step 5: spawn in-process worker (serve path only)
    if !no_worker && ferro_queue::Queue::has_registered_jobs() {
        Self::spawn_in_process_worker();
    }
}
```

Note: the exact implementation details (whether the D-07 warn block is merged into step 3 or
kept separate, whether the bc handle is re-fetched after the Redis attach) are Claude's
Discretion. The sketch above is illustrative.
