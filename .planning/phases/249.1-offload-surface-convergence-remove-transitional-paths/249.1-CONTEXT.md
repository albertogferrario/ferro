# Phase 249.1: Offload surface convergence (remove transitional paths) - Context

**Gathered:** 2026-08-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Leave the `#[offload]` work-distribution surface (built across phases 244–249) with **one
canonical code path**. Incremental delivery introduced transitional and fallback branches so
each phase's slice would function before the next landed; this phase removes them, per the
feature-branch convention that old code is **deleted, not deprecated**.

**No new capability. No behavioral change** to the fire-and-forward delivery loop. The Phase 247
integration suite and the full offload unit suite are the regression guard — they must pass
unchanged. OFFLOAD-01..06 stay mapped to their delivering phases; this is an architecture-
convergence sweep with no requirement of its own.

Out of scope: any change to the offload *contract* (macro surface, handle type, result path,
scaling model), and any pre-existing legacy path that predates phase 244.

</domain>

<decisions>
## Implementation Decisions

### D-01 — Single registration path via a framework-default broadcaster
The persist-only fallback exists only because a headless worker-only process may have **no**
`Broadcaster` in the container (`App::get::<Broadcaster>()` → `None`). To make persist-then-
broadcast the single path (SC#1) **without** pushing setup burden onto consumers:

- When bootstrap registered no `Broadcaster`, the **framework provides a default in-process
  `Broadcaster`** so `App::get::<Broadcaster>()` is always `Some` by the time the offload hooks
  register.
- `register_offload_hooks()` (the persist-only variant) is **deleted**;
  `register_offload_hooks_with_broadcaster()` becomes the sole registration function.
- Worker-only deployments get a default in-process hub that publishes to nobody. This is
  harmless: the broadcaster-aware hook is already best-effort and swallows send failures /
  zero-subscriber sends (`offload.rs` `broadcast_delta`), and the snapshot remains the
  authoritative record (Phase 247 D-02 / Pitfall 5).
- **Rejected:** `Option<Arc<Broadcaster>>` single fn (keeps a runtime persist-vs-broadcast
  branch inside the hook); requiring consumers to always register a `Broadcaster` (breaks
  existing worker-only boots).

### D-02 — Full linearization of `run_common_boot`
`framework/src/app.rs::run_common_boot` currently registers the hook at **four** call sites
(the `redis-transport` attach block with two early-`return`s, plus the bottom `if/else`) and
spawns the in-process worker in **three** places. Converge to one linear flow:

1. run `bootstrap_fn`; init the queue DB connection (unchanged guards),
2. **ensure a `Broadcaster`** (per D-01),
3. **attach the shared transport** if `transport_redis_url` is configured (the existing
   feature-gated Redis attach; `with_transport` still runs before any WebSocket client connects
   — Pitfall WR-03),
4. **register the offload result hook once**,
5. **spawn the in-process worker once** when `!no_worker && has_registered_jobs()`.

Removes all duplicate registration/spawn calls and the early-`return`s. Preserves the WR-01
ordering constraints and the D-07 feature-off + URL-set `warn!`.

### D-03 — Narrow sweep boundary (244–249 introductions only)
Remove only transitional / "for compatibility" / dual-path constructs **introduced during
244–249**. Pre-existing legacy that predates offload is explicitly **kept** — it is load-bearing
for real old data / deployments and is a separate concern:
- `ferro-queue/src/dispatcher.rs` `#[deprecated(since = "0.2.0")]` dispatch alias — **keep**.
- `ferro-queue/src/db.rs` legacy-row timestamp fallbacks (`created_at` for rows predating a
  column) — **keep**.
- `ferro-broadcast` legacy signing / "ok" sentinel auth paths — **keep**.

### D-04 — Cleanliness verification: one-time grep, comment neutralization
- SC#2 ("structural grep is clean") is evidenced by a **one-time grep** — record the command
  and its clean output in the phase artifacts (VERIFICATION). No permanent CI grep-guard test
  is added (over-engineering for a one-time sweep; behavior is guarded by the 247 suite).
- `OffloadResult::Pending` is confirmed a **plain additive enum variant** with no dead
  compatibility handling in production code. The only "backward-compat" text lives in the
  `offload_result_pending_round_trip` **test** comments/assertions, which are a legitimate
  serde-additivity regression guard. **Keep the variant and the test; reword the "backward-
  compat" comments to neutral** (e.g. "existing completed/failed envelopes still deserialize"),
  per the repo-voice convention and the no-"for compatibility"-comments rule.

### Claude's Discretion
- **How the default `Broadcaster` is installed** (D-01): registering it as a singleton via
  `App::singleton(..)` — so `App::get::<Broadcaster>()` returns it consistently everywhere,
  mirroring the Redis path's `App::singleton(bc2)` — is the recommended default, but the exact
  construction (singleton vs local-to-boot) is left to planning as long as the single
  registration path holds.
- Exact final flow control of the flattened `run_common_boot` (helper extraction, ordering of
  the `warn!`), provided D-02's five steps and the WR-01/WR-03 ordering constraints are met.
- Precise neutral wording of the reworded `Pending` test comments.
- The exact grep pattern set used as SC#2 evidence.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `register_offload_hooks_with_broadcaster()` already handles the zero-subscriber / no-transport
  case gracefully (best-effort send, `warn!`-logged and swallowed) — the default broadcaster in
  D-01 needs no new tolerance logic.
- `App::singleton()` / `App::get::<Broadcaster>()` — the container already replaces the
  `Broadcaster` singleton on the Redis attach path; the same mechanism installs the default.
- `ferro_broadcast::Broadcaster` in-process hub — the existing default transport; no new type.

### Established Patterns
- Feature-branch convention: delete replaced code, no versioned names, no "removed code"
  comments (CLAUDE.md Architecture Principles).
- Best-effort result delivery with the snapshot as the authoritative record (247 D-02): the
  publish-to-nobody default hub is consistent with this.
- Behavior-preserving refactor guarded by an existing integration suite (the 247 tests).

### Integration Points
- `run_common_boot` is the single shared boot step for both `serve` and `run_worker` (248) — the
  linearization affects both entry paths and must keep the WR-03 "attach transport before any
  WebSocket client connects" ordering.
- `ferro-queue::register_offload_result_hook` is `OnceLock` — re-registration is silently
  ignored; the single call site makes this a non-issue.

</code_context>

<specifics>
## Specific Ideas

- The in-tree comments currently contradict themselves — `app.rs` says the `None`-broadcaster
  fallback is both "preserved for headless worker-only deployments" and "removed by Phase
  249.1." D-01 resolves this: the worker-only need is real, so removal is achieved by
  guaranteeing a default broadcaster, not by dropping the capability. Remove the now-stale
  "Phase 249.1 removes it" and "preserved for…" comments as part of the sweep.
- Convergence target is one linear `run_common_boot` and one registration function — the reader
  should see a single canonical result-hook path, not a menu of branches.

</specifics>
