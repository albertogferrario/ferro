<objective>
Land F5: two related runtime gaps shipped together per D-F5 in CONTEXT.md.

(a) `Input` components declaring `input_type: "file"` currently produce no `<input type="file">` because `InputType` has no `File` variant — serde falls back to the `Text` default. Add the variant, the `accept` prop, and the render arm.

(b) `Form` components declaring `enctype: "multipart/form-data"` currently render with the browser default encoding (`application/x-www-form-urlencoded`) because `FormProps` has no `enctype` field. Add the field, emit the attribute when set.

Per D-F5: shipping either alone unblocks nothing. A `<form>` without `enctype=multipart/form-data` cannot carry a file; a file input on a form encoded as urlencoded is encoded as text. Single plan, two emitter changes, one self-check that proves the combination.

Purpose: the consumer's staff create form (avatar upload, JPEG/PNG/WebP up to 5 MB) becomes spec-authorable. Removes the consumer-side band-aid (Content-Type branching in every file-upload controller).

Output:
- `ferro-json-ui/src/component.rs` — `InputType::File` enum variant, `InputProps.accept` field, `FormProps.enctype` field.
- `ferro-json-ui/src/render/form.rs` — `render_input` `InputType::File` arm, `render_form` enctype emission, three new tests pin the behavior.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer-authored spec → `Input[type=file]` render | The spec author controls the `accept` value; it becomes an HTML attribute. |
| browser-submitted multipart body → server handler | Multipart parsing happens at the consumer's controller; ferro-json-ui does not validate the file content. |
| browser → consumer server | The `enctype="multipart/form-data"` attribute changes how the browser encodes the body; CSRF and authorization remain the server's responsibility. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-175-06-01 | S (Spoofing) / I (Information disclosure) | the `accept` attribute as a security control | accept | The `accept` attribute is a **client-side advisory hint only** — browsers do not enforce it on the actual file content. A user can pick any file via the file picker regardless of `accept`. The spec layer must NOT claim it provides server-side MIME enforcement. **Consumers MUST validate the uploaded file's MIME type server-side** (CLAUDE.md "validate all inputs"). This is documented as a comment on the `accept` field. The framework does not enforce this; ferro-json-ui's responsibility ends at emitting the hint. |
| T-175-06-02 | D (Denial of Service) | multipart body size | accept | ferro-json-ui emits HTML only; it does not parse multipart bodies. The DoS surface for large multipart bodies lives in the consumer's controller and/or the framework's `Request::file()` primitive (Phase 158). Out of scope for this plan — F5 does not change parsing. The consumer must apply request-size limits at the controller layer. |
| T-175-06-03 | T (Tampering) | CSRF on multipart-encoded forms | mitigate | The `enctype="multipart/form-data"` attribute does not affect CSRF protection — the form action URL is still subject to the framework's CSRF middleware. ferro-json-ui's emission of `enctype` does not interact with CSRF tokens. CSRF protection lives at the framework layer (the consumer's `Form` action endpoint MUST be CSRF-protected just like any non-multipart endpoint; nothing changes in this plan). |
| T-175-06-04 | I (Information disclosure) | file input emitting `value=""` would echo a server-controlled path | mitigate | The `InputType::File` render arm explicitly omits the `value` attribute. Even if a `default_value` or `data_path` is set on `InputProps`, the file arm ignores it. Browsers reject `value` on file inputs as a security restriction; emitting it would either be silently ignored or trigger a console error. The omission is intentional and pinned by the `input_file_renders_file_type_and_accept` test's negative assertion. |
| T-175-06-05 | I (Information disclosure) | XSS via `accept` value | mitigate | The `accept` value is passed through `html_escape` before insertion into the HTML attribute, matching the pattern used by every other attribute emitter in `render_input`. A hostile spec author could pass `image/jpeg" onfocus="…`; the escape neutralizes it. |
</threat_model>
