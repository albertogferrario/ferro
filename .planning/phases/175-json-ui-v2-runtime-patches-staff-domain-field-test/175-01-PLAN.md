## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer-authored spec → ferro-json-ui parser | A hostile or accidentally-malformed JSON spec crosses this boundary; the parser must terminate. |
| in-memory Spec → render walker | Recursive walk over the element graph; stack depth is the resource at risk. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-175-01-01 | D (Denial of Service) | `Spec::from_json` depth validator | mitigate | `MAX_NESTING_DEPTH = 16` is the DoS guard. Parse cost is linear in node count, not depth; the limit caps stack usage of the recursive walker. 16 is small enough that the worst-case stack frame at the deepest leaf is bounded by `16 * sizeof(walker_frame)` (~few KB), well under any reasonable Rust thread stack. New consumer evidence required to raise further; reject any plan proposing >32 without it. |
| T-175-01-02 | D (Denial of Service) | `render_element` walker | accept | The walker tripwire at `depth > MAX_NESTING_DEPTH + 1` is a belt-and-braces guard for hand-mutated specs that bypass `from_json`. Render output is a comment string; no exception propagates. The cost of reaching the tripwire is bounded by the parse-time limit. |
| T-175-01-03 | I (Information disclosure) | walker tripwire diagnostic | accept | The new diagnostic comment names the depth and the limit. Both are static information — the depth equals MAX_NESTING_DEPTH+2, the limit is a published constant. No PII, no internal addresses, no secrets leaked. |
| T-175-01-04 | T (Tampering) | cycle detector vs depth tripwire | mitigate | Splitting the diagnostic strings means a real cycle (revisit of an already-walked node) is no longer misattributed to depth-limit exhaustion. The parse-time `SpecError::Cycle { path }` continues to fire on revisit; only the cosmetic message of the walker comment changed. The cycle detector itself is unchanged. |
</threat_model>
