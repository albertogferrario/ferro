<objective>
Fix the metrics 404 path explosion vulnerability where unmatched routes store raw request paths as HashMap keys, allowing bot scanners to create unlimited entries.

Purpose: Eliminate a DoS vector — every unique 404 URL creates a permanent HashMap entry. Bot probes like `/wp-admin/x`, `/.env`, `/api/v99/random` grow the store unboundedly.
Output: Metrics store bounded by registered routes + 1 "UNMATCHED" bucket, with a safety cap.
</objective>

<task type="auto">
  <name>Task 1: Normalize unmatched routes and cap metrics entries</name>
  <files>framework/src/middleware/metrics.rs, framework/src/metrics/mod.rs</files>
  <action>
  Two changes:

  1. In `framework/src/middleware/metrics.rs` line 58, change the fallback from raw path to a fixed bucket:
     - Current: `request.route_pattern().unwrap_or_else(|| path.to_string())`
     - Change to: `request.route_pattern().unwrap_or_else(|| "UNMATCHED".to_string())`
     This bounds metrics entries to `registered_routes + 1` instead of unbounded.

  2. In `framework/src/metrics/mod.rs`, add a safety cap to `record_request`:
     - Add `const MAX_ROUTE_ENTRIES: usize = 1000;` to the module.
     - Before the `entry()` call in `record_request`, check `store.routes.len() >= MAX_ROUTE_ENTRIES`. If at cap AND the key doesn't already exist, return early (skip recording). Existing keys must still be updated.
     - This is a defense-in-depth measure — normalization handles the common case, the cap prevents any other unbounded growth scenario.
  </action>
  <verify>cargo test -p ferro-rs --lib metrics -- --nocapture</verify>
  <done>Unmatched routes normalized to "UNMATCHED". Entry cap prevents unbounded growth. All existing metrics tests pass.</done>
</task>
