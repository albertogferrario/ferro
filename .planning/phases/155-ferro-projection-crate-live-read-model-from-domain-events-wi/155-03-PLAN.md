<objective>
Land the SeaORM persistence layer for ferro-projection: the `projection_snapshots` table schema (via `migration.rs`) and the `Model` / `Entity` / `ActiveModel` types (via `entity.rs`). After this plan, the persistence layer is ready for plan 05 to drive `apply_event`'s upsert via `OnConflict::columns([ProjectionName, Key])`.

This plan implements the **composite primary key** pattern — the single load-bearing dimension that has no in-workspace precedent (RESEARCH.md §Technical Concerns #1, PATTERNS.md §"No Analog Found" first row). All current ferro-* entities use single-column PKs (UUID or non-UUID); ferro-projection's `(projection_name, key)` composite PK is the v0 first use. The pattern is well-documented in SeaORM 1.1.x docs:

- **At the entity level (D-24):** annotate BOTH columns with `#[sea_orm(primary_key, auto_increment = false)]`. SeaORM's DeriveEntityModel sees the two annotations and generates the composite `PrimaryKey` impl. Composite PK lookups use a tuple: `Entity::find_by_id((name, key))`.
- **At the migration level (D-24):** declare the composite PK via `.primary_key(Index::create().col(ProjectionName).col(Key))` inside the `Table::create()` builder. The two columns themselves are NOT marked `.primary_key()` individually (that would create two single-column PKs which is a schema error).

Migration table name: `projection_snapshots`. Migration ident name (for the SeaORM migrator's tracking table): `"m20260514_000001_create_projection_snapshots_table"` per RESEARCH.md §Technical Concerns #6 (Phase 154 used `m20260513`, Phase 155 ships one day later in the design timeline).

Purpose: provide a working SeaORM persistence surface that plan 05's `apply_event` can drive (`OnConflict::columns([Column::ProjectionName, Column::Key]).update_columns([Column::State, Column::Version, Column::UpdatedAt])`). The composite-PK smoke test is the **proving artefact** for RESEARCH.md §Risks R3 (composite PK no-workspace-precedent risk).
