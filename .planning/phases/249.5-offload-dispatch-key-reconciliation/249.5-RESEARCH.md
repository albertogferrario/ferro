# Phase 249.5: Offload Dispatch-Key Reconciliation — DISPATCH-KEY-01 (GAP CLOSURE)

**Researched:** 2026-08-15
**Domain:** Rust proc-macro emission, ferro-queue worker dispatch, integration test harness
**Confidence:** HIGH — all claims verified against current source

---

## Summary

The milestone audit identified a systematic dispatch key mismatch that prevents any
`#[offload]`-derived job from ever being claimed and run on the `QUEUE_CONNECTION=db`
path. The two ends of the dispatch handshake are using different keys:

- **Enqueue** (`dispatcher.rs:191`) writes `job_type = self.job.name()`, which for a
  derived job resolves to the **bare struct ident string** (e.g.,
  `"ReportsBuildMonthlyJob"`) — a compile-time string literal stored in
  `job_ident_str` and emitted verbatim by the macro (`offload.rs:377`).
- **Worker registration and lookup** (`worker.rs:184`, `worker.rs:484`) both use
  `std::any::type_name::<J>()`, which includes the full module path (e.g.,
  `"myapp::reports::ReportsBuildMonthlyJob"`).

The `handlers.get(&job_type)` call in `spawn_job` therefore always misses for derived
jobs, triggering the "No handler registered — releasing job for retry" branch
(`worker.rs:487–491`). The job release-loops until its `max_retries` are exhausted
and the row is parked as failed — no snapshot or delta is ever produced.

The fix is a one-line change in `ferro-macros/src/offload.rs`: substitute the
compile-time bare-ident literal `#job_ident_str` in the emitted `fn name()` body with
the runtime expression `std::any::type_name::<Self>()`. The `Job` trait's `fn name()`
returns `&'static str`; `type_name` also returns `&'static str`, so the return type
matches without change. The macro's module-level doc comment already describes this
intended behavior and must be updated to match the corrected implementation.

A companion integration test must exercise the full enqueue→claim→dispatch path for a
derived job declared in a non-crate-root module (to prove the fully-qualified key
includes the module segment and still matches).

**Primary recommendation:** Change one expression in the macro's `emit_job_items`
function; update the doc comment; add one DB-backed integration test.

## Verification: Audit Claims vs. Current Source

### Claim 1: Enqueue writes `job_type = self.job.name()`

**VERIFIED** — `ferro-queue/src/dispatcher.rs:191`:

```rust
let job_type = self.job.name().to_string();
```

This is inside `dispatch_to_queue()`, which is the path taken when
`QUEUE_CONNECTION` is anything other than `"sync"`. The sync path
(`dispatch_immediately`, lines 145–176) never writes to the DB at all, so the
key mismatch is irrelevant there. The `job_type` local is then passed to
`crate::db::enqueue(conn, queue, &job_type, ...)` on line 194.

### Claim 2: Derived `name()` returns the bare struct ident literal

**VERIFIED** — `ferro-macros/src/offload.rs:236–237, 376–378`:

```rust
// line 236
let job_ident_str = job_ident.to_string();

// lines 376-378 (inside the quote! block)
fn name(&self) -> &'static str {
    #job_ident_str
}
```

`job_ident` is constructed at line 144 as `format_ident!("{}{}Job", trait_ident,
method_pascal)`. Its `to_string()` yields the bare identifier (e.g.,
`"ReportsBuildMonthlyJob"`) — no module path, no crate prefix. This is the value
written to the `job_type` column.

The module-level doc comment at lines 24–31 says "the DB `job_type` column is
populated by `type_name` at enqueue time." This is **incorrect** as of the current
implementation — the column is populated by `self.job.name()`, which for derived jobs
is the bare ident, not `type_name`. The comment accurately describes the desired
post-fix behavior but misdescribes the current behavior.

### Claim 3: Worker registers and looks up by `std::any::type_name::<J>()`

**VERIFIED** — `ferro-queue/src/worker.rs`:

Registration at line 184:
```rust
let type_name = std::any::type_name::<J>().to_string();
// ...
self.handlers.insert(type_name, handler);   // line 204
```

Lookup in `spawn_job` at line 484:
```rust
let handler = match handlers.get(&job_type) {
```

Where `job_type` (line 469) is `job_row.job_type.clone()` — i.e., whatever string
was written to the `job_type` column at enqueue time. If that column holds the bare
ident but `handlers` was keyed by the fully-qualified `type_name`, the `get` returns
`None` every time.

The "No handler registered" warning is at line 487; the short-delay release is at
lines 489–491.

### Claim 4: Hand-written jobs are unaffected

**VERIFIED** — `ferro-queue/src/job.rs:49–51`:

```rust
fn name(&self) -> &'static str {
    std::any::type_name::<Self>()
}
```

The default `Job::name()` implementation already returns `type_name`, so hand-written
jobs that do not override `name()` match the worker's registration key exactly. Only
`#[offload]`-derived jobs override `name()` with the bare ident literal.

## Standard Stack (for the fix)

### Core

| Component | Location | Version | Why Standard |
|---|---|---|---|
| `proc_macro2` / `quote` | ferro-macros/Cargo.toml | workspace | All macro emission uses this |
| `std::any::type_name` | Rust stdlib | stable | The target expression for the fix |
| `&'static str` | Return type of `Job::name()` | — | `type_name::<T>()` returns `&'static str` |

**No new dependencies** — the fix touches only the string expression in an existing
`quote!` block.

### Fix expression

The current emitted body:
```rust
fn name(&self) -> &'static str {
    #job_ident_str          // bare literal, e.g. "ReportsBuildMonthlyJob"
}
```

Must become:
```rust
fn name(&self) -> &'static str {
    ::std::any::type_name::<Self>()
}
```

`Self` is in scope inside the `impl ::ferro::queue::Job for #job_ident` block; the
generated code refers to `Self` without ambiguity. The `::std::any::type_name::<Self>()`
expression compiles to a `&'static str` referencing a string interned by the compiler
for each concrete type, including its full module path. The `::std::` prefix follows
the project convention of emitting only fully-qualified paths in macro output.

In `quote!` terms, the substitution replaces `#job_ident_str` with the token stream
`::std::any::type_name::<Self>()`. No local variable (`job_ident_str`) is removed
from `emit_job_items` — it is still used for the `Error::job_failed` diagnostic in
`call_expr`/`value_capture_expr`, for the doc comment, and for `JobRegistrarEntry.name`.

```
              │
              ▼
```

```
              │   handlers was keyed by:
              │   type_name::<J>() = "myapp::reports::ReportsBuildMonthlyJob"
              │
              └─ Some(handler) → execute → snapshot → delta ✓
```

### Recommended Project Structure

No structural changes — the fix is a targeted edit to one expression inside the
existing `emit_job_items` function and a doc-comment update.

### Test harness pattern (from existing tests)

All existing DB-backed tests follow the same pattern, established in `shutdown.rs` and
`worker_runtime.rs`:

```rust
// 1. Temp-file SQLite — never in-memory (avoids connection-sharing issues)
let db_file = tempfile::NamedTempFile::new().unwrap();
let db_url = format!("sqlite://{}?mode=rwc", db_file.path().display());
let conn = Database::connect(&db_url).await.unwrap();

// 2. Inline migrator
struct TestMigrator;
#[async_trait]
impl MigratorTrait for TestMigrator {
    fn migrations() -> Vec<Box<dyn MigrationTrait>> {
        vec![Box::new(CreateJobsTable)]
    }
}
TestMigrator::up(&conn, None).await.unwrap();

// 3. Use ferro_queue::{enqueue, claim, delete_job, ...} directly
// or WorkerLoop::drain_for_test() for full dispatch
```

**Key insight for the new test:** `WorkerLoop` requires a `&'static DatabaseConnection`
(see `worker.rs:252`). The existing `run()` and `drain_for_test()` methods call
`crate::db::Queue::connection()`, which returns the global static. To use
`drain_for_test()` the test must call `Queue::init(conn).await` to set the global —
but `OnceLock` only accepts the first write, making this approach problematic in a
multi-test binary.

The workaround used by `worker_runtime.rs` is to **not** call `WorkerLoop::drain_for_test()`
but to call `claim()`/`delete_job()` directly. For the new test we need the worker to
actually execute the handler (not just claim), so we need `drain_for_test`. This means
the new test either:

(a) Uses `Queue::init()` once in the binary (acceptable if it runs alone or is the
    first test), or
(b) Calls `spawn_job` indirectly by calling `WorkerLoop::drain_for_test()` after
    calling `Queue::init()`.

The safest approach is to isolate the new test in its own file (each integration test
file compiles as a separate binary in Rust), calling `Queue::init()` once at the top
of the single outer `#[tokio::test]` function.

**The new test must declare its derived job in a nested module** so the fully-qualified
`type_name` differs from the bare ident:

```rust
// ferro-queue/tests/dispatch_key_derived_job.rs

mod reports {
    use ferro_queue::{async_trait, Error, Job};
    use serde::{Deserialize, Serialize};

    #[derive(Debug, Clone, Serialize, Deserialize)]
    pub struct BuildMonthlyJob { pub month: u32 }

    #[async_trait]
    impl Job for BuildMonthlyJob {
        // Post-fix: name() inherits default → type_name::<Self>()
        async fn handle(&self) -> Result<(), Error> {
            DISPATCHED.store(true, Ordering::SeqCst);
            Ok(())
        }
    }
}
```

The test then enqueues `reports::BuildMonthlyJob`, registers it with a `WorkerLoop`,
calls `drain_for_test()`, and asserts the job was claimed (row deleted) and the
`DISPATCHED` flag is set. A second assertion confirms the job was not release-looped
(attempt count stays at 0 on the row — or the row no longer exists after execution).

### Why the milestone missed this (Task 7)

All existing offload tests exercise either:
- Sync mode (no DB involvement, no key mismatch possible),
- The inventory registration count only (`registered_job_count() >= 1`), or
- Raw `enqueue/claim` with hand-supplied type strings (bypassing `Job::name()`).

None of them call `WorkerLoop::drain_for_test()` (or `run()`) on a derived job that
was enqueued via `self.job.name()`. The key mismatch only manifests when the full
enqueue→worker→claim→dispatch chain runs end-to-end on the db path.

## Common Pitfalls

### Pitfall 1: Removing `job_ident_str` from `emit_job_items`

**What goes wrong:** The variable `job_ident_str` appears in multiple places in
`emit_job_items` beyond `fn name()`: in `Error::job_failed` diagnostic messages inside
`call_expr`/`value_capture_expr` (lines 262–264, etc.) and in the `JobRegistrarEntry.name`
field (line 409). Removing the variable breaks all of these.

**Prevention:** Keep `job_ident_str` as-is; only replace its use in the `fn name()`
body. The substitution is surgical: one occurrence of `#job_ident_str` in the `impl
Job` block, not the variable declaration.

### Pitfall 2: Module-path instability caveat in the doc comment

**What goes wrong:** The post-fix `name()` returns `type_name::<Self>()`, which
includes the full module path. Moving the enclosing struct to a different module
changes the key and breaks dispatch for jobs already in the queue. This is a real
operational consequence and must be documented.

**Prevention:** The module-level doc comment in `offload.rs` (lines 23–31) already
documents this correctly under "Dispatch key caveat (Pitfall 2)." After the fix, the
comment's statement about `type_name` will match the actual implementation. The
doc-comment on the emitted struct (lines 356–363) also mentions this. Both must be
audited for accuracy post-fix.

### Pitfall 3: OnceLock collision in the integration test

**What goes wrong:** `Queue::init()` uses a `OnceLock` that accepts only one write.
Calling it from two test functions in the same binary panics on the second call (or
returns `Err`). Using `Queue::connection()` without calling `init()` panics.

**Prevention:** Wrap the entire new integration test in a single outer `#[tokio::test]`
function (the pattern established in `worker_runtime.rs`). This gives one
`Queue::init()` call per binary. The new test file compiles as its own binary, so it
does not share the `OnceLock` with other test files.

### Pitfall 4: `drain_for_test` timing

**What goes wrong:** `drain_for_test()` spawns handlers via `tokio::spawn`. After the
loop exits (three consecutive idle rounds), in-flight spawned tasks may not have
completed. Asserting the `DISPATCHED` flag immediately after `drain_for_test()` returns
can be a race.

**Prevention:** `drain_for_test()` calls `tokio::task::yield_now()` between claim
rounds and then sleeps `sleep_duration` for three idle rounds. With a short
`sleep_duration` (e.g., `Duration::from_millis(50)`) and a fast `handle()`, this is
sufficient. Use a channel or `AtomicBool` with a brief `yield_now` after
`drain_for_test()` returns, or use `drain_for_test` with a sufficiently long
`sleep_duration` to give spawned tasks time to complete.

### Pitfall 5: Test-collapse false-green (`-- <scenario_fn>` filter)

**What goes wrong:** If the single outer test function is named something short and
another test file happens to contain a function whose name contains the same substring,
a `cargo test -- <partial_name>` filter can match zero real test functions yet exit 0.

**Prevention:** Use a long, unique test function name (e.g.,
`dispatch_key_derived_job_enqueue_claim_dispatch_suite`). Verify with
`cargo test -p ferro-queue --test dispatch_key_derived_job -- --list` that exactly one
test function is listed.

### New integration test structure

File: `ferro-queue/tests/dispatch_key_derived_job.rs`

```rust
//! SC: DISPATCH-KEY-01 — an #[offload]-derived job declared in a nested module
//! is enqueued (db path), claimed, and executed by a WorkerLoop exactly once.
//!
//! Covers the gap identified in the 2026-08-15 re-audit: derived jobs use bare
//! ident as the dispatch key (enqueue side), but the worker registers handlers
//! by type_name. After the fix, both sides use type_name.

use std::sync::atomic::{AtomicBool, Ordering};

use sea_orm::Database;
use sea_orm_migration::MigratorTrait;

use ferro_queue::{async_trait, Error, Job, Queue, WorkerConfig, WorkerLoop, CreateJobsTable};
use serde::{Deserialize, Serialize};
use tempfile::NamedTempFile;

// ---------------------------------------------------------------------------
// Derived job in a nested module — ensures type_name includes the module segment
// ---------------------------------------------------------------------------

mod reports {
    use super::*;

    pub static DISPATCHED: AtomicBool = AtomicBool::new(false);

    #[derive(Debug, Clone, Serialize, Deserialize)]
    pub struct BuildMonthlyJob {
        pub month: u32,
    }

    // Hand-written impl — uses the default Job::name() = type_name::<Self>()
    // This mirrors what the fixed macro emits.
    #[async_trait]
    impl Job for BuildMonthlyJob {
        async fn handle(&self) -> Result<(), Error> {
            DISPATCHED.store(true, Ordering::SeqCst);
            Ok(())
        }
    }
}

struct TestMigrator;

#[async_trait::async_trait]
impl MigratorTrait for TestMigrator {
    fn migrations() -> Vec<Box<dyn sea_orm_migration::MigrationTrait>> {
        vec![Box::new(CreateJobsTable)]
    }
}

/// DISPATCH-KEY-01: derived job is claimed and dispatched exactly once on the db path.
///
/// One outer tokio::test — avoids OnceLock collision (Queue::init is global).
#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn dispatch_key_derived_job_enqueue_claim_dispatch_suite() {
    // 1. Temp-file SQLite.
    let db_file = NamedTempFile::new().unwrap();
    let db_url = format!("sqlite://{}?mode=rwc", db_file.path().display());
    let conn = Database::connect(&db_url).await.unwrap();
    TestMigrator::up(&conn, None).await.unwrap();
    Queue::init(conn).await.expect("Queue::init failed");

    // 2. Register the job with a WorkerLoop (mimicking WorkerLoop::from_registry
    //    after the macro fix — the registration key is type_name::<BuildMonthlyJob>).
    let mut config = WorkerConfig::default();
    config.sleep_duration = std::time::Duration::from_millis(50);
    let mut worker = WorkerLoop::new(config);
    worker.register::<reports::BuildMonthlyJob>();

    // 3. Enqueue the job on the db path.
    //    PendingDispatch::new(job).dispatch().await writes job_type = job.name()
    //    = type_name::<BuildMonthlyJob>() (post-fix) to the jobs table.
    ferro_queue::dispatch(reports::BuildMonthlyJob { month: 7 })
        .await
        .expect("enqueue failed");

    // 4. Drain: claim + execute. The worker must find the handler
    //    (handlers.get(&job_type) succeeds because both sides use type_name).
    worker.drain_for_test().await.expect("drain failed");

    // 5. Assert dispatched exactly once and not release-looped.
    assert!(
        reports::DISPATCHED.load(Ordering::SeqCst),
        "DISPATCH-KEY-01: handle() was never called — the job was release-looped, \
         indicating the dispatch key mismatch is not fixed"
    );
}
```

**Note on QUEUE_CONNECTION:** `dispatch()` calls `PendingDispatch::new(job).dispatch()`,
which checks `QueueConfig::is_sync_mode()`. The test must ensure `QUEUE_CONNECTION` is
not set to `"sync"` (the default when unset is db mode). The test should either
unset the env var or set it to `"db"` at the start.

## Runtime State Inventory

This is a code/macro fix with no rename or migration component. There is no stored
data, live service config, OS-registered state, secrets, or build artifacts tied to
the dispatch-key value that would persist across the fix.

**One operational note:** Any jobs already enqueued in a real application's database
with the old bare-ident `job_type` value will not be reclaimable after the fix — the
worker will no longer have a handler under that key. Since this project is pre-production
(`ferro-rs` 0.3.9 on crates.io, no live deployments with the v16.4 offload feature),
this is not a migration concern for this phase. The docs should note the module-rename
caveat.

## Open Questions

1. **QUEUE_CONNECTION env var in the new integration test**
   - What we know: `QueueConfig::is_sync_mode()` reads `QUEUE_CONNECTION`; the test
     must not have it set to `"sync"` or the job will execute in-process and never hit
     the DB path.
   - What's unclear: whether CI has `QUEUE_CONNECTION` set globally.
   - Recommendation: explicitly `std::env::remove_var("QUEUE_CONNECTION")` or
     `std::env::set_var("QUEUE_CONNECTION", "db")` at the start of the test, wrapped
     in a drop-guard (following the `dispatcher.rs` test pattern).

2. **`drain_for_test()` returns before spawned tasks complete**
   - What we know: `drain_for_test()` calls `yield_now()` and sleeps 3 × `sleep_duration`
     after the last claim round, then returns.
   - What's unclear: whether 150ms (3 × 50ms) is sufficient for the `AtomicBool` to
     be set by the spawned task.
   - Recommendation: set `sleep_duration = Duration::from_millis(100)` in the test
     config (300ms total idle wait), or assert with a brief poll loop.
