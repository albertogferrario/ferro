## Warnings

### WR-01: `std::env::set_var` without prior env cleanup risks cross-test pollution if the binary is ever extended

**File:** `framework/tests/dispatch_key_derived_job.rs:73`
**Issue:** `std::env::set_var("QUEUE_CONNECTION", "db")` mutates a process-global variable unconditionally and does not restore it at the end of the function. Within this binary the test is the sole test function, so there is currently no pollution hazard. However, the `QUEUE_CONNECTION` write is not bracketed by any teardown, and `#[serial_test::serial]` serializes within the same binary but not across integration-test binaries (each has its own process, so cross-binary isolation is fine). The real risk is additive: if a second test function is added to this binary in the future it will inherit the `"db"` value whether or not it expects synchronous dispatch.

The existing analog `offload_result_round_trip.rs` has the same pattern and no restoration there either, so this is a project-wide convention rather than an isolated defect in this phase. Still worth flagging because this binary is the most likely candidate for test additions given its focused fixture setup.

**Fix:** Either document the invariant explicitly (one test only, single binary) or wrap with a restore guard:
```rust
let _guard = {
    let prev = std::env::var("QUEUE_CONNECTION").ok();
    std::env::set_var("QUEUE_CONNECTION", "db");
    scopeguard::defer_on_unwind!(if let Some(v) = prev { std::env::set_var("QUEUE_CONNECTION", v); });
    ()
};
```
A lighter alternative — acceptable given the existing codebase convention — is a prominent comment:
```rust
// NOTE: mutates a process-global env var. This binary must remain single-test;
// any addition here must either restore the var or also set QUEUE_CONNECTION=db.
std::env::set_var("QUEUE_CONNECTION", "db");
```

### IN-01: Unused import `Job` in the test file

**File:** `framework/tests/dispatch_key_derived_job.rs:11`
**Issue:** `ferro_queue::Job` is imported but never referenced directly in the test body. The `#[offload]` macro derives the `impl Job` automatically; the test code itself does not call any `Job` trait methods.
**Fix:** Remove `Job` from the import list:
```rust
use ferro_queue::{dispatch, CreateJobsTable, Queue, WorkerConfig, WorkerLoop};
```
The plan template included it (plan lines 229) and the gate passed because `#![allow(dead_code)]` at file scope suppresses the unused-import warning. Once removed, the file-level `allow` can stay or be narrowed — it is still needed for the `Month` struct (exported `pub` but only used internally).

### IN-02: The `DISPATCHED` atomic does not reset between potential re-runs of the same binary under test harnesses that reuse process state

**File:** `framework/tests/dispatch_key_derived_job.rs:23`
**Issue:** `pub static DISPATCHED: AtomicBool = AtomicBool::new(false)` is process-global and is never reset to `false` after the test. Under standard `cargo test` each integration-test binary runs in a fresh process so this is not a practical problem today. It is worth noting because `Queue::init` uses a `OnceLock` (already flagged in the plan's context section) and `bootstrap()` is also a one-shot call; the test cannot be run twice in the same process regardless — the `DISPATCHED` reset is the least of the re-run constraints. No code change required; this is informational.
**Fix:** No action required. A comment next to the static noting the single-run constraint is sufficient if future authors are expected to maintain this binary:
```rust
// Process-global; never reset. This binary executes exactly one test function
// and relies on a fresh process per `cargo test` invocation.
pub static DISPATCHED: AtomicBool = AtomicBool::new(false);
```
