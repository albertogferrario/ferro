<objective>
Add ThemeMiddleware to the framework with resolver chain, 3 concrete resolvers, task-local context, and CSS injection into the JSON-UI rendering pipeline.

Purpose: Enables per-request theme selection for multi-tenant white-labeling. ThemeMiddleware mirrors the existing TenantMiddleware pattern exactly -- resolver chain with first-match semantics, task-local storage, and framework re-exports behind a feature flag. Three concrete resolvers implement the locked resolution order: TenantContext.theme -> request header -> app default. TenantThemeResolver uses moka TTL cache for loaded themes, matching the TenantLookup caching pattern. The JSON-UI render pipeline injects the active theme's CSS into LayoutContext.head so the browser resolves semantic token classes.

Output: framework/src/theme/ module with ThemeMiddleware, ThemeResolver trait, 3 concrete resolvers (TenantThemeResolver, HeaderThemeResolver, DefaultResolver), current_theme() accessor, framework Cargo.toml/lib.rs wiring, and CSS head injection in json_ui/mod.rs.

       **3 concrete resolvers per CONTEXT.md locked decision "Resolution order: TenantContext.theme -> request header -> app default":**

       a) `TenantThemeResolver` -- reads theme name from TenantContext, loads from disk with moka cache:
          ```rust
          pub struct TenantThemeResolver {
              /// moka TTL cache: theme_name -> Arc<Theme>
              cache: moka::sync::Cache<String, Arc<Theme>>,
              /// Base directory containing theme subdirectories
              themes_dir: String,
          }

          impl TenantThemeResolver {
              pub fn new(themes_dir: impl Into<String>) -> Self {
                  Self {
                      cache: moka::sync::Cache::builder()
                          .time_to_live(std::time::Duration::from_secs(300))
                          .max_capacity(100)
                          .build(),
                      themes_dir: themes_dir.into(),
                  }
              }
          }

          #[async_trait]
          impl ThemeResolver for TenantThemeResolver {
              async fn resolve(&self, _req: &Request) -> Option<Arc<Theme>> {
                  // Pull theme name from TenantContext (already resolved by TenantMiddleware)
                  let tenant = current_tenant()?;
                  let theme_name = tenant.plan.as_deref()?;
                  // NOTE: Uses tenant.plan as theme name for now. When a dedicated
                  // theme_name field is added to TenantContext, switch to that.
                  // For v1, the plan name doubles as theme selector.
                  // Check moka cache
                  if let Some(cached) = self.cache.get(theme_name) {
                      return Some(cached);
                  }
                  // Load from disk, cache it
                  let path = format!("{}/{}", self.themes_dir, theme_name);
                  let theme = Arc::new(Theme::from_path(&path).ok()?);
                  self.cache.insert(theme_name.to_string(), Arc::clone(&theme));
                  Some(theme)
              }
          }
          ```
          Uses `moka::sync::Cache` (already in framework deps via TenantLookup). 5-minute TTL, 100 capacity.
          Reads `current_tenant()` for the theme name -- requires TenantMiddleware to run before ThemeMiddleware.
          Note: TenantContext does not have a dedicated `theme_name` field yet. For now, this resolver uses `tenant.plan` as a configurable stand-in. Users can also provide a custom ThemeResolver implementation that reads from any TenantContext field. When a `theme_name` field is added to TenantContext in a future phase, this resolver will be updated.

       b) `HeaderThemeResolver` -- reads `X-Theme` request header:
          ```rust
          pub struct HeaderThemeResolver {
              themes_dir: String,
              cache: moka::sync::Cache<String, Arc<Theme>>,
          }

          impl HeaderThemeResolver {
              pub fn new(themes_dir: impl Into<String>) -> Self {
                  Self {
                      themes_dir: themes_dir.into(),
                      cache: moka::sync::Cache::builder()
                          .time_to_live(std::time::Duration::from_secs(300))
                          .max_capacity(100)
                          .build(),
                  }
              }
          }

          #[async_trait]
          impl ThemeResolver for HeaderThemeResolver {
              async fn resolve(&self, req: &Request) -> Option<Arc<Theme>> {
                  let theme_name = req.header("x-theme")?;
                  if let Some(cached) = self.cache.get(theme_name) {
                      return Some(cached);
                  }
                  let path = format!("{}/{}", self.themes_dir, theme_name);
                  let theme = Arc::new(Theme::from_path(&path).ok()?);
                  self.cache.insert(theme_name.to_string(), Arc::clone(&theme));
                  Some(theme)
              }
          }
          ```

    In `framework/src/json_ui/mod.rs`, in the `render_html` method, after the Tailwind CDN script and custom_head are appended to `head`, inject the theme CSS:

    ```rust
    // After existing head assembly (tailwind_cdn + custom_head):
    #[cfg(feature = "theme")]
    {
        use crate::theme::context::current_theme;
        if let Some(theme) = current_theme() {
            head.push_str(&format!("<style>{}</style>", theme.css));
        }
    }
    ```

    This injects the theme's CSS (which contains `@theme` directives) as an inline `<style>` tag. The Tailwind CDN script (loaded before it in the `<head>`) processes the `@theme` block at runtime, registering the custom properties and generating utility classes like `bg-primary`, `text-surface`, etc.

    The injection MUST happen:
    - AFTER the Tailwind CDN `<script>` tag (so CDN can process `@theme`)
    - AFTER custom_head (user's custom head content takes lower priority)
    - BEFORE plugin CSS assets (plugins should layer on top of theme)
