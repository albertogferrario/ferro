## Warnings

### WR-01: Recompute hook uses `?` placeholders without Postgres branch

**File:** `app/src/controllers/mcp.rs:95-119`

**Issue:** The recompute hook issues two raw SQL statements via
`Statement::from_sql_and_values`. Both use `?` positional placeholders:

```
"SELECT order_id FROM line_items WHERE id = ? AND tenant_id = ?"   (line 97)
"UPDATE orders SET total = (SELECT ... WHERE order_id = ? ...) WHERE id = ? AND tenant_id = ?"   (line 115-118)
```

`Statement::from_sql_and_values` does **not** translate placeholders — the SQL is
passed verbatim to the sqlx driver (documented in
`framework/src/validation/rules_async.rs:94-95`). Postgres requires `$1`/`$2`
positional syntax; `?` is a MySQL/SQLite convention. The existing `check_is_manager`
function in the same file (line 47-54) gets this right with an explicit `match
backend { DatabaseBackend::Postgres => "... $1", _ => "... ?" }`.

The sample app is SQLite-only today, so this silently passes all tests. If the
sample is ever pointed at Postgres — which `Cargo.toml` already enables with
`"sqlx-postgres"` — both statements will produce a runtime `DbErr` on every
line-item write, breaking the recompute hook entirely.

**Fix:** Mirror the backend-match pattern already present in `check_is_manager`:

```rust
// id-lookup on delete
let backend = db.get_database_backend();
let lookup_sql = match backend {
    sea_orm::DatabaseBackend::Postgres =>
        "SELECT order_id FROM line_items WHERE id = $1 AND tenant_id = $2",
    _ =>
        "SELECT order_id FROM line_items WHERE id = ? AND tenant_id = ?",
};
// ...
// recompute UPDATE
let update_sql = match backend {
    sea_orm::DatabaseBackend::Postgres =>
        "UPDATE orders SET total = (\
             SELECT COALESCE(SUM(amount), 0) FROM line_items \
             WHERE order_id = $1 AND deleted_at IS NULL\
         ) WHERE id = $2 AND tenant_id = $3",
    _ =>
        "UPDATE orders SET total = (\
             SELECT COALESCE(SUM(amount), 0) FROM line_items \
             WHERE order_id = ? AND deleted_at IS NULL\
         ) WHERE id = ? AND tenant_id = ?",
};
```

Alternatively, extract a shared `placeholder(backend, n)` helper (already exists in
`framework/src/write/mod.rs:184`) and build the SQL strings programmatically, as
the framework itself does.

### WR-02: Cross-tenant safety of the recompute UPDATE depends on `order_id` being trusted

**File:** `app/src/controllers/mcp.rs:112-122`

**Issue:** The recompute UPDATE is:

```sql
UPDATE orders SET total = (SELECT COALESCE(SUM(amount), 0)
                           FROM line_items
                           WHERE order_id = ? AND deleted_at IS NULL)
 WHERE id = ? AND tenant_id = ?
```

The `WHERE id = ? AND tenant_id = ?` predicate correctly scopes the UPDATE to the
calling tenant's order. The inner SELECT, however, does **not** filter
`line_items.tenant_id = ?`. If a data-integrity invariant were ever violated and a
`line_items` row carried a different `tenant_id` than its parent order (e.g. due to
a bug in an external import or a future migration), the SUM would silently include
foreign-tenant line items.

This is a defence-in-depth gap, not an exploitable attack path given the current
application (all line-item writes enforce `tenant_id` injection via the CRUD kernel,
and there is no cross-tenant order-id collision risk with auto-increment). However,
the inner subquery is cheap and the existing code already demonstrates the pattern:
the outer UPDATE is tenant-scoped, so extending the same predicate to the inner
SELECT costs nothing and closes the gap permanently.

**Fix:** Add `AND tenant_id = ?` to the inner SELECT and pass `tenant_id` as an
additional bound parameter:

```sql
UPDATE orders SET total = (
    SELECT COALESCE(SUM(amount), 0)
      FROM line_items
     WHERE order_id = ? AND tenant_id = ? AND deleted_at IS NULL
) WHERE id = ? AND tenant_id = ?
```

With bound values: `[order_id, tenant_id, order_id, tenant_id]` (adjusting `$N`
indices for Postgres).

## Info

### IN-01: `line_items` migration omits FK constraint from `order_id` to `orders.id`

**File:** `app/src/migrations/m20260624_create_line_items_table.rs:21`

**Issue:** `orders` declares an FK from `orders.tenant_id → tenants.id` (see
`m20260611_create_orders_table.rs:39-43`). The `line_items` migration declares
`order_id` as `big_integer().not_null()` with no corresponding FK to `orders.id`.
Without the FK, the DB cannot enforce referential integrity: a `create_line_item`
call with a non-existent `order_id` will INSERT successfully, and the subsequent
recompute hook will silently produce `total = 0` (the COALESCE result) on an order
that may not exist, or succeed against the wrong order in a future schema.

For a sample app this is acceptable (SQLite does not enforce FKs by default, and the
phase scope is the derived-field mechanism, not schema hardening), but the omission
is worth noting for any consumer that copies the migration pattern for production use.

**Fix (if hardening is desired):** Add a `ForeignKey` constraint mirroring the
existing `tenants` FK pattern:

```rust
.foreign_key(
    ForeignKey::create()
        .from(LineItems::Table, LineItems::OrderId)
        .to(Orders::Table, Orders::Id),
)
```
