<task type="auto">
  <name>Task 1: Create built-in JS runtime</name>
  <files>ferro-json-ui/src/runtime.rs, ferro-json-ui/src/lib.rs</files>
  <action>
Create `ferro-json-ui/src/runtime.rs` with a `pub(crate) const FERRO_RUNTIME_JS: &str` containing vanilla JS (~5-10KB readable, not minified).

The runtime handles three concerns:

1. **SSE connection management** — Reads `data-sse-url` from the `<body>` element. If present, opens an `EventSource` connection. On each message, parses JSON payload and dispatches to live-value and toast handlers. No config needed from user — just set `data-sse-url="/your/events"` on body.

2. **Live-value replacement** — When an SSE message contains `{key: "metric_name", value: "42"}`, finds all elements with `data-sse-target="metric_name"` and replaces their `textContent` with the new value. This is how StatCard values update in real time.

3. **Toast display/stacking/auto-dismiss** — When an SSE message contains `{toast: {message, variant, timeout}}`, creates a toast element in the `[data-toast-container]` element. Toast styling: fixed top-right stack, variant colors (info=blue-500, success=green-500, warning=yellow-500, error=red-500), fade-in animation via Tailwind `transition-opacity`. Auto-dismiss after timeout seconds (default 5). Manual dismiss via close button. Stack multiple toasts vertically with gap.

4. **Checklist dismiss** — When a `[data-dismissible]` element's dismiss button is clicked, hide the element. When all checkboxes in a `[data-checklist-key]` element are checked, hide the element.

5. **Notification dropdown toggle** — Click on `[data-notification-toggle]` shows/hides `[data-notification-dropdown]`.

6. **Sidebar mobile toggle** — Click on `[data-sidebar-toggle]` toggles `hidden` class on `[data-sidebar]` for mobile hamburger behavior.

The JS must:
- Use an IIFE `(function() { ... })()` — no global pollution
- Use `var` not `let`/`const` for maximum browser compat
- Use `document.addEventListener('DOMContentLoaded', init)` for auto-initialization
- Be purely declarative: reads data attributes, no configuration objects

Add `pub(crate) mod runtime;` to lib.rs (not public — internal to the crate).

  <action>
Add `DashboardLayout` to layout.rs.

**DashboardLayoutConfig** struct (not a Component — a layout configuration):
```rust
pub struct DashboardLayoutConfig {
    pub sidebar: SidebarProps,
    pub header: HeaderProps,
    pub sse_url: Option<String>,  // data-sse-url for JS runtime
}
```

**DashboardLayout** struct:
```rust
pub struct DashboardLayout {
    pub config: DashboardLayoutConfig,
}
```

Implement `Layout` for `DashboardLayout`:
- Uses `base_document` helper for the HTML shell
- Injects `FERRO_RUNTIME_JS` as a `<script>` tag in the scripts section (import from `crate::runtime::FERRO_RUNTIME_JS`)
- Renders sidebar from `config.sidebar` using the sidebar render function from render.rs (call `crate::render::render_sidebar` or inline the HTML generation using `html_escape` — use the same approach as AppLayout which calls the `sidebar()` partial)
- Actually, DashboardLayout should render sidebar/header DIRECTLY from the SidebarProps/HeaderProps, not call render_component. The sidebar in the layout is the persistent shell, not a component in the view tree. Render it inline using `html_escape` on all user strings.
- Sidebar HTML structure: `<aside data-sidebar class="...">` with responsive classes — `hidden md:block` on desktop (visible), hamburger toggle for mobile. Fixed position. Width 64 (w-64).
- Header HTML structure: `<header class="...">` with business name, notification bell (with `data-notification-toggle`), unread badge, user avatar/logout dropdown. Sticky top.
- Content area: `<main class="flex-1 p-6 md:ml-64">` containing the ferro_wrapper div
- Mobile hamburger button: visible only on small screens (`md:hidden`), with `data-sidebar-toggle` attribute
- If `sse_url` is Some, add `data-sse-url="{url}"` to the `<body>` element
- Add `<div data-toast-container class="fixed top-4 right-4 z-50 flex flex-col gap-2"></div>` for toast stacking

Register "dashboard" in `LayoutRegistry::new()` — BUT since DashboardLayout needs config data that varies per request, the approach should be: register a default DashboardLayout with empty config in the registry, and let users create custom DashboardLayout instances. Actually, the better approach per the existing pattern: DashboardLayout is NOT auto-registered (unlike default/app/auth which have no dynamic config). Instead, users register it at app startup with their config, OR DashboardLayout provides a builder. Keep it simple: DashboardLayout::new(config) creates an instance, users register it via `register_layout("dashboard", DashboardLayout::new(config))`. The LayoutRegistry::new() does NOT auto-register "dashboard" — users must register it themselves.

Update lib.rs exports: add `DashboardLayout` and `DashboardLayoutConfig` to the public API (these ARE user-facing — users need to construct and register them).
