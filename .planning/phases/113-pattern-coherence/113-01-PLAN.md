  <action>
Audit all 10 files containing `.unwrap()` in code examples (~32 occurrences). For each occurrence, apply the correct replacement based on context:

**In handler context (function with `#[handler]`, returns Response):**
- `req.get::<T>().unwrap()` -> `req.get::<T>().ok_or_else(|| HttpResponse::bad_request())?`
- `data["field"].as_str().unwrap()` -> `data["field"].as_str().ok_or_else(|| HttpResponse::bad_request())?`
- `App::get::<T>().unwrap()` -> `App::get::<T>().ok_or_else(|| HttpResponse::internal_server_error())?`
- `.await.unwrap()` -> `.await?` (if Result type compatible with Response)

**In setup/main context (non-handler, startup code):**
- `Theme::from_path("...").unwrap()` -> `Theme::from_path("...").expect("theme directory not found")`
- `serde_json::to_value(&x).unwrap()` -> `serde_json::to_value(&x).expect("serialization is infallible")`
- Configuration/builder chains: use `.expect("descriptive message")`

**In test context (#[tokio::test], #[ferro_test], #[test]):**
- Keep `.unwrap()` or convert to `.expect("descriptive message")` for better diagnostics
- Do NOT convert to `?` (test functions return `()`)

**Leave alone if:**
- The unwrap is on an infallible operation with a clear comment explaining why
- It's in a migration-guide BEFORE example showing old pattern

Be pragmatic — not every unwrap needs the full ok_or_else treatment. Use judgment per the research guidance.
  </action>

  </verify>
