<objective>
Extend `token.rs` to handle the device-code grant. Today `token_exchange` hard-rejects any
`grant_type != "authorization_code"`. Replace the gate with a `match` on `grant_type`: keep the
auth-code path unchanged (extracted into `token_exchange_auth_code`), and add
`token_exchange_device_code` for `urn:ietf:params:oauth:grant-type:device_code`.

The device arm reads the `DeviceGrant` by `device_code` and returns RFC 8628 §3.5 outcomes:
`expired_token` (missing or `now - created_at > 600`), `slow_down` (Pending + polled faster than
interval), `authorization_pending` (Pending), `access_denied` (Denied), or — on Approved — mints
the JWT via the IDENTICAL `build_claims` + `mint_token` call as the auth-code arm, then forgets
BOTH cache keys (single-use).

Purpose: SC-3 — device-code token polling state machine + one-issuer invariant.
Output: dispatch + device arm + the SC-3 device-arm unit tests in `token.rs`.

`token.rs` is not touched by any Wave-1 plan, but the device arm consumes the `DeviceGrant` type +
cache-key helpers from Plan 01 → Wave 2, depends_on 203-01. No file overlap with Plan 03.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| polling client → POST /token (device arm) | untrusted client polls with an opaque device_code; must not bypass single-use or claims invariants |
| token arm → ferro-cache | reads/overwrites DeviceGrant; forgets both keys on issuance |
| token arm → jwt.rs | mints the bearer token; must be claims-identical to the auth-code path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-203-DEVICECODE-REPLAY | Tampering | Approved arm | mitigate | get-then-forget on issuance: `Cache::forget` BOTH `mcp:device:{device_code}` and `mcp:usercode:{normalized}` before returning the token (T-199-02 discipline); a replayed device_code then hits `expired_token`. |
| T-203-DEVICECODE-EXPIRY | Information Disclosure | TTL guard | mitigate | explicit `now - created_at > 600` guard returns `expired_token` even if cache TTL reset on put-overwrite extended the entry. ASVS V3. |
| T-203-CLAIMS-DIVERGE | Spoofing / Confusion | Approved mint | mitigate | `build_claims(grant.user_id, grant.tenant_id, &config.app_url, 3600)` + `mint_token` — byte-identical call to the auth-code arm; asserted by `device_grant_token_claims_identical_to_auth_code`. One token issuer. |
| T-203-DEVICECODE-BRUTE | Spoofing | device_code lookup | accept | device_code is 256-bit entropy; brute-forcing the cache key within 600s is infeasible. Endpoint-level rate-limiting beyond RFC `slow_down` is an explicit hardening deferral (CONTEXT Deferred Ideas). |
| T-203-POLL-RACE | Tampering | concurrent poll vs approve | accept | non-atomic get+put on `InMemoryCache`; benign — a poll racing approval gets `authorization_pending` and retries (RESEARCH A3). RFC does not mandate atomic CAS. |
</threat_model>
