<objective>
Add the three HTTP handlers to `device.rs` (built on the Plan 01 primitives):

1. `device_authorization` (public POST) — validate `client_id` via `find_by_client_id`, generate
   device_code + user_code, store both cache entries (status Pending, user/tenant None), and return
   the exact RFC 8628 §3.2 JSON.
2. `device_verification_get` (GET /device) — unauth → `store_oauth_return_to` + 302 `/auth/login`;
   authed + valid user_code → confirm+consent HTML; else code-entry form.
3. `device_verification_post` (POST /device) — CSRF `ct_eq`; approve captures `Auth::id()` +
   `current_tenant()` and writes Approved; deny writes Denied; render terminal HTML.

Purpose: SC-1 (device_authorization response) + SC-2 (verification page, login-resume, user/tenant
binding). Token polling (SC-3) is Plan 04; route mounting is Plan 05.
Output: three `#[ferro::handler]` fns + supporting HTML-render helpers in `device.rs`, with
handler-level unit tests for the response shape and code-entry/confirm branching.

This plan re-edits `device.rs` (owned by Plan 01) → Wave 2, depends_on 203-01.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device/CLI → POST /device_authorization | untrusted client; client_id must be a registered client |
| browser → GET/POST /device | untrusted form input crosses into a session-bearing handler; CSRF + tenant binding apply |
| handler → ferro-cache | DeviceGrant written/overwritten; user/tenant must come from session, not form |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-203-INVALID-CLIENT | Spoofing | `device_authorization` | mitigate | `find_by_client_id` rejects unregistered clients with `invalid_client` before issuing codes (parity with auth-code flow). ASVS V5. |
| T-203-CSRF | Tampering | `device_verification_post` | mitigate | `get_csrf_token()` + `subtle::ct_eq` constant-time compare on `_token`; mismatch → 400 (identical to consent.rs). ASVS V3. |
| T-203-TENANT-BYPASS | Elevation of Privilege | approve path | mitigate | `tenant_id = current_tenant().map(|t| t.id)` captured from session under TenantMiddleware (mounted in Plan 05); never read from form input. ASVS V4. |
| T-203-OPEN-REDIRECT | Spoofing | `store_oauth_return_to` | mitigate | return_url constructed by the handler itself as `/device?user_code=...`; user controls only the (normalized, charset-constrained) user_code value, never the path/host. |
| T-203-XSS | Tampering | verification HTML | mitigate | every untrusted string (`client_name`, echoed user_code) passes through `crate::authorize::html_escape`. ASVS V5. |
| T-203-DEVICECODE-FORM-LEAK | Information Disclosure | hidden `device_code` field | accept | device_code already transmitted in cleartext to the polling device over TLS; embedding in a same-origin server-rendered form is not a new disclosure (RESEARCH §Security Domain). |
</threat_model>
