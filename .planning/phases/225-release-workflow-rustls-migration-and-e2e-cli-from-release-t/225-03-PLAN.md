## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| e2e job <-> crates.io | e2e-drift runs `cargo install ferro-cli` and both jobs `cargo build` generated code that resolves ferro-rs from crates.io |
| e2e-tag job <-> build-job artifact | e2e-tag downloads and executes the just-built `ferro` binary within the same workflow run |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-225-06 | Tampering | e2e-tag executes a downloaded binary | accept | `actions/download-artifact@v4` retrieves an artifact produced by the SAME workflow run's `build` job — no external/untrusted source. Within the GitHub-hosted ephemeral runner trust boundary. |
| T-225-07 | Tampering | e2e-drift `cargo install ferro-cli` pulls from crates.io | mitigate | crates.io is an authenticated, immutable, checksummed registry; this is the binary explicitly under test (the published artifact). Recommend keeping `--locked` when ferro-cli ships a Cargo.lock to pin the transitive set; drop only if publication omits it (RESEARCH A3). Job runs on an ephemeral runner with no secrets exposure beyond default GITHUB_TOKEN. |
| T-225-08 | Denial of Service | generated-app `cargo build` overflows runner disk | mitigate | `CARGO_PROFILE_DEV_DEBUG=false` + `CARGO_INCREMENTAL=0` set in the build step (RESEARCH Pitfall 6); debug (not --release) build keeps the dep graph small. |
| T-225-09 | Repudiation | a red e2e silently blocks releases (D-10 sequencing) | mitigate | `continue-on-error: true` on both jobs + TODO(D-10) comment recording the explicit flip condition; the job reports without blocking until template alignment ships. |
</threat_model>
