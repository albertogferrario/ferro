<objective>
Fix two issues discovered during Chrome UAT verification of the Proximity app.

**Issue 1: SQLite lacks trig functions for Haversine geo queries.**
The `find_nearby` and `find_nearby_posts` functions in `app-proximity/src/models/geo.rs` use SQL `acos`, `cos`, `sin`, `radians` — functions available in PostgreSQL but not in SQLite. Queries fail at runtime.

**Issue 2: Number inputs reject decimal values.**
HTML `<input type="number">` defaults to `step="1"`, which rejects decimal lat/lng values like `45.4642`. The `InputProps` struct in ferro-json-ui has no `step` field, so there's no way to set `step="any"` or a custom step.

Purpose: Make the Proximity app functional with SQLite and allow decimal number input in JSON-UI forms.

Output: Haversine queries computed in Rust instead of SQL. InputProps gains a `step` field rendered as an HTML attribute. Proximity forms set `step="any"` on lat/lng inputs.
</objective>

  <name>Task 1: Replace SQL Haversine with Rust-side distance calculation</name>
  <files>app-proximity/src/models/geo.rs</files>
  <action>
SQLite does not provide `acos`, `cos`, `sin`, or `radians` functions. Instead of registering custom SQLite functions (fragile, driver-specific), compute Haversine distance in Rust after fetching bounding-box candidates.

**For `find_nearby`:**
1. Keep the bounding box pre-filter (pure arithmetic, works in SQLite).
2. Remove `expr_as(Expr::cust(&haversine_sql), "distance")` — no SQL trig.
3. Remove `Expr::cust(format!("{} < {}", &haversine_sql, radius_km))` filter.
4. Remove `order_by(Expr::cust(&haversine_sql), Order::Asc)`.
5. Fetch bounding-box candidates into a raw struct without `distance` field.
6. After fetching, compute Haversine in Rust for each row, filter by `radius_km`, sort by distance ascending, take first 50.

**For `find_nearby_posts`:**
Same approach — fetch bounding-box candidates from the posts+users join, compute distance in Rust, filter + sort.

**Haversine function in Rust:**
```rust
fn haversine_km(lat1: f64, lng1: f64, lat2: f64, lng2: f64) -> f64 {
    let r = 6371.0;
    let dlat = (lat2 - lat1).to_radians();
    let dlng = (lng2 - lng1).to_radians();
    let a = (dlat / 2.0).sin().powi(2)
        + lat1.to_radians().cos() * lat2.to_radians().cos() * (dlng / 2.0).sin().powi(2);
    r * 2.0 * a.sqrt().asin()
}
```

**Keep `NearbyUser` and `NearbyPost` structs with their `distance: f64` field.** Populate distance after the query. Use an intermediate struct without `distance` for the DB query, then map to the final struct with computed distance.

The `bounding_box` function stays unchanged — it uses only arithmetic (no SQL trig).
