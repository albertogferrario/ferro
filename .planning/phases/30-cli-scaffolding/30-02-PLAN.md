  <name>Task 1: Restructure API call with system prompt, prefill, caching, temperature, and timeout</name>
  <files>ferro-cli/src/ai.rs</files>
  <action>
Rewrite `call_anthropic()` to use Anthropic best practices. The function signature changes to accept system prompt separately from user message:

```rust
pub fn call_anthropic(system: &str, user_prompt: &str) -> Result<String, String>
```

**Changes to `call_anthropic()`:**

1. **Client with timeout:**
Replace `reqwest::blocking::Client::new()` with:
```rust
let client = reqwest::blocking::Client::builder()
    .timeout(std::time::Duration::from_secs(60))
    .build()
    .map_err(|e| format!("Failed to create HTTP client: {e}"))?;
```

2. **Default model → Sonnet:**
Change default from `"claude-opus-4-6"` to `"claude-sonnet-4-5"`. `FERRO_AI_MODEL` env var override still works.

3. **System prompt with cache_control:**
Use the `system` parameter as an array of blocks. The second block (the large catalog+example content) gets `cache_control`:
```rust
"system": [
    {
        "type": "text",
        "text": system
    }
]
```
Note: The system prompt is passed as a single string. If it exceeds 1024 tokens (which it will — the catalog alone is ~1500 tokens), Anthropic caches it automatically when `cache_control` is set. Wrap the entire system string in one block with `cache_control: {"type": "ephemeral"}`.

4. **Temperature 0.2:**
Add `"temperature": 0.2` to the request body for deterministic code generation.

5. **Assistant prefill:**
Add an assistant message to force code output without markdown fences:
```rust
"messages": [
    {"role": "user", "content": user_prompt},
    {"role": "assistant", "content": "//!"}
]
```

6. **Anthropic version header:**
Keep `2023-06-01` (stable, supports all features we need).

**Final request body structure:**
```rust
let body = serde_json::json!({
    "model": model,
    "max_tokens": 8192,
    "temperature": 0.2,
    "system": [
        {
            "type": "text",
            "text": system,
            "cache_control": {"type": "ephemeral"}
        }
    ],
    "messages": [
        {"role": "user", "content": user_prompt},
        {"role": "assistant", "content": "//!"}
    ]
});
```

7. **Prepend prefill to response:**
Since the assistant prefill `//!` is not included in the response text, prepend it:
```rust
let text = json["content"][0]["text"].as_str()...;
Ok(format!("//!{}", text))
```

<task type="auto">
  <name>Task 2: Restructure prompt with system/user separation and few-shot example</name>
  <files>ferro-cli/src/ai.rs</files>
  <action>
Rewrite `build_view_context()` to return a tuple of `(system_prompt, user_prompt)` instead of a single concatenated string:

```rust
pub fn build_view_context(name: &str, description: &str) -> (String, String)
```

**System prompt (static, cacheable):**
Combine role definition + component catalog + few-shot example into a single string:

```
You are a Ferro framework JSON-UI view code generator. Generate only valid Rust source code for src/views/ files.

Rules:
- Import only types actually used from `use ferro::{...};`
- Use the builder pattern: `JsonUiView::new().title().layout().component()`
- Use .layout("app") unless the view is for auth (use "auth")
- Use real route handler names for actions when matching routes exist
- Use data_path bindings for form fields when matching model fields exist
- Return ONLY Rust source code, no explanation

{COMPONENT_CATALOG}

<example>
Input: user_list view showing all users in a table with edit and delete actions
Output:
//! User List JSON-UI view

use ferro::{
    Action, Component, ComponentNode, JsonUiView, TableColumn, TableProps, TextElement, TextProps,
};

pub fn view() -> JsonUiView {
    JsonUiView::new()
        .title("User List")
        .layout("app")
        .component(ComponentNode {
            key: "heading".to_string(),
            component: Component::Text(TextProps {
                content: "User List".to_string(),
                element: TextElement::H1,
            }),
            action: None,
            visibility: None,
        })
        .component(ComponentNode {
            key: "users_table".to_string(),
            component: Component::Table(TableProps {
                columns: vec![
                    TableColumn { key: "name".to_string(), label: "Name".to_string(), format: None },
                    TableColumn { key: "email".to_string(), label: "Email".to_string(), format: None },
                ],
                data_path: "users".to_string(),
                row_actions: Some(vec![
                    Action::get("user_controller.edit"),
                    Action::delete("user_controller.destroy").confirm_danger("Delete user"),
                ]),
                empty_message: Some("No users found.".to_string()),
                sortable: None,
                sort_column: None,
                sort_direction: None,
            }),
            action: None,
            visibility: None,
        })
}
</example>
```

The few-shot example uses the actual Ferro types and builder pattern so the model sees a concrete, correct example. Use the static template's structure as a starting reference but make the example richer (includes Table with actions) to demonstrate more patterns.

**User prompt (dynamic, per-request):**
Contains only the per-request context:
```
{models_section}
{routes_section}

Generate `src/views/{name}.rs`:
View name: {name}
Description: {description}
```

The models and routes sections use the same `scan_models()` and `scan_routes()` functions (unchanged). They go in the user prompt because they change per-project.

**Update callers:**
The caller in `make_json_view.rs` changes from:
```rust
let prompt = ai::build_view_context(&file_name, desc);
match ai::call_anthropic(&prompt) { ... }
```
To:
```rust
let (system, user_prompt) = ai::build_view_context(&file_name, desc);
match ai::call_anthropic(&system, &user_prompt) { ... }
```
