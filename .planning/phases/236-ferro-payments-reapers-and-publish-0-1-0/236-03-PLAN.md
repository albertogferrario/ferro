<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| reaper → money state (release) | release_expired flips reserved→released; releasing a PAID intent would discard a real payment's side effects. |
| reaper → Stripe refund (reconcile) | reconcile resolves refund state; a re-issued refund on a Failed status is real money out twice. |
| concurrent ticks / webhook | Two reaper ticks or a reaper+webhook can target the same row. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-236-02 | Tampering | release_expired | mitigate | `mark_released` is a GuardedUpdate `reserved→released` only; a paid row returns Ok(false) → no-op. find_expired (Plan 01) already excludes non-reserved rows. Per-intent txn means one failure cannot corrupt sibling rows. |
| T-236-04 | Tampering | reconcile (Failed branch) | mitigate | D-09 hard prohibition on auto-retry: Failed → `tracing::warn!` only, no `create_refund*` call. Test `reconcile_failed_no_retry` asserts the mock recorded zero refund-creation calls. |
| T-236-04b | Tampering | reconcile double-resolve | mitigate | `mark_refunded` GuardedUpdate no-op (Ok(false)) on a row already refunded by the webhook → second resolver skips; `refunded_at IS NULL` finder predicate prevents re-selection on the next tick. |
| T-236-02b | Repudiation | per-intent error log | accept | Each skipped/failed row emits a structured `tracing` event with intent_id for operator audit; sufficient for a recovery job (no formal audit-log requirement here). |
</threat_model>
