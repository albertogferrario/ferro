<objective>
Package the two reaper methods (Plan 03) as ferro-queue–compatible Job structs the
consumer schedules via cron. This is the killer artifact of the phase: a consumer
schedules recovery in two cron entries and every money-stuck edge case self-heals.

Purpose: The Job structs are the consumer-facing scheduling skin over the
`PaymentService<L>` reaper methods. They follow the established
`ferro_stripe::ProcessStripeWebhook` template exactly — a serde-skipped runtime
`Arc` handle injected via `::new()` — so the queue's retry/backoff machinery wraps
the recovery logic without the reaper logic knowing about the queue.
Output: `ferro-payments/src/reaper.rs` with both Job structs, the `ferro-queue`
dependency in `Cargo.toml`, and the re-exports in `lib.rs`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| queue runtime → reaper logic | A job deserialized off the queue carries no runtime handle; if `handle()` ran against a missing service it could silently no-op (recovery never runs) or panic. |
| serialized job payload → money state | The job is the entry point that triggers release/refund-resolution; a corrupt/forged payload must not be able to drive the money path with attacker-controlled state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-236-05 | Denial of Service | handle() with no service injected | mitigate | `service.as_ref().ok_or_else(JobFailed)` errors loudly with a constructor-naming message rather than panicking or silently skipping — the queue retries/surfaces the failure. Test `job_no_service_injected` asserts the clean error. |
| T-236-06 | Tampering / Spoofing | serialized job payload | mitigate | The struct has NO serialized identity fields — the only state is the `#[serde(skip)]` runtime handle (always re-injected locally via `::new`). A forged payload cannot smuggle a billable_id or amount: the job selects rows at execution time from the DB, never from the payload. |
| T-236-07 | Elevation of Privilege | reaper money path via queue | accept | The reaper methods (Plan 03) own the GuardedUpdate no-op + per-intent isolation invariants; the Job wrapper adds no new write surface. No additional mitigation needed at this layer. |
</threat_model>
