<!-- Publish mechanics, divergence facts, token scoping. -->

Git access: SSH is denied for this repo; HTTPS works via the gh credential helper:
```bash
git -c credential.helper='!gh auth git-credential' fetch https://github.com/albertogferrario/ferro.git master
git -c credential.helper='!gh auth git-credential' pull --rebase https://github.com/albertogferrario/ferro.git master
```

Local divergence (project memory): local `master` carries a WIP commit
`f53ee35e` ("SegmentedControl + SidebarLayout primitives") above the published
`5509e7af`, diverged from the remote 0.2.68 bump. `origin/master` recurrently lies
(stale). Workspace Cargo.toml local version is `0.2.69`. The TRUE published tip must
be confirmed against crates.io / the latest `v*` tag AFTER the rebase, not from
`origin/master`.

publish.yml behaviour (the auto-publish trigger):
- A push to master where the workspace version is NOT yet tagged (`v<version>`) and a
  library crate changed → CI publishes. If `v<version>` already exists, CI auto-bumps
  the patch. So the pushed version must be greater than the latest `v*` tag.
- CI publishes ferro-stripe (Wave 1b) and ferro-payments (Wave 1c) using the
  `CARGO_REGISTRY_TOKEN` secret — BUT that token is publish-update only. For a crate
  that already exists on crates.io it works; for the brand-new `ferro-payments` it does
  NOT (cannot publish-new). Hence the local bootstrap.

Token scoping: the CI `CARGO_REGISTRY_TOKEN` is publish-update only. The operator's
local terminal token must have publish-new scope for the first `cargo publish -p
ferro-payments`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local tree → crates.io | A published version is immutable; a non-monotonic or wrongly-scoped publish poisons the release and cannot be undone (only yanked). |
| operator terminal → crates.io token | The publish-new token grants crate creation; it must be the operator's personal token used locally, never committed or echoed into CI. |
| Stripe test key (Plan 05) → repo/CI | The gated integration test reads a Stripe secret from env; it must never be committed, hardcoded, or leaked into the published crate. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-236-08 | Tampering | non-monotonic version push | mitigate | Task 2 confirms the TRUE published tip from the latest `v*` tag + crates.io (NOT the stale `origin/master`) and bumps strictly greater; the acceptance criteria assert version > tag. A non-monotonic push fails CI auto-publish before any crate ships. |
| T-236-09 | Spoofing / Elevation | wrong publish token | mitigate | The first publish of ferro-payments is an explicit operator-gated LOCAL `cargo publish` with a publish-new token (Task 1 confirms it); the CI publish-update token is never used to create the new crate. |
| T-236-10 | Information disclosure | Stripe secret leak | mitigate | The integration test (Plan 05) reads `STRIPE_TEST_SECRET_KEY` from env only and skips when absent; it is never committed and the `#[ignore]` gate keeps it out of the default CI run. `cargo publish` ships source only — no env values. Operator verifies no secret is in the diff before push. |
| T-236-11 | Repudiation | release provenance | accept | The milestone `v<NEW_VERSION>` tag + the version-bump commit provide the release audit trail; the stale-ref fix keeps local/remote consistent. Sufficient for this project's conventions. |
</threat_model>
