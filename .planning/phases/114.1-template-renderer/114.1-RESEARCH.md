## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01:** Output is a `serde_json::Value` organized as a nested object grouped by domain entity — e.g.,
`{ "business": { "name": "...", "phone": "..." }, "products": [...], "actions": [...], "states": {...} }`

**D-02:** Top-level keys are semantic groups derived from the ServiceDef: entity fields, actions, and state machine states — not a flat key dump.

**D-03:** Template variable names use the field names as-is from the ServiceDef. A field named `"total"` with meaning `Money` appears as `total` in the context, not remapped.

**D-04:** `FieldMeaning` drives which fields are included (all fields with semantic meaning) — it does not rename fields.

**D-05:** Actions appear as rich objects: `{ "name": "add_to_cart", "display_name": "Add to Cart", "inputs": [...] }` — not just string identifiers.

**D-06:** This gives template authors enough metadata to render action buttons with labels and wire up `data-action` attributes without a second lookup.

**D-07:** All state machine states are included as typed enum values with display names — e.g., `{ "states": [{ "name": "pending", "display_name": "In attesa" }, ...] }`

**D-08:** Transitions are included so templates can show available actions per state (status badges, allowed operations).

- Test structure and fixture design
- Whether to add a `TemplateContext` wrapper struct or return raw `serde_json::Value`

## Summary

Phase 114.1 adds a `TemplateRenderer` struct that implements the existing `Renderer` trait in
`ferro-projections`. The renderer's job is to translate a `ServiceDef` into a `serde_json::Value`
that template engines (MiniJinja in downstream consumers) can use as a context object.

The output is a nested JSON object with semantic top-level groups: one key per meaningful field
category (or a flat `"fields"` group), an `"actions"` array, and a `"state_machine"` object
containing states and transitions. All field names are preserved as-is from the ServiceDef.
Actions are rich objects preserving their inputs and display names. State machine states include
display names and their outgoing transitions.

The `JsonUiRenderer` in `render/json_ui.rs` provides the canonical reference pattern — it iterates
`service.fields`, `service.actions`, and (optionally) `service.state_machine`, filtering and
mapping each into JSON. `TemplateRenderer` follows the same traversal pattern but produces a flat
data context instead of a UI component tree.

**Primary recommendation:** Create `ferro-projections/src/render/template.rs` implementing `Renderer`
for `TemplateRenderer`. Use `serde_json::json!` macro with direct field name preservation. Return
raw `serde_json::Value` (no wrapper struct — consistent with how `JsonUiRenderer` works and keeps
serialization simple for MiniJinja).

### Pattern 1: Renderer Trait Implementation

Every renderer in the crate follows this shape:

```rust
// Source: ferro-projections/src/render/json_ui.rs

pub struct JsonUiRenderer;

impl Renderer for JsonUiRenderer {
    fn render(
        &self,
        service: &ServiceDef,
        intents: &[IntentScore],
        ctx: &RenderContext,
    ) -> Result<serde_json::Value, Error> {
        // traverse service, build Value
    }
}
```

`TemplateRenderer` follows the same shape. The `intents` and `ctx` parameters are accepted but
the template renderer does not need intent scores to determine layout — it produces a complete
context object regardless of intent. The `ctx.mode` may optionally filter out write-only fields
(`Display` mode) or read-only fields (`Input` mode), but this is left to Claude's discretion.

### Pattern 2: Field Traversal

`JsonUiRenderer` iterates `service.fields` with a readable filter and system-field exclusion:

```rust
// Source: ferro-projections/src/render/json_ui.rs (render_browse)
service.fields
    .iter()
    .filter(|f| f.readable && !is_system_field(&f.meaning))
    .map(...)
```

For `TemplateRenderer`, D-04 says `FieldMeaning` drives inclusion. The safe interpretation:
include all fields that have a non-system meaning (exclude `Identifier`, `CreatedAt`, `UpdatedAt`
using the existing `is_system_field()` helper from `render/mod.rs`).

Field names are preserved as-is (D-03). Each field entry in the output object uses `field.name`
as the key — the template author uses `{{ total }}` not `{{ price }}`.

### Pattern 3: Action Representation

D-05 specifies actions as rich objects. The mapping from `ActionDef` fields is direct:

```rust
// Derived from ferro-projections/src/action.rs ActionDef structure
json!({
    "name": action.name,
    "display_name": action.display_name.as_deref().unwrap_or(&action.name),
    "inputs": action.inputs.iter().map(|i| json!({
        "name": i.name,
        "required": i.required,
        "data_type": i.data_type,
    })).collect::<Vec<_>>(),
})
```

### Pattern 4: State Machine Representation

D-07 and D-08 specify states with display names and transitions. The mapping reads
`service.state_machine` (an `Option<StateMachine>`):

```rust
// Derived from ferro-projections/src/state.rs structures
json!({
    "initial_state": sm.initial_state,
    "states": sm.states.iter().map(|s| json!({
        "name": s.name,
        "display_name": s.display_name.as_deref().unwrap_or(&s.name),
        "is_final": s.is_final,
    })).collect::<Vec<_>>(),
    "transitions": sm.transitions.iter().map(|t| json!({
        "from": t.from,
        "event": t.event,
        "to": t.to,
    })).collect::<Vec<_>>(),
})
```

### Pattern 5: Re-export in lib.rs

The existing pattern (one line added to `ferro-projections/src/lib.rs`):

```rust
// Current line (reference):
pub use render::json_ui::JsonUiRenderer;

// New line to add:
pub use render::template::TemplateRenderer;
```

### Anti-Patterns to Avoid

- **Flat key dump:** D-02 explicitly rejects putting all fields at the root level of the output. Group them under a `"fields"` object or similar semantic key.
- **Renaming fields by meaning:** D-03 prohibits remapping. A `Money` field named `"total"` stays `"total"`, not `"amount"` or `"price"`.
- **Wrapper struct:** Avoid adding a `TemplateContext` typed struct — the `Renderer` trait returns `serde_json::Value`, and adding a struct just means an extra `serde_json::to_value()` call. Return `json!({...})` directly, consistent with `JsonUiRenderer`.
- **Panicking on missing state machine:** `service.state_machine` is `Option<StateMachine>`. When absent, omit the `"state_machine"` key from the output (or include `null`) — do not error.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| snake_case → Title Case | Custom converter | `field_display_name()` in `render/mod.rs` | Already tested, handles edge cases |
| System field detection | Custom match | `is_system_field()` in `render/mod.rs` (pub(crate)) | Already encodes the exclusion rules |
| JSON object construction | `HashMap` + `serde_json::to_value` | `serde_json::json!` macro | More readable, less allocation overhead |

**Key insight:** All necessary traversal utilities already exist in the crate. `TemplateRenderer`
is primarily a new mapping layer, not a new infrastructure layer.

## Common Pitfalls

### Pitfall 1: Forgetting `pub(crate)` Boundary on Helpers

**What goes wrong:** `is_system_field()` is declared `pub(crate)` in `render/mod.rs`, not `pub`.
Calling it from `render/template.rs` works because both are within the same crate. Attempting to
re-export it or call it from outside the crate will fail to compile.

**How to avoid:** Use `use super::is_system_field;` inside `template.rs` — same import pattern as
`json_ui.rs` uses `use super::{field_display_name, is_system_field, ...}`.

### Pitfall 2: Missing `intents` Length Guard

**What goes wrong:** `JsonUiRenderer` does `intents.get(ctx.intent_index).ok_or_else(...)` and
returns an `Error::Render` if the slice is empty. If `TemplateRenderer` skips this guard and
`intents` is an empty slice, downstream callers may pass an empty slice when they only want a
template context and don't care about intents.

**How to avoid:** Since `TemplateRenderer` doesn't use intents, it can simply ignore them and
not access `intents[ctx.intent_index]`. No guard is needed — but the function must accept the
parameter for trait compliance.

### Pitfall 3: `display_name` Fallback Consistency

**What goes wrong:** Several fields on `ActionDef`, `StateDef`, and `ServiceDef` are
`Option<String>`. Inconsistent fallback (sometimes using `name`, sometimes empty string) leads
to templates rendering blank labels.

**How to avoid:** Always fall back to `.name` for display purposes:
`action.display_name.as_deref().unwrap_or(&action.name)`.

### Pitfall 4: Clippy `-D warnings` Will Reject Unused Imports

**What goes wrong:** The project enforces `cargo clippy --all --all-targets -- -D warnings`.
Importing from `json_ui.rs` helpers that aren't needed (e.g., field-to-component mapping
functions) causes unused import warnings that fail CI.

**How to avoid:** Only import what `template.rs` actually uses: `super::field_display_name`,
`super::is_system_field`, and the type imports for `ServiceDef`, `IntentScore`, etc.

## Code Examples

### Minimal Renderer Skeleton

```rust
// Source pattern: ferro-projections/src/render/json_ui.rs

use serde_json::{json, Value};

use crate::error::Error;
use crate::intent::IntentScore;
use crate::service::ServiceDef;

use super::{is_system_field, RenderContext, Renderer};

/// Template context renderer for MiniJinja and similar template engines.
///
/// Produces a structured `serde_json::Value` context from a `ServiceDef`.
/// Top-level keys are semantic groups: `fields`, `actions`, `state_machine`.
pub struct TemplateRenderer;

impl Renderer for TemplateRenderer {
    fn render(
        &self,
        service: &ServiceDef,
        _intents: &[IntentScore],
        _ctx: &RenderContext,
    ) -> Result<Value, Error> {
        let fields: serde_json::Map<String, Value> = service
            .fields
            .iter()
            .filter(|f| !is_system_field(&f.meaning))
            .map(|f| {
                (
                    f.name.clone(),
                    json!({
                        "name": f.name,
                        "meaning": f.meaning,
                        "required": f.required,
                    }),
                )
            })
            .collect();

        let actions: Vec<Value> = service
            .actions
            .iter()
            .map(|a| {
                json!({
                    "name": a.name,
                    "display_name": a.display_name.as_deref().unwrap_or(&a.name),
                    "inputs": a.inputs.iter().map(|i| json!({
                        "name": i.name,
                        "required": i.required,
                    })).collect::<Vec<_>>(),
                })
            })
            .collect();

        let state_machine = service.state_machine.as_ref().map(|sm| {
            json!({
                "initial_state": sm.initial_state,
                "states": sm.states.iter().map(|s| json!({
                    "name": s.name,
                    "display_name": s.display_name.as_deref().unwrap_or(&s.name),
                    "is_final": s.is_final,
                })).collect::<Vec<_>>(),
                "transitions": sm.transitions.iter().map(|t| json!({
                    "from": t.from,
                    "event": t.event,
                    "to": t.to,
                })).collect::<Vec<_>>(),
            })
        });

        Ok(json!({
            "service": service.display_name.as_deref().unwrap_or(&service.name),
            "fields": fields,
            "actions": actions,
            "state_machine": state_machine,
        }))
    }
}
```

### Test Pattern (following crate conventions)

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use crate::{
        ActionDef, DataType, FieldMeaning, InputDef,
        ServiceDef, StateDef, StateMachine, Transition,
        derive_intents,
    };
    use crate::render::{RenderContext, Renderer};

    fn order_service() -> ServiceDef {
        ServiceDef::new("order")
            .display_name("Order")
            .field("id", DataType::Integer, FieldMeaning::Identifier)
            .field("total", DataType::Float, FieldMeaning::Money)
            .field("status", DataType::String, FieldMeaning::Status)
    }

    #[test]
    fn fields_use_original_names() {
        let svc = order_service();
        let intents = derive_intents(&svc);
        let result = TemplateRenderer.render(&svc, &intents, &RenderContext::default()).unwrap();
        let fields = result["fields"].as_object().unwrap();
        assert!(fields.contains_key("total"));
        assert!(fields.contains_key("status"));
        // System field excluded
        assert!(!fields.contains_key("id"));
    }

    #[test]
    fn actions_include_display_name_and_inputs() {
        let svc = ServiceDef::new("cart")
            .field("id", DataType::Integer, FieldMeaning::Identifier)
            .action(
                ActionDef::new("add_to_cart")
                    .display_name("Add to Cart")
                    .input(InputDef::new("quantity", DataType::Integer, FieldMeaning::Quantity))
            );
        let intents = derive_intents(&svc);
        let result = TemplateRenderer.render(&svc, &intents, &RenderContext::default()).unwrap();
        let actions = result["actions"].as_array().unwrap();
        assert_eq!(actions.len(), 1);
        assert_eq!(actions[0]["name"], "add_to_cart");
        assert_eq!(actions[0]["display_name"], "Add to Cart");
    }

    #[test]
    fn state_machine_states_and_transitions_present() {
        let sm = StateMachine::new("lifecycle")
            .initial("pending")
            .state(StateDef::new("pending").display_name("In attesa"))
            .state(StateDef::new("done").display_name("Completato").final_state())
            .transition(Transition::new("pending", "complete", "done"));
        let svc = ServiceDef::new("order")
            .field("id", DataType::Integer, FieldMeaning::Identifier)
            .state_machine(sm);
        let intents = derive_intents(&svc);
        let result = TemplateRenderer.render(&svc, &intents, &RenderContext::default()).unwrap();
        let states = result["state_machine"]["states"].as_array().unwrap();
        assert_eq!(states.len(), 2);
        assert_eq!(states[0]["name"], "pending");
        assert_eq!(states[0]["display_name"], "In attesa");
        let transitions = result["state_machine"]["transitions"].as_array().unwrap();
        assert_eq!(transitions.len(), 1);
    }

    #[test]
    fn no_state_machine_omits_key() {
        let svc = order_service();
        let intents = derive_intents(&svc);
        let result = TemplateRenderer.render(&svc, &intents, &RenderContext::default()).unwrap();
        assert!(result["state_machine"].is_null());
    }
}
```

## Open Questions

1. **`"fields"` as object vs array**
   - What we know: D-02 says top-level keys are semantic groups; D-03 says field names are keys
   - What's unclear: Should `"fields"` be a JSON object keyed by field name (enabling `{{ fields.total.required }}`), or a JSON array (enabling `{% for field in fields %}`)?
   - Recommendation: Use an **object** keyed by field name — it allows both access patterns (iterate `.values()`, access by name), and is more idiomatic for MiniJinja template variable injection. If array is preferred, it's a trivial change.

2. **`RenderMode` filtering**
   - What we know: `ctx.mode` is `Display` or `Input`; `FieldDef` has `readable` and `writable` flags
   - What's unclear: Should `Display` mode exclude `writable: false` fields? Should `Input` mode exclude `readable: false` fields?
   - Recommendation: For the initial implementation, include all non-system fields regardless of mode. The consuming template can choose what to render. If mode-based filtering is needed, it can be added as a follow-up.
