    ```rust
    use std::collections::HashMap;

    use ferro_projections::ServiceDef;

    /// Returns the names of actions in `service` whose preconditions are not
    /// explicitly denied by `evaluated_guards`.
    ///
    /// Semantics: absent key = allow (default-open); `Some(false)` = deny.
    ///
    /// This is a list-time VISIBILITY filter evaluated once per request from a
    /// pre-computed guard map. It is NOT the live guard evaluator. Per-record
    /// enforcement happens at `dispatch_write` time via the live `GuardEvaluatorFn`;
    /// this function only controls what a surface (MCP tools/list or the Inertia
    /// substrate) SHOWS. It must never be used as an authorization gate.
    ///
    /// Single guard-visibility evaluation site: both `ferro-mcp-server`'s
    /// `tools/list` and the Inertia delivery helper call this function.
    pub fn permitted_actions(
        service: &ServiceDef,
        evaluated_guards: &HashMap<String, bool>,
    ) -> Vec<String> {
        service
            .actions
            .iter()
            .filter(|action| {
                !action
                    .preconditions
                    .iter()
                    .any(|p| evaluated_guards.get(p) == Some(&false))
            })
            .map(|a| a.name.clone())
            .collect()
    }
    ```

    `hides_action_when_guard_is_false`, `absent_guard_key_allows_action`,
    `explicit_true_allows_action`. Use the real `ServiceDef`/`ActionDef`/`GuardDef` builder
    method names (verify against ferro-projections before use).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pre-computed guard map → visibility filter | `evaluated_guards: HashMap<String,bool>` is populated by the host from live DB state once per request. `permitted_actions` reads it to decide what to SHOW. |
| surface listing → write execution | Actions shown by `permitted_actions` are advisory. Actual authorization happens later at `dispatch_write` (guards re-evaluated by the live `GuardEvaluatorFn`). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-263-03 | Elevation of privilege | `permitted_actions` treated as an authorization gate instead of a visibility filter | mitigate | Rustdoc states explicitly it is visibility-only; per-record enforcement is `dispatch_write`'s live `GuardEvaluatorFn`. This plan changes NO write path. An attacker calling a hidden action still hits the server-side guard at write time. |
| T-263-04 | Elevation of privilege (regression) | The lift accidentally widens the MCP tool set (an action previously hidden becomes visible) | mitigate | 1:1 extraction — the lifted fn filters ONLY on `action.preconditions` (identical to the old loop), never on the transition guard. `guard_visibility_unchanged_after_lift` regression test + full `cargo test -p ferro-mcp-server` pin byte-equivalent output. |
| T-263-05 | Repudiation / drift | Two guard-visibility sites diverge over time | mitigate | Acceptance criterion asserts exactly one `Some(&false)` evaluation site via grep across `framework/src` + `ferro-mcp-server/src`. |

Server-side write enforcement is unchanged by this plan; no authorization bypass introduced.
