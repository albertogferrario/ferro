# Phase 202 — UI Design Contract

> Visual and interaction contract for Phase 202 (Login-resume contract + magic-link sample app).
> Generated by gsd-ui-researcher. Consumed by gsd-planner, gsd-executor, gsd-ui-auditor.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — server-driven JSON-UI (ferro-json-ui/v2 schema) |
| Preset | not applicable |
| Component library | ferro-json-ui built-in set (Card, Form, Input, Button, Text) |
| Icon library | none — no icons in scope for these views |
| Font | inherited from ThemeMiddleware default theme (`Theme::default_theme()`) |

**Note:** This is not a React/Tailwind SPA. There is no frontend build. All UI is authored as
JSON view files in `app/src/views/*.json`, rendered server-side via `JsonUi::render_file(...)`,
and themed by the already-mounted `ThemeMiddleware`. Spacing, typography, and color tokens are
resolved by the theme at render time — this contract specifies the JSON-UI component structure
and copywriting, not raw CSS values.

---

## Spacing Scale

JSON-UI spacing is expressed via the `max_width` prop on Form (`"narrow"`) and the semantic
`layout` prop on the view root. The auth layout centers a narrow card — no per-element spacing
overrides are authored in view files.

| Token | Value | Usage in JSON-UI |
|-------|-------|-----------------|
| xs | 4px | Icon gaps (not used in these views) |
| sm | 8px | Compact inline gaps |
| md | 16px | Default field/element spacing |
| lg | 24px | Section padding within card |
| xl | 32px | Auth card horizontal margins |
| 2xl | 48px | Auth layout vertical centering padding |
| 3xl | 64px | Page-level outer spacing |

Exceptions: none. The `max_width: "narrow"` Form prop maps to the theme's narrow content
width. No custom px values are authored in view files — all sizing is semantic.

---

## Typography

These are theme-resolved semantic roles documenting what `ThemeMiddleware` renders for each
component — view files author zero typography props. Two weights only.

| Role | Size | Weight | Line Height | JSON-UI Usage |
|------|------|--------|-------------|---------------|
| Body | 16px | 400 | 1.5 | Input labels, form helper text |
| Label | 14px | 400 | 1.4 | Field labels (`Input.props.label`) |
| Heading | 20px | 600 | 1.2 | Card title (`Card.props.title`) |

---

## Color

Color is provided by `Theme::default_theme()` (the embedded default, CWD-independent since
commit `10263291`). View files reference semantic roles, not hex values.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | theme surface | Auth page background, outer layout |
| Secondary (30%) | theme card surface | Card background (`variant: "elevated"`) |
| Accent (10%) | theme primary | Submit button (`variant: "default"`) only |
| Destructive | theme destructive | Error state text bound via `{ "$data": "/error" }` |

Accent reserved for: the primary submit `Button` only. The `variant: "default"` Button maps to
the theme's primary/accent color. No other element in these two views uses accent.

## View File Contract

This section is the primary deliverable. It specifies the exact JSON-UI structure for both
view files introduced or modified in this phase. The executor must author these files verbatim.

### View 1: `app/src/views/login.json` (REPLACE existing)

**Purpose:** Email-only "send login link" request form. Replaces the current email+password form.
Renders when `GET /auth/login` is called.

**Structure:**

```json
{
  "$schema": "ferro-json-ui/v2",
  "title": "Sign in",
  "layout": "auth",
  "root": "card",
  "elements": {
    "card": {
      "type": "Card",
      "props": {
        "title": "Sign in",
        "description": "Enter your email to receive a login link.",
        "variant": "elevated"
      },
      "children": ["form"]
    },
    "form": {
      "type": "Form",
      "props": {
        "action": { "handler": "/auth/login", "method": "POST" },
        "method": "POST",
        "max_width": "narrow"
      },
      "children": ["email", "submit"]
    },
    "email": {
      "type": "Input",
      "props": {
        "field": "email",
        "label": "Email",
        "input_type": "email",
        "required": true,
        "data_path": "/email",
        "error": { "$data": "/error" }
      }
    },
    "submit": {
      "type": "Button",
      "props": {
        "label": "Send login link",
        "button_type": "submit",
        "variant": "default"
      }
    }
  }
}
```

**Deleted from existing login.json:** the `"password"` Input element and its entry in
`form.children`. No other structural change.

**Error state:** The `error` prop on the `email` Input binds to `{ "$data": "/error" }`. The
request-link handler passes `json!({"error": "No account found for this email."})` when the
email is not registered, or nothing when valid. The same data binding is reused in the
`login_confirm.json` verify-error path (see below).

---

### View 2: `app/src/views/login_confirm.json` (NEW)

**Purpose:** Confirmation page rendered after `POST /auth/login` succeeds. Shows "Check your
email" messaging. In development (`APP_ENV=local`) the magic link is surfaced as a clickable
anchor so acceptance tests and developers can follow it. In non-dev the link is not shown.

**Structure:**

```json
{
  "$schema": "ferro-json-ui/v2",
  "title": "Check your email",
  "layout": "auth",
  "root": "card",
  "elements": {
    "card": {
      "type": "Card",
      "props": {
        "title": "Check your email",
        "description": "A login link has been sent. It expires in 15 minutes.",
        "variant": "elevated"
      },
      "children": ["body", "dev_link"]
    },
    "body": {
      "type": "Text",
      "props": {
        "content": "Click the link in the email to sign in. If you don't see it, check your spam folder."
      }
    },
    "dev_link": {
      "type": "Button",
      "props": {
        "label": { "$data": "/dev_link_label" },
        "href": { "$data": "/dev_link" },
        "variant": "outline",
        "visible": { "$data": "/dev_mode" }
      }
    }
  }
}
```

**Data contract (handler must pass):**

In development (`Environment::is_development()` is true):
```rust
json!({
    "dev_mode": true,
    "dev_link": verify_url,           // e.g. "http://localhost:3000/auth/verify?token=XXX"
    "dev_link_label": "Open login link (dev only)"
})
```

In production:
```rust
json!({
    "dev_mode": false,
    "dev_link": "",
    "dev_link_label": ""
})
```

The `visible` binding hides the `dev_link` Button entirely when `dev_mode` is false. The
executor must confirm that the `Button` component respects a `visible: false` prop (hides
without rendering the anchor element). If the Button component does not support `visible`,
use two separate files or an `$if` wrapper element — the constraint is that the raw verify URL
must not appear in the rendered HTML in non-dev mode.

**Fallback if `visible` prop is unsupported:** Replace `dev_link` with a `Link` component or
inline conditional in the handler: render `login_confirm_dev.json` in dev and
`login_confirm.json` (without the dev_link element) in production.

---

### Error path: invalid/expired token (`GET /auth/verify?token=...` — bad token)

**Handler behavior:** Re-render `login.json` with `json!({"error": "This login link has
expired or is invalid. Request a new one."})`. No new view file — reuses the existing
`login.json` with the `error` data binding.

## Interaction Contract

| Interaction | Trigger | Handler | Outcome |
|-------------|---------|---------|---------|
| Request link | `POST /auth/login` with `email` field | `request_link` handler | Success: render `login_confirm.json`. Unknown email: re-render `login.json` with error. |
| Verify token | `GET /auth/verify?token=XXX` | `verify_magic_link` handler | Valid token: Auth::login + `oauth_resume_redirect("/")`. Invalid/expired: re-render `login.json` with error. |
| Dev link click | Click Button in `login_confirm.json` | Browser navigates to `dev_link` | Issues `GET /auth/verify?token=XXX` — same as email link click. |
