  <name>Task 1: Implement Process, Analyze, and Track intent layouts</name>
  <files>ferro-projections/src/render/json_ui.rs</files>
  <action>
Add three intent layout methods to JsonUiRenderer, replacing the remaining `todo!()` stubs:

1. **render_process:** Workflow control panel for state-machine-driven services.
   Components produced:
   - **Card** (state display): title = service display name
     - **Badge** child: current state from `ctx.current_state` or "Unknown" with data_path `"/data/state"`. Variant: "default".
     - **Alert** child (if guards exist on current state's transitions): informational alert listing guard requirements
   - **Transition actions:** For each action that has a transition_trigger:
     - **Button** per available action: `label: action.display_name or action.name`, `variant: "default"`, action handler `format!("{}.{}", service.name, action.name)`
   - If no state machine defined, fall back to render_focus (a Process service without state machine is just a detail view)

   In Input mode: show form fields alongside transition buttons (editing process data while progressing state).

2. **render_analyze:** Analytical table view for time-series/measure data.
   Components produced:
   - **Table** with ALL readable non-system fields as columns (unlike Browse which may limit columns). Use `field_to_column()` for format hints. `sortable: true`, `sort_direction: "desc"`.
   - Key difference from Browse: Analyze tables include DateTime columns prominently and are sorted descending by default (most recent first). No Pagination (analytical views show all data).
   - If the service has numeric fields (Money, Quantity, Percentage), add a **Card** above the table with a DescriptionList showing summary stat labels with data_path bindings (e.g., "/data/summary/total", "/data/summary/average"). These are structural placeholders — actual computation happens at the framework layer.

   Note: JSON-UI has no chart components. Don't fake charts with Progress bars. The sortable Table IS the analytical view. Acknowledge this limitation with a code comment.

3. **render_track:** Status timeline/audit list view.
   Components produced:
   - **Table** with columns:
     - Status field → Badge column (using field_to_column format)
     - DateTime/CreatedAt fields → included (unlike other intents where system fields are hidden). Track views WANT temporal ordering visible.
     - EntityName fields → included for identification
     - Other non-system readable fields → included
   - `sortable: true`, default sort on DateTime column desc
   - **Pagination** below table (audit trails can be long)
   - Key difference from Browse: Track views INCLUDE DateTime system fields and sort by them. Status column uses Badge rendering.

Remove all `todo!()` stubs from the render() dispatch match arm.

Tests per intent:
- render_process: produces Card+Badge+action Buttons when state machine present, falls back to Focus without state machine
- render_process: includes transition buttons for actions with transition_trigger
- render_analyze: produces sortable Table with all readable fields, no Pagination
- render_analyze: includes summary Card when numeric fields exist
- render_track: produces Table with Status Badge column + DateTime columns visible
- render_track: includes Pagination
- render_track: sorts by DateTime desc

   - current_state set on Process service affects Badge content

4. **Doctest on JsonUiRenderer:**
   Add a doc example showing basic usage:
   ```rust
   use ferro_projections::{ServiceDef, DataType, FieldMeaning, derive_intents, JsonUiRenderer, Renderer, RenderContext};

   let product = ServiceDef::new("product")
       .display_name("Product")
       .field("id", DataType::Integer, FieldMeaning::Identifier)
       .field("name", DataType::String, FieldMeaning::EntityName)
       .field("price", DataType::Float, FieldMeaning::Money);

   let renderer = JsonUiRenderer;
   let result = renderer.render(&product, &intents, &RenderContext::default());
   assert!(result.is_ok());
   ```
