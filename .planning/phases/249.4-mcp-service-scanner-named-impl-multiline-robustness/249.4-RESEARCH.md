## Summary

The scanner in `ferro-mcp/src/tools/list_services.rs` has two sites where it reads a
`#[service(...)]` attribute from a single trimmed source line: `:151-153`
(`scan_services_from_files`, which registers the `ServiceItem`) and `:387-389`
(`scan_offload_methods_from_files`, which sets `current_concrete` so `flush_block` can
correlate `#[offload]` methods). Both sites use `trimmed.find('(')` followed by
`trimmed.find(')')` and succeed only when the opening `(` and closing `)` appear on the same
trimmed line. When the attribute is written across multiple physical lines the second `find`
returns `None`, the service is silently dropped at site 1, and `current_concrete` is never set
at site 2, so `flush_block` (`:589`) discards any methods collected for that block.

The fix, locked in CONTEXT.md, is a shared "logical-line" pre-pass that accumulates physical
lines until the paren depth of any in-progress `#[service(...)]` attribute reaches zero, then
emits one logical line. Both scan functions consume the normalized line stream in place of
`content.lines()`. The join helper is a single correctness locus, mirrors the paren-depth
logic already in `extract_inner_params` (`:549-569`), and leaves the three-state offload
machine and the `#[service(...)]` registration loop otherwise untouched. After joining,
`extract_service_impl_name` (`:263-273`, WR-01, already shipped) is called verbatim on the
inner text — no new extraction logic is needed.

**Primary recommendation:** Implement `normalize_service_lines(content: &str) -> Vec<String>`
near `extract_inner_params`, replace both `for line in content.lines()` loops with
`for line in logical_lines.iter().map(String::as_str)`, and add one unit test on the helper
plus one mirrored fixture test. The change touches exactly one file and three logical
locations.

### Fix Site 2 — `scan_offload_methods_from_files` (lines 387–389)

```rust

if trimmed.starts_with("#[service(") {
    if let Some(start) = trimmed.find('(') {
```

Two consequences of the multi-line form at this site:

1. `current_concrete` is never set (stays `None` from the previous `flush_block`, or its

2. `flush_block` is called with whatever `current_concrete` was before — potentially
   attributing collected methods to the wrong service.
3. The `continue` is reached in all cases, so `current_concrete` is not updated. Any
   `#[offload]` methods on the trait will be collected into `block_methods` but then
   discarded at `flush_block` (`:589`: "No matching ServiceItem — discard") because the
   concrete name was never set (SC#2 violated).

### `flush_block` discard path (line 589)

```rust
// CURRENT (list_services.rs:571-591)
fn flush_block(
    concrete: &Option<String>,
    trait_name: &Option<String>,
    methods: &mut Vec<OffloadableMethod>,
    services: &mut [ServiceItem],
) {
    if methods.is_empty() { return; }
    for svc in services.iter_mut() {
        let matches = concrete.as_deref() == Some(svc.name.as_str())
            || trait_name.as_deref() == Some(svc.name.as_str());

}
```

cause is that site 2 never sets `current_concrete`.

## Architecture Patterns

### Pattern 1: Paren-Depth Accumulator (existing — to mirror)

The `FnCollecting` state machine (`:502-531`) and `extract_inner_params` (`:549-569`) already
balance parens by incrementing on `(` and decrementing on `)`. The join helper applies the
same principle at the attribute level:

```rust
// Source: ferro-mcp/src/tools/list_services.rs:549-569 (extract_inner_params)
fn extract_inner_params(buf: &str) -> String {
    let mut depth: i32 = 0;
    let mut result = String::new();
    for ch in buf.chars() {
        match ch {
            '(' => { depth += 1; result.push(ch); }
            ')' => {
                if depth == 0 { break; }
                depth -= 1;
                result.push(ch);
            }
            _ => result.push(ch),
        }
    }
    result
}
```

The join helper is the same pattern applied line-by-line instead of char-by-char, starting
accumulation on `#[service(` and stopping when depth reaches zero.

[VERIFIED: ferro-mcp/src/tools/list_services.rs:549-569]

### Pattern 2: Proposed join helper

```rust
// Suggested implementation (Claude's discretion for exact signature per D-discretion)
fn normalize_service_lines(content: &str) -> Vec<String> {
    let mut result: Vec<String> = Vec::new();
    let mut accumulating: Option<String> = None;
    let mut paren_depth: i32 = 0;

    for line in content.lines() {
        let trimmed = line.trim();

        if let Some(ref mut acc) = accumulating {
            // Continuation of a multi-line #[service(...)]
            if !acc.is_empty() {
                acc.push(' ');
            }
            acc.push_str(trimmed);
            for ch in trimmed.chars() {
                match ch {
                    '(' => paren_depth += 1,
                    ')' => paren_depth -= 1,
                    _ => {}
                }
            }
            if paren_depth <= 0 {
                // Attribute closed — emit the joined line
                result.push(accumulating.take().unwrap());
                paren_depth = 0;
            }
        } else if trimmed.starts_with("#[service(") {
            // Compute depth on this line alone
            let mut depth: i32 = 0;
            for ch in trimmed.chars() {
                match ch { '(' => depth += 1, ')' => depth -= 1, _ => {} }
            }
            if depth <= 0 {
                // Already closed on this line — pass through unchanged
                result.push(line.to_string());
            } else {
                // Attribute continues — start accumulation
                accumulating = Some(trimmed.to_string());
                paren_depth = depth;
            }
        } else {
            result.push(line.to_string());
        }
    }

    // If file ends mid-attribute (malformed), flush whatever we have
    if let Some(acc) = accumulating {
        result.push(acc);
    }

    result
}
```

### Anti-Patterns to Avoid

- **Joining all `#[...(` lines, not just `#[service(`:** Other attributes like `#[offload(queue
  = "...")]` are already handled correctly by `detect_offload_attr` on single lines; joining
  them would mutate lines the `FnCollecting` machine reads and is not needed. Key the join on
  `#[service(` specifically.
- **Using the pre-pass on `fn` lines:** The `FnCollecting` state machine already handles
  multi-line `fn` signatures via its own paren-depth counter. A pre-pass that joins `fn` lines
  would duplicate that logic and corrupt the buffer that `FnCollecting` accumulates across
  calls to `buf.push_str(trimmed)`.
- **Allocating a `Vec<String>` per file per scan call (minor):** Both `scan_services_from_files`
  and `scan_offload_methods_from_files` already allocate per file. One `Vec<String>` from the
  pre-pass per file is acceptable; the alternative (an iterator adapter) avoids collecting all
  lines before iterating but complicates the borrow model. Either is fine; the simpler
  `Vec<String>` approach is preferred for readability.
- **Stripping indentation during join:** Preserve the trimmed form that `trimmed.starts_with`
  checks expect. The single-line path already does `let trimmed = line.trim()` at the top of
  each loop iteration; the joined line should also be trimmed so existing checks continue to
  work. The proposed helper emits trimmed continuation lines joined by a space, matching how
  single-line attributes appear after `trim()`.

## Common Pitfalls

### Pitfall 1: Joining Continues Past `]`

**What goes wrong:** A `#[service(Type)]` attribute closes with `)` followed by `]`. If depth
tracking counts `[` and `]` rather than only `(` and `)`, depth never goes negative on the
`)` because `[` raised it.

**Why it happens:** Mixing bracket types in the depth counter.

**How to avoid:** Count only `(` / `)` in the join helper, matching how `extract_inner_params`
works. The `]` that ends the outer attribute bracket is irrelevant for detecting the inner
close of `service(...)`.

**Warning signs:** Single-line `#[service(Type)]` gets treated as multi-line (accumulation
never terminates).

[VERIFIED: ferro-mcp/src/tools/list_services.rs:549-569 — extract_inner_params counts only `(`/`)` and `[`/`]` for generics inside method params, but the join helper only needs `(`/`)`]

### Pitfall 2: The `continue` at Fix Site 2 Fires Before Setting `current_concrete`

**What goes wrong:** The `continue` at line `:403` fires regardless of whether `find(')')`
succeeded (line `:389`). After the fix, the helper ensures `)` is always found on the joined
line, so this is no longer an issue — but if the pre-pass is applied only to site 1 and not
site 2, site 2 still drops the attribute.

**Why it happens:** Both loops need the same normalized line stream.

**How to avoid:** Call `normalize_service_lines` (or its equivalent) at the top of both
`scan_services_from_files` and `scan_offload_methods_from_files`, not just one of them.

[VERIFIED: ferro-mcp/src/tools/list_services.rs:383-403]

### Pitfall 3: Accumulation Starts on a Non-Service Line Containing `#[service(`

**What goes wrong:** A comment `// see #[service(Foo)]` or a string literal containing the
prefix triggers accumulation.

**Why it happens:** The `starts_with` check is applied to the trimmed line without
distinguishing comments.

**How to avoid:** The existing loops already do `let trimmed = line.trim()`. A `//` line
starts with `//`, not `#[`; a `///` doc comment similarly starts with `///`. The only
realistic false-positive is a string literal that starts with the attribute prefix at the
beginning of the trimmed line, which is not a real authoring form. The existing scanner has
the same limitation at site 1/2 today and it has not caused issues.

### Pitfall 4: Forgetting to Also Normalize the `singleton!` / `bind!` Pass

**What goes wrong:** `scan_services_from_files` runs two separate `for line in content.lines()`
loops — one for `#[service(...)]` / `#[injectable]` (`:147-170`) and a second for
`singleton!` / `bind!` (`:172-204`). The pre-pass needs to be applied to the first loop.
The second loop scans for macro invocations that are always single-line by their nature, so it
does not require normalization and can continue to use `content.lines()` directly.

**Why it happens:** Forgetting the second loop exists and normalizing only the first.

**How to avoid:** Within `scan_services_from_files`, assign `let logical_lines =
normalize_service_lines(&content);` once, replace the first `for line in content.lines()`
with `for line in logical_lines.iter().map(String::as_str)`, and leave the second
`for line in content.lines()` untouched — or let Claude's discretion decide whether to share
the pre-pass across both (CONTEXT.md leaves this open).

[VERIFIED: ferro-mcp/src/tools/list_services.rs:147-204]

### Pitfall 5: Clippy `needless_collect` or `into_iter().map(...)` Warning

**What goes wrong:** `Vec<String>` collected then immediately iterated as `iter().map(…)` may
trigger `needless_collect` in some Clippy versions if the iterator could be chained directly.

**Why it happens:** Clippy lint `clippy::needless_collect`.

**How to avoid:** Return the `Vec<String>` from the helper and iterate with
`logical_lines.iter().map(String::as_str)`. This is explicit and Clippy-clean — it is the
same pattern that collecting to a `Vec` before iterating over it uses throughout this
codebase. Alternatively, return `impl Iterator<Item = String>` from the helper, but that
requires naming the return type or boxing, which adds complexity. The `Vec<String>` approach
is simpler and equally correct.

### Pitfall 6: Test Naming Collision with Existing `scan_offload_methods` Test

**What goes wrong:** Adding a test function also named `scan_offload_methods` causes a compile
error.

**How to avoid:** Name the new tests distinctly, for example:
`scan_offload_methods_multiline_service_attr` (SC#1+SC#2) and
`scan_offload_methods_singleline_regression` (SC#3).

[VERIFIED: ferro-mcp/src/tools/list_services.rs:660 — existing test is `fn scan_offload_methods`]

## Edge-Case Analysis

This section answers the six edge-case questions from the research prompt directly.

### 1. Trailing comma inside the attribute

```rust
#[service(
    impl = ReportBuilder,
    fake = FakeBuilder,   // ← trailing comma
)]
```

`extract_service_impl_name` splits on `,` and iterates each part. An empty part from the
trailing comma is `""` after `trim()`; `strip_prefix("impl")` returns `None` for it; the loop
continues and returns `inner.to_string()` on the first matching `impl` part. Trailing commas
are already tolerated by the existing WR-01 path — confirmed by the test at `:626`.

[VERIFIED: ferro-mcp/src/tools/list_services.rs:263-273, 617-636]

### 2. Generics with `<...>` and nested angle brackets

```rust
#[service(
    impl = Builder<Report, Month>,
)]
```

The join helper counts only `(` / `)`. Angle brackets in the type name do not affect depth
tracking. After joining, the inner text is `" impl = Builder<Report, Month>,"`. The existing
`extract_service_impl_name` does `split(',')` then returns the `impl =` value; the generic
type survives as `"Builder<Report, Month>"`. No issue.

### 3. Attribute closing `)]` — `)` before `]`

```rust
#[service(
    impl = Foo,
)]          ← ')' at depth 1→0, then ']' is part of the attribute syntax
```

The join helper stops accumulation when the paren depth reaches zero, which happens on `)`
before `]`. The emitted logical line is `"#[service( impl = Foo, )]"`. Then `find(')')` in
the scan loop finds the `)` before `]`, and `find('(')` finds the first `(`. The slice
`[start+1..end]` is `" impl = Foo, "`. Correct.

### 4. Single-line `#[service(Type)]` — must pass through unchanged

The proposed helper checks `if depth <= 0` after counting paren depth on the opening line.
For `#[service(ReportBuilder)]` the net depth is `+1 - 1 = 0 ≤ 0`, so the line is emitted
directly to `result` without starting accumulation. Single-line behavior is fully preserved
(SC#3).

### 5. Lines where `#[service(` is indented

`scan_services_from_files` does `let trimmed = line.trim()` before the `starts_with` check.
In the proposed helper, lines are also checked after `trim()` (the helper takes `content: &str`
and does `let trimmed = line.trim()` internally). Indented lines are handled correctly.

### 6. Non-service lines that contain `(` without closing

Lines not starting with `#[service(` (after trim) are passed through directly regardless of
their paren content. The join helper only enters accumulation on the `#[service(` prefix.
