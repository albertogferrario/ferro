# Phase 249.4: MCP service scanner — multi-line `#[service(...)]` robustness - Context

**Gathered:** 2026-08-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the `ferro-mcp` static offload scanner (`ferro-mcp/src/tools/list_services.rs`) parse
multi-line `#[service(...)]` attributes. The scanner currently requires the opening `(` and
closing `)` on the same trimmed source line at two sites — `scan_services_from_files`
(`:151-153`, which registers the `ServiceItem`) and `scan_offload_methods_from_files`
(`:387-389`, which sets the enclosing block's concrete name for offload-method correlation).
An attribute whose parens span multiple physical lines matches `starts_with("#[service(")`
but `find(')')` returns `None`, so the service is silently dropped and any `#[offload]`
methods on its trait are orphaned and discarded in `flush_block` (`:589`). This degrades
offload introspection (OFFLOAD-06) for the multi-line authoring form.

**Scope is WR-02 only.** WR-01 — the `#[service(impl = X, fake = Y)]` named form — is already
shipped in 249/249.1 via `extract_service_impl_name` (`:263-273`) with passing tests
(`:617-635`). Do NOT re-implement named-impl extraction. This phase only adds cross-line
accumulation so that both single-line and multi-line spellings of every already-supported
form reach the existing extraction path.

Static parsing only. No change to `ferro-macros`, `ferro-queue`, or the offload runtime.

</domain>

<decisions>
## Implementation Decisions

### Accumulation mechanism
- **D-01:** Fix the two same-line assumptions with a **shared "logical-line" pre-pass** that
  joins any `#[service(...)]` attribute whose parens span multiple physical lines into a
  single logical line, then feed the logical-line stream to both scan loops. This changes only
  the *line source* each loop iterates (`content.lines()` → the normalized logical lines) —
  the delicate three-state offload machine and the `#[service(...)]` registration loop stay
  otherwise untouched. Chosen because it is the least invasive edit to the stateful offload
  walker and fixes both sites through one code path.
- **D-02:** Stay **line-based**; do NOT migrate the scanner to a `syn` AST parse. This carries
  forward Phase 249 D-04 (static line parsing is the deliberate data source, works before the
  app compiles/runs). The join helper reuses the paren-depth balancing already established in
  `extract_inner_params` (`:549-569`) and the `FnCollecting` state (`:502-531`).

### Fix locus
- **D-03:** Both affected sites (`scan_services_from_files:151-153` and
  `scan_offload_methods_from_files:387-389`) consume the **same** shared helper — a single
  correctness locus, no duplicated accumulation logic. The helper is unit-testable in
  isolation (D-07).

### Forms & extraction scope
- **D-04:** The join handles the multi-line spelling of **every** already-supported form:
  positional (`#[service(\n Type\n)]`), named (`#[service(\n impl = X,\n fake = Y,\n)]`), and
  the bare/typeless variants. Balancing is on paren depth, so nested `<…>` generics in an impl
  type are unaffected. Trailing commas inside the attribute are tolerated (the existing
  `extract_service_impl_name` already `split(',')`-tolerates them).
- **D-05:** After joining, inner-name extraction stays at **parity with the existing
  single-line path** — run the joined inner text through `extract_service_impl_name`
  (unchanged). Do NOT add depth-aware inner extraction beyond what the single-line path does,
  and do NOT strip `//` comments embedded inside an attribute. Those are not real authoring
  forms and adding them is scope creep. This preserves SC#3 (no single-line regression) by
  routing single- and multi-line forms through identical extraction.

### Test strategy
- **D-06:** Add a focused **unit test on the new join helper** — assert that a multi-line
  `#[service(...)]` (positional and named) collapses to one logical line while a single-line
  attribute and ordinary code lines pass through unchanged.
- **D-07:** Add a **temp-dir fixture test** mirroring the existing `scan_offload_methods`
  test (`:659`) but with the `#[service(...)]` attribute written across multiple lines, and
  assert (a) the service is surfaced (SC#1) and (b) its trait's `#[offload]` methods correlate
  to it (SC#2). Keep/assert a single-line fixture alongside it for the no-regression guarantee
  (SC#3). Follow the existing `#[cfg(test)] mod tests` conventions in the file.

### Claude's Discretion
- Exact signature/return shape of the join helper (e.g. `Vec<String>` logical lines vs a
  joined `String` re-split by the caller) — either satisfies D-01/D-03.
- Helper name and where in the file it lives (near `extract_inner_params` is natural).
- Whether the two call sites share one `let logical_lines = …` at the top of each function or
  a small iterator adapter — implementation detail.
- Whether to consolidate the two separate `for line in content.lines()` passes inside
  `scan_services_from_files` onto the normalized stream, or only the `#[service(...)]` pass
  (the `singleton!`/`bind!` passes are unaffected by this bug).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `extract_service_impl_name` (`list_services.rs:263-273`) — WR-01 extraction; reused
  unchanged on the joined inner (D-05). Its tests (`:617-635`) are the WR-01 regression guard.
- `extract_inner_params` (`:549-569`) + the `FnCollecting` paren-depth counter (`:502-531`) —
  the established balancing pattern the multi-line join helper mirrors (D-01).
- `scan_offload_methods` temp-dir fixture test (`:659`) — the template for the new multi-line
  correlation test (D-07).

### Established Patterns
- Line-based static scanning is intentional (Phase 249 D-04) — the scanner runs before the app
  is built. The multi-line problem is *already solved for `fn` signatures* via paren-depth
  accumulation; this phase applies the same idea to the `#[service(...)]` attribute.
- Tests live in an in-file `#[cfg(test)] mod tests`; fixture tests write a `.rs` file into a
  temp `src/` dir and invoke the scanner directly.

### Integration Points
- Both scan entry points feed `list_services` output (`ServiceItem { name, binding_type,
  methods }`). `flush_block` correlates offload methods to a service by concrete/trait name; a
  service dropped at fix site 1 leaves no `ServiceItem` to correlate to, and a block whose
  concrete name is never set at fix site 2 mis-correlates — so BOTH sites must accept the
  multi-line form for SC#1 (surfaced) and SC#2 (correlated) to hold.

</code_context>

<specifics>
## Specific Ideas

- The motivating authoring form is the multi-line named service, commonly with a trailing
  comma:

  ```rust
  #[service(
      impl = ReportBuilder,
      fake = FakeBuilder,
  )]
  pub trait ReportsService: Send + Sync {
      #[offload]
      async fn build_monthly(&self, tenant_id: i64, month: Month) -> Report;
  }
  ```

  After the fix, `list_services` must surface `ReportBuilder` and correlate `build_monthly`
  (and any other `#[offload]` methods on the trait) to it — exactly as the single-line form
  does today.

</specifics>
