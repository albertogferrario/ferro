# Phase 249.4 Plan 01: MCP Service Scanner Multi-Line `#[service(...)]` Robustness Summary

**One-liner:** Paren-depth pre-pass (`normalize_service_lines`) that joins multi-line `#[service(...)]` attributes into single logical lines, wired into both scan functions so the named multi-line form surfaces services and correlates `#[offload]` methods correctly.

## What Was Built

The `ferro-mcp` static offload scanner (`ferro-mcp/src/tools/list_services.rs`) had two sites —
`scan_services_from_files` and `scan_offload_methods_from_files` — that required the opening `(`
and closing `)` of a `#[service(...)]` attribute to appear on the same trimmed source line. When
the attribute spanned multiple physical lines, `find(')')` returned `None`, the service was silently
dropped at site 1, and `current_concrete` was never set at site 2 — causing `flush_block` to discard
any `#[offload]` methods collected for that block.

The fix is a shared `normalize_service_lines(content: &str) -> Vec<String>` helper that:

- Iterates physical lines; when a `#[service(` line's parens are not balanced on that line,
  accumulates subsequent trimmed lines (joined by a single space) until paren depth reaches `<= 0`.
- Counts only `(` / `)` (never `[` / `]`), mirroring `extract_inner_params`.
- Keys exclusively on the `#[service(` prefix; all other lines — `fn` signatures, `#[offload]`,
  comments — pass through unchanged, keeping the `FnCollecting` state machine orthogonal.
- Includes an EOF flush guard for malformed/unterminated attributes.

Both scan functions now call `normalize_service_lines(&content)` after reading the file and iterate
`logical_lines.iter().map(String::as_str)` instead of `content.lines()`. The `singleton!`/`bind!`
second loop in `scan_services_from_files` remains on `content.lines()` (those macro invocations are
single-line by nature).

After normalization, inner-name extraction is unchanged: the joined inner text is fed verbatim to
the existing `extract_service_impl_name` (WR-01, shipped in Phase 249/249.1).
