<objective>
Add actionable hints to FrameworkError variants so every error message guides the developer toward a fix.

Purpose: Error messages are the highest-leverage DX improvement — they affect every interaction. Currently errors say what went wrong but not how to fix it.
Output: Enhanced error messages with "hint:" suggestions on all developer-facing FrameworkError variants.
</objective>

<task type="auto">
  <name>Task 1: Add hint field and enhance FrameworkError messages</name>
  <files>framework/src/error.rs</files>
  <action>
Add a `hint()` method to `FrameworkError` that returns an `Option<String>` with actionable guidance for each variant:

- **ServiceNotFound**: `"Register with App::bind::<{type_name}>() in your bootstrap.rs or a service provider"`
- **ParamError**: `"Check your route definition includes :{param_name} or verify the request body contains this field"`
- **ModelNotFound**: `"Verify the {model_name} exists in the database, or check that the route parameter matches a valid ID"`
- **ParamParse**: `"Route received '{param}' but expected a valid {expected_type}. Check the URL parameter format."`
- **Database**: `"Check DATABASE_URL in .env and verify the database is running"`
- **Internal**: No hint (message is user-provided)
- **Domain**: No hint (message is user-provided)
- **ValidationError**: No hint (message already describes the rule)
- **Validation**: No hint (already has field-level detail)
- **Unauthorized**: `"Check that the handler's form request authorize() returns true, or verify the user has the required permissions"`

Then update the `Into<HttpResponse>` implementation (in response.rs or wherever FrameworkError converts to HTTP) to include the hint in the JSON response body when present. The JSON response for errors should be:

```json
{
  "message": "Service 'app::services::MyService' not registered in container",
  "hint": "Register with App::bind::<app::services::MyService>() in your bootstrap.rs or a service provider"
}
```

Only include the `"hint"` key when `hint()` returns `Some(...)`. Do NOT include hints in production when `APP_ENV` or `FERRO_ENV` is "production" — hints are for development only. Check for the env var in the response conversion. If env detection is too complex (no easy access to env in the From impl), always include hints — they're developer-facing APIs, not user-facing.

Do NOT change the Display impl (thiserror messages stay the same for logging). The hint is only in HTTP JSON responses.
  </action>
  <verify>cargo test --all-features -p framework && cargo clippy -p framework -- -D warnings</verify>
  <done>All FrameworkError variants that benefit from hints return actionable guidance. JSON error responses include "hint" field. Existing tests pass.</done>
</task>
