Research conducted 2026-02-28 to inform architectural decisions across all phases.

## 1. Industry Landscape: Agent-Driven UI Standards (2025-2026)

Three emerging standards are directly relevant to Ferro's projection architecture:

### Google A2UI (Agent-to-User Interface)
- **What:** Declarative JSON protocol for agent-driven interfaces (v0.9, Apache 2.0)
- **Architecture:** Agent sends JSON describing UI intent → Client renderer maps abstract components to native widgets
- **Component model:** Flat adjacency list with ID references, exactly one `root` per surface
- **Actions:** Server actions (named events + context) and local actions (client-side function calls)
- **Data binding:** JSON Pointers (RFC 6901), two-way binding on inputs
- **Component catalog:** Text, Image, Icon, Video, AudioPlayer, Row, Column, List, Card, Tabs, Modal, TextField, CheckBox, DateTimeInput, ChoicePicker, Slider, Button, Divider
- **Key insight:** Security through declarative-only format — agent can only request components from a pre-approved catalog
- **Relevance to Ferro:** A2UI's separation of "UI intent" from "rendering" validates our Intent→Renderer architecture. Their component catalog maps closely to JSON-UI components.

### MCP Apps (SEP-1865, Anthropic + OpenAI)
- **What:** Standardized interactive UIs in Model Context Protocol
- **Architecture:** `ui://` URI scheme for visual interfaces, HTML in sandboxed iframes
- **Communication:** JSON-RPC over postMessage, bidirectional
- **Key insight:** MCP Apps chose HTML-in-iframe, A2UI chose abstract components. Both are valid rendering targets for our IntentGraph.

### AICF (AI-Integrated Composable Frontend)
- **What:** Reference architecture for safe, observable, policy-constrained UI generation
- **Key concepts:** Intent modeling, capability registries, runtime composition pipelines, governance at UI layer
- **Key insight:** "Capability registries" parallel our ServiceDef concept — declarative descriptions of what a service can do.

### Implications for Ferro
Our architecture (ServiceDef → IntentGraph → Renderer) is well-aligned with the industry direction. The key difference: we start from **business service definitions**, not from agent conversations. This is more structured and predictable. Our renderers could eventually target A2UI or MCP Apps as output formats.

## 2. Semantic Type Systems (FieldMeaning Design)

### Metabase Semantic Types (most comprehensive reference)
Complete enumeration of ~40 semantic types:

**Universal:** Entity key, Foreign key
**Numeric:** Quantity, Score, Percentage, Currency, Discount, Income, Latitude, Longitude, Category
**Temporal:** Creation date/time/timestamp, Joined date/time/timestamp, Birthday
**Text:** Entity name, Email, URL, Image URL, Avatar URL, Category, Name, Title, Description, Product, Source, City, State, Country, ZipCode
**Collection:** JSON

### Key Design Principle
> "Semantic types only add meaning; they should not be used for type casting."

This confirms our approach: `FieldMeaning::Money` on a `DataType::Float` tells the renderer "format as currency" without changing the underlying type.

### Recommended FieldMeaning Enum (expanded from plan)
```
// Core
Money, Percentage, Quantity, Score
// Identity
Identifier, ForeignKey, EntityName
// Contact
Email, Phone, Url, ImageUrl, AvatarUrl
// Personal
Person, Birthday
// Temporal
DateTime, CreatedAt, UpdatedAt, Duration
// Status
Status, Category, Boolean
// Content
FreeText, Title, Description, RichText
// Visual
Image, Color, Icon
// Location
Latitude, Longitude, Address, City, Country, ZipCode
// Custom
Custom(String)
```

This is broader than the original plan's 16 variants. Start with the original 16, expand as needed during Phase 93 field test.

## 3. State Machine Design Patterns

### XState (JavaScript, industry standard)
- Machine definitions are serializable JSON objects with `id`, `initial`, `states`
- Effects (guards, actions) are **string references** resolved at runtime — exactly matching our design decision
- SCXML compatibility provides formal semantics
- Actor model for composition of multiple machines
- **Key insight:** XState's separation of "machine definition" (serializable) from "machine instance" (runtime) is exactly what we're doing with ServiceDef vs runtime.

### Rust State Machine Crates
- **RuState:** Inspired by XState, MachineBuilder pattern, serde investigation ongoing
- **pure_hfsm:** Serializable `builder::StateMachines` as description, converted to runnable machine as second step — matches our schema-only philosophy
- **rust-fsm:** DSL-based FSM framework
- **type-state-builder:** Compile-time state machines, zero runtime overhead

### Recommendation
Don't depend on any of these crates. Our state machine is **schema-only** (no execution engine). A simple struct with states (Vec<String>), transitions (Vec<Transition>), and validation logic is sufficient. XState's design philosophy is the model to follow, but the implementation is trivial enough to own.

## 4. Graph Libraries in Rust

### petgraph
- Fast, flexible graph data structures and algorithms
- `DiGraph` for directed graphs
- Cycle detection via `is_cyclic_undirected`, `tarjan_scc`, `kosaraju_scc`
- BFS/DFS as iterators
- **serde-1** feature for serialization
- No native support for state-dependent edges (would need custom implementation)

### Recommendation
**Don't use petgraph.** Our IntentGraph is small (typically 5-15 nodes) and the edges are state-dependent (filtered by current state, permissions, available actions). A custom graph implementation with:
- `Vec<IntentNode>` for nodes
- `Vec<IntentEdge>` for edges (with guard conditions)
- Current position tracking

This keeps the dependency tree minimal and the graph logic transparent. petgraph would be overkill and obscure the domain-specific edge filtering logic.

## 5. Medium-Agnostic UI Abstraction

### Academic Reference: MAUI Architecture
"Multimodal AI-augmented User Interface" architecture provides abstractions to separate multimodal input/output from application logic. Key concept: the **ViewModel exposes application capabilities** by supplying tools applicable to a currently visible view.

### NLX Touchpoint
Rich multimodal interface serving as a "dynamic layer" on top of applications, allowing users to interact via text or voice while controlling digital elements.

### Key Design Principle
> "Primary-auxiliary interaction paradigm: users select the most appropriate input method according to the task type."

### Implications for Intent Design
Our Intent enum should express **what the user wants to do**, not **how they do it**:
- `Browse` → "show me a list" (HTML: table, Voice: "you have 5 orders", Spatial: floating cards)
- `Focus` → "show me details" (HTML: card, Voice: "order #123 is...", Spatial: expanded panel)
- `Confirm` → "are you sure?" (HTML: modal, Voice: "say yes to confirm", Spatial: gesture prompt)

The three families (Orientation / Action / Movement) are sound. They map to:
- **Orientation:** Where am I? What can I see?
- **Action:** What can I do here?
- **Movement:** Where can I go from here?

## 6. Key Architectural Validations

| Decision | Validated By | Confidence |
|----------|-------------|------------|
| Schema-only, not closures | XState, pure_hfsm, A2UI | High |
| FieldMeaning drives rendering | Metabase, A2UI component properties | High |
| Intent is medium-agnostic | A2UI, MAUI, AICF | High |
| IntentGraph as directed graph with cycles | Navigation patterns, A2UI surface model | High |
| String guards, not closures | XState effect separation | High |
| Custom graph, not petgraph | Small graph size, state-dependent edges | Medium |
| Component catalog approach | A2UI, JSON-UI existing pattern | High |

## 7. Risks Identified

1. **Intent taxonomy granularity.** Too few intents = forced mapping in renderer. Too many = fragmented logic. A2UI uses ~15 component types; our Intent enum should stay under 12 variants.

2. **FieldMeaning explosion.** Metabase has 40+ semantic types. Start with 16, add conservatively. `Custom(String)` is the escape hatch.

3. **Graph generation complexity.** The ServiceDef→IntentGraph projection must handle: missing state machines (stateless services), empty action lists, circular navigation. Each needs a clear default behavior.

4. **Renderer coupling.** If JsonUiRenderer needs special cases for every intent, the abstraction is leaking. Watch for this in Phase 90 — it's the canary.
