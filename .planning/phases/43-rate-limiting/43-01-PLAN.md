<task type="auto">
  <name>Task 1: Fix InMemoryCache increment TTL and add CacheStore::expire()</name>
  <files>framework/src/cache/store.rs, framework/src/cache/memory.rs, framework/src/cache/redis.rs</files>
  <action>
The InMemoryCache `increment()` method currently sets `expires_at: None` on counter entries, meaning they never expire. Rate limiting requires TTL on counter keys. Fix this by adding an `expire()` method to the `CacheStore` trait:

1. **Add `expire()` to `CacheStore` trait** in `store.rs`:
   ```rust
   async fn expire(&self, key: &str, ttl: Duration) -> Result<bool, FrameworkError>;
   ```
   Returns true if the key existed and TTL was set.

2. **Implement in `InMemoryCache`** (`memory.rs`):
   - Find the entry by prefixed key, update its `expires_at` to `Some(Instant::now() + ttl)`.
   - Return `Ok(true)` if key found, `Ok(false)` if not.

3. **Implement in `RedisCache`** (`redis.rs`):
   - Use Redis `EXPIRE` command: `conn.expire(&key, ttl.as_secs() as i64).await`
   - Return the boolean result.

4. **Add `Cache::expire()` static method** in `cache/mod.rs`:
   ```rust
   pub async fn expire(key: &str, ttl: Duration) -> Result<bool, FrameworkError> {
       let store = Self::store()?;
       store.expire(key, ttl).await
   }
   ```

This is needed so the rate limiter can: `Cache::increment(key, 1)` then `Cache::expire(key, window_duration)` — matching the standard Redis INCR+EXPIRE rate limiting pattern. The InMemoryCache implementation ensures the same behavior without Redis.
  </action>

  <done>CacheStore trait has expire() method. InMemoryCache and RedisCache both implement it. Cache facade exposes Cache::expire().</done>

<task type="auto">
  <name>Task 2: Refactor rate_limit.rs with Limit, define/named, cache-backed storage</name>
  <files>framework/src/middleware/rate_limit.rs, framework/src/middleware/mod.rs, framework/src/lib.rs</files>
  <action>
Complete rewrite of `framework/src/middleware/rate_limit.rs`. Delete the existing code entirely and replace with the new implementation. Key types and behaviors:

**1. `Limit` struct** — Declarative rate limit configuration:
```rust
pub struct Limit {
    pub max_requests: u32,
    pub window_seconds: u64,
    key: Option<String>,
    response_fn: Option<Arc<dyn Fn() -> HttpResponse + Send + Sync>>,
}
```
Builder methods: `per_second(max)`, `per_minute(max)`, `per_hour(max)`, `per_day(max)`, `.by(key: impl Into<String>)`, `.response(fn)`.

**2. `RateLimiter` — Static registry** using `OnceLock<DashMap<String, LimiterFn>>`:
- `RateLimiter::define(name: &str, f: impl Fn(&Request) -> LimiterResponse)` — Register a named limiter. The closure receives `&Request` and returns either a single `Limit` or `Vec<Limit>`. Use an enum `LimiterResponse` that impls `From<Limit>` and `From<Vec<Limit>>`.
- `RateLimiter::resolve(name: &str, req: &Request) -> Option<Vec<Limit>>` — Look up and evaluate named limiter.
- Keep `RateLimiter::per_minute(n)`, `per_hour(n)` etc as convenience constructors that create inline `Limit` values (not registered globally).

**3. Cache-backed rate limit check** — Core algorithm:
```rust
async fn check_rate_limit(limit: &Limit, identifier: &str) -> RateLimitResult
```
- Key format: `rate_limit:{name}:{identifier}:{window_number}` where `window_number = unix_secs / window_seconds`
- Call `Cache::increment(key, 1)`. If cache fails, allow the request with a warning log (fail-open).
- If `increment` returns 1 (first request in window), call `Cache::expire(key, Duration::from_secs(window_seconds + 1))`.
- Compare count against `max_requests`. Return `Allowed` or `Exceeded` with appropriate headers data.

**4. `Throttle` — Middleware implementation**:
- `Throttle::named(name: &str) -> Self` — Creates a throttle that resolves from RateLimiter registry at request time.
- `Throttle::per_minute(max)`, `Throttle::per_hour(max)` etc — Inline limits without registry lookup.
- **Implement `Middleware` trait directly on `Throttle`** (not via `into_middleware()`). This allows `Throttle::named("api")` to be used directly as middleware on routes.
- When multiple limits from a named limiter: check all limits, first exceeded triggers 429.

**5. IP extraction** — Keep existing logic for `get_client_ip()`:
- Check `X-Forwarded-For` (first entry), `X-Real-IP`, fallback to "unknown".
- Extract as a standalone function `fn get_client_ip(request: &Request) -> String` reusable by Limit's default key.

**6. Response headers** — Fix existing bug:
- Add `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` to BOTH Ok and Err responses.
- For 429 response, also add `Retry-After` header.
- When multiple limits, use the most restrictive (lowest remaining) for header values.

**7. Delete old types**: Remove `RateLimitConfig`, `RateLimitEntry`, `RateLimitStore`, `RateLimiters`, `ThrottleBuilder`, `ThrottleWindow`. Remove `with_decay` dead code.

**8. Update exports** in `middleware/mod.rs`:
- Export: `Limit`, `RateLimiter`, `Throttle`, `LimiterResponse`
- Remove: `RateLimitConfig`, `RateLimitStore`, `RateLimiters`, `ThrottleBuilder`

**9. Update `framework/src/lib.rs`** re-exports:
- Replace `RateLimitConfig, RateLimiter, RateLimiters, Throttle` with `Limit, RateLimiter, Throttle, LimiterResponse`

**Important implementation details:**
- `RateLimiter::define()` closure signature: `Fn(&Request) -> T where T: Into<LimiterResponse>`. Store as `Arc<dyn Fn(&Request) -> Vec<Limit> + Send + Sync>` internally after wrapping with conversion.
- The `Limit.key` field: if `None`, defaults to client IP. The `.by()` method lets users override.
- For `Throttle::named()`: if the named limiter doesn't exist, log a warning and allow the request (fail-open, avoids crash from misconfiguration).
- All tests in this file should be removed — they'll be rewritten in Plan 02.
  </action>
