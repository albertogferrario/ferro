# Phase 80: x-mcp OpenAPI Extensions - Research

**Researched:** 2026-02-28
**Domain:** OpenAPI vendor extensions for MCP tool enrichment
**Confidence:** HIGH

<research_summary>
## Summary

Researched how to add `x-mcp` vendor extensions to OpenAPI specs generated by Ferro's `make:api`, and how to consume them in `ferro-api-mcp`. Both sides of the pipeline have first-class extension support: utoipa 5.x provides `OperationBuilder::extensions()` for emission, and openapiv3 2.2.0 preserves all `x-*` fields in `Operation.extensions: IndexMap<String, Value>`.

The ecosystem is converging on operation-level vendor extensions for MCP enrichment. Speakeasy's `x-speakeasy-mcp` is the most documented pattern, supporting tool name override, description, scopes, and behavioral hints (destructive, idempotent, readOnly). AWS Labs and Redocly also support `x-mcp` extensions. No single standard exists yet — Ferro should use `x-mcp` prefix for portability.

Key industry insight from Stainless and Xata: AI-facing descriptions differ from developer docs. Condensed descriptions improve tool selection; simpler schemas increase correct invocation. Don't expose every endpoint — curate what matters.

**Primary recommendation:** Define 4 operation-level extensions (`x-mcp-tool-name`, `x-mcp-description`, `x-mcp-hint`, `x-mcp-hidden`). Emit them from `build_openapi_spec()` using utoipa's `OperationBuilder::extensions()`. Consume them in `ferro-api-mcp`'s `parse_spec()` via `operation.extensions.get()`. Update `make:api` template to emit enriched specs.
</research_summary>

<architecture_patterns>
## Architecture Patterns

### Pattern 1: Extension Schema Definition

Ferro's `x-mcp` extensions live at the **operation level** in OpenAPI specs:

```json
{
  "paths": {
    "/api/v1/users": {
      "get": {
        "operationId": "api.users.index",
        "summary": "List users",
        "x-mcp-tool-name": "list_users",
        "x-mcp-description": "List all users with optional pagination. Returns array of user objects.",
        "x-mcp-hint": "Use page and per_page query params to paginate. Default 25 per page.",
        "responses": { "200": { "description": "OK" } }
      }
    },
    "/api/v1/internal/metrics": {
      "get": {
        "operationId": "api.metrics.index",
        "summary": "Internal metrics",
        "x-mcp-hidden": true,
        "responses": { "200": { "description": "OK" } }
      }
    }
  }
}
```

### Extension Schema

| Extension | Type | Required | Purpose |
|-----------|------|----------|---------|
| `x-mcp-tool-name` | string | No | Override auto-generated tool name. Short, snake_case, AI-friendly. |
| `x-mcp-description` | string | No | AI-optimized description (replaces summary for MCP). Condensed, action-oriented. |
| `x-mcp-hint` | string | No | Usage guidance for the AI agent. Parameter tips, expected workflows, common patterns. |
| `x-mcp-hidden` | boolean | No | Exclude this operation from MCP tool registration. Default false. |

### Pattern 2: Emitting Extensions in utoipa (build_openapi_spec)

```rust
use utoipa::openapi::extensions::Extensions;

// In build_openapi_spec(), after building the operation:
let mut op = OperationBuilder::new()
    .tag(tag)
    .summary(Some(summary.clone()))
    .operation_id(route.name.clone());

// Build x-mcp extensions
let mut extensions = Extensions::builder().build();
extensions.insert(
    "x-mcp-tool-name".to_string(),
    serde_json::Value::String(mcp_tool_name),
);
extensions.insert(
    "x-mcp-description".to_string(),
    serde_json::Value::String(mcp_description),
);
if let Some(hint) = mcp_hint {
    extensions.insert(
        "x-mcp-hint".to_string(),
        serde_json::Value::String(hint),
    );
}

op = op.extensions(Some(extensions));
let operation = op.build();
```

### Pattern 3: Consuming Extensions in openapiv3 (parse_spec)

```rust
// In parse_spec(), when building ApiOperation from an openapiv3 Operation:
let mcp_tool_name = operation.extensions
    .get("x-mcp-tool-name")
    .and_then(|v| v.as_str())
    .map(String::from);

let mcp_description = operation.extensions
    .get("x-mcp-description")
    .and_then(|v| v.as_str())
    .map(String::from);

let mcp_hint = operation.extensions
    .get("x-mcp-hint")
    .and_then(|v| v.as_str())
    .map(String::from);

let hidden = operation.extensions
    .get("x-mcp-hidden")
    .and_then(|v| v.as_bool())
    .unwrap_or(false);

// Skip hidden operations
if hidden {
    continue;
}

// Use x-mcp overrides, fall back to existing behavior
let tool_name = mcp_tool_name
    .unwrap_or_else(|| generate_tool_name(operation.operation_id.as_deref(), method, path));
let description = mcp_description
    .unwrap_or_else(|| build_description(operation, &tool_name));
```

### Pattern 4: Tool Name Generation for make:api

Generate AI-friendly tool names from route semantics:

```
GET    /api/v1/users        -> list_users
GET    /api/v1/users/{id}   -> get_user
POST   /api/v1/users        -> create_user
PUT    /api/v1/users/{id}   -> update_user
DELETE /api/v1/users/{id}   -> delete_user
```

These are more natural for AI agents than the current `api_users_index` pattern.

### Pattern 5: AI-Optimized Descriptions

Developer docs and AI descriptions serve different audiences:

| Developer summary | AI-optimized x-mcp-description |
|-------------------|-------------------------------|
| "List users" | "List all users with optional pagination. Returns array of user objects with id, name, email." |
| "Create user" | "Create a new user. Requires name and email in request body. Returns the created user." |
| "Delete user" | "Permanently delete a user by ID. This action cannot be undone." |

Condensed but complete — includes what it does, what it needs, what it returns.

### Anti-Patterns to Avoid
- **x-mcp at root level only:** Root-level extensions lack per-operation granularity. Always use operation-level.
- **Verbose descriptions:** Every token in tool descriptions competes with reasoning tokens. Keep descriptions under 2-3 sentences.
- **Exposing internal endpoints:** Metrics, health checks, admin-only routes should use `x-mcp-hidden: true`.
- **Duplicating existing metadata:** Don't repeat operationId in x-mcp-tool-name unless changing it. Only add extensions that provide new information.
</architecture_patterns>

<dont_hand_roll>
## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Extension serialization | Custom JSON injection | utoipa `Extensions::builder()` | Proper serde flatten, type-safe |
| Extension parsing | Manual JSON key scanning | `operation.extensions.get("x-mcp-*")` | openapiv3 already deserializes all x-* into IndexMap |
| Tool name formatting | Complex naming heuristics | Simple `{verb}_{resource}` from method + path | Consistent, predictable, matches AI expectations |
| Description enrichment | AI prompt generation at runtime | Static descriptions in OpenAPI spec | Cached in OnceLock, no runtime overhead |

**Key insight:** Both utoipa and openapiv3 have first-class extension support. The implementation is straightforward — emit HashMap entries on one side, read IndexMap entries on the other. The real work is deciding what metadata to include, not how to transport it.
</dont_hand_roll>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Extension Keys Must Start with "x-"
**What goes wrong:** Custom fields without the `x-` prefix are silently dropped or cause validation errors.
**Why it happens:** OpenAPI spec requires vendor extensions to start with `x-`. openapiv3's deserializer explicitly filters for this prefix.
**How to avoid:** Always use `x-mcp-` prefix. Validate in tests that extensions survive round-trip serialization.
**Warning signs:** Extensions appear in utoipa output but disappear after openapiv3 parsing.

### Pitfall 2: utoipa Extensions Require serde_json::Value
**What goes wrong:** Trying to insert raw strings or non-Value types into Extensions.
**Why it happens:** Extensions wraps `HashMap<String, serde_json::Value>`, not `HashMap<String, String>`.
**How to avoid:** Always wrap values with `serde_json::Value::String(...)` or `serde_json::Value::Bool(...)`.
**Warning signs:** Compile errors on `extensions.insert()`.

### Pitfall 3: Overriding Tool Names Can Break Uniqueness
**What goes wrong:** Two operations with the same `x-mcp-tool-name` create duplicate MCP tools.
**Why it happens:** Manual name overrides bypass the auto-deduplication in `generate_tool_name`.
**How to avoid:** Validate uniqueness of all tool names (both auto-generated and x-mcp overrides) after parsing. Warn on duplicates.
**Warning signs:** MCP client shows fewer tools than expected; tool calls route to wrong operation.

### Pitfall 4: OnceLock Cache Invalidation
**What goes wrong:** Adding extensions to `build_openapi_spec` doesn't take effect because the spec is cached in OnceLock.
**Why it happens:** `CACHED_SPEC_JSON` and `CACHED_DOCS_HTML` are static OnceLock — once set, they never change.
**How to avoid:** This is working as designed (single-build caching). Just ensure extensions are added before the first call to `openapi_json_response()`. No action needed unless hot-reload of extensions is required (it's not).
**Warning signs:** Spec JSON shows old output despite code changes. Fix: restart the server.

### Pitfall 5: x-mcp-description vs summary Confusion
**What goes wrong:** AI agent sees two descriptions — the OpenAPI `summary` and the `x-mcp-description` — and it's unclear which wins.
**Why it happens:** Not documenting the priority clearly.
**How to avoid:** In ferro-api-mcp, x-mcp-description takes priority over summary/description. Document this in the spec schema. `make:api` should only emit x-mcp-description when it differs from summary.
**Warning signs:** Redundant descriptions in MCP tool listing.
</common_pitfalls>

<code_examples>
## Code Examples

### Emitting Extensions via utoipa OperationBuilder
```rust
// Source: utoipa 5.x docs — OperationBuilder::extensions()
use utoipa::openapi::extensions::Extensions;
use utoipa::openapi::path::OperationBuilder;
use serde_json::Value;

fn build_operation_with_mcp_extensions(
    tag: &str,
    summary: &str,
    mcp_tool_name: &str,
    mcp_description: &str,
) -> utoipa::openapi::path::Operation {
    let mut extensions = Extensions::builder().build();
    extensions.insert(
        "x-mcp-tool-name".to_string(),
        Value::String(mcp_tool_name.to_string()),
    );
    extensions.insert(
        "x-mcp-description".to_string(),
        Value::String(mcp_description.to_string()),
    );

    OperationBuilder::new()
        .tag(tag)
        .summary(Some(summary))
        .extensions(Some(extensions))
        .build()
}
```

### Emitting Extensions via #[utoipa::path] Macro

### Consuming Extensions in openapiv3
```rust
// Source: openapiv3 2.2.0 — Operation.extensions field
use openapiv3::{OpenAPI, Operation, ReferenceOr};

fn extract_mcp_metadata(operation: &Operation) -> McpMetadata {
    McpMetadata {
        tool_name: operation.extensions
            .get("x-mcp-tool-name")
            .and_then(|v| v.as_str())
            .map(String::from),
        description: operation.extensions
            .get("x-mcp-description")
            .and_then(|v| v.as_str())
            .map(String::from),
        hint: operation.extensions
            .get("x-mcp-hint")
            .and_then(|v| v.as_str())
            .map(String::from),
        hidden: operation.extensions
            .get("x-mcp-hidden")
            .and_then(|v| v.as_bool())
            .unwrap_or(false),
    }
}

struct McpMetadata {
    tool_name: Option<String>,
    description: Option<String>,
    hint: Option<String>,
    hidden: bool,
}
```

### Generate AI-Friendly Tool Names from Route Semantics
```rust
// Source: Ferro-specific — improving on current auto_summary pattern
fn mcp_tool_name_from_route(method: &str, path: &str) -> String {
    let resource = extract_resource_name(path);
    let singular = singularize(&resource);

    match (method, has_path_param(path)) {
        ("GET", false) => format!("list_{resource}"),
        ("GET", true) => format!("get_{singular}"),
        ("POST", _) => format!("create_{singular}"),
        ("PUT" | "PATCH", _) => format!("update_{singular}"),
        ("DELETE", _) => format!("delete_{singular}"),
        _ => format!("{}_{}", method.to_lowercase(), resource),
    }
}
// "/api/v1/users" GET -> "list_users"
// "/api/v1/users/{id}" DELETE -> "delete_user"
```

### Generate AI-Optimized Descriptions
```rust
// Source: Ferro-specific — enriched descriptions for AI agents
fn mcp_description_from_route(method: &str, path: &str, fields: &[&str]) -> String {
    let resource = extract_resource_name(path);
    let singular = singularize(&resource);

    match (method, has_path_param(path)) {
        ("GET", false) => format!(
            "List all {resource} with optional pagination via page and per_page query parameters."
        ),
        ("GET", true) => format!(
            "Get a single {singular} by ID. Returns the full {singular} object."
        ),
        ("POST", _) => {
            let field_list = fields.join(", ");
            format!(
                "Create a new {singular}. Required fields in body: {field_list}."
            )
        }
        ("PUT" | "PATCH", _) => format!(
            "Update an existing {singular} by ID. Send only the fields to change in the body."
        ),
        ("DELETE", _) => format!(
            "Permanently delete a {singular} by ID. This action cannot be undone."
        ),
        _ => format!("{method} {path}"),
    }
}
```

## State of the Art (2025-2026)

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Generic operationId as tool name | x-mcp-tool-name override | 2025 | AI agents get natural names (list_users vs api_users_index) |
| Developer-facing summary only | Separate AI-facing description | 2025 | Better tool selection by LLMs (Stainless, Xata findings) |
| All endpoints exposed as tools | Curated with x-mcp-hidden | 2025 | Fewer, higher-quality tools improve AI accuracy |
| Per-vendor extensions (x-speakeasy-mcp) | Emerging x-mcp convention | 2025-2026 | Portability across MCP bridges |

**Industry patterns discovered:**
- **Speakeasy**: `x-speakeasy-mcp` with name, description, scopes, behavioral hints, and global scope-mapping via regex patterns
- **Stainless**: Config-driven transforms in `stainless.yaml` rather than spec extensions; focuses on SDK generation
- **AWS Labs**: openapi-mcp-server with authentication, metrics, and operation filtering
- **Xata**: Auto-generate from spec, then curate. Developer docs != AI instructions.
- **FastMCP**: Uses standard OpenAPI tags for MCP tool categorization

**Ferro's approach (recommended):**
Use portable `x-mcp-*` extensions at operation level. This is simpler than Speakeasy's scope-mapping and more portable than Stainless's config files. Ferro's `make:api` generates these automatically from route semantics (method + path + model fields), so no manual annotation is needed for typical CRUD APIs.

**Deprecated/outdated:**
- Root-level-only x-mcp extensions (per-operation is the standard now)
- Vendor-locked extension prefixes for simple metadata (use `x-mcp-*` for portability)
</sota_updates>

<open_questions>
## Open Questions

1. **Should x-mcp-hint include response format information?**
   - What we know: Current MCP tools return pretty-printed JSON. AI agents benefit from knowing the response shape.
   - What's unclear: Whether response schema info belongs in the hint or as a separate `x-mcp-response-hint` extension.
   - Recommendation: Include basic response info in `x-mcp-hint` for Phase 80. If demand grows, split into a separate extension later.

2. **Should make:api emit x-mcp extensions in the generated template code or in build_openapi_spec?**
   - What we know: Currently `make:api` generates a `docs.rs` file that calls `build_openapi_spec()`. The framework's `build_openapi_spec()` reads route metadata.
   - What's unclear: Whether to put x-mcp generation in the framework function (automatic for all Ferro apps) or in the generated template (customizable per app).
   - Recommendation: Framework-level in `build_openapi_spec()` — derives x-mcp extensions from the same route metadata it already has. This means all Ferro apps get MCP extensions automatically, not just `make:api` output.

3. **Tool annotations: should x-mcp extensions include behavioral hints?**
   - What we know: ferro-api-mcp already derives ToolAnnotations from HTTP method (GET=readOnly, DELETE=destructive). Speakeasy supports behavioral hints in extensions.
   - What's unclear: Whether to also emit them in the OpenAPI spec or keep them derived from HTTP method.
   - Recommendation: Don't emit behavioral hints in extensions — they're redundant with HTTP method semantics which ferro-api-mcp already handles. Keep the extension schema minimal.
</open_questions>
