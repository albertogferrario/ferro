<objective>
Add x-mcp vendor extensions to Ferro's OpenAPI spec output so that any Ferro API automatically emits AI-friendly tool names, descriptions, and hints.

Purpose: All Ferro apps get MCP-optimized metadata in their OpenAPI specs without manual annotation. ferro-api-mcp (and any other MCP bridge) can consume these extensions for better tool names and descriptions.
Output: `build_openapi_spec()` emits `x-mcp-tool-name` and `x-mcp-description` on every operation.
</objective>

<task type="auto">
  <name>Task 1: Add mcp_tool_name and mcp_description helper functions</name>
  <files>framework/src/api/openapi.rs</files>
  <action>
Add two new private functions below the existing `auto_summary` function:

1. `mcp_tool_name(method: &str, path: &str) -> String` — generates snake_case AI-friendly tool names:
   - Reuse existing `extract_resource_name()` and `singularize()` helpers
   - Pattern: GET collection → `list_{resource}`, GET with param → `get_{singular}`, POST → `create_{singular}`, PUT/PATCH → `update_{singular}`, DELETE → `delete_{singular}`, fallback → `{method}_{resource}`
   - Examples: GET /api/v1/users → "list_users", DELETE /api/v1/users/{id} → "delete_user"

2. `mcp_description(method: &str, path: &str) -> String` — generates AI-optimized descriptions:
   - GET collection → "List all {resource} with optional pagination."
   - GET with param → "Get a single {singular} by ID."
   - POST → "Create a new {singular}."
   - PUT/PATCH → "Update an existing {singular} by ID."
   - DELETE → "Permanently delete a {singular} by ID."
   - fallback → "{method} {path}"

Add unit tests for both functions covering all HTTP method/path combinations (collection, single resource, nested resources, fallback). Follow the existing test pattern in the file.
  </action>
  <verify>cargo test --all-features -p ferro-framework -- openapi::tests::mcp_ passes all new tests</verify>
  <done>mcp_tool_name and mcp_description functions exist with tests covering GET/POST/PUT/PATCH/DELETE for both collection and single-resource paths</done>
</task>

<task type="auto">
  <name>Task 2: Wire x-mcp extensions into OperationBuilder</name>
  <files>framework/src/api/openapi.rs</files>
  <action>
In `build_openapi_spec()`, after building the operation with OperationBuilder, add x-mcp extensions before calling `.build()`:

1. Add import: `use utoipa::openapi::extensions::Extensions;` (and `serde_json::Value` if not already imported)
2. Inside the route iteration loop, after the path parameter loop and before `let operation = op.build();`:
   - Call `mcp_tool_name(&route.method, &route.path)` to get the tool name
   - Call `mcp_description(&route.method, &route.path)` to get the description
   - Create extensions: `let mut extensions = Extensions::builder().build();`
   - Insert `x-mcp-tool-name` as `Value::String(mcp_name)`
   - Insert `x-mcp-description` as `Value::String(mcp_desc)`
   - Apply: `op = op.extensions(Some(extensions));`
3. Update the existing `build_spec_basic` test to verify x-mcp extensions appear in the output. After checking the GET /api/v1/users operation, also assert:
   - `get_op.extensions` contains key `x-mcp-tool-name` with value `"list_users"`
   - `get_op.extensions` contains key `x-mcp-description` with value starting with `"List all users"`
4. Add a new test `spec_extensions_in_json` that builds a spec, serializes to JSON, parses back with serde_json, and verifies x-mcp keys appear in the operation JSON.

Note: utoipa 5 Extensions struct uses `HashMap<String, serde_json::Value>` with serde flatten. The extensions() method on OperationBuilder takes `Option<Extensions>`. If the Extensions type doesn't have `insert()` directly, access the inner HashMap — check the actual API. The research indicates `Extensions` wraps a HashMap and has builder/insert support.
  </action>
  <verify>cargo test --all-features -p ferro-framework -- openapi::tests passes all tests (including updated build_spec_basic and new spec_extensions_in_json)</verify>
  <done>build_openapi_spec() emits x-mcp-tool-name and x-mcp-description on every operation, verified via unit tests and JSON serialization round-trip</done>
</task>
