<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM → tool handler | LLM-generated `serde_json::Value` is passed to handler closures |
| tool handler → LLM | handler results (and errors) are sent back to the model |
| dispatch loop → provider | repeated provider calls; an unbounded loop is a cost/availability risk |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-166-01 | DoS (runaway loop / cost) | ToolRegistry::dispatch | mitigate | `max_iterations` REQUIRED at construction (no Default, no zero-arg ctor, no override); hard `Error::ToolIterationLimit` at the cap; warn@5. Verified by `tool_registry_enforces_max_iterations`. |
| T-166-02 | Information disclosure (error leak to model/log) | tool error surfacing | mitigate | `ToolError { message }` is the only thing surfaced to the LLM; handler errors are mapped to it, never passed through as raw panics, stack traces, or DB-constraint strings. Verified by `dispatch_surfaces_tool_error` + `tool_error_is_model_legible`. |
| T-166-03 | Tampering (untrusted LLM tool input) | handler input validation | accept (with note) | The SDK passes raw LLM `serde_json::Value` to handlers and provides the normalized `parameters_schema`; handler implementations are responsible for validating their own inputs before privileged actions. The SDK itself executes no privileged action. Documented in ToolDef rustdoc. |
| T-166-04 | Information disclosure (API key in error) | complete_with_tools provider errors | mitigate | Reuse the existing `Error::Provider { status, message }` pattern whose message carries provider response text only — never the API key/auth header (existing 165 constraint). |
</threat_model>
