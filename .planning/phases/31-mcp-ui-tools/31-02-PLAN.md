<task type="auto">
  <name>Task 1: Create json_ui_inspect MCP tool</name>
  <files>ferro-mcp/src/tools/json_ui_inspect.rs, ferro-mcp/src/tools/mod.rs, ferro-mcp/src/service.rs</files>
  <action>
Create `ferro-mcp/src/tools/json_ui_inspect.rs` following the existing list_models.rs scanning pattern.

The tool scans `src/views/*.rs` files in the project for JSON-UI view functions and returns structured information about each.

**Scanning approach (regex-based for speed):**
1. Walk `{project_root}/src/views/` directory for `.rs` files (skip `mod.rs`)
2. For each file, regex-match `pub fn (\w+)\(\).*->.*JsonUiView` to find view functions
3. Extract the function name
4. Regex-match `.title\("([^"]+)"\)` to extract the view title
5. Regex-match `.layout\("([^"]+)"\)` to extract the layout name
6. Regex-match `Component::(\w+)` to list which component types are used
7. Regex-match `Action::(get|new|delete)\("([^"]+)"\)` to list action references

Output types:
```
JsonUiViewList { views: Vec<ViewInfo>, total: usize }
ViewInfo {
    name: String,          // function name
    file: String,          // relative path from project root
    title: Option<String>, // extracted .title() value
    layout: Option<String>,// extracted .layout() value
    components_used: Vec<String>,  // Component:: variant names found
    actions: Vec<String>,          // Action handler references found
}
```

Accept an optional `filter` parameter. When provided, filter views by name substring match (case-insensitive).

Register in service.rs:
- Params: `JsonUiInspectParams { filter: Option<String> }`
- Tool name: `json_ui_inspect`
- Description: explain when to use (understanding existing views, before modifying or adding views, checking which components a view uses) and what it combines with (json_ui_catalog for component reference, json_ui_generate for creating new views, get_handler for the handler that renders the view)

Add `pub mod json_ui_inspect;` to tools/mod.rs.

When `src/views/` doesn't exist, return `{ "views": [], "total": 0 }` (not an error — the project may not have JSON-UI views yet).

Include unit tests: test_empty_project (no views dir), test_serialization.

  <done>json_ui_inspect tool registered, scans src/views/*.rs, extracts view metadata (name, title, layout, components, actions), handles missing views dir gracefully</done>
</task>

<task type="auto">
  <name>Task 2: Create json_ui_generate MCP tool</name>
  <files>ferro-mcp/src/tools/json_ui_generate.rs, ferro-mcp/src/tools/mod.rs, ferro-mcp/src/service.rs</files>
  <action>
Create `ferro-mcp/src/tools/json_ui_generate.rs` that assembles context for an agent to generate a new JSON-UI view.

**Key design decision:** This tool does NOT call Anthropic. It provides structured context so the consuming agent can write the view itself. This avoids double-LLM calls (the agent IS the LLM).

The tool assembles:
1. **Component catalog** — The COMPONENT_CATALOG string (same as CLI's ai.rs). Embed the same content as a const string in this module. Do NOT import from ferro-cli (different crate).
2. **Model fields** — Scan `src/models/*.rs` using the same regex approach as ferro-cli's `scan_models()`. Reimplement here (different crate, can't share code).
3. **Route definitions** — Scan `src/routes.rs` by reading the file and extracting route patterns. Use regex: `\.(get|post|put|patch|delete)\("([^"]+)".*?(\w+)::(\w+)\)` to extract method, path, module, function. Simpler than CLI's full parser but sufficient for context.
4. **Existing views** — List existing view files in src/views/ (just names, not full inspection)
5. **Example** — A complete example of a well-structured view (similar to the CLI's few-shot example)

Output types:
```
JsonUiGenerationContext {
    component_catalog: String,     // Full COMPONENT_CATALOG text
    models: Vec<ModelContext>,     // { name, fields: Vec<{ name, type_name }> }
    routes: Vec<RouteContext>,     // { method, path, handler }
    existing_views: Vec<String>,   // file names of existing views
    example: String,               // Complete view example code
    conventions: ViewConventions,  // Naming and structure conventions
}
ModelContext { name: String, fields: Vec<FieldContext> }
FieldContext { name: String, type_name: String }
RouteContext { method: String, path: String, handler: String }
ViewConventions {
    file_location: String,         // "src/views/{name}.rs"
    function_signature: String,    // "pub fn view() -> JsonUiView"
    import_pattern: String,        // "use ferro::{...};"
    layout_default: String,        // "app"
}
```

Accept optional parameters:
- `model`: Optional model name — if provided, include only that model's fields (focused context for model-specific views)
- `description`: Optional view description — passed through to help the agent understand intent

Register in service.rs:
- Params: `JsonUiGenerateParams { model: Option<String>, description: Option<String> }`
- Tool name: `json_ui_generate`
- Description: explain when to use (creating a new JSON-UI view, getting context for view generation, understanding available models and routes for view building) and what it combines with (json_ui_catalog for detailed component reference, list_models for full model details, code_templates with category json_view for boilerplate)

Add `pub mod json_ui_generate;` to tools/mod.rs.

Include unit tests: test_conventions_populated, test_example_not_empty, test_serialization.
