<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local working tree -> origin/master via git push | The human authorizes the push; CI receives the new ref. |
| origin/master -> GitHub Actions runner with crates.io token -> crates.io | Only CI has the `publish-update` token. The token is bound to existing crate names, so it cannot register new crates — only update existing ones. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-156-06-01 | Spoofing | git push triggers CI publish | mitigate | Push requires the human's git credentials; CI verifies the commit ref. Multi-step gate (human + CI workflow). |
| T-156-06-02 | Tampering | Workspace version bumped incorrectly (skipped, repeated, downgraded) | mitigate | Task 1 acceptance criteria pins the version to "exactly one patch increment above the read value" and the verify command greps for a semver-shaped line. Verify gate also re-checks. |
| T-156-06-03 | Information disclosure | CHANGELOG entry mentions internal phase numbers | accept | CHANGELOG entries already reference phase numbers (151, 152, 153, 154, 155 entries do). Public-facing convention. |
| T-156-06-04 | Repudiation | Crates.io publish action recorded by CI | mitigate | GitHub Actions logs are tamper-evident and tied to the actor (the bot account). |
| T-156-06-05 | DoS | publish workflow fails mid-publish, leaving partial state | accept | Publish action is per-crate; failure of one crate does not corrupt others. Phase 156 only updates `ferro-rs`, so partial-publish risk is single-crate scope. |
| T-156-06-06 | Elevation of privilege | publish-update token only updates existing crates | mitigate | Per project memory: CI publish token is `publish-update`-scoped, NOT `publish-new`. Phase 156 introduces no new crate (D-13), so the existing token suffices. |
</threat_model>
