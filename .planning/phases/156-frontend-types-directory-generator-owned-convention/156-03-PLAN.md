<objective>
Extend the Dockerfile renderer so that, when a project has a frontend, the rendered Dockerfile includes a dedicated Rust-toolchain stage (`types-gen`) that regenerates `frontend/src/types/` and the frontend-builder stage copies the regenerated types in before running `npm run build`. The renderer stays pure (no I/O); a new `resolve_ferro_version` helper does the Cargo.lock parsing on behalf of callers (wired into the call sites in Plan 04).

Purpose: This is the load-bearing fix for the killer feature — without it, every consumer's `docker build` fails at `tsc` because the gitignored `frontend/src/types/` is absent from the build context. The change is renderer-local and additive (no behavior change when `has_frontend == false`).
Output: Updated `DockerContext` struct, two new template constants (`TYPES_GEN_STAGE_BODY`, `FRONTEND_STAGE_WITH_TYPES_COPY_BODY`), updated `render_dockerfile`, new `resolve_ferro_version` helper, and four new renderer tests covering presence/absence/ordering/no-unresolved-tokens.
</objective>

**Edit 4 — Add the `resolve_ferro_version` helper.**

Add this `pub(crate)` function at the bottom of the file's pub-fn region (after `read_rust_channel`, before the `// =====` docker-compose section comment marker). Do NOT place it inside the `mod tests` block.

```rust
/// Phase 156 §6 (D-16/D-21): resolve the ferro-cli version to pin in the
/// `types-gen` Docker stage. Parses the project's `Cargo.lock` for the
/// `ferro-rs` package; falls back to the current binary's own version
/// (`env!("CARGO_PKG_VERSION")`) when the lockfile is absent or has no
/// `ferro-rs` entry. Never returns an empty string.
///
/// This function is shared with `crate::commands::docker_init` and
/// `crate::doctor::checks::docker_template_drift` (Plan 04), which both
/// construct `DockerContext` at the I/O boundary and pass the resolved
/// version into the pure renderer.
pub(crate) fn resolve_ferro_version(project_root: &Path) -> String {
    if let Ok(lock) = fs::read_to_string(project_root.join("Cargo.lock")) {
        if let Ok(parsed) = lock.parse::<Value>() {
            if let Some(pkgs) = parsed.get("package").and_then(|v| v.as_array()) {
                for pkg in pkgs {
                    let name = pkg.get("name").and_then(|n| n.as_str());
                    let ver = pkg.get("version").and_then(|v| v.as_str());
                    if name == Some("ferro-rs") {
                        if let Some(v) = ver {
                            return v.to_string();
                        }
                    }
                }
            }
        }
    }
    env!("CARGO_PKG_VERSION").to_string()
}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Dockerfile renderer -> generated Dockerfile -> Docker daemon | Renderer is pure; the rendered string flows into a Dockerfile consumed by `docker build`. Template-injection risk: any unescaped `{{FERRO_VERSION}}` substitution that comes from untrusted input could inject shell metacharacters into `cargo install ferro-cli --version <X>` |
| Cargo.lock parsing -> resolve_ferro_version -> ferro_version field | `Cargo.lock` is read from the project root; an attacker who can write to the project's Cargo.lock could inject a malformed version string |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-156-03-01 | Tampering | Cargo.lock-derived ferro_version flows into `cargo install --version {{FERRO_VERSION}}` | mitigate | `cargo install --version <X>` rejects malformed version strings (cargo validates the semver-like input). Even if Cargo.lock is attacker-controlled, the injection surface is `cargo install`'s argument validation, not arbitrary shell. The Dockerfile uses `RUN cargo install ferro-cli --version {{X}} --locked` — no shell interpolation of `{{X}}`. Acceptable. |
