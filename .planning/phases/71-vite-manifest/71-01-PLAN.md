# Phase 71-01: Read Vite Manifest for Production Asset Paths

<objective>
Fix production asset loading by reading Vite's manifest.json to resolve hashed asset filenames instead of hardcoding `/assets/main.js` and `/assets/main.css`.
</objective>

<context>
## The Problem

In `ferro-inertia/src/response.rs` lines 440-441, production mode hardcodes:
```html
<script type="module" src="/assets/main.js"></script>
<link rel="stylesheet" href="/assets/main.css">
```

But Vite generates hashed filenames like `main-BiRGL2vC.js`. The actual mapping is in
`public/assets/.vite/manifest.json`:
```json
{
  "src/main.tsx": {
    "file": "assets/main-BiRGL2vC.js",
    "isEntry": true,
    "css": ["assets/main-DXEjMDJ3.css"]
  }
}
```

## How It Should Work

1. On first request (or at startup), read `public/assets/.vite/manifest.json`
2. Look up the entry point (configured in `InertiaConfig`, default `src/main.tsx`)
3. Extract the `file` (JS) and `css` array from the manifest entry
4. Generate `<script>` and `<link>` tags with the actual hashed paths
5. Cache the parsed manifest (it doesn't change at runtime in production)

## InertiaConfig

The config already has an `entry_point` field used in dev mode. In production, this same field
should be the key to look up in manifest.json.

Current config fields:
- `entry_point`: e.g., `"src/main.tsx"` (used as Vite dev server script path)
- `development`: bool (switches between dev/prod HTML templates)

## Vite Manifest Format

Standard Vite 5 manifest.json structure:
```json
{
  "<entry_point>": {
    "file": "assets/<name>-<hash>.js",
    "src": "<entry_point>",
    "isEntry": true,
    "css": ["assets/<name>-<hash>.css"]
  }
}
```

- The key matches the Rollup input path (e.g., `src/main.tsx`)
- `file` is the JS output path relative to `outDir`
- `css` is an array of CSS output paths (may be empty or missing)
- Paths are relative to the build output directory

## Manifest Location

Vite 5 places the manifest at `<outDir>/.vite/manifest.json`.
For mkmenu: `public/assets/.vite/manifest.json`.

The location should be configurable but default to `public/assets/.vite/manifest.json`.
</context>

<steps>
1. Create `ferro-inertia/src/manifest.rs` with:
   - `ViteManifest` struct that wraps `HashMap<String, ManifestEntry>`
   - `ManifestEntry` struct: `file: String`, `css: Option<Vec<String>>`, `is_entry: Option<bool>`
   - `ViteManifest::load(path: &str) -> Option<ViteManifest>` reads and parses the JSON
   - `ViteManifest::resolve(entry: &str) -> Option<ResolvedAssets>` looks up entry, returns JS path + CSS paths
   - `ResolvedAssets` struct: `js: String`, `css: Vec<String>`
   - Use `std::sync::OnceLock` to cache the parsed manifest (read once, reuse forever)
   - Expose a function `resolve_assets(manifest_path: &str, entry_point: &str) -> ResolvedAssets` that returns the cached result or falls back to unhashed defaults

2. Add `manifest_path` field to `InertiaConfig`:
   - Default: `"public/assets/.vite/manifest.json"`
   - Builder method: `.manifest_path("custom/path")`

3. Update `InertiaResponse::to_response()` production branch:
   - Call `resolve_assets(&self.config.manifest_path, &self.config.entry_point)`
   - Generate `<script>` tags from `resolved.js`
   - Generate `<link rel="stylesheet">` tags from `resolved.css` (may be multiple)
   - Prepend `/` to paths from manifest since they're relative (e.g., `assets/main-xxx.js` → `/assets/main-xxx.js`)

4. Add `mod manifest;` to `ferro-inertia/src/lib.rs`

5. Run verification:
   - `cargo fmt --all -- --check`
   - `cargo clippy --all --all-targets -- -D warnings`
   - `cargo test --all-features`
</steps>
