## Component selection algorithm

| Option | Description | Selected |
|--------|-------------|----------|
| A — Lookup table only | Hardcoded `(DataType, FieldMeaning) → component name` table inside ferro-json-ui, no Catalog cross-check | |
| B — Catalog metadata scan | Extend `ComponentSpec` with `meaning_hints: Vec<FieldMeaning>` and pick by introspection | |
| C — Auditable table cross-checked against Catalog | Single `MEANING_COMPONENT_TABLE` + drift guard against `Catalog::components` (recommended) | ✓ |

**Selected:** C
**Notes:** "Which component renders Money in Display mode" is a designer choice, not derivable. Option B couples Catalog metadata to projection concerns (violates Phase 117 D-03's slot-only metadata convention). Option C keeps the design intent in one auditable place while consistency-by-construction is preserved by drift guard + `Catalog::validate(&spec)` at the end of `Spec::from_service_def`.

## Props construction (typed vs raw JSON)

| Option | Description | Selected |
|--------|-------------|----------|
| A — Typed Props for all elements | Including plugins (would require typed plugin surface) | |
| B — Raw JSON for all elements | Mirrors current `field_map.rs` pattern, faster to write | |
| C — Typed for built-ins, raw JSON for plugins (recommended) | Compile-time safety where typed surface exists | ✓ |

**Selected:** C
**Notes:** Typed Props catch prop-name typos at compile time; matches Phase 115 D-03. Plugins have no typed surface, so emission via `serde_json::Value` is the only option. Catalog's per-component schema validates either path.

## Intent layout vocabulary

| Option | Description | Selected |
|--------|-------------|----------|
| A — Single root element with all field-children | Matches current naive impl | |
| B — Built-in declarative per-intent templates | New private vocabulary owned by ferro-json-ui | |
| C — `ferro-theme::IntentSlotTemplate` vocabulary, ctx.templates override (recommended) | Reuses existing 8-slot vocabulary; re-enables `VisualContext.templates` plumbing | ✓ |

**Selected:** C
**Notes:** Vocabulary already exists (`title`, `body`, `fields`, `actions`, `relationships`, `pagination`, `metadata`, `stats`) and is the documented theme override surface. `VisualContext.templates` is currently dead — wiring fixes that. Re-inventing would fragment the design.
