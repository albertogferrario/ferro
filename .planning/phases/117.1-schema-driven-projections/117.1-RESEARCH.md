## Summary

Phase 117.1 is a purely internal refactor — it creates a schema-driven pipeline inside `ferro-json-ui/src/projection/` that replaces approximately 350 LOC of hardcoded match arms in `field_map.rs` + `relationship_map.rs` + `mod.rs` with a three-layer design: (1) an auditable `MEANING_COMPONENT_TABLE` validated against the Catalog, (2) typed `*Props` construction via serde, and (3) an intent-to-layout dispatch table that activates the `ferro-theme` slot vocabulary currently dormant in `VisualContext.templates`.

The codebase is in excellent shape for this work. The CONTEXT.md has already resolved all architectural decisions. This research phase serves primarily to ground those decisions in the actual code shapes, identify non-obvious implementation constraints surfaced by reading the code directly, and catalogue the complete set of typed Props structs the builder will need to construct — so the planner can produce precise task breakdowns without guessing.

The killer feature is the "consistent by construction" guarantee: `Spec::from_service_def` calls `Catalog::validate` on every output, so the projector and catalog are provably in sync at every test run. No other path in the codebase achieves this today.

**Primary recommendation:** Implement in the file order `error.rs → component_map.rs → intent_layout.rs → builder.rs → delete field_map.rs + relationship_map.rs → thin JsonUiRenderer wrapper → update lib.rs re-exports`. Each file is independently testable in that order.

### Pattern 1: MEANING_COMPONENT_TABLE — Static Auditable Dispatch Table

**What:** A `&'static [(FieldMeaning, ComponentChoice)]` that replaces three parallel match functions with a single source of truth. `ComponentChoice` carries `display`, `input`, and `column` component name choices per meaning.

**When to use:** Any time `FieldMeaning` drives component selection.

**Concrete shape derived from reading `field_map.rs` and `component.rs`:**

```rust
// ferro-json-ui/src/projection/component_map.rs
// [VERIFIED: field_map.rs lines 22-103 for display choices, 116-263 for input,
//            269-293 for column. component.rs lines 64-78 for InputType variants.]

pub struct ComponentChoice {
    /// Built-in component type name for Display mode. None = hide.
    pub display: Option<&'static str>,
    /// Built-in component type name for Input mode. None = no form control.
    pub input: Option<&'static str>,
    /// Built-in component type name for column mode (DataTable). None = exclude.
    pub column: Option<&'static str>,
}

// One row per FieldMeaning variant (18 named + Custom fallback below)
static MEANING_COMPONENT_TABLE: &[(FieldMeaning, ComponentChoice)] = &[
    // FieldMeaning::Identifier — display as Text span, input as hidden, exclude from columns
    // FieldMeaning::ForeignKey — display None, input as Select, column None
    // FieldMeaning::EntityName — Text/Input(text)/Column
    // FieldMeaning::Email — Text/Input(email)/Column
    // FieldMeaning::Phone — Text/Input(tel)/Column
    // FieldMeaning::Url — Text/Input(url)/Column
    // FieldMeaning::ImageUrl — Avatar/Input(url)/Column
    // FieldMeaning::Money — Text/Input(number+step)/Column(format=currency)
    // FieldMeaning::Percentage — Progress/Input(number+min/max)/Column
    // FieldMeaning::Quantity — Text/Input(number)/Column
    // FieldMeaning::Status — Badge(default)/Select/Column
    // FieldMeaning::Category — Badge(secondary)/Select/Column
    // FieldMeaning::Boolean — Badge(outline)/Switch/Column(format=boolean)
    // FieldMeaning::FreeText — Text/Input(textarea)/Column
    // FieldMeaning::CreatedAt — Text/Input(text,disabled)/Column(format=datetime)
    // FieldMeaning::UpdatedAt — Text/Input(text,disabled)/Column(format=datetime)
    // FieldMeaning::DateTime — Text/Input(text)/Column(format=datetime)
    // FieldMeaning::Sensitive — None/Input(password,no data_path)/None
    // NOTE: Custom(_) is handled by a fallback function, not a table row,
    // because FieldMeaning::Custom contains a String (not Copy).
];
```

**Non-obvious constraint:** `FieldMeaning::Custom(String)` cannot be a static table row because `String` is not `'static`. The lookup function must handle it as a fallback after exhausting the static table. [VERIFIED: `ferro-projections/src/field.rs` line 54 — `Custom(String)`, not `Custom(&'static str)`.]

**Non-obvious constraint 2:** `ComponentChoice::column` is not the same as a column definition — it names which built-in component drives column rendering, but the actual `Column` struct (with `key`, `label`, `format`) is built separately by `emit_fields`. The table's `column` field is currently best modelled as `Option<()>` (include/exclude) plus the `format` hint embedded in the `build_column_props` helper. [VERIFIED: `component.rs` line 128-133 — `Column { key, label, format: Option<ColumnFormat> }` is what `DataTableProps.columns` expects.]

### Pattern 2: Typed Props Construction

**What:** Each slot emit function builds a typed Props struct and calls `serde_json::to_value(&props).unwrap()` to produce the `Element.props` payload.

**Concrete API surface required (derived from `component.rs`):**

| Slot / Usage | Component | Required Props Fields |
|-------------|-----------|----------------------|
| fields (display) | `Text` | `content: String, element: TextElement` [VERIFIED: component.rs line 317-320] |
| fields (display) | `Badge` | `label: String, variant: BadgeVariant` [VERIFIED: component.rs line 294-298] |
| fields (display) | `Avatar` | `alt: String, src: Option<String>` [VERIFIED: component.rs line 465-467] |
| fields (display) | `Progress` | `value: u8` [VERIFIED: component.rs line 440-443] |
| fields (input) | `Input` | `field: String, label: String, input_type: InputType` [VERIFIED: component.rs line 228-256] |
| fields (input) | `Select` | `field: String, label: String, options: Vec<SelectOption>` [VERIFIED: component.rs line 261-280] |
| fields (input) | `Switch` | needs investigation — `SwitchProps` at offset ~347 |
| Browse/Track root | `DataTable` | `columns: Vec<Column>, data_path: String` [VERIFIED: component.rs line 741-750] |
| Focus root | `Card` | `title: String` [VERIFIED: component.rs line 144-152] |
| Collect/Input root | `Form` | `action: Action` (required) [VERIFIED: component.rs line 183-196] |
| Process root | `KanbanBoard` | `columns: Vec<KanbanColumnProps>` [VERIFIED: component.rs line 765-769] |
| Summarize root | `StatCard` | `label: String, value: String` [VERIFIED: component.rs line 543-553] |

**Critical finding — FormProps requires `action: Action`:** `FormProps.action` is required (no `Option`, no `#[serde(default)]`). [VERIFIED: component.rs line 186.] The projector emitting a Form in Input mode must provide an Action. The naive v1 renderer does NOT do this — it emits `("Form", vec![])` without any `action` prop. This means either (a) the new pipeline provides a placeholder `Action` (e.g., `Action { handler: format!("/{name}"), method: HttpMethod::Post, ... }`) or (b) `Catalog::validate` will reject the generated Form spec because `action` is missing.

**This is a gap in the existing v1 renderer that Phase 117.1 must resolve.** The planner should add a task for defining the placeholder Action shape for auto-projected Forms. Recommendation: `Action { handler: format!("/{}", service.name), method: None, confirm: None, ... }` with a module-level rustdoc note that callers can override via `ctx` or post-projection mutation.

### Pattern 3: Intent → Layout via `default_template(Intent)`

**What:** `intent_layout.rs` provides a `pub fn default_template(intent: &Intent) -> IntentModeTemplates` covering all 7 structural intents.

**`ThemeTemplates` shape** [VERIFIED: ferro-theme/src/template.rs lines 46-75]:
- 7 fields, each `Option<IntentModeTemplates>`, keyed by intent name (snake_case)
- `IntentModeTemplates { display: IntentSlotTemplate, input: IntentSlotTemplate }`
- `IntentSlotTemplate { slots: Vec<String>, layout: Option<String> }`

**Resolution chain in `Spec::from_service_def`:**
```rust
let effective = ctx.templates
    .as_ref()
    .and_then(|t| pick_intent_template(t, &intent))   // returns Option<&IntentModeTemplates>
    .cloned()
    .unwrap_or_else(|| default_template(&intent));
```

`pick_intent_template` is a match on `Intent` variant that indexes into `ThemeTemplates`. [VERIFIED: ThemeTemplates has named fields `browse`, `focus`, `collect`, `process`, `summarize`, `analyze`, `track` — so matching is by variant, not by index.]

**Non-obvious constraint:** `ThemeTemplates.browse` is `Option<IntentModeTemplates>`, not `IntentModeTemplates`. When the user provides a `ThemeTemplates` with `browse: None`, the projector must fall back to `default_template(Intent::Browse)`. The override semantics are: "if the theme supplies ANY template for this intent, use it entirely; otherwise use the built-in default." [VERIFIED: template.rs lines 48-54 — all fields are `Option`.]

### Pattern 4: Two-Pass Validation (generate then validate)

**What:** `Catalog::validate(&spec)` runs after spec construction and before returning from `Spec::from_service_def`. Failure is `Err(ProjectionError::CatalogValidation(Vec<CatalogError>))`.

**Catalog::validate API** [VERIFIED: catalog.rs lines 630-712]:
- Stage 1: type-name whitelist check (O(1) per element)
- Stage 2: per-element Props JSON Schema validation
- Stage 3: full-spec envelope validation (cached jsonschema::Validator)
- Returns `Result<(), Vec<CatalogError>>`

**Important subtlety:** Stage 2 skips elements where `el.props.is_null()`. [VERIFIED: catalog.rs line 659.] If a slot emit function produces a null-props element, validation will pass silently. This means: every element the projector produces MUST have non-null props for the validation guarantee to hold. The typed Props approach (D-04) ensures this — `serde_json::to_value` of any `*Props` struct produces a JSON object, never null.

**Debug vs release semantics (D-06):**
```rust
match global_catalog().validate(&spec) {
    Ok(()) => Ok(spec),
    Err(errors) => {
        #[cfg(debug_assertions)]
        panic!("ProjectionError: catalog validation failed: {:?}", errors);
        Err(ProjectionError::CatalogValidation(errors))
    }
}
```

**What:** A `#[test]` in `component_map.rs` iterates `MEANING_COMPONENT_TABLE` and asserts every non-None component name in `ComponentChoice` is a key in `global_catalog().components`.

**Prior art in codebase** [VERIFIED: catalog.rs lines 1004-1019]:

### Anti-Patterns to Avoid

- **Calling `global_catalog()` inside slot emit functions:** `global_catalog()` initializes the OnceLock on first call. Call it once at the top of `Spec::from_service_def` and pass `&Catalog` down. Avoids repeated atomic reads.
- **Returning `Value::Null` for hidden fields:** The v1 `field_to_display` returns `Value::Null` for `ForeignKey` and `Sensitive`. The new pipeline must NOT insert null-valued elements into the Spec — instead, skip them entirely (do not call `spec.elements.insert`). Inserting null-props elements passes Stage 2 validation but would create orphan elements in the Spec.
- **Using `SpecBuilder.element(id, el).prop(k, v)` for typed Props:** The v1 renderer uses this one-prop-at-a-time API. Phase 117.1 should build a full typed `*Props` struct, call `serde_json::to_value`, and set `el.props` directly — bypassing the fluent `.prop()` API entirely. [VERIFIED: ElementBuilder has `.prop(k, v)` but also allows constructing Element directly from struct fields — spec.rs lines 171-187.]
- **Re-implementing `field_display_name`:** Already exists in `ferro-projections::render::field_display_name`. Import it via `ferro_projections::render::field_display_name`. [VERIFIED: render/mod.rs lines 66-80.]
- **Implementing exhaustive `FieldMeaning` match in multiple places:** The `MEANING_COMPONENT_TABLE` lookup function should be the single match point. Slot emit functions (`emit_fields`, `emit_metadata`) call it — they don't match on `FieldMeaning` directly.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON Schema validation of generated Spec | Custom validator | `global_catalog().validate(&spec)` | Three-stage validator already compiled once in Phase 117 (catalog.rs line 589) |
| Props → JSON serialization | Manual JSON construction | `serde_json::to_value(&typed_props)` | Typed structs catch field name typos at compile time |
| Component type registry | Custom HashMap | `global_catalog().components` | Already populated at first call, O(1) lookup |
| snake_case → Title Case | Custom string function | `ferro_projections::render::field_display_name` | Already tested, handles edge cases |
| System field detection | Custom predicate | `ferro_projections::render::is_system_field` | Already covers Identifier/CreatedAt/UpdatedAt |
| Spec construction + structural validation | Manual HashMap assembly | `Spec::builder()` → `.build()` | Runs cycle detection, depth check, dangling ref check |
| Error types | Custom `Box<dyn Error>` | `thiserror::Error` derive on `ProjectionError` | Consistent with SpecError, CatalogError in the same crate |

**Key insight:** Every primitive this phase needs already exists — the work is wiring them together, not building new infrastructure.

## Common Pitfalls

### Pitfall 1: FormProps.action is Required

**What goes wrong:** `serde_json::to_value(FormProps { action: ??? })` fails at compile time because `action` has no default. The existing v1 renderer emits Form without props, which passes Stage 2 validation only because `el.props.is_null()` skips it. The new pipeline must provide a real Action.

**Why it happens:** `FormProps.action: Action` is required (no `Option`). [VERIFIED: component.rs line 186.]

**How to avoid:** `emit_form_root` in `builder.rs` constructs `Action { handler: format!("/{}", service.name), method: Some(HttpMethod::Post), ... }` as the form submit target. Document this as a convention-based default; Phase 118 will allow callers to override.

**Warning signs:** Clippy error "missing field `action` in initializer" or catalog Stage 2 PropsInvalid error for "Card" / "Form" with "missing required property".

### Pitfall 2: MEANING_COMPONENT_TABLE Cannot Cover Custom(String)

**What goes wrong:** Exhaustive match on `FieldMeaning` in the lookup function requires handling `Custom(String)`, but `Custom` contains a heap-allocated `String` which prevents use in a static pattern. A `match meaning { FieldMeaning::Custom(_) => ... }` works fine at runtime but cannot appear in a `static` initializer pattern.

**Why it happens:** `FieldMeaning::Custom(String)` is not a unit variant. [VERIFIED: field.rs line 54.]

**How to avoid:** The lookup function has two parts: (1) iterate `MEANING_COMPONENT_TABLE` comparing known variants, (2) an `else` branch for `FieldMeaning::Custom(_)` that returns the Text/Input/Column fallback triple hardcoded in the function. This is not a violation of D-01 — the static table covers all 18 named variants; the runtime branch covers custom meanings only.

**Warning signs:** "patterns are not allowed in statics" compiler error, or exhaustiveness warning about `Custom` variant not covered.

### Pitfall 3: Spec Nesting Depth Limit

**What goes wrong:** `SpecBuilder::build()` enforces `MAX_NESTING_DEPTH = 3`. [VERIFIED: spec.rs line 37.] A deeply-slotted spec (root container → slot section → field element → child element) can hit this limit.

**Why it happens:** The slot vocabulary uses nested layouts. Browse intent: root `DataTable` (depth 1) has no children in the element graph because `DataTable.columns` is a `Vec<Column>` prop, not child element IDs. Focus intent: root `Card` (depth 1) → children for each field element (depth 2) → no grandchildren. The depth limit is not a concern for leaf components, but `KanbanBoard` with column children and KanbanColumn with card children could reach depth 3.

**How to avoid:** Keep the element tree flat. `KanbanBoard.columns` is a `Vec<KanbanColumnProps>` prop (not element IDs). [VERIFIED: component.rs line 765.] So KanbanBoard is a single root element with all columns embedded in props — no children element IDs needed. The Process intent layout emits one `KanbanBoard` element, depth 1.

**Warning signs:** `SpecError::DepthExceeded` during `SpecBuilder::build()`.

### Pitfall 4: DataTableProps.columns vs DescriptionListProps.items Field Shape

**What goes wrong:** `emit_fields` for Browse uses `DataTableProps.columns: Vec<Column>` where `Column { key, label, format }`. For Focus it uses `DescriptionListProps.items: Vec<DescriptionItem>`. These are different structs requiring different builders.

**Why it happens:** Two different display modes for the same set of fields use different container components with different column/item shapes. [VERIFIED: component.rs line 741 for DataTableProps, line 390 for DescriptionListProps.]

**How to avoid:** `build_column_props(field: &FieldDef) -> Column` and `build_description_item(field: &FieldDef, value: &str) -> DescriptionItem` are separate helpers in `component_map.rs`. The slot emit function `emit_fields` takes a `container_type: &str` parameter and branches on it, or `emit_fields_as_columns` / `emit_fields_as_list` are separate functions.

**Warning signs:** Catalog Stage 2 PropsInvalid error for DataTable mentioning "columns must be array of objects with key/label".

### Pitfall 5: DescriptionItem shape unknown — investigate during implementation

**What goes wrong:** `DescriptionItem` struct is defined in `component.rs` around line 380 (between DescriptionListProps at line 390 and other types). Its field names are not verified in this research pass.

**How to avoid:** During Wave 0 / first task, read `DescriptionItem` struct fields before writing `build_description_item`. [ASSUMED: field shape is `{ label: String, value: String }` based on common pattern, but not verified at line level.]

### Pitfall 6: `Catalog::validate` OnceLock initialization in tests

**What goes wrong:** `global_catalog()` is a `OnceLock` initialized once. Tests that register plugins with `register_plugin()` pollute the global registry before `global_catalog()` first call, which can cause unexpected catalog states in parallel tests.

**Why it happens:** Phase 117 documented this [VERIFIED: catalog.rs line 965-994 — `build_builtins_only()` is the test helper for isolation].

**How to avoid:** Phase 117.1 tests that need a clean catalog should use `Catalog::build_builtins_only()` (test-only fn, already defined in catalog.rs). The drift guard test uses `global_catalog()` which is fine (it's testing the real catalog).

### Pitfall 7: Relationship slot uses `NavigationHint::Tab` — no `Tab` component for auto-projection

**What goes wrong:** The v1 `relationship_to_component` maps `Tab` to a fragment with `tab_label` and `tab_key` fields [VERIFIED: relationship_map.rs lines 37-41] — not a built-in `Tabs` component. Phase 117.1's `RELATIONSHIP_COMPONENT_TABLE` must decide whether `Tab` → `"Tabs"` component (which requires `TabsProps { default_tab, tabs: Vec<Tab> }`) or is lifted to the intent_layout level.

**How to avoid:** Per D-09, `Tab` relationships are "lifted by intent_layout into a Tabs container". The intent_layout `relationships` slot emit function handles `Tab`-hint relationships specially — it groups all Tab relationships into one `Tabs` element rather than emitting one element per relationship. This requires the emit function to pre-scan `service.relationships` for `Tab` hints before building elements.

```rust
// ferro-json-ui/src/projection/builder.rs
// Source: derived from CONTEXT.md D-08 + current mod.rs:119-154 shape

use ferro_projections::{IntentScore, ServiceDef};
use crate::{Spec, catalog::global_catalog};
use super::{VisualContext, RenderMode, error::ProjectionError};
use super::component_map::lookup_component;
use super::intent_layout::{default_template, pick_intent_template};

impl Spec {
    #[cfg(feature = "projections")]
    pub fn from_service_def(
        service: &ServiceDef,
        intents: &[IntentScore],
        ctx: &VisualContext,
    ) -> Result<Spec, ProjectionError> {
        if intents.is_empty() {
            return Err(ProjectionError::EmptyIntents);
        }
        let intent_score = intents.get(ctx.intent_index)
            .ok_or(ProjectionError::IntentIndexOutOfBounds {
                requested: ctx.intent_index,
                available: intents.len(),
            })?;

        // D-11: Input mode collapses all intents to Form.
        let spec = if ctx.mode == RenderMode::Input {
            build_input_spec(service, ctx)?
        } else {
            let template = ctx.templates
                .as_ref()
                .and_then(|t| pick_intent_template(t, &intent_score.intent))
                .cloned()
                .unwrap_or_else(|| default_template(&intent_score.intent));
            build_display_spec(service, &intent_score.intent, &template, ctx)?
        };

        // D-06: always validate; panic in debug, Err in release.
        match global_catalog().validate(&spec) {
            Ok(()) => Ok(spec),
            Err(errors) => {
                #[cfg(debug_assertions)]
                panic!("Projector emitted invalid spec: {:?}", errors);
                Err(ProjectionError::CatalogValidation(errors))
            }
        }
    }
}
```

### 2. `ComponentChoice` + table lookup

```rust
// ferro-json-ui/src/projection/component_map.rs
// Source: derived from field_map.rs exhaustive mapping + component.rs typed Props

use ferro_projections::FieldMeaning;

pub struct ComponentChoice {
    pub display: Option<&'static str>,
    pub input: Option<&'static str>,
    pub column: Option<&'static str>,
}

const FALLBACK: ComponentChoice = ComponentChoice {
    display: Some("Text"),
    input: Some("Input"),
    column: Some("Column"),
};

// Table is &[(FieldMeaning, ComponentChoice)] — but FieldMeaning is not Copy
// and contains Custom(String), so we use a function-based dispatch instead:
pub fn lookup_meaning(meaning: &FieldMeaning) -> ComponentChoice {
    match meaning {
        FieldMeaning::Identifier    => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: None         },
        FieldMeaning::ForeignKey    => ComponentChoice { display: None,             input: Some("Select"), column: None         },
        FieldMeaning::EntityName    => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::Email         => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::Phone         => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::Url           => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::ImageUrl      => ComponentChoice { display: Some("Avatar"),   input: Some("Input"),  column: Some("Text") },
        FieldMeaning::Money         => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::Percentage    => ComponentChoice { display: Some("Progress"), input: Some("Input"),  column: Some("Text") },
        FieldMeaning::Quantity      => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::Status        => ComponentChoice { display: Some("Badge"),    input: Some("Select"), column: Some("Text") },
        FieldMeaning::Category      => ComponentChoice { display: Some("Badge"),    input: Some("Select"), column: Some("Text") },
        FieldMeaning::Boolean       => ComponentChoice { display: Some("Badge"),    input: Some("Switch"), column: Some("Text") },
        FieldMeaning::FreeText      => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::CreatedAt     => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::UpdatedAt     => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::DateTime      => ComponentChoice { display: Some("Text"),     input: Some("Input"),  column: Some("Text") },
        FieldMeaning::Sensitive     => ComponentChoice { display: None,             input: Some("Input"),  column: None         },
        FieldMeaning::Custom(_)     => FALLBACK,
    }
}
```

**Note:** The `column` field in `ComponentChoice` is a semantic flag (include/exclude + format hint), not a component type name. A `Column { key, label, format }` struct is built by `build_column_for_field`, not by instantiating a "Column component". The `column: Some("Text")` entries above indicate "include this field as a column" — the actual `Column` struct construction happens in `emit_fields_as_columns`.

### 5. `ProjectionError` enum

```rust
// ferro-json-ui/src/projection/error.rs
// Source: CONTEXT.md D-06 variants + thiserror pattern from SpecError/CatalogError

use thiserror::Error;
use crate::catalog::CatalogError;
use crate::spec::SpecError;

#[derive(Debug, Error)]
pub enum ProjectionError {
    #[error("intent_index {requested} out of bounds (have {available} intents)")]
    IntentIndexOutOfBounds { requested: usize, available: usize },

    #[error("cannot project service with no intents")]
    EmptyIntents,

    #[error("projector referenced unknown component '{type_name}'")]
    UnknownComponent { type_name: String },

    #[error("catalog validation failed: {}", format_catalog_errors(.0))]
    CatalogValidation(Vec<CatalogError>),

    #[error("spec build failed: {0}")]
    SpecBuild(#[from] SpecError),
}

fn format_catalog_errors(errors: &[CatalogError]) -> String {
    errors.iter().map(|e| e.to_string()).collect::<Vec<_>>().join("; ")
}
```
