# Phase 117.1: Schema-Driven Projections - Context

**Gathered:** 2026-04-18
**Status:** Ready for planning
**Mode:** `--auto` — decisions auto-selected for an implementation that consumes the Phase 117 `Catalog`, replaces the v1 hand-coded `field_to_*` / `relationship_to_component` helpers with a schema-driven pipeline, and re-introduces the `ThemeTemplates` slot vocabulary that the naive Phase 115 renderer ignored. Downstream agents may override any auto-choice by editing this file before `/gsd-plan-phase`.

<domain>
## Phase Boundary

Bridge `ferro-projections` (`ServiceDef` + `IntentScore[]`) to `ferro-json-ui` v2 (`Spec`) through a schema-driven pipeline. Concretely:

- Introduce `Spec::from_service_def(service: &ServiceDef, intents: &[IntentScore], ctx: &VisualContext) -> Result<Spec, ProjectionError>` — the new public projection constructor required by ROADMAP success criterion 1. Lives in `ferro-json-ui/src/projection/`, gated by the existing `projections` feature flag.
- Replace the placeholder `JsonUiRenderer::render` body and the dead-code `field_map.rs` / `relationship_map.rs` modules with a schema-driven pipeline that:
  1. Maps `(DataType, FieldMeaning, RenderMode)` → built-in component name via a single auditable table whose rows are validated against `global_catalog().components` at build time (drift = compile-time panic on first call).
  2. Builds typed `*Props` values for built-in components, serialises them with `serde_json::to_value`, and assembles a flat v2 `Spec` (root + per-field child elements).
  3. Maps `NavigationHint` → component the same way, fed into intent-specific slot lists.
  4. Reads the intent's slot list from `ctx.templates` (when supplied) or from the built-in default `IntentModeTemplates` baked into the projector. The slot vocabulary is `ferro-theme`'s existing one (`title`, `body`, `fields`, `actions`, `relationships`, `pagination`, `metadata`, `stats`).
  5. Returns the assembled spec after `global_catalog().validate(&spec)` succeeds. Validation failure is a programmer error (panic in debug, `Err(ProjectionError::CatalogValidation(_))` in release) — projector and catalog being inconsistent by construction is the killer feature of this phase.
- Delete `ferro-json-ui/src/projection/field_map.rs` and `ferro-json-ui/src/projection/relationship_map.rs` (clean break; ROADMAP success criterion 5).
- Rewrite `JsonUiRenderer::render` as a one-liner that delegates to `Spec::from_service_def`. The `Renderer` impl signature stays unchanged.
- Update consumers (`ferro-mcp/src/tools/render_projection.rs`, `framework/src/lib.rs` re-exports, sample app) to consume the new pipeline. The MCP tool's external API shape is unchanged — only its internals call `Spec::from_service_def`.

**What this phase does NOT do** (locked by ROADMAP / earlier phases — do not re-open):
- Change `Spec` / `Element` shape (Phase 115).
- Change the renderer walker, `BUILTIN_TYPES`, or HTML emission (Phase 116).
- Modify `Catalog`, `ComponentSpec`, or `global_catalog()` API (Phase 117).
- Add `$data` / `$template` expression resolution (Phase 118).
- Add a page loader / file-watcher (Phase 119).
- Update CLI / MCP generation tools to use two-tier AI strategy (Phase 120).
- Convert a real gestiscilo page (Phase 121).
- Touch `ferro-projections` crate (the boundary in `ferro-projections/CLAUDE.md` forbids JSON-UI dependencies; all new code lives in `ferro-json-ui` behind the `projections` feature).
- Introduce a new vocabulary for intent slots (the `ferro-theme` `IntentSlotTemplate` vocabulary already exists and is reused).
- Validate or rewrite plugin component selection (plugins do not participate in the meaning→component table; they're addressable by `type_name` only and out of the auto-projection path for Phase 117.1).

<decisions>
## Implementation Decisions

### D-01: Component selection via auditable table validated against the Catalog
**Decision:** Replace the hardcoded `field_to_input` / `field_to_display` / `field_to_column` match arms with a single `MEANING_COMPONENT_TABLE: &[(DataType, FieldMeaning, ComponentChoice)]` where `ComponentChoice` carries the built-in component names for `display` / `input` / `column` modes.

**Rationale:**
- "Which component renders Money in Display mode" is a designer choice, not a derivable property — it must be authored explicitly.
- The Catalog (Phase 117) supplies the JSON Schema and the existence of each chosen component; the projector validates table rows against `global_catalog().components` at build time. Mismatch panics with a clear message at first call (parallels the BUILTIN_SPECS drift guard in Phase 117 D-07).
- This kills the string-typed `json!({ "type": "Text", ... })` blob pattern of `field_map.rs` while keeping the design intent in one auditable place.

**Why:** Auto-mode picked option C (table + Catalog cross-check) over A (lookup table only) and B (scan Catalog for `meaning_hint` metadata). Option B would couple Catalog metadata to projection concerns (violates Phase 117 D-03's slot-only metadata convention); option A loses the consistency-by-construction guarantee.

**How to apply:** Introduce `MEANING_COMPONENT_TABLE` in `ferro-json-ui/src/projection/component_map.rs` (new file) with one row per `FieldMeaning` variant (19 rows) and a wildcard fallback for `Custom(_)`. The table is `&[(...)]`, exhaustively covers every `FieldMeaning` variant, and a `#[test]` enforces exhaustiveness.

### D-02: Mapping table lives in `ferro-json-ui`, not `ferro-projections`
**Decision:** All projection-to-component code stays in `ferro-json-ui/src/projection/`. The `ferro-projections` crate gains nothing.

**Why:** `ferro-projections/CLAUDE.md` explicitly forbids rendering dependencies. The Renderer trait's modality-agnostic design (Phase 133) puts visual-specific concerns in the visual crate. The current `projection/` directory is exactly the right home.

**How to apply:** New file `ferro-json-ui/src/projection/component_map.rs` (replaces `field_map.rs` and `relationship_map.rs`). Public surface re-exported through `ferro-json-ui/src/projection/mod.rs` only behind the `projections` feature.

### D-03: Per-meaning row carries display + input + column choices in one place
**Decision:** Each `MEANING_COMPONENT_TABLE` row exposes:
```rust
struct ComponentChoice {
    display: Option<&'static str>,   // None = hide in display mode (e.g., Sensitive, ForeignKey)
    input:   Option<&'static str>,   // None = no form control (e.g., system-only fields)
    column:  Option<&'static str>,   // None = exclude from data tables
}
```

**Why:** Auto-mode picked option B (one row per meaning, mode keys inside) over A (three parallel tables) and C (Catalog metadata). One row per meaning = single point of truth for "what does Money look like" instead of three.

**How to apply:** A 19-row table with one row per non-`Custom` `FieldMeaning`. `Custom(_)` falls back to a `Text`/`Input`/`column` triple. `Sensitive` rows have `display: None, column: None` (mirrors the Phase-1 `Value::Null` returns in current `field_to_display`). `ForeignKey` rows have `display: None, column: None` and `input: Some("Select")`.

### D-04: Typed Props for built-ins, serialised via `serde_json::to_value`
**Decision:** When the projector emits a built-in component, it constructs the typed `*Props` struct from `ferro-json-ui/src/component.rs` and serialises with `serde_json::to_value(&typed_props).unwrap()`. Plugin components (out of scope for the meaning table per the boundary above) would use raw JSON.

**Why:** Auto-mode picked option C (typed for built-ins, raw JSON for plugins). Typed construction catches prop-name typos at compile time and mirrors Phase 115 D-03 ("Props structs survive as the validation source of truth"). Plugins have no typed surface, so plugin emission, when it eventually appears, would use raw JSON validated by the Catalog instead.

**How to apply:** Helper functions per emitted component (`build_text_props(&FieldDef, …)`, `build_input_props(&FieldDef, …)`, etc.) live in `component_map.rs`. Each returns `serde_json::Value`. Drift between typed Props and the table is caught by `Catalog::validate(&spec)` at the end of `Spec::from_service_def`.

### D-05: Intent layouts use ferro-theme's `IntentSlotTemplate` vocabulary
**Decision:** The eight slot names defined by `ferro_theme::IntentSlotTemplate` (`title`, `body`, `fields`, `actions`, `relationships`, `pagination`, `metadata`, `stats`) are the projection vocabulary. Each intent has a built-in `IntentModeTemplates` default that names which slots to fill and which outer container component to use. `ctx.templates` (already on `VisualContext`) overrides any default.

**Why:** This vocabulary already exists and is the documented theme override surface. Re-inventing it would fragment the design. Plugging the projector into it re-enables the templates plumbing currently dead in `VisualContext` (the field is set but never consulted — see `ferro-json-ui/src/projection/mod.rs:52-54`).

**How to apply:**
- `ferro-json-ui/src/projection/intent_layout.rs` (new file) provides `pub fn default_template(intent: Intent) -> IntentModeTemplates` covering all seven structural intents plus a sensible `Intent::Custom(_)` default (Card+fields).
- `Spec::from_service_def` resolves the effective template as `ctx.templates.as_ref().and_then(|t| pick(t, intent_index)).unwrap_or_else(|| default_template(intent))`.
- Each slot name maps to a deterministic emit function (`emit_title`, `emit_fields`, `emit_actions`, …) that produces a `Vec<(String, Element)>` to insert into `spec.elements`. The outer container (`layout: Some("DataTable" | "Card" | "Form" | "KanbanBoard" | "StatCard")`) becomes the root element with the slot outputs threaded into its `children` (single-slot containers) or its typed slot fields (multi-slot containers per Phase 116 D-06).

**Slot ↔ intent baseline (Display mode):**
| Intent     | Layout component | Slots filled                              |
|------------|------------------|-------------------------------------------|
| Browse     | `DataTable`      | `title`, `fields` (→ columns), `pagination` |
| Focus      | `Card`           | `title`, `fields` (→ DescriptionList), `relationships`, `actions` |
| Collect    | `Form`           | `title`, `fields`, `actions`              |
| Process    | `KanbanBoard`    | `title`, `body` (state lanes), `actions`  |
| Summarize  | `StatCard`       | `title`, `stats`, `metadata`              |
| Analyze    | `Card`           | `title`, `body`, `metadata`               |
| Track      | `DataTable`      | `title`, `fields`, `metadata`             |

(In Input mode every intent collapses to `Form` + `fields` + `actions` to mirror current behaviour and avoid surprising form ergonomics.)

### D-06: Catalog validation runs on every output (success criterion 4)
**Decision:** `Spec::from_service_def` calls `global_catalog().validate(&spec)` before returning `Ok`. Failure short-circuits to `Err(ProjectionError::CatalogValidation(Vec<CatalogError>))`. In `cfg(debug_assertions)` builds the same failure additionally panics with the validation report so test runs fail loudly.

**Why:** Auto-mode picked option A (always validate). ROADMAP criterion 4 is explicit ("two-pass: generate then validate"). The cost is one HashMap lookup + per-element schema check — trivial relative to render time. Opt-in validation defeats "consistent by construction".

**How to apply:** Single call at the end of `Spec::from_service_def`. New `ProjectionError` enum (thiserror-derived) in `ferro-json-ui/src/projection/error.rs` with variants: `IntentIndexOutOfBounds { requested, available }`, `EmptyIntents`, `UnknownComponent { type_name }` (caught before validation), `CatalogValidation(Vec<CatalogError>)`, `SpecBuild(SpecError)`.

### D-07: Clean-break delete of v1 helpers (success criterion 5)
**Decision:** Delete `ferro-json-ui/src/projection/field_map.rs` and `ferro-json-ui/src/projection/relationship_map.rs` outright (and their tests). `ferro-json-ui/src/projection/mod.rs` drops the `pub mod field_map; pub mod relationship_map;` declarations.

**Why:** Auto-mode picked option A (delete). Both modules are dead code in the Phase 115/116 codebase (grep confirms no callers outside their own files). Pre-1.0 + the project-wide "no migration shims" stance (Phase 115 D-21) make deletion the right move. Their tests are translated into integration tests on `Spec::from_service_def`.

**How to apply:** `git rm` on the two files; remove the two `pub mod` lines; relocate the `is_datetime_field` / `is_numeric_field` helpers from `projection/mod.rs` into `component_map.rs` if the new pipeline still needs them (or delete them if it doesn't — they're currently `#[allow(dead_code)]`).

### D-08: Public projection constructor: `Spec::from_service_def`
**Decision:** Add `impl Spec { pub fn from_service_def(service: &ServiceDef, intents: &[IntentScore], ctx: &VisualContext) -> Result<Spec, ProjectionError> { … } }` in `ferro-json-ui/src/projection/builder.rs` (new file), gated by `#[cfg(feature = "projections")]`. `JsonUiRenderer::render` becomes a thin wrapper.

**Why:** Matches ROADMAP success criterion 1's exact signature. Lifting the logic onto `Spec` (rather than burying it in the `Renderer` impl) gives consumers a direct, well-named entry point that doesn't require constructing a renderer struct.

**How to apply:** `Spec::from_service_def` lives on `Spec` via an `impl` block in the projection module (Rust orphan rule allows this since `Spec` is local). `JsonUiRenderer::render` body collapses to `Spec::from_service_def(service, intents, ctx).map_err(|e| Error::Render(e.to_string()))`.

### D-09: Relationships projected through a parallel table
**Decision:** Replace `relationship_to_component` with `RELATIONSHIP_COMPONENT_TABLE: &[(NavigationHint, &'static str)]` and a `build_relationship_props(&RelationshipDef, …)` helper. Driven by the `relationships` slot in the intent layout.

**Why:** Auto-mode picked option C (relationships embedded in intent layouts via the `relationships` slot, NOT a separate top-level concern). The current `relationship_to_component` already maps `NavigationHint` → component but is unwired; this phase wires it through the slot vocabulary.

**How to apply:** Mapping: `Inline → Text`, `Link → Button`, `Tab → (lifted by intent_layout into a Tabs container)`, `Nested → Table`, `Hidden → omit`. The `relationships` slot emit function consults this table per `service.relationships`.

### D-10: System-field handling preserved
**Decision:** The new pipeline preserves the existing `is_system_field` filter from `ferro-projections::render` for Browse/Track column lists and Collect form input lists. System fields (`Identifier`, `CreatedAt`, `UpdatedAt`) are excluded from `fields` slot emission. They appear in `metadata` slot when an intent layout requests it.

**Why:** Mirrors current `columns_value` behaviour and matches user expectation that an "edit form" doesn't contain `id` / `created_at` inputs.

**How to apply:** The `emit_fields` function filters via `is_system_field` for inclusion in the `fields` slot. The `emit_metadata` function (used by Track/Summarize) emits the system fields as a read-only `DescriptionList`.

### D-11: `RenderMode::Input` collapses every intent to a Form
**Decision:** When `ctx.mode == RenderMode::Input`, the projector ignores intent-specific layouts and emits a `Form` outer container with `fields` + `actions` slots populated from the service. This preserves current naive behaviour ("Input mode → Form") while keeping the intent dispatch table coherent.

**Why:** Mirrors `resolve_element` in the current naive renderer (every `(_, RenderMode::Input)` arm returns `("Form", vec![])`). Input layouts per intent are deferred — see D-22.

**How to apply:** `Spec::from_service_def` checks `ctx.mode` first; Input mode bypasses the per-intent template lookup and uses a fixed `("Form", ["fields", "actions"])` layout.

### D-12: Module layout
**Decision:** `ferro-json-ui/src/projection/` ends Phase 117.1 with:
- `mod.rs` — re-exports (`pub use builder::*; pub use error::*;`), `RenderMode`, `VisualContext`, `JsonUiRenderer`. Dispatch logic gone.
- `builder.rs` — `Spec::from_service_def` + private slot orchestration.
- `component_map.rs` — `MEANING_COMPONENT_TABLE`, typed `build_*_props` helpers, drift checks.
- `intent_layout.rs` — `default_template(Intent) -> IntentModeTemplates`, slot-name dispatch, `(intent, mode)` → outer container.
- `relationship_map.rs` — *DELETED.* (Logic absorbed into `component_map.rs` + the `relationships` slot emit function in `builder.rs` or a `relationship_emit.rs` sibling — planner picks the file split.)
- `field_map.rs` — *DELETED.*
- `error.rs` — `ProjectionError` enum.

**Why:** Each file ≤ 600 LOC at completion. The split mirrors the responsibilities (table / typed props / intent layouts / orchestration) so future contributors find the right edit site quickly.

**How to apply:** Planner decides whether `relationship_emit.rs` is its own file or absorbed; the rest is fixed.

### D-13: Drift guard test
**Decision:** A `#[test]` in `component_map.rs` asserts that every component name appearing in `MEANING_COMPONENT_TABLE` exists in `global_catalog().components` (or `plugin_components`). Mismatch fails CI loudly.

**Why:** Catches the "added a meaning row referring to a Catalog component that was renamed/deleted" failure mode at test time, not first-call panic.

**How to apply:** Build `global_catalog()` in the test, iterate the table, assert containment. Parallels Phase 117 D-07's drift guard.

### D-14: ServiceDef with no `display_name` falls back to title-cased `name`
**Decision:** Mirror current `ferro-projections::ServiceDef::from_model` behaviour — `display_name` defaults to `snake_to_title(service.name)`. Preserves existing test expectations and matches the Phase 135 derivation bridge.

**Why:** Consistency across the projection surface. Avoids surprising "title is the snake_case service name" output in projector consumers.

**How to apply:** `emit_title` slot helper consults `service.display_name.as_deref().unwrap_or(&service.name)` and applies `field_display_name` (from `ferro-projections::render`) to the fallback.

### D-15: Plugins are out of scope for auto-projection in Phase 117.1
**Decision:** The meaning table emits only built-in components. A `ServiceDef` cannot, in this phase, declare "render this field via the Map plugin." Plugins remain addressable in hand-authored Specs.

**Why:** Plugin auto-projection requires extending `JsonUiPlugin` with field-meaning hints — that's its own design (see Phase 117 D-15 for the parallel concern at Catalog level). Out of scope for projection; deferred.

**How to apply:** No code; documentation note in the projector's module-level rustdoc that plugin auto-projection lands later.

- Whether to introduce a `ComponentChoice::display_only(&'static str)` constructor as syntactic sugar for the table rows or keep struct-literal init — purely stylistic.

## Existing Code Insights

### Reusable Assets (Phase 117.1 consumes as-is)
- `global_catalog()` — `OnceLock`-frozen singleton; per-call cost is one HashMap lookup.
- `Catalog::components: HashMap<String, ComponentSpec>` — every built-in name keyed for O(1) presence checks (drift guard).
- `Catalog::validate(&spec)` — two-stage validator (type-name pre-dispatch + per-element JSON Schema). Phase 117.1 calls this exactly once per `Spec::from_service_def` invocation.
- `Catalog::component_schema(name)` — per-component schema; useful for tests asserting projector output matches.
- `BUILTIN_TYPES` (`render/mod.rs`) — paired with `Catalog::components` keys; either is a valid drift target.
- `ferro_projections::derive::derive_intents(&service)` — produces ranked `IntentScore`s; the projector itself doesn't call this (caller's responsibility), but it's the upstream of `intents` argument.

<specifics>
## Specific Ideas

- **The Catalog is the contract; the projector is its first non-trivial consumer.** Phase 117 shipped the `Catalog` with two test consumers (drift guard, validation tests) but no production caller that actually generates a Spec from a service definition. Phase 117.1 is that consumer. If the Catalog's API has any sharp edge, it will appear here first — the planner should expect a small tweak to `Catalog` ergonomics (e.g., a `contains_built_in(&str) -> bool` helper) and treat it as in-scope rather than a Phase 117 reopen.
- **Slot vocabulary reuse is a quiet design win.** `ferro-theme::IntentSlotTemplate` exists, has the right shape, and is currently dead because nothing reads it. Wiring the projector to it gives theme authors a real lever (override per-intent layouts in `theme.json`) without inventing a parallel concept. This is the first place themes get to influence projection structure, not just CSS tokens.
- **Drift guard is load-bearing.** With the meaning table auditable in one file, future component renames in `BUILTIN_TYPES` will fail the drift test before they fail in production. This is the "consistent by construction" guarantee the killer-feature framing demands.
- **Two-pass (generate then validate) is the killer-feature framing.** It is what makes "schema-driven projections" mean something concrete: every `Spec` the projector emits is, by construction, indistinguishable from a Spec a human (or AI) wrote against the same Catalog. That symmetry is what Phase 119 (page loader) and Phase 120 (AI generation) will lean on.
- **Typed Props for built-ins is the right cost/benefit.** A typo in a JSON-built `"data_paht"` would surface only at validation time (or render-blank); a typo in `InputProps { data_paht: ... }` is a compile error. The cost is one `serde_json::to_value` call per element — negligible.
- **Don't put the meaning table in `ferro-projections`.** It's tempting (mapping FieldMeaning to "something" feels schema-ish) but it would couple ferro-projections to ferro-json-ui component names, breaking the modality-agnostic promise of v11.5. The right home is `ferro-json-ui/src/projection/component_map.rs` — schema goes one way (in), component decisions go the other (out).
- **Plugin auto-projection is genuinely deferred, not just unscoped.** Plugin authors don't currently expose any "preferred for which `FieldMeaning`" hint, and adding one is a Catalog-API change that should be designed deliberately, not slipped into Phase 117.1. The deferred-ideas section captures this.
- **Resist the urge to make `Spec::from_service_def` also resolve `$data` expressions.** Phase 118's hard cap on the expression language is the load-bearing architectural choice for v12.0; introducing expression resolution in 117.1 would entangle the two. Keep the projector emitting `data_path` strings; let Phase 118 evaluate them.

</specifics>

<deferred>
## Deferred Ideas

- **Plugin auto-projection** — extending `JsonUiPlugin` with a `meaning_hints() -> &[FieldMeaning]` so the projector can choose plugin components for a meaning. Requires Catalog-API design; defer.
- **Per-intent input layouts** (D-11) — instead of every Input-mode intent collapsing to `Form`, allow Process/Track inputs to be wizard / stepper / drawer flows. Out of Phase 117.1's scope.
- **Custom slot emitters** — letting theme authors register their own slot-emit functions (e.g., a "summary_chart" slot for Summarize). Requires plugin-style registration; defer to a v13.0 theme-system phase.
- **Validation error formatter** — `ProjectionError::CatalogValidation`'s `Vec<CatalogError>` could be rendered to a developer-friendly diff against the offending Spec. Nice-to-have for DX; defer.
- **Snapshot tests via fixture JSON** — a `tests/projection_fixtures/` directory of `(service.json, intents, mode) → expected spec.json` pairs would make regressions auditable. Phase 117.1 ships inline tests; fixture corpus is a follow-up if churn warrants.
- **Conditional fields based on guards / preconditions** — render input fields conditionally based on `ServiceDef::guards`. Requires Phase 118's `$data`/`$template` for client-visible state derivation; defer.
- **Internationalisation of slot labels** — slot emit functions currently produce English labels via `field_display_name`. `ferro-lang` integration is a separate concern; defer.
- **Action wiring in the `actions` slot** — Phase 117.1 emits relationship and field elements but does NOT wire `service.actions: Vec<ActionDef>` into Buttons inside the `actions` slot beyond a placeholder ("Action wiring deferred to Phase 118+ when the action pipeline integrates with `$data` / handler routing"). Planner can decide whether the placeholder is empty or a button list with `href="#"` — both are acceptable Phase 117.1 outputs.
- **Workflow / state-machine awareness in Process intent** — Process layout currently emits a `KanbanBoard` keyed by `ctx.current_state`. Full state-machine projection (deriving column structure from `service.state_machine.states`) is in scope only as a stretch goal — defer to a follow-up if implementation budget tightens.
- **Multi-modal projection variants** — voice/text channel renderers consuming the same intent layouts (CHAN-01 / CHAN-02 in REQUIREMENTS.md). v14.0 territory.
- **Reviewed Todos** — none. The `gsd-tools todo match-phase 117.1` query returned `todo_count: 0` so there are no outstanding ideas to fold or defer at this phase.
