# Phase 117.1: Code Review Report

**Reviewed:** 2026-04-18
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

The Phase 117.1 projection pipeline is cleanly factored: catalog, meaning dispatch, intent layout, and slot-based builder each live in their own module with good cohesion. Error types are modelled with `thiserror`, validation happens at a single well-documented choke point, and every `serde_json::to_value` call on typed Props uses `.expect` with a correct rationale. Drift guards (`BUILTIN_SPECS.len() == BUILTIN_TYPES.len()`, test `meaning_table_components_exist_in_catalog`) are in place.

Two correctness concerns stand out. First, `ComponentChoice` carries `display` / `input` / `column` opt-in fields that are partially *ignored* by the slot emitters — meanings with `display: None` (Sensitive, ForeignKey) and `column: None` (ImageUrl, Sensitive, Identifier, ForeignKey) still flow into display lists and DataTable columns, which can leak sensitive data. Second, `build_display_spec` allocates `root_children: Vec<String>` but never wires it into the final `Spec`, so any future layout that wants to add children at the outer builder level will silently drop them.

The remaining findings are low-risk: silent no-op branches, unused helpers left to avoid dead-code warnings, and duplicated format-map logic between `build_column_for_field` and `build_description_item`.

## Warnings

### WR-01: `choice.display` and `choice.column` are never consulted — Sensitive fields can leak

**File:** `ferro-json-ui/src/projection/builder.rs:283-298` and `ferro-json-ui/src/projection/builder.rs:396-418`
**Issue:** `lookup_meaning` explicitly encodes `display: None` for `FieldMeaning::Sensitive` and `FieldMeaning::ForeignKey`, and `column: None` for `Identifier`, `ForeignKey`, `ImageUrl`, and `Sensitive`. However, `emit_datatable_root` and `emit_fields_as_description_list` filter only on `!is_system_field(&f.meaning)` — they never call `lookup_meaning(&f.meaning)` to honour `choice.display` / `choice.column`. A field with meaning `Sensitive` (e.g. a password hash) on a writable, readable `FieldDef` will therefore:
- Appear in the DataTable columns for Browse/Track intents (as `Text` with no masking).
- Appear in the DescriptionList rendered for Focus intents.

The same applies to `ImageUrl` (silently rendered as `Text` in columns instead of being excluded) and `ForeignKey` (never meant to show in display views per the table).

In Input mode the collapse to Form does check `choice.input` (`builder.rs:192`), but Display mode does not.

**Fix:** Gate slot emission on `lookup_meaning(&field.meaning)`:

```rust
// emit_datatable_root
let columns: Vec<Column> = service
    .fields
    .iter()
    .filter(|f| f.readable && !is_system_field(&f.meaning))
    .filter(|f| lookup_meaning(&f.meaning).column.is_some())
    .map(build_column_for_field)
    .collect();

// emit_fields_as_description_list
let items: Vec<DescriptionItem> = service
    .fields
    .iter()
    .filter(|f| f.readable && !is_system_field(&f.meaning))
    .filter(|f| lookup_meaning(&f.meaning).display.is_some())
    .map(build_description_item)
    .collect();
```

Add a regression test: a `ServiceDef` with a `Sensitive` field whose `readable` is `true` must produce a Spec that contains neither a `Text` column nor a `DescriptionItem` for it.

### WR-02: `root_children` allocated in `build_display_spec` but never wired into the Spec

**File:** `ferro-json-ui/src/projection/builder.rs:240, 268-274`
**Issue:** `build_display_spec` declares `let mut root_children: Vec<String> = Vec::new();` at line 240 and passes `&mut root_children` to `emit_card_root` — but `emit_card_root` ends by attaching children directly to the returned `ElementBuilder` via `el.child(id.clone())` at line 335. The vector that the outer function owns is therefore populated but never used. For the four other layouts (`DataTable`, `Form`, `KanbanBoard`, `StatCard`), `root_children` is simply allocated, passed to none of them, and discarded.

If a future layout (or a refactor) decides to wire children at the outer level using `root_children`, the code compiles without warning and silently produces a spec without children — there's no drift guard. The shape also obscures intent: reading `build_display_spec` suggests children are collected centrally, when in fact the Card branch mutates the element inline.

**Fix:** Either:
1. Delete `root_children` and the `&mut root_children` parameter on `emit_card_root`, keeping the inline child-attachment at line 334-336. Simplest and matches the actual dataflow.
2. Flip the responsibility: have every emit function return `(ElementBuilder, Vec<String>)` and wire children uniformly in `build_display_spec`. More uniform but a larger diff.

Given the Plan 03+ note that other layouts are "deferred", option 1 is the minimal fix. Drop the parameter from `emit_card_root`'s signature and from the call site at `builder.rs:248`.

### WR-03: `emit_statcard_root` drops metadata into `aux` orphans, not wired to any parent

**File:** `ferro-json-ui/src/projection/builder.rs:361-388`
**Issue:** `emit_statcard_root` builds a `dropped: Vec<String>` locally, calls `emit_metadata(service, aux, &mut dropped)`, but never uses `dropped`. The metadata DescriptionList gets pushed onto `aux` (and therefore into the final `spec.elements` at `builder.rs:271-272`) but is not referenced by any element's `children`. The resulting Spec contains an orphan element: `metadata_list` lives in `spec.elements` but is unreachable from `root` via `children`.

This is not rejected by `Spec::builder().build()` per the comment at line 371-373 ("catalog validation permits orphan aux elements"), but it means:
1. The element is allocated and validated but never rendered. Dead payload that wastes bandwidth.
2. The comment contradicts `spec.rs` semantics if structural validation ever tightens to require reachability (a common invariant for tree-shaped UIs).
3. A Summarize intent with `slots = ["title", "stats", "metadata"]` therefore *looks* like it renders metadata but in fact silently drops it.

**Fix:** Either:
1. Don't emit metadata for StatCard at all (change `emit_statcard_root` to ignore the metadata slot and document that StatCard has no metadata sink).
2. Change the layout contract: StatCard becomes a child of a `Card` wrapper when metadata is requested, and the DescriptionList becomes a sibling of StatCard inside that wrapper.
3. Confirm that `SpecBuilder` tolerates orphans and add an explicit test that covers this orphan-element path so the contract is pinned.

Option 2 matches the "intent layout" framing best but is a scope expansion. At minimum, add a test in `builder.rs::tests` that a Summarize projection contains `metadata_list` in `spec.elements` and document the orphan-element decision in `CONTEXT.md`.

### WR-04: `input_props_for` falls back to `build_input_props` on unknown type names, silently masking schema drift

**File:** `ferro-json-ui/src/projection/builder.rs:215-226`
**Issue:** The unreachable-branch fallback silently rewrites any unknown `type_name` into an `InputProps` payload. The comment says the drift guard in `component_map.rs` prevents this in practice — but that guard only checks that `choice.display` / `choice.input` reference *existing* built-ins; it does not prove that every `choice.input` value is one of `"Input" | "Select" | "Switch"`. If a future commit adds a new meaning mapped to, say, `input: Some("DatePicker")`, the emitter will silently emit `InputProps` (likely invalid for the `DatePicker` schema) and trigger a validation failure many layers downstream instead of a clear dispatch error.

**Fix:** Change the fallback to surface a `ProjectionError::UnknownComponent`:

```rust
fn input_props_for(type_name: &str, field: &FieldDef) -> Result<serde_json::Value, ProjectionError> {
    match type_name {
        "Input" => Ok(build_input_props(field)),
        "Select" => Ok(build_select_props(field)),
        "Switch" => Ok(build_switch_props(field)),
        other => Err(ProjectionError::UnknownComponent {
            type_name: other.to_string(),
        }),
    }
}
```

Propagate the `Result` up through `build_input_spec`. Add a unit test that a hand-constructed `ComponentChoice { input: Some("Nonexistent"), .. }` triggers `UnknownComponent` instead of silent coercion.

## Info

### IN-01: `build_avatar_props` is defined but never called

**File:** `ferro-json-ui/src/projection/component_map.rs:191-200`
**Issue:** `build_avatar_props` is a `pub` function documented as "Build `AvatarProps` for Display mode (ImageUrl meaning)" and covered by the 117.1-01-PLAN as one of the 11 required builders. However, `builder.rs` never calls it: `emit_fields_as_description_list` always goes through `build_description_item`, and the `ImageUrl` display mapping (`lookup_meaning` returns `display: Some("Avatar")`) is not honoured because, as per WR-01, `choice.display` is never consulted. The reserved `_reserved_props_noop` helper at `builder.rs:545-550` suppresses three helpers but *not* `build_avatar_props`, suggesting the Plan-02 reservation list itself is incomplete.
**Fix:** Once WR-01 is addressed, `build_avatar_props` will be called by a dispatch that matches on `choice.display`. Until then, either add it to `_reserved_props_noop` (cosmetic) or delete it and re-introduce in Plan 03 (minimal-surface discipline per `CLAUDE.md`).

### IN-02: `_reserved_props_noop` and `_plan_02_reserved` are dead-code workarounds

**File:** `ferro-json-ui/src/projection/builder.rs:42-44, 544-550`
**Issue:** Both helpers exist solely to silence the unused-import / dead-code warnings for builders that haven't been wired in yet. This is an acknowledged scaffolding technique but adds cost: future readers have to trace why `build_badge_props` is imported and then immediately discarded, and a missing name in `_reserved_props_noop` (IN-01) is a latent CI failure once `-D warnings` clippy pass runs. The project-wide CLAUDE.md rule "delete old code when replacing — no versioned functions" applies here: keep only the builders actually called by Plan 02.
**Fix:** In the next plan that wires these builders in, delete both `_reserved_props_noop` and `_plan_02_reserved`. Until then, ensure every helper file exports a name that at least *one* call site consumes — if it cannot be deleted, it should be private.

### IN-03: Duplicate format-mapping logic between `build_column_for_field` and `build_description_item`

**File:** `ferro-json-ui/src/projection/component_map.rs:273-287, 290-304`
**Issue:** Both functions compute `format` from `field.meaning` with identical match arms (Money → Currency, CreatedAt/UpdatedAt/DateTime → DateTime, Boolean → Boolean, else None). If a future meaning (e.g. `Percentage` → `Percent`) is added, it must be remembered in two places.
**Fix:** Extract a helper:
```rust
fn column_format_for(meaning: &FieldMeaning) -> Option<ColumnFormat> {
    match meaning {
        FieldMeaning::Money => Some(ColumnFormat::Currency),
        FieldMeaning::CreatedAt | FieldMeaning::UpdatedAt | FieldMeaning::DateTime
            => Some(ColumnFormat::DateTime),
        FieldMeaning::Boolean => Some(ColumnFormat::Boolean),
        _ => None,
    }
}
```
and call from both builders.

### IN-04: `emit_card_root` silently skips unknown slot names

**File:** `ferro-json-ui/src/projection/builder.rs:311-324`
**Issue:** The catch-all `_ => {}` arm silently drops slot names that are not `title|fields|relationships|actions|metadata|body`. A theme override with a typo (e.g. `"filds"` instead of `"fields"`) produces an empty section with no diagnostic signal. Intent layouts are small and auditable, but theme overrides are developer-authored and this is where typos will land.
**Fix:** Either (a) emit a `tracing::warn!` when an unknown slot name is encountered, or (b) add a `strict_slots: bool` flag on `VisualContext` that elevates unknown slots to `ProjectionError::UnknownSlot`. Option (a) is the lower-risk default; preserve the silent contract for backward compatibility.

### IN-05: Hardcoded path prefix `"/data/{service.name}"`

**File:** `ferro-json-ui/src/projection/builder.rs:174, 292, 474` and `component_map.rs:219, 251, 263`
**Issue:** Six call sites construct paths like `format!("/data/{}", service.name)` or `format!("/{}", service.name)` inline. This is a placeholder per the docstring ("Phase 118+ resolves a real route"), but the duplication makes the v118 refactor larger than it needs to be.
**Fix:** Introduce a small helper in `builder.rs`:
```rust
fn data_path_for(name: &str) -> String { format!("/data/{name}") }
fn action_path_for(name: &str) -> String { format!("/{name}") }
```
and route all six call sites through them. The eventual route-resolution refactor becomes a single-function change.

### IN-06: `sanitize_schema` recursion is not depth-bounded

**File:** `ferro-json-ui/src/catalog.rs:371-397`
**Issue:** `walk` is fully recursive over untrusted schema input (plugin schemas from `JsonUiPlugin::props_schema()` are explicitly treated as untrusted per D-20 / RESEARCH H-3). A maliciously deep schema (e.g. 50 000 nested objects) would overflow the stack before `jsonschema::validator_for` had a chance to reject it. In practice plugins are developer-authored and this is a low-probability attack, but the comment at line 566 emphasizes plugin schemas are untrusted input.
**Fix:** Either (a) add an explicit depth limit (`fn walk(v: &mut Value, depth: usize)` with `if depth > MAX_SCHEMA_DEPTH { return; }`), or (b) rely on the OS stack guard and document the decision. Matches the `MAX_NESTING_DEPTH` pattern already present in `spec.rs` for user-provided specs.
