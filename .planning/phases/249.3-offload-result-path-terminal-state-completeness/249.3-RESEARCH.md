## User Constraints (from CONTEXT.md)

### Locked Decisions

**Sync-mode result path (edge a)**
- D-01: Sync mode routes through the same `persist_offload_outcome` hook the async worker uses — full parity (snapshot + best-effort redacted delta).
- D-02: `dispatch_immediately()` is reworked to call `handle_with_value()` instead of `handle()`, capture the `Result<Option<Value>, Error>`, and pass it to `persist_offload_outcome(self.handle_key.as_deref(), outcome, conn)` for both success and failure branches.
- D-03: Sync-mode `dispatch()` still returns `Err(e)` on failure (unchanged, non-breaking dual signal).
- D-04: Terminal envelope is persisted exactly once in sync mode. No double-write with any residual `failed()` persistence.

**Reaper terminal envelope (edge b)**
- D-05: A reaper-parked row with a `handle_key` must record a terminal-error envelope through the same `persist_offload_outcome` hook (snapshot + redacted delta).
- D-06: Envelope error message reuses `"visibility timeout exceeded"` already written to `jobs.error`.
- D-07: Envelope persistence for parked rows is best-effort; the park must never be blocked or rolled back by a snapshot/broadcast failure.

### Claude's Discretion
- D-08: Exact reaper write seam (how parked rows are surfaced to the caller for per-row persistence).
- D-09: Sync-mode connection source for the hook (`Queue::connection()` or other).

## Summary

Phase 249.3 closes two silent-drop edges in the offload result path. The codebase is
well-structured around a single hook (`persist_offload_outcome` in
`ferro-queue/src/dispatcher.rs:51–59`) that both edges must call; the research
confirms this hook is already fully wired and idempotent on its own side — the
missing calls are purely at the two identified sites.

**Sync-mode edge (SC#1).** `dispatch_immediately()` (`dispatcher.rs:145–176`)
calls `self.job.handle()` and discards the return value, never touching
`self.handle_key`. The fix is small and self-contained: switch to
`self.job.handle_with_value()`, capture the `Result<Option<Value>, Error>`, and
call `persist_offload_outcome(self.handle_key.as_deref(), outcome, conn)`.
**Connection availability is confirmed:** `run_common_boot` (`framework/src/app.rs:429–431`)
calls `Queue::init(conn)` unconditionally (guarded by `is_initialized()`) even in
sync mode before any dispatch can occur, so `Queue::connection()` is available.
**No double-write risk:** the derived `Job::impl` emits NO `failed()` override
(`ferro-macros/src/offload.rs:394`, comment: "No `failed()` override is emitted").
The upsert nature of `snapshot_write` (INSERT OR REPLACE) makes a hypothetical
double-write idempotent regardless.

**Pending marker in sync mode.** `persist_pending` fires through
`enqueue_and_mark_pending` (`framework/src/offload.rs:350–366`), which wraps
`job.offload()`. In sync mode `offload()` calls `PendingDispatch::new(self).with_handle_key(key).dispatch()`,
which routes to `dispatch_immediately()` — the job executes before `offload()`
returns. The pending write in `enqueue_and_mark_pending` therefore comes AFTER the
terminal outcome is written. Because `snapshot_write` is a plain UPSERT the ordering
is safe either way (later write wins), but in practice the terminal write occurs first
and the pending write overwrites it — which would leave the snapshot as `pending`.
This is the correct fix target: `dispatch_immediately()` must write its terminal
outcome, and that write will naturally overwrite any stale pending row the caller
writes after the fact. The planner should note this ordering in the sync-mode fix so
the test verifies the final snapshot is terminal, not pending.

**Reaper edge (SC#2).** `db::reaper()` (`db.rs:486–542`) is a pure two-statement
bulk UPDATE inside a single transaction with no access to the hook. It has no return
value (returns `Result<(), Error>`). The reaper is called from the worker loop at
`worker.rs:348` and `worker.rs:405` (the `drain_for_test` path). The cleanest
portable seam is a SELECT-before-park approach: before committing the park UPDATE,
query the to-be-parked candidate rows (SELECT their `id` and `handle_key` where
`status='claimed' AND claimed_at < cutoff AND attempts + 1 >= max_retries`), then
let the reaper return those pairs to the call-site in the worker loop, which calls
`persist_offload_outcome` per row after the txn commits.

**Primary recommendation:** Both fixes route through the existing
`persist_offload_outcome` seam with no new crate dependencies or hook interfaces.

## Research Flag Answers (Concrete, Verified)

### RF-1: Sync-mode DB connection availability

**Verdict: AVAILABLE. `Queue::connection()` is safe to call in sync-mode applications.**

`framework/src/app.rs:429–431` [VERIFIED: source]:
```rust
if !ferro_queue::Queue::is_initialized() {
    let conn = Self::get_database_connection().await;
    let _ = ferro_queue::Queue::init(conn).await;
}
```
This runs in `run_common_boot`, which is the single framework boot path invoked by
both `serve` and `worker`. It runs unconditionally regardless of
`QUEUE_CONNECTION` value. `Queue::init` stores the connection in
`GLOBAL_CONNECTION: OnceLock<DatabaseConnection>` (`db.rs:21`).

`dispatch_to_queue` already calls `crate::db::Queue::connection()` without checking
sync mode (`dispatcher.rs:180`); the same call is correct for `dispatch_immediately`.

In tests that exercise the sync-mode path directly (e.g., `ferro-queue/tests/offload_round_trip.rs`),
`Queue::init` is not called because those tests use `dispatch` without invoking the
framework boot path. For these tests the hook will be unregistered and
`persist_offload_outcome` will no-op (correct per D-02 guard). For tests that need to
verify the full snapshot path in sync mode (`249.3-SC#1`), the test must call
`Queue::init` and `register_offload_hooks_with_broadcaster` before dispatching, matching
the pattern in `framework/tests/offload_result_round_trip.rs:241–244`.

### RF-2: Pending marker in sync mode

**Verdict: `persist_pending` fires AFTER the job executes in sync mode; the terminal write from `dispatch_immediately` must happen first.**

Trace (`framework/src/offload.rs:350–366` [VERIFIED: source]):
```rust
pub async fn enqueue_and_mark_pending<J>(job: J, db: &DatabaseConnection) -> ... {
    let handle = job.offload().await?;          // (1) calls dispatch → dispatch_immediately → handle_with_value → persist_outcome
    if let Err(e) = persist_pending(handle.key(), db).await { ... }  // (2) pending write AFTER
    Ok(handle)
}
```

`Offloadable::offload()` (`ferro-queue/src/offload.rs:118–126` [VERIFIED: source]):
```rust
async fn offload(self) -> Result<OffloadHandle<Self::Output>, Error> {
    let key = HandleKey::new();
    crate::PendingDispatch::new(self)
        .with_handle_key(key.as_str().to_string())
        .dispatch()               // sync mode: runs job inline before returning
        .await?;
    Ok(OffloadHandle::new(key))
}
```

In sync mode `dispatch()` calls `dispatch_immediately()` which executes the job
synchronously before `offload()` returns. So when `enqueue_and_mark_pending` calls
`persist_pending`, the job has already finished. The terminal envelope (from the fixed
`dispatch_immediately`) lands first; the pending write would then overwrite it with
`{"status":"pending"}` — a regression. This ordering issue does NOT affect the async
(db-queue) path because there `dispatch()` only enqueues the row and returns immediately.

**Consequence for planning:** The SC#1 test must invoke `dispatch_immediately` directly
(via `PendingDispatch::new(job).with_handle_key(key).dispatch()` with `QUEUE_CONNECTION=sync`)
rather than going through `enqueue_and_mark_pending`, or must verify that the final
snapshot is terminal (completed/failed) and not pending. The fix in
`dispatch_immediately` itself is correct regardless; the ordering hazard is a caller
concern — `enqueue_and_mark_pending` is not the intended call path for sync-mode
offload dispatch in production (sync mode is development/test only).

**Snapshot write is an UPSERT.** `ferro-projection::snapshot_write` uses INSERT OR REPLACE
semantics on the composite PK `(projection_name, key)` [VERIFIED: pattern confirmed by
test in `framework/src/offload.rs:598–623` that writes pending then reads it back]. Any
ordering is therefore safe from a data-integrity standpoint; the temporal concern above
is a semantic one (wrong final status), not a correctness/crash concern.

### RF-3: No double-persist

**Verdict: NO double-persist risk. The derived `Job::impl` emits NO `failed()` override after Phase 249.1.**

`ferro-macros/src/offload.rs:392–403` [VERIFIED: source]:
```rust
/// No `failed()` override is emitted — the async worker path persists terminal
/// errors directly from `spawn_job`/`handle_failure` (D-10 correction).
async fn handle_with_value(&self) -> ... {
    let svc = ::ferro::App::make::<dyn #trait_ident>().expect(#expect_msg);
    #value_capture_expr
}
```
The comment is explicit: no `failed()` override. The `Job` trait's default `failed()`
(`job.rs:83`) merely logs; it does NOT call `persist_offload_outcome`.

The async worker success path (`worker.rs:547–557` [VERIFIED: source]) calls
`persist_offload_outcome` directly from `spawn_job` when `success_value.is_some()`.
The `handle_failure` function (`worker.rs:605–633` [VERIFIED: source]) calls
`persist_offload_outcome` for terminal failures.

Neither path goes through `failed()`. There is no residual `failed()` persistence.

A direct `persist_offload_outcome` call in `dispatch_immediately` produces exactly one
write per sync-mode dispatch. Even if a double-write occurred, `snapshot_write`'s
upsert semantics make it idempotent.

### RF-4: Reaper write seam — portable SELECT-before-park approach

**Current `reaper()` signature** (`db.rs:486` [VERIFIED: source]):
```rust
pub async fn reaper(
    conn: &DatabaseConnection,
    queue: &str,
    visibility_timeout: std::time::Duration,
) -> Result<(), Error>
```
Returns `Result<(), Error>` — no rows returned.

**Two-statement bulk UPDATE structure** (`db.rs:500–541` [VERIFIED: source]):
- Step 1: requeue rows with `attempts + 1 < max_retries`
- Step 2: park rows with `attempts + 1 >= max_retries` (sets `status='failed'`, `error='visibility timeout exceeded'`)

Both steps run inside one transaction. No RETURNING clause is used.

**Portability constraint.** SQLite supports `UPDATE ... RETURNING` since SQLite 3.35.0
(March 2021), and the codebase already uses it in `claim_sqlite` (`db.rs:446–458`).
However, the reaper's park UPDATE selects by condition (`WHERE status='claimed' AND
claimed_at < cutoff AND attempts + 1 >= max_retries`), not by a set of known IDs.
A RETURNING clause on the park UPDATE would be the cleanest approach on both backends.

**Recommended seam (Option A — SELECT before park, portable, explicit):**

Add a new function (or extend `reaper()`) that, before executing the park UPDATE,
issues a SELECT to collect `(id, handle_key)` for rows that will be parked:

```sql
SELECT id, handle_key FROM jobs
WHERE status='claimed' AND claimed_at < {cutoff}
AND attempts + 1 >= max_retries AND queue = {queue}
AND handle_key IS NOT NULL
```

This SELECT runs INSIDE the same transaction as the park UPDATE (between the two
existing UPDATE statements), ensuring the same rows are identified and then parked.
The selected pairs are returned from `reaper()` as a new return type:

```rust
pub async fn reaper(
    conn: &DatabaseConnection,
    queue: &str,
    visibility_timeout: std::time::Duration,
) -> Result<Vec<(i64, String)>, Error>  // (id, handle_key) of parked rows with a handle
```

The worker call-site (`worker.rs:348` and `worker.rs:405`) receives this Vec and
iterates to call `persist_offload_outcome` per row — AFTER the reaper transaction commits
(best-effort, per D-07). Each persistence failure is logged and swallowed without
blocking the next row or the park itself.

**Alternative (Option B — RETURNING clause):**

For Postgres, use `UPDATE ... RETURNING id, handle_key` on the park step. For SQLite,
use a SELECT before the park UPDATE. Abstract via a backend-specific arm in the
existing `backend` match pattern. More complex, same net result. Not recommended unless
test evidence shows the SELECT-before-park has a correctness gap (it does not, given
the txn).

**Recommended approach:** SELECT-before-park inside the same txn. Simpler, portable,
and the pattern is consistent with how `claim_sqlite` works (SELECT inside txn).

**Error message** (`db.rs:526` [VERIFIED: source]):
```rust
"UPDATE jobs SET status='failed', error='visibility timeout exceeded', failed_at={pp1} ..."
```
The string `"visibility timeout exceeded"` is hardcoded in the park UPDATE. The hook
call must use the same string as D-06 requires.

**Best-effort placement:** persistence calls go AFTER `reaper()` returns (txn
committed), not inside the txn. A persistence failure must not prevent the next row
from being processed.

## Architecture Patterns

### Sync-mode fix data flow

```
PendingDispatch::dispatch()
  └─ is_sync_mode() = true
      └─ dispatch_immediately()          ← CHANGED
            ├─ handle_with_value()       ← SWITCH from handle()
            │     returns Ok(Some(val)) or Err(msg)
            ├─ [on success] persist_offload_outcome(handle_key, Ok(val), conn)
            │                             ← NEW CALL
            ├─ delete_job / no-op in sync (no DB row)
            ├─ [on failure] persist_offload_outcome(handle_key, Err(msg), conn)
            │                             ← NEW CALL (before returning Err)
            └─ return Ok(()) or Err(e)  ← UNCHANGED (D-03 dual signal)
```

### Reaper edge fix data flow

```
WorkerLoop::run() / drain_for_test()
  └─ db::reaper(conn, queue, timeout)   ← CHANGED (new return type)
        ├─ txn.begin()
        ├─ [Step 1] UPDATE requeue (attempts+1 < max_retries)
        ├─ [Step 2a] SELECT id, handle_key WHERE will-be-parked AND handle_key IS NOT NULL  ← NEW
        ├─ [Step 2b] UPDATE park (status='failed', error='visibility timeout exceeded')
        ├─ txn.commit()
        └─ return Vec<(i64, String)>    ← NEW: (id, handle_key) pairs

  worker call-site (worker.rs:348 / :405):
    let parked = db::reaper(conn, queue, timeout).await?;
    for (_, handle_key) in parked {    ← NEW LOOP
        persist_offload_outcome(        ← NEW CALL per row
            Some(&handle_key),
            Err("visibility timeout exceeded".to_string()),
            conn,
        ).await;                        // best-effort, swallow errors (D-07)
    }
```

### Anti-Patterns to Avoid

- **Persistence inside the reaper transaction:** A hook failure must not block or
  roll back the park (D-07). Keep persistence outside the txn.
- **Calling `handle()` in sync mode after the fix:** `handle_with_value()` calls
  `handle()` internally for non-offload jobs (via its default impl). Do not call
  both; switch completely to `handle_with_value()`.
- **Using `enqueue_and_mark_pending` for the SC#1 test:** In sync mode this writes
  a pending marker after the terminal outcome, regressing the snapshot to `pending`.
  Tests for SC#1 must call `dispatch_immediately` via
  `PendingDispatch::new(job).with_handle_key(key).dispatch()` with `QUEUE_CONNECTION=sync`.

### Target `dispatch_immediately` (after fix)

```rust
async fn dispatch_immediately(self) -> Result<(), Error> {
    let job_name = self.job.name();

    if self.delay.is_some() {
        tracing::debug!(job = %job_name, "Job delay ignored in sync mode");
    }
    if self.tenant_id.is_some() {
        tracing::debug!(job = %job_name, tenant_id = ?self.tenant_id,
            "for_tenant() ignored in sync mode — current task tenant context applies");
    }
    tracing::debug!(job = %job_name, "Executing job synchronously");

    let conn = if crate::db::Queue::is_initialized() {
        Some(crate::db::Queue::connection())
    } else {
        None
    };

    match self.job.handle_with_value().await {          // ← switch to handle_with_value
        Ok(success_value) => {
            tracing::debug!(job = %job_name, "Job completed successfully");
            if let Some(conn) = conn {
                if let Some(val) = success_value {
                    persist_offload_outcome(self.handle_key.as_deref(), Ok(val), conn).await;
                } else if self.handle_key.is_some() {
                    // Unit return: persist Ok(Value::Null)
                    persist_offload_outcome(
                        self.handle_key.as_deref(),
                        Ok(serde_json::Value::Null),
                        conn,
                    ).await;
                }
            }
            Ok(())
        }
        Err(e) => {
            tracing::error!(job = %job_name, error = %e, "Job failed");
            if let Some(conn) = conn {
                persist_offload_outcome(
                    self.handle_key.as_deref(),
                    Err(e.to_string()),
                    conn,
                ).await;
            }
            self.job.failed(&e).await;
            Err(e)                                       // D-03: still return Err
        }
    }
}
```

**Note on `Queue::is_initialized()` guard:** The guard is needed because
existing unit tests in `ferro-queue/tests/offload_round_trip.rs` set
`QUEUE_CONNECTION=sync` without calling `Queue::init` — they only test that
`handle()` executes, not the snapshot path. The guard prevents a panic in those
tests. When the framework boot path is used (as in the SC#1 integration test),
`Queue::init` is always called first.

## Common Pitfalls

### Pitfall 1: `Queue::connection()` panic in unit tests
**What goes wrong:** Unit tests in `ferro-queue` that set `QUEUE_CONNECTION=sync`
but do not call `Queue::init` will panic when the fixed `dispatch_immediately` calls
`Queue::connection()`.
**Root cause:** `Queue::connection()` panics if `GLOBAL_CONNECTION` is not set.
**How to avoid:** Guard the connection fetch with `Queue::is_initialized()`. If
`None`, the hook call is skipped (handle_key is also typically `None` in such tests,
so `persist_offload_outcome` would no-op anyway).
**Warning signs:** `Queue not initialized. Call Queue::init() first.` panic in
sync-mode tests.

### Pitfall 2: Pending marker overwrites terminal outcome in sync mode
**What goes wrong:** If the SC#1 test uses `enqueue_and_mark_pending`, the pending
write comes after `dispatch_immediately` writes the terminal outcome, leaving the
snapshot as `Pending`.
**Root cause:** In sync mode `offload()` executes the job inline before returning to
`enqueue_and_mark_pending`. The pending write then clobbers the terminal outcome.
**How to avoid:** SC#1 test MUST use direct dispatch (`PendingDispatch::new(job).with_handle_key(key).dispatch()`)
rather than `enqueue_and_mark_pending`. Production callers using the async queue
path are unaffected.
**Warning signs:** `read_result` returns `Some(Pending)` in the SC#1 test after
dispatch completes.

### Pitfall 3: Reaper persistence inside the transaction
**What goes wrong:** If `persist_offload_outcome` is called inside the reaper
transaction and fails, it may leave the txn in an error state or silently interfere
with the park UPDATE's commit.
**Root cause:** D-07 requires the park to never be blocked or rolled back by a
snapshot failure.
**How to avoid:** Persistence calls go AFTER `reaper()` returns (txn committed),
at the worker call-site. Each call is best-effort, errors logged and swallowed.
**Warning signs:** Reaper tests failing on persistence errors when the hook is
not registered.

### Pitfall 4: Unit success value from `handle_with_value` returning `None`
**What goes wrong:** For jobs where `handle_with_value`'s default impl runs
(`self.handle().await.map(|_| None)`), the success case returns `Ok(None)`. A
naive `if let Some(val) = success_value` guard skips the `persist_offload_outcome`
call entirely, leaving no terminal snapshot for handle-key jobs with unit output.
**Root cause:** The async worker path (`worker.rs:549`) has the same guard — it only
persists when `success_value.is_some()`. But derived `handle_with_value` for a
`-> ()` method returns `Ok(Some(Value::Null))` (not `Ok(None)`), so this works
on the db path. The sync path after the fix calls `handle_with_value` on the actual
derived job, which returns `Ok(Some(Null))`. The problem arises only for non-derived
jobs that call the default `handle_with_value` (which returns `Ok(None)`) while also
setting a `handle_key`.
**How to avoid:** In `dispatch_immediately`, when `handle_key` is `Some` and
`success_value` is `None`, persist `Ok(Value::Null)` as the terminal outcome so the
handle always resolves to a terminal state. The example code above shows this pattern.

### Pitfall 5: Reaper SELECT sees rows the park UPDATE won't park
**What goes wrong:** A race between the SELECT and the park UPDATE inside the same
transaction could theoretically produce a row in the candidate list that the UPDATE
skips (e.g., if the WHERE condition changes between SELECT and UPDATE). In SQLite
with DEFERRED transactions this is not an issue because the txn holds a write lock;
in Postgres `SELECT` inside a `BEGIN` reads its snapshot. The txn's consistency
guarantees the SELECT and UPDATE operate on the same visible state.
**How to avoid:** Run the SELECT inside the same transaction (between the requeue
and park UPDATEs). Do not run it outside the txn.

### Deterministic reaper trigger

The reaper condition is: `status='claimed' AND claimed_at < (now - visibility_timeout)
AND attempts + 1 >= max_retries`. Make it deterministic in tests by:
- Setting `claimed_at` to a timestamp in the distant past (e.g., `Utc::now() - chrono::Duration::hours(1)`).
- Using `visibility_timeout = Duration::from_millis(1)` (minimal timeout so any claimed row
  is immediately eligible).
- Inserting rows directly via `insert_job` (the test helper in `ferro-queue/src/db.rs:1018`),
  noting that it does not set `handle_key` — tests will need a variant that sets it.

Existing reaper tests (`db.rs:1180–1263` [VERIFIED: source]) show the pattern:
`insert_job` with `claimed_at = ten_min_ago` and `max_retries > attempts`, then call
`reaper(..., Duration::from_secs(5 * 60))`.

## Open Questions (RESOLVED)

1. **Success value for `handle_with_value` returning `Ok(None)` with a handle key.**
   - What we know: The default `Job::handle_with_value` returns `Ok(None)` for non-derived
     jobs. Non-offload sync jobs do not have a `handle_key`, so `persist_offload_outcome`
     no-ops. This is safe.
   - What's unclear: If a non-derived job somehow sets a `handle_key` AND returns `Ok(None)`,
     should the sync path persist `Ok(Value::Null)` or skip persistence?
   - RESOLVED: Persist `Ok(Value::Null)` when `handle_key` is `Some` and `success_value` is
     `None`, so the handle always resolves terminally. This matches the behaviour of
     `persist_result(&(), db)` which also writes `Value::Null`. Implemented in Plan 249.3-01.

2. **`insert_job` test helper does not accept `handle_key`.**
   - What we know: `db.rs:1018` defines `insert_job` with a fixed signature that omits
     `handle_key` (inserts `NULL`).
   - What's unclear: Whether to add a new `insert_job_with_handle` helper or extend the
     existing one with a `handle_key: Option<&str>` parameter.
   - RESOLVED: Add `insert_job_with_handle` as a separate helper to keep existing test
     call-sites unchanged. Implemented in Plan 249.3-02.
