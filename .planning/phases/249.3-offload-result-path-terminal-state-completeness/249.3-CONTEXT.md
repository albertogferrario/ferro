# Phase 249.3: Offload result-path terminal-state completeness - Context

**Gathered:** 2026-08-16
**Status:** Ready for planning
**Mode:** `--auto` (recommended defaults selected without interactive questioning)

<domain>
## Phase Boundary

Guarantee an `OffloadHandle` always resolves to a **terminal state** (`completed`
or `failed`), never an indefinite `Ok(None)`. Two silent-drop edges remain open
after Phases 246/247 and are closed here:

- **(a) Sync mode** (`QUEUE_CONNECTION=sync`, the unset default):
  `PendingDispatch::dispatch_immediately()` (`ferro-queue/src/dispatcher.rs:145`)
  calls `job.handle()` rather than `handle_with_value()`, ignores `self.handle_key`,
  and never invokes `persist_offload_outcome`. A caller holding the handle reads
  `Ok(None)` forever (246 WR-01).
- **(b) Reaper-parked jobs**: `db::reaper()` (`ferro-queue/src/db.rs:474`) bulk-`UPDATE`s
  timed-out `claimed` rows to `status='failed'` but never persists a terminal-error
  envelope under the handle key, so a subscribed caller waits to its own timeout
  instead of observing the failure (246 WR-02).

This phase hardens **OFFLOAD-03** ("a failed run records a terminal error state — no
silent drop") at its two edges. It adds no new envelope shape, no new transport, and
no new crate dependency — both fixes reuse the existing framework result hook.

**Out of scope:** any change to the envelope schema, the broadcast transport (246.1),
the subscribe/resolve helpers (247), the `ferro worker` runtime (248), or MCP
introspection (249). Success is measured by the three ROADMAP success criteria.

</domain>

<decisions>
## Implementation Decisions

### Sync-mode result path (edge a)
- **D-01:** Sync mode routes through the **same `persist_offload_outcome` hook** the
  async worker uses — full parity, snapshot **and** best-effort redacted delta, not a
  snapshot-only shortcut. The hook (`framework::register_offload_hooks_with_broadcaster`,
  `framework/src/offload.rs:291+`) already persists the snapshot then best-effort
  broadcasts the redacted delta (247 D-01/D-02), so reuse is the minimal-code path and
  keeps sync/async behavior identical. SC#1 only requires the snapshot read-back, but
  parity costs nothing extra here and avoids a sync-only divergence.
- **D-02:** `dispatch_immediately()` is reworked to call **`handle_with_value()`** (not
  `handle()`), capture the `Result<Option<serde_json::Value>, Error>`, and pass the
  outcome to `persist_offload_outcome(self.handle_key.as_deref(), outcome, conn)` for
  **both** the success (`Ok(Some(value))`) and failure (`Err(msg)`) branches. The
  no-op guard inside `persist_offload_outcome` (handle_key `None` or hook unregistered)
  keeps non-offload sync jobs unaffected.
- **D-03:** Sync-mode `dispatch()` **still returns `Err(e)` on failure** (unchanged,
  non-breaking, useful inline in dev/test) **in addition to** persisting the failed
  envelope — dual signal. The handle contract (SC#1: reads a terminal `failed`, not
  `Ok(None)`) is satisfied by the persisted envelope; the raw `Result` return is a
  lower-level convenience for direct `.dispatch()` callers and is not sacrificed for
  async parity.
- **D-04:** The terminal envelope is persisted **exactly once** in sync mode. Reconcile
  with any residual derived-`Job::failed()` persistence so the direct
  `persist_offload_outcome` call does not double-write (upsert on the composite PK makes
  a double-write idempotent, but a single write is the intended path — confirm during
  research whether `failed()` still persists post-247/249.1 convergence).

### Reaper terminal envelope (edge b)
- **D-05:** A reaper-parked row **with a `handle_key`** must record a terminal-error
  envelope through the **same `persist_offload_outcome` hook** — which persists the
  `failed` snapshot **and** emits the redacted delta. SC#2 requires a subscribed caller
  to *observe the failure* rather than wait to timeout; observation requires the delta,
  so a snapshot-only write is insufficient for this edge.
- **D-06:** The envelope error message **reuses the existing `"visibility timeout
  exceeded"` string** already written to the `jobs.error` column by the park `UPDATE`
  (`db.rs:526`), for consistency between the DB row and the snapshot envelope. Per 247
  D-05 the client-facing delta is redacted to the non-sensitive terminal marker; the raw
  `"visibility timeout exceeded"` string lives only in the snapshot (authorized/server
  read-back).
- **D-07:** Envelope persistence for parked rows is **best-effort** (246 T-246-05, 247
  D-02): the `status='failed'` DB row remains the authoritative terminal state and the
  park must **never** be blocked or rolled back by a snapshot/broadcast failure. A hook
  that is unregistered or errors is logged and swallowed.

### Claude's Discretion (left to planning/research)
- **D-08 (reaper write seam):** `db::reaper()` is today a pure bulk-`UPDATE` with no hook
  access, and `persist_offload_outcome` lives in `dispatcher` behind the framework hook.
  The exact seam is a **planning decision**, mirroring how 246 D-05 / 247 D-03 deferred
  their propagation mechanism. Locked contract: **the reaper must surface which rows it
  just parked together with their `handle_key`** (e.g. select the to-be-parked candidates
  before the bulk park, or have the park step return affected `(id, handle_key)` rows),
  so the caller can persist a terminal envelope for each parked row that carries a handle.
  Recommended home for the persistence call is the worker's reaper call-site
  (`worker.rs:348`, `worker.rs:405`), which already has the hook path and the
  `&'static DatabaseConnection`.
- **D-09:** Sync-mode connection source for the hook — `crate::db::Queue::connection()`
  vs. a threaded connection — is Claude's discretion, subject to the research flag below.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `dispatcher::persist_offload_outcome(handle_key, Result<Value,String>, &'static conn)`
  — the single seam both edges call; already no-ops on `None` handle / unregistered hook.
- The async worker's success and `handle_failure` paths (`worker.rs:547`, `:598`) are the
  reference for wiring the sync and reaper edges consistently.
- `handle_with_value()` (`job.rs:78`) — returns `Ok(Option<Value>)`; sync mode switches to
  this from `handle()` to capture the success value.

### Established Patterns
- Persistence + broadcast are **best-effort, never fail the job** (246/247). Both new
  edges inherit this — the authoritative terminal state is the DB row / snapshot, not the
  delta.
- Envelope is a tagged discriminator `{status: completed|failed|pending, value|error}`
  (246 D-07); this phase writes only `completed`/`failed`, no new tag.
- Generated/facade code emits only `::ferro::*` paths and `ferro-queue` never depends on
  `ferro-projection` (246 D-11) — preserved: both edges reach persistence through the
  already-registered hook, not a new dependency.

### Integration Points
- Sync edge: `dispatch_immediately()` gains a call into `persist_offload_outcome` using the
  queue's `&'static DatabaseConnection`.
- Reaper edge: the worker's reaper call-site persists envelopes for parked handle-key rows
  returned by a reaper that now surfaces them.

### Research flags (verify before/while planning)
- **Sync-mode connection availability:** confirm `crate::db::Queue::connection()` is
  initialized in sync mode (`QUEUE_CONNECTION=sync`), since the snapshot store needs a
  `&'static DatabaseConnection`. If the queue connection is not set in sync mode, identify
  the connection the projection snapshot store uses and thread it in.
- **Pending marker in sync mode:** confirm whether the 247 framework `persist_pending`
  fires for a sync `.offload()` call; the terminal write is an upsert either way, but this
  determines whether the sync path overwrites a `pending` row or creates the row fresh.
- **No double-persist:** verify whether the derived `Job::failed()` still persists an
  envelope after the 247/249.1 convergence, to keep the sync-mode terminal write single.

</code_context>

<specifics>
## Specific Ideas

- SC#2's wording ("a subscribed caller observes the failure rather than waiting to
  timeout") is the load-bearing constraint for the reaper edge: it mandates a **broadcast
  delta**, not merely a snapshot — which is why both edges route through the full hook
  rather than a snapshot-only helper.
