# Phase 249.3: Code Review Report

**Reviewed:** 2026-08-16
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Phase 249.3 closes two silent-drop edges in the offload result path. The implementation
is architecturally sound: both edges route through the existing `persist_offload_outcome`
hook, no new crate dependency touches `ferro-queue`, persistence runs after the reaper
transaction commits, and the framework hook correctly redacts the raw error from
client-facing deltas. The SQL predicate symmetry between the SELECT-before-park and the
park UPDATE is correct — they operate on the same txn snapshot against the same WHERE
condition (with the SELECT adding `AND handle_key IS NOT NULL` as intended).

One warning-level issue requires attention before the phase is closed: the SC#2
integration test sets `QUEUE_CONNECTION=db` without a RAII drop guard, so a panic
during test setup leaks the env var and can alter behavior of downstream serial tests.
Two info items flag a mildly over-exposed public API symbol and an unused id field in
the reaper's return type.

No blocking issues. The fix is correct and the tests are genuine (a revert of either
edge would cause a compilation error or assertion failure, not a silent pass).

## Warnings

### WR-01: Missing env-var drop guard in `reaper_terminal_envelope` test

**File:** `framework/tests/reaper_terminal_envelope.rs:244`

**Issue:** `std::env::set_var("QUEUE_CONNECTION", "db")` is called at the top of the
`reaper_terminal_envelope` test function with no RAII guard. If the test panics before
completion (for example, if `Queue::init` returns `Err` and `.expect()` fires at line
265, or if `setup_db` fails), `QUEUE_CONNECTION` remains set to `"db"` for the remainder
of the process. Because `QueueConfig::is_sync_mode()` treats an absent env var as `true`
(sync mode, the development default), leaked `"db"` silently changes the dispatch
behavior of any subsequent serial test that does not explicitly set the var. The
`sync_mode_terminal_state.rs` file handles this correctly with `EnvGuard`; the same
pattern is missing here.

**Fix:** Wrap the env-var assignment in the same `EnvGuard` that `sync_mode_terminal_state.rs`
defines, or add an equivalent RAII struct in the reaper test file:

```rust
// At the top of reaper_terminal_envelope():
let _env = EnvGuard::set("QUEUE_CONNECTION", "db");
// ...remove the bare std::env::set_var("QUEUE_CONNECTION", "db") line
```

The `EnvGuard` from `sync_mode_terminal_state.rs` is not reachable here (it lives in a
different integration test module), so a local copy is needed — or extract it to a
shared test-support module. Either approach is fine for the v1 bar.

## Info

### IN-01: `persist_offload_outcome` promoted to `pub` solely for integration-test use

**File:** `ferro-queue/src/dispatcher.rs:51` / `ferro-queue/src/lib.rs:64`

**Issue:** `persist_offload_outcome` was `pub(crate)` before this phase. The promotion to
`pub` is driven entirely by `framework/tests/reaper_terminal_envelope.rs`, which imports
it as `ferro_queue::persist_offload_outcome`. The framework's production code
(`framework/src/offload.rs`) does not call this function directly — it uses the hook
registration path (`register_offload_result_hook`) as intended by D-11. Exposing the
function publicly widens the stable API surface of `ferro-queue` beyond what production
semantics require. A downstream application could call it directly, bypassing the hook
mechanism and writing raw snapshots outside the registered lifecycle.

**Fix:** Add `#[doc(hidden)]` to signal the symbol is not part of the public contract
while keeping `pub` for cross-crate test reachability:

```rust
/// Invoke the offload-result hook if registered.
///
/// No-op when the hook is not registered …
#[doc(hidden)]  // implementation detail; used by framework integration tests
pub async fn persist_offload_outcome(…) { … }
```

This is the standard Rust convention for crate-internal symbols that must be `pub` for
integration-test access. A feature-gated re-export (`#[cfg(any(test, feature = "testing"))]`)
would be the strictest option but is heavier than warranted for a single test helper.

### IN-02: `Vec<(i64, String)>` return type carries an unused `id` field

**File:** `ferro-queue/src/db.rs:490` / `ferro-queue/src/worker.rs:354,421`

**Issue:** `reaper()` returns `Vec<(i64, String)>` — pairs of `(job_id, handle_key)` —
but every call-site destructures the tuple as `(_, handle_key)`, discarding the id.
The integration test (`run_reaper_with_persistence`, `reaper_terminal_envelope.rs:452`)
does the same. The id was presumably included for potential future use (e.g., marking a
specific job in a follow-up operation), but it adds unused data to every returned row and
makes the API's intent ambiguous: a reader of the call-site sees `(_, handle_key)` and
wonders whether the underscore is intentional or an oversight.

**Fix:** Narrow the return type to `Vec<String>` (handle keys only) and update the SELECT
to drop the `id` column:

```sql
SELECT handle_key FROM jobs
WHERE status='claimed' AND claimed_at < {sc1}
AND attempts + 1 >= max_retries AND queue = {sc2}
AND handle_key IS NOT NULL
```

```rust
// reaper return type
) -> Result<Vec<String>, Error>

// worker call-sites
for handle_key in parked {
    crate::dispatcher::persist_offload_outcome(Some(&handle_key), …).await;
}
```

If id is retained intentionally for an imminent use, a type alias or named struct
(`struct ParkedHandle { id: i64, key: String }`) would make the intent explicit and
suppress the `_` destructuring pattern at all call-sites.
