<domain>
## Phase Boundary

Replace the Phase 122/122.1/123/124 deploy machinery with a simpler, heuristic-
light shape. Cut ~1500 LOC → ~375 LOC. Reduce heuristics from 6 to 1. Delete
3 MCP deploy tools and fold surviving checks into `ferro doctor`. Source:
`.planning/phases/122.2-deploy-simplification/SCOPE.md` (13 sections, every
decision locked).

Two architectural rules:
1. **Cargo.toml `[package.metadata.ferro.deploy]` = provider-neutral Dockerfile
   inputs.** runtime_apt, copy_dirs, ferro_version. Describes the image.
2. **`.do/app.yaml` = DO's own spec, user-owned after scaffold.** `do:init` is
   a one-shot generator. User edits the file directly afterward.

### Key schema: Cargo.toml metadata
```toml
[package.metadata.ferro.deploy]
runtime_apt = ["chromium", "fonts-liberation"]   # default: []
copy_dirs   = ["themes", "lang", "public", "migrations"]  # default: these 4
ferro_version = "0.1.87"                          # optional override
```

### Key insight: .env.production, not .env.example
`.env.example` is a tutorial file (inline comments, localhost defaults) — the
source of every 122.1 parser bug. `.env.production` is production-shaped.
`do:init` reads only keys from `.env.production`, emits a commented scaffold.
Values never land in `.do/app.yaml`.

### Key insight: ferro is on crates.io
Verified during discussion: `framework/Cargo.toml` declares `ferro-rs v0.1.87`,
`.github/workflows/publish.yml` exists, repo is public. Four features predicated
on "private ferro git repos" (GITHUB_TOKEN, git config, path→git rewriter,
--ferro-ref, ref pre-flight) are obsolete.

### Key insight: Ferro has no opinion on secrets
User explicitly chose "Option A — Ferro has no opinion." `.do/app.yaml` contains
no secret values. User manages secrets via DO dashboard, doctl, or whatever.
`deploy_diff_env` MCP tool is deleted because the values it compared don't
exist anymore.

  confirms this is correct DX.
- Order of deletion vs addition — planner should delete old code in an early

<specifics>
## Specific Ideas

- Delete old code BEFORE introducing new code. Otherwise there's too much
  simultaneous churn on the same files.
- Each feature area (docker renderer, app.yaml renderer, env parser, mcp
  revert, doctor update, ignore static, golden delete) can be its own plan.
- Live UAT against gestiscilo/app at the end of the phase is the real proof
  point. Plan verification should include running `ferro docker:init` and
  `ferro do:init` against gestiscilo and diffing the results against expected.
- The single surviving heuristic (`is_test_like_bin`) should stay in a clearly
  named function with a code comment explaining why this heuristic alone
  survived the simplification.
- Golden tests are replaced by unit tests on each renderer/parser/helper.
  Target: one `#[cfg(test)] mod tests` per file, every public function covered.

</specifics>
