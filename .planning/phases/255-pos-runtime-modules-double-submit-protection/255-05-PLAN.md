       function initDisableOnSubmit(btn) {

           if (!form && btn.getAttribute('form')) { form = document.getElementById(btn.getAttribute('form')); }

           form.addEventListener('submit', function(e) {
               if (btn._submitted) { e.preventDefault(); return; }

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (browser) -> server POST | The confirm POST crosses from the untrusted client into the write path; a double-tap or replay can produce a duplicate mutation. |
| runtime guard (client) vs server dedupe | The client guard is a UX affordance; the actual dedupe boundary is the server-side framework::write idempotency hook. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-255-10 | Tampering / Denial of service (double-submit / replayed POST) | confirm form submission | mitigate | Layered: (1) client guard data-disable-on-submit disables the button on first submit (form submit event, bfcache-safe); (2) documented server dedupe via dispatch_write idempotency_key on (tenant_id, key); (3) PRG. Documented in write-kernel.md. |
| T-255-11 | Elevation of privilege (client-guard bypass: JS off / crafted POST) | double-submit client guard | transfer | The client guard is NOT a security control. The authoritative dedupe is the server-side framework::write idempotency hook (keyed on tenant_id + idempotency_key), which cannot be bypassed from the client. The docs explicitly frame the client guard as UX and the idempotency key as the control. |
</threat_model>
