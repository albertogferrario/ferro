<threat_model>
This plan creates the persistent schema boundary (migration + entity) for the `reservations` table. There is no caller-supplied SQL or user-controlled identifier surface; the threat model is limited to schema correctness and dialect portability.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration.rs → SQLite/Postgres DDL | The migration produces DDL that runs in the consumer's DB; column types and index definitions cross this boundary |
| entity.rs `Model` → caller code | `Model` fields are read by `Resource::held` queries and the kernel; field types are the durable contract between the entity layer and the application layer |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-154-03-SCHEMA | T | migration.rs DDL | mitigate | The migration is exclusively SeaORM-DSL; no raw SQL strings; SeaORM's `Table::create` + `ColumnDef` emits dialect-portable DDL (verified by the SQLite test in Task 1). The dialect-specific risk is the `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` on `held_at` — SeaORM's `Expr::current_timestamp()` handles the dialect translation. |
| T-154-03-i32 | I | entity.rs `quantity: i32` | mitigate | Storing as i32 (matches SeaORM INTEGER) opens a theoretical "negative quantity via direct DB mutation" surface. The kernel's INSERT path always sets quantity from a `u32` value (Plan 05 hold method), so legitimate writes are safe. RESEARCH Pitfall 6 documents this; the kernel will add a `if row.quantity < 0 { return Err(...) }` guard when constructing `ReservationHandle` (Plan 04 / 05). |
| T-154-03-INDEX | D | Missing index → slow held lookup | mitigate | Both composite indexes from D-40 are created in the up() migration; the index existence is verified in `migration_creates_reservations_table_and_indexes`. Without the indexes, `Resource::held` queries scan the full table — performance issue, not correctness, but the test asserts they exist. |
| T-154-03-DOWN | D | down() drops table — destructive | mitigate | down() drops the `reservations` table wholesale. Consumers running `MigratorTrait::down` would lose all reservation data. This is a SeaORM-convention destructive operation; no application-level mitigation required. The consumer's deploy pipeline owns the decision to run `down()`. |
</threat_model>
