## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** `$each` is a spec-level directive on any element entry in `Spec.elements`. Wire syntax: `"element_id": { "type": "X", "$each": { "path": "/data_array_path", "as": "row" }, "props": { "key": { "$data": "/row/field" } } }`. At resolve time, ferro instantiates one element per row in the data array, with the loop variable bound to `$data` paths that start with `/row/`. Auto-suffixed IDs (`element_id-0`, `element_id-1`, …) prevent collisions. Children referenced by the templated element get the same auto-suffix applied.
- **D-02:** `$each` closes 3 of the 4 cassa heterogeneous-iteration sites (orders kanban list, new order ProductTile list, product detail magazzino_links_rows). The 4th (orders detail conditional actions) needs `$if`.
- **D-03:** `$if` is a spec-level directive for **conditional emission**. Wire syntax: `"element_id": { "type": "X", "$if": { "path": "/flag", "operator": "equals", "value": true }, "props": { ... } }`. Elements whose `$if` evaluates falsy are NOT rendered at all (no hidden DOM, no JS). Missing IDs in `children` arrays that point to absent elements are silently skipped.
- **D-04:** REUSE `ferro-json-ui/src/visibility.rs` evaluator for `$if` predicates. Do NOT add a parallel expression engine. WHEN evaluation happens differs (resolve-time for `$if`, render-time for `visible`); the expression syntax is shared.
- **D-05:** Do NOT ship a separate `$template` element (covered by `$each`).
- **D-06:** Add `SpecBuilder` ergonomic methods accepting nested Rust types and emitting the flat element map. `SpecBuilder::element(id, type_name).child(...).child(...).build()` walks the nesting and emits the flat `elements` map with `children: Vec<String>` of IDs auto-generated by structural position.
- **D-07:** `SpecBuilder` ergonomic layer is NOT a Component-style nested API — it is a flat-map-emitter with ergonomic syntax. `Spec` runtime type stays canonical (flat map of `Element`); the nested DSL is sugar over construction only.
- **D-08:** Document the decision rubric in `docs/src/json-ui/spec-construction.md`: "Static spec → JSON file + `render_file`. Homogeneous iteration → JSON file + `$each`. Conditional emission → JSON file + `$if`. Heterogeneous runtime construction → Rust + `SpecBuilder`."
- **D-09:** Ship `ferro json-ui:migrate-v1` as a `ferro-cli` subcommand. Input: a controller file using `make_node(id, Component::X(props))` patterns. Output: a stub JSON spec file under `src/views/{module}/{controller}.json` with the flat elements map pre-generated, plus a rewritten controller using `JsonUi::render_file(...)`. Cases involving runtime branching or `Spec::builder()` fall-throughs get a `// TODO: codemod could not auto-translate` marker, not a silent skip.
- **D-10:** Codemod operates on a single file per invocation. No directory-recursive mode. Each migration needs human review.
- **D-11:** Codemod gates: AST-based (use `syn`), not regex-based. Idempotent (running on an already-migrated file is a no-op + warning). Dry-run flag (`--dry-run`) prints the proposed JSON spec and controller rewrite without writing.
- **D-12:** Spec validator MUST emit a clear error when a `$each` `path` resolves to a non-array `$data` value, when an `$if` `path` resolves to a missing key (vs falsy), and when `$each.as` collides with a reserved name. These errors land at `Spec::validate` time, not at render time.
- **D-13:** Both `$each` and `$if` MUST be reflected in `ferro-mcp`'s `json_ui_catalog` tool output.

### Claude's Discretion

- Exact JSON wire syntax (`$each` vs `each` vs `__each__` etc.) — `$`-prefix is the established convention from `$data` / `$template`; this research confirms `$each` and `$if`.
- Whether `$each` produces a `Vec<Element>` slot in the parent's `children` field, or spawns the templated element AND each clone as separate entries in `Spec.elements` with the parent's `children` rewritten — implementation detail. **This research recommends:** entries-in-`Spec.elements` map, parent's `children` rewritten. Reason: keeps the flat-map invariant intact and the render path unchanged. See §Resolve Pipeline below.
- Whether the codemod ships with hand-curated migration patterns or generates them from `ferro-mcp`'s `code_templates` — implementation choice. **This research recommends:** hand-curated for Phase 163; `code_templates` integration can come later if it earns its weight.

- Host-based tenancy gap (separate phase).
- Auth-related friction items, blast-radius items, component-catalog items, MCP `json_ui_verify_action` tool — all OWNED by Phase 162.
- Cassa UI redesign — Phase 163 does NOT redesign cassa; gestiscilo decides that separately.

## Summary

Phase 163 lands two **spec-level directives** (`$each`, `$if`) that expand at **resolve time** (after parse, before render), plus a **`SpecBuilder` ergonomic layer** (flat-map emitter with nested DSL syntax), plus a **`ferro json-ui:migrate-v1` AST codemod**. All four deliverables plug into existing seams. No new crates. No spec-format break (additive optional fields on `Element`).

The critical architectural invariant: **`$each` and `$if` expand at resolve time, before render**. By the time `render_spec_to_html` runs, `$each` has been expanded to N concrete elements with auto-suffixed IDs, and `$if`-falsy elements have been deleted from the map. The render path stays unchanged.

The primary technical risks are: (1) **`$template` is already a taken keyword** in `ferro-json-ui/src/expression.rs` (line 30 — used as template-string-interpolation directive, NOT element instantiation) — this is why CONTEXT D-05 rejects a `$template` element type. (2) The Element's wire deserialization must learn `$each` and `$if` keys at the same level as `type` / `props` / `children` — straightforward via `#[serde(rename = "$each")]` on new optional fields. (3) `Spec::validate` (currently `validate_structure` at spec.rs:416) must run **before** resolve — directives are validated against the spec graph, not against runtime data — the non-array-path and missing-key errors fire when the user calls `Spec::from_json`, before any data is bound.

**Primary recommendation:** Wave the work as: Wave 1 = directive types + Element struct deltas + serde round-trip; Wave 2 = resolve-time expansion + visibility re-use + auto-suffix rule; Wave 3 = `Spec::validate` extensions for D-12; Wave 4 = `SpecBuilder` ergonomic methods + decision-rubric docs; Wave 5 = `ferro-cli` codemod (depends on Wave 1 types) + MCP catalog surface for directives.

- `ferro-json-ui/src/resolve.rs:35–41` — `resolve_actions` (passes 1): mutates each `el.action.url` from handler name to URL via callback.

- `framework/src/json_ui/mod.rs:40–45` — `JsonUi::resolve` orchestrates: clone spec, run `resolve_actions`, run `resolve_expressions`. **Phase 163 inserts a new pass `expand_directives` BEFORE `resolve_actions`.** Order: clone → `expand_directives` → `resolve_actions` → `resolve_expressions` → render. ### Visibility evaluator (D-04 reuse target)

- `ferro-json-ui/src/visibility.rs:43–50` — `Visibility` enum: `And { and }`, `Or { or }`, `Not { not }`, `Condition(VisibilityCondition)`.
- `ferro-json-ui/src/visibility.rs:11–25` — `VisibilityOperator`: `Exists`, `NotExists`, `Eq`, `NotEq`, `Gt`, `Lt`, `Gte`, `Lte`, `Contains`, `NotEmpty`, `Empty`. **CONTEXT D-03 uses `"operator": "equals"` in the example wire syntax — the existing enum variant is `Eq` (snake_case = `"eq"`). The planner MUST decide either (a) align CONTEXT wire syntax to existing `eq` operator, or (b) add an `equals` alias.** Recommend (a) — keep one canonical name; document `eq` in the directive examples.
- `ferro-json-ui/src/visibility.rs:70–78` — `Visibility::evaluate(&self, data: &serde_json::Value) -> bool`. Infallible — malformed/missing/type-mismatch all return `false`. **This signature is directly usable from the directive resolver** — `Visibility::Condition(VisibilityCondition { path, operator, value })` is exactly the shape `$if` needs.

### `$data` path semantics (load-bearing for `$each` scoping)

- `ferro-json-ui/src/data.rs:19–45` — `resolve_path(data, path) -> Option<&Value>`. Slash-separated path against a JSON value. `/segment/segment/...` where segments are object keys or array indices (numeric strings). Used by `expression.rs`, `visibility.rs`, render data.rs.
- `ferro-json-ui/src/expression.rs:42–66` — `resolve_value` walks `props: Value` recursively, detecting single-key objects `{"$data": "/path"}` (line 68–75: `is_data_expr`). **Phase 163's `$each` scoping decision:** when `$each: { as: "row" }` is in effect, paths starting with `/row/...` must resolve against the current iteration's row value, not against `spec.data`. The cleanest implementation is **string substitution at expansion time** — when cloning the templated element, walk its props and rewrite `/row/...` paths to literal data-bound forms (either pre-resolve `{"$data": "/row/field"}` to the actual value, or rewrite to a globally-unique path like `/_each_row_<id>/field`). See §Resolve pipeline below for the recommended approach.

## Proposed deltas per decision (D-01 through D-13)

### D-01: `$each` spec-level directive

**Element struct delta** (`ferro-json-ui/src/spec.rs` after line 91):

```rust
/// Optional iteration directive: instantiate one element per row in a
/// data array. Resolved before render; the templated element is replaced
/// by N clones with auto-suffixed IDs.
#[serde(default, skip_serializing_if = "Option::is_none", rename = "$each")]
pub each: Option<EachDirective>,

/// Optional conditional-emission directive: element exists only when
/// the predicate evaluates true. Resolved before render; falsy → deleted
/// from the element map (no hidden DOM).
#[serde(default, skip_serializing_if = "Option::is_none", rename = "$if")]
pub if_: Option<crate::visibility::VisibilityCondition>,
```

**New types** (same file):

```rust
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct EachDirective {
    /// Slash-separated path to a JSON array in `Spec.data`.
    pub path: String,
    /// Loop-variable name bound during expansion. Paths starting with
    /// `/{as}/...` in the templated element's props resolve to the current row.
    pub as_: String,  // serde: #[serde(rename = "as")]
}
```

Note: `as_` is needed because `as` is a Rust keyword. Use `#[serde(rename = "as")]`.

**Wire-format example** (CONTEXT D-01 verbatim):

```json
"order_cards": {
  "type": "Card",
  "$each": { "path": "/orders", "as": "order" },
  "props": {
    "title": { "$data": "/order/order_number" },
    "description": { "$template": "{/order/customer_name} · {/order/time_ago}" }
  }
}
```

After expansion (data has 3 orders with IDs 7, 12, 19):

```json
"order_cards-0": { "type": "Card", "props": { "title": "ORD-1001", "description": "Alice · 2m ago" } },
"order_cards-1": { "type": "Card", "props": { "title": "ORD-1002", "description": "Bob · 5m ago" } },
"order_cards-2": { "type": "Card", "props": { "title": "ORD-1003", "description": "Carol · 10m ago" } }
```

The parent's `children` array referring to `"order_cards"` is rewritten to `["order_cards-0", "order_cards-1", "order_cards-2"]`.

### D-03: `$if` spec-level directive

Reuses `crate::visibility::VisibilityCondition` (already exported from `visibility.rs`). The struct has `{ path, operator, value: Option<Value> }` (visibility.rs:28–35). **No new condition struct needed** — D-04 reuse fits exactly.

Wire-format example (CONTEXT D-03 verbatim, with `eq` operator name aligned to existing enum):

```json
"btn_advance": {
  "type": "Button",
  "$if": { "path": "/can_advance", "operator": "eq", "value": true },
  "props": { "label": { "$data": "/advance_label" } }
}
```

**`$if` vs `visible` distinction (locked):**

| Aspect | `$if` (Phase 163) | `visible` (existing) |
|--------|--------|-----------------------|
| When evaluated | Resolve time | Render time |
| Falsy behavior | Element deleted from `Spec.elements` | Element renders with `hidden` attribute / no-op return |
| DOM presence | None | Hidden `<div>` (or empty string) |
| Child references | Silently skipped (render layer already does this) | Children render as normal but parent is hidden |
| Cost of toggle | Re-resolve required | DOM-only (cheap) |

### D-04: REUSE `visibility.rs` evaluator — **mechanically verified**

The `Visibility::evaluate(data: &Value) -> bool` signature (visibility.rs:70) is directly callable from the directive resolver. The `evaluate_condition` private helper (visibility.rs:80–121) does the actual path resolution and operator dispatch. Since `$if` payload is a single `VisibilityCondition` (not the wrapping enum with `And`/`Or`/`Not`), Phase 163 can call:

```rust
// in resolve.rs::expand_directives
use crate::visibility::{Visibility, VisibilityCondition};

fn if_passes(cond: &VisibilityCondition, data: &Value) -> bool {
    // Wrap in the Visibility::Condition enum variant to reuse evaluate().
    Visibility::Condition(cond.clone()).evaluate(data)
}
```

Alternatively the planner can lift `evaluate_condition` from a private function (line 80) to crate-public — same result, less allocation. Both approaches are surgical.

**Open question for the planner:** Whether `$if` should accept the full `Visibility` enum (with `And`/`Or`/`Not`) or only `VisibilityCondition`. CONTEXT D-03 example shows a single condition. Recommend supporting the full enum for symmetry — costs nothing because `Visibility` already deserializes via `#[serde(untagged)]`.

### D-05: NO `$template` element

**Pitfall: the keyword `$template` is already taken.** `ferro-json-ui/src/expression.rs:30` defines `EXPR_TEMPLATE_KEY: &str = "$template"` as a template-string-interpolation directive (e.g., `{"$template": "Hi, {/name}!"}` → produces `"Hi, Alice"`). A `$template` element would collide semantically with this existing prop-value directive. CONTEXT D-05 ("Do NOT ship a separate `$template` element") is doubly justified — both because `$each` subsumes templating AND because the keyword is occupied.

If the four-bullet rationale needs a confirming sentence in docs: "`$template` is reserved for the prop-level string-interpolation directive (resolved by `resolve_expressions`); element-level templating is covered by `$each`."

### D-06: `SpecBuilder` ergonomic methods

**Existing surface** (`spec.rs:222–299`): `SpecBuilder::element(id, ElementBuilder) -> Self` takes a pre-built `ElementBuilder` and adds children BY ID only (no nesting). The new ergonomic layer adds methods on `SpecBuilder` (or a parallel `NestedSpecBuilder`) that accept fully nested builders and emit flat-map output.

**Sketch** (one option — additive, no breaking change to existing API):

```rust
impl SpecBuilder {
    /// Add an element AND its children in one nested call. Auto-generates
    /// child IDs by structural position: `{parent_id}-0`, `{parent_id}-1`, ...
    /// Recursively flattens — emits one entry per leaf in the nested tree.
    /// Returns Self (consuming, like other builder methods).
    pub fn element_nested(mut self, id: impl Into<String>, el: NestedElement) -> Self {
        let id: String = id.into();
        if self.root.is_none() { self.root = Some(id.clone()); }
        self.flatten_nested(&id, el);
        self
    }

    fn flatten_nested(&mut self, id: &str, el: NestedElement) {
        let mut child_ids = Vec::new();
        for (idx, child) in el.children.into_iter().enumerate() {
            let child_id = format!("{id}-{idx}");
            self.flatten_nested(&child_id, child);
            child_ids.push(child_id);
        }
        let mut leaf = ElementBuilder {
            type_name: el.type_name,
            props: el.props,
            children: child_ids,
            action: el.action,
            visible: el.visible,
        };
        self.elements.insert(id.to_string(), leaf.build());
    }
}

/// Mirror of ElementBuilder but with nested children of type `NestedElement`.
pub struct NestedElement {
    type_name: String,
    props: serde_json::Map<String, serde_json::Value>,
    children: Vec<NestedElement>,
    action: Option<Action>,
    visible: Option<Visibility>,
}
```

The naming, exact API surface, and whether to introduce `NestedElement` vs reuse `ElementBuilder` with new `.nest(child)` methods is **planner discretion**. The structural guarantee is: **the output of `.build()` is still the canonical flat `Spec.elements` map.** No nested runtime representation.

### D-07: SpecBuilder is NOT a Component-style nested API

The existing API (`SpecBuilder.element(id, ElementBuilder).element(id, ElementBuilder)...`) is already flat. D-07 codifies that the ergonomic layer above is **sugar over construction** — the `Spec` runtime type remains the flat map of `Element`. This is enforced by the `flatten_nested` recursion above: the nested DSL exists only at builder-call time; once `.build()` returns, the nested representation is gone.

```markdown
## Homogeneous iteration → JSON file + `$each`

- Example: kanban order cards with `$each: { path: "/orders", as: "order" }`

## Conditional emission → JSON file + `$if`
- Single template, branches on a flag
- Example: action button visible only when `/can_advance == true`

## Heterogeneous runtime construction → Rust + `SpecBuilder`
- Element graph cannot be expressed declaratively (multi-branch nested structure
  computed from complex domain state)
- Example: order detail view with N status-dependent action buttons
  where each button's URL is computed from order data
```

### D-12: Spec validator errors

New `SpecError` variants (`spec.rs:98–121`):

```rust
#[error("element '{element_id}' has `$each.path = \"{path}\"` resolving to non-array data")]
EachPathNotArray { element_id: String, path: String },

#[error("element '{element_id}' has `$if.path = \"{path}\"` resolving to a missing key (vs falsy)")]
IfPathMissing { element_id: String, path: String },

#[error("element '{element_id}' has `$each.as = \"{name}\"` colliding with reserved name")]
EachAsReservedName { element_id: String, name: String },
```

**Subtlety on `IfPathMissing`:** the existing `Visibility::evaluate` collapses missing-path to `false` (Eq) or `true` (NotEq) per visibility.rs:84–93. CONTEXT D-12 explicitly distinguishes "missing key (vs falsy)" — this means at **validation time** (not at evaluation time), the validator checks that the `$if.path` corresponds to a key that EXISTS in `spec.data`'s shape (or in any data the spec might receive). Since `spec.data` may be `Value::Null` (handler binds data per request), this check is best-effort.

**Recommendation for the planner:** D-12's "missing key" check fires only when `spec.data` is non-null (i.e., the spec has embedded sample data) AND the path resolves to `None` (key absent, not present-but-null). For runtime data, the check cannot fire at `Spec::from_json` time. Document this in the validator's rustdoc.

**Reserved-name list for `$each.as`:** at minimum `data`, `props`, `_root`, plus any names that collide with `$data` interpretation. Recommend reserving `[data, root, _root, _each, this, self]` — six names. Document in `EachDirective` rustdoc.

**Validation function placement:** `validate_directives` in spec.rs, called from `validate_structure` between `validate_no_dangling` and `detect_cycle`. The directive validator iterates `spec.elements`, and for each element with `each: Some(...)` or `if_: Some(...)`, runs the three checks.

### Current pipeline (no directives)

```

                                                  ↓
                                          (handler attaches data via merge_data)
                                                  ↓
JsonUi::resolve(spec):
  1. resolve_actions (action.handler → action.url)
```

### Phase 163 pipeline (with `$each` / `$if`)

```
Spec::from_json(json) → validates structure (incl. directive validation D-12) → returns Spec
                                                  ↓
                                          (handler attaches data via merge_data)
                                                  ↓
JsonUi::resolve(spec):
  0. expand_directives  ← NEW PASS
     - For each element with $if: evaluate predicate against spec.data.
       If false: delete element from Spec.elements.
     - For each element with $each: resolve path to Vec<Value> in spec.data.
       For each row at index i:
         - Clone the templated element.
         - Rewrite props: substitute /{as}/... paths to row-scoped paths.
         - Auto-suffix the cloned element's children IDs.
         - Insert as "{id}-{i}" into Spec.elements.
       Delete the original templated element.
       Update any parent's children list to reference the cloned IDs.
  1. resolve_actions (unchanged — operates on the post-expansion element set)
  2. resolve_expressions (unchanged — same)
                                                  ↓
JsonUi::build_response → render_spec_to_html → HTML
```

**Important subtlety surfacing here:** the `card` references `order_badge` and `order_dropdown` as children. **Recommended rule (planner confirms):** When a templated element's children are themselves templated by the SAME `$each` path-and-as combination, the child IDs are correlated by index. Concretely:

```rust
// In expand_directives:
// For each $each-templated element, scan its `children` list for IDs that point
// to other $each elements with matching {path, as}. Rewrite to correlated indexes.
// All other children stay literal (or get their own independent expansion).
```

**Alternative — simpler but more verbose:** require the user to inline the badge/dropdown inside the card via nested element references that ALSO use `$each`. This pushes complexity to the spec author. Recommend NOT going this route.

**Alternative — co-iteration syntax:** introduce a sibling-grouping concept where one `$each` directive covers multiple sibling elements. Out of scope for Phase 163.

**Heterogeneous slice (the conditional row_actions):** `order_dropdown.props.items` is `{ "$data": "/order/row_actions" }` — meaning the controller builds the per-order row_actions array in Rust (preserves the existing `status.advance_label()` / `status.can_pay()` logic). This is acceptable hybrid: structure declarative, per-row content data-driven. The full conditional-actions migration (per FRICTION cassa/orders.rs:754) requires `$if` on individual button elements — not on a row_actions array — and is the 4th cassa site D-02 cites.

### Pass invariants

1. **Validation runs before expansion** — directive validation (D-12) checks the static spec graph, NOT the expanded one. The validator sees one `order_card` element with `$each`, not N expanded clones.
2. **Cycle detection runs on the static spec** — the templated element can self-reference safely; expansion does not create new cycles (the rewritten children IDs are new strings).
3. **Depth check runs on the static spec** — same reason. After expansion, the depth IS unchanged (the templated element occupies the same depth slot as its replacements).
4. **No nested `$each`** — recommend rejecting at validation time. CONTEXT defers this; recommend the planner add a validation error `NestedEach` or document the behavior as "undefined" with a planned restriction in a follow-up phase. **Open question for the planner.**
5. **`$each` and `$if` on the same element** — recommend evaluating `$if` first; if false, skip `$each` expansion entirely. Document in `$if` rustdoc.

## Auto-suffix rule (with worked example)

**Rule:** When expanding `"X"` with `$each` producing N entries, IDs become `X-0`, `X-1`, ..., `X-{N-1}`.

**Children of templated element:**
- If a child ID belongs to ANOTHER `$each`-templated element with **matching `{path, as}` directive**, the child is correlated by index: cloned element `X-i` references child `Y-i`.
- If a child ID is a LITERAL element (not templated), all N clones reference the same literal element.
- If a child ID is a templated element with a DIFFERENT `{path, as}`, the behavior is undefined — recommend the planner reject this at validation time as `MismatchedEach`.

### AST visitor outline

```rust
// ferro-cli/src/commands/json_ui_migrate_v1.rs
use syn::visit::{self, Visit};
use syn::{File, ItemFn, ExprCall, ExprStruct};

pub fn run(file: String, dry_run: bool) {
    // 1. Read source file.
    let src = std::fs::read_to_string(&file)?;
    // 2. Parse with syn.
    let parsed: File = syn::parse_file(&src)?;
    // 3. Idempotency check: scan for existing `JsonUi::render_file` calls.
    //    If file already uses render_file exclusively, emit warning and exit.
    if file_already_migrated(&parsed) {
        eprintln!("warning: {file} appears already migrated (uses render_file). Skipping.");
        return;
    }
    // 4. Visit each `ItemFn` (handler). For each:
    //    a. Find `JsonUiView::new(title, vec![...])` calls.
    //    b. Walk the vec! body via `MakeNodeVisitor` to collect ComponentNodes.
    //    c. Each `make_node(key, Component::X(props))` becomes one Element entry:
    //       - id = key
    //       - type = "X" (variant name)
    //       - props = struct-literal fields → JSON object (recursively)
    //    d. Each `make_node_with_action(key, Component::X(props), action)` adds
    //       an "action": {...} field to the element.
    //    e. Track parent/child IDs from struct fields like `fields: vec![...]`
    //       (FormProps.fields → Form.children), `buttons` (ButtonGroup.buttons),
    //       etc. — produce children: Vec<String>.
    // 5. Emit JSON spec file at src/views/{module}/{handler_fn_name}.json.
    // 6. Rewrite controller handler bodies to JsonUi::render_file calls (preserve
    //    function signature, imports, helper calls).
    // 7. If --dry-run: print proposed changes to stdout; do not write.
    // 8. Cases the codemod cannot handle (runtime branching, Spec::builder
    //    fall-through, dynamic key generation): emit
    //    `// TODO: ferro json-ui:migrate-v1 could not auto-translate this handler`
    //    above the function body, leave body intact.
}

struct MakeNodeVisitor {
    elements: serde_json::Map<String, serde_json::Value>,
    root_id: Option<String>,
}

impl<'ast> Visit<'ast> for MakeNodeVisitor {
    fn visit_expr_call(&mut self, call: &'ast ExprCall) {
        // Match make_node(...) / make_node_with_action(...) syntactically.
        // Extract the key literal and the Component variant expression.
        // Recurse into struct fields containing Vec<ComponentNode>.
        visit::visit_expr_call(self, call);
    }
}
```

### Idempotency

The codemod's idempotency check (step 3 above) scans the parsed AST for:
- `JsonUi::render_file` calls — if any handler uses this, treat the file as migrated.
- Absence of `make_node` / `make_node_with_action` / `JsonUiView::new` references.

If both conditions hold, emit `warning: {file} appears already migrated. No changes made.` and exit zero. This makes the codemod safely re-runnable.

### Failure modes the codemod handles gracefully

| Pattern | Action |
|---------|--------|
| `let view = if cond { make_node(...) } else { make_node(...) }` | Emit TODO marker, skip handler |
| `Spec::builder()...build()` | Emit TODO marker (already v2, not v1) |
| Runtime keys from `format!("{}_{}", ...)` | Emit TODO marker (codemod cannot statically determine key) |
| `fields: some_helper_fn()` returning `Vec<ComponentNode>` | Emit TODO marker (cross-function flow analysis out of scope) |

### Test discipline (codemod-specific)

- Unit tests: each transformation rule has a fixture pair (input `.rs` → expected `.json` + expected rewritten `.rs`). Tests live alongside `json_ui_migrate_v1.rs`.
- Snapshot test: full file round-trip on the `auth.rs` example above.
- Idempotency test: run codemod twice on the migrated output; second run is a no-op + warning.

## Common Pitfalls

### Pitfall 1: `$template` keyword collision

**What goes wrong:** Proposing a `$template` element type clashes with the existing prop-level `$template` directive in `expression.rs:30`.

**Why it happens:** `$`-prefixed names are a shared namespace across element-level (e.g., `$each`, `$if`) and prop-level (e.g., `$data`, `$template`) directives.

**How to avoid:** D-05 locks the rejection. The planner should document the namespace split in `spec-construction.md`: "Element-level directives appear as keys on an Element JSON object (`$each`, `$if`). Prop-level directives appear inside `props` values (`$data`, `$template`)."

**Warning signs:** A test or PR that introduces a new top-level `$X` keyword without checking `expression.rs:29-30`.

### Pitfall 2: Cycle / depth validators running on expanded elements

**What goes wrong:** Running `detect_cycle` or `check_depth` AFTER expansion sees N replicated branches, blowing up depth or detecting false cycles.

**Why it happens:** The naive resolve ordering is "validate first, then expand". The correct ordering is "validate the static spec, expand, then trust the expanded result without re-validating."

**How to avoid:** D-12 mandates validation at `Spec::from_json` time (before any data binding). Expansion happens in `JsonUi::resolve` (per request). The expanded result is NOT re-validated — by construction it cannot introduce cycles (new IDs are fresh strings) and depth is unchanged (the templated slot is replaced by clones at the same depth).

**Warning signs:** A code path that calls `validate_structure` after `expand_directives`.

### Pitfall 3: `$each` data path scoping leaks

**What goes wrong:** A cloned templated element's prop has `{"$data": "/row/field"}` but the row is no longer in scope by the time `resolve_expressions` runs. The path resolves to `Value::Null`.

**Why it happens:** `$data` resolves against `spec.data` (expression.rs:36). The loop variable `row` is bound only during expansion.

**How to avoid (two approaches):**

a. **Pre-resolve during expansion:** while cloning, walk the templated element's props and inline-substitute `/{as}/...` paths with literal values from the current row. After expansion, the clones have no `$data` markers referring to `/row/...`. `resolve_expressions` is a no-op for these clones.

b. **Rewrite paths during expansion:** while cloning, rewrite `/{as}/...` paths to globally-unique paths like `/_each_<id>_<i>/...`, and inject these into `spec.data` as `_each_<id>_<i>: <row_value>`. Then `resolve_expressions` resolves them normally.

Approach (a) is simpler and avoids polluting `spec.data`. Recommend (a) for Phase 163.

**Warning signs:** Tests where rendered output shows `null` where a row field was expected.

### Pitfall 4: `$if` evaluator's missing-path semantics

**What goes wrong:** D-12 says `$if.path` missing → `IfPathMissing` error at validation. But `Visibility::evaluate` (D-04 reuse) silently returns `false` for missing paths. The semantic gap is "validator strict, evaluator lenient."

**Why it happens:** Validation runs against the static spec (which may have null `spec.data`); evaluation runs against per-request data.

**How to avoid:** Document the two-layer semantics: (1) validator checks the path *exists in the spec.data shape* if spec.data is non-null at parse time; (2) at evaluation time (per-request), missing paths follow `Visibility::evaluate`'s leniency. The validator's check is best-effort — it cannot enforce schema constraints on per-request data without an explicit schema.

**Warning signs:** Tests that assert `IfPathMissing` fires when spec.data is null.

### Pitfall 5: Codemod silent skip of branching handlers

**What goes wrong:** Codemod encounters `if cond { make_node(...) } else { make_node(...) }` and skips the handler entirely without leaving any signal.

**Why it happens:** AST visitor doesn't know how to fold runtime branches into a static spec.

**How to avoid:** D-09 mandates "cases involving runtime branching get a `// TODO: codemod could not auto-translate` marker, not a silent skip." Implement by collecting all skipped handlers and either (a) inserting the TODO comment before each in the rewritten file, or (b) emitting a summary report alongside the migrated file.

**Warning signs:** A migrated file that omits some handlers without explanation.

### Pitfall 6: Codemod overwrites existing files

**What goes wrong:** Codemod runs against a controller that already has a partially migrated state; it overwrites custom code.

**Why it happens:** No idempotency check.

**How to avoid:** D-11 mandates idempotency. The codemod's first action must be to scan the parsed AST for `JsonUi::render_file` calls — if any handler already uses render_file, treat the file as migrated and exit zero with a warning. Document in `--help` text.

**Warning signs:** A user running the codemod twice and losing manual changes between runs.

```rust
use crate::data::resolve_path;
use crate::visibility::{Visibility, VisibilityCondition};

pub fn expand_directives(spec: &mut Spec) {
    let data = spec.data.clone();
    expand_if(spec, &data);
    expand_each(spec, &data);
    rewrite_parent_children(spec);
}

fn expand_if(spec: &mut Spec, data: &Value) {
    let to_delete: Vec<String> = spec.elements.iter()
        .filter_map(|(id, el)| {
            el.if_.as_ref().and_then(|cond| {
                let passes = Visibility::Condition(cond.clone()).evaluate(data);
                (!passes).then(|| id.clone())
            })
        })
        .collect();
    for id in to_delete {
        spec.elements.remove(&id);
    }
}

fn expand_each(spec: &mut Spec, data: &Value) {
    // Collect templated elements (those with $each).
    let templates: Vec<(String, Element)> = spec.elements.iter()
        .filter_map(|(id, el)| el.each.as_ref().map(|_| (id.clone(), el.clone())))
        .collect();

    for (tmpl_id, tmpl_el) in templates {
        let each = tmpl_el.each.as_ref().unwrap();
        let Some(rows) = resolve_path(data, &each.path).and_then(|v| v.as_array()) else {
            // Validator should have caught this; emit no clones and remove template.
            spec.elements.remove(&tmpl_id);
            continue;
        };

        for (i, row) in rows.iter().enumerate() {
            let clone_id = format!("{tmpl_id}-{i}");
            let mut clone = tmpl_el.clone();
            clone.each = None; // strip directive from clones
            // Pre-resolve /{as}/... paths in props using this row.
            inline_resolve_row_paths(&mut clone.props, &each.as_, row);

            // to correlated indexes (i.e., child becomes "{child_id}-{i}").
            for child in &mut clone.children {
                if is_correlated_each(&tmpl_el, child, spec) {
                    *child = format!("{child}-{i}");
                }
            }
            spec.elements.insert(clone_id, clone);
        }

        // Remove the original template.
        spec.elements.remove(&tmpl_id);
    }
```

```rust
// ferro-json-ui/src/spec.rs (new private fn called from validate_structure)
fn validate_directives(spec: &Spec) -> Result<(), SpecError> {
    const RESERVED_EACH_AS: &[&str] = &["data", "root", "_root", "_each", "this", "self"];

    for (id, el) in &spec.elements {
        if let Some(each) = &el.each {
            // Check `as` reserved-name collision.
            if RESERVED_EACH_AS.contains(&each.as_.as_str()) {
                return Err(SpecError::EachAsReservedName {
                    element_id: id.clone(),
                    name: each.as_.clone(),
                });
            }
            // Check `path` resolves to array if spec.data is non-null.
            if !spec.data.is_null() {
                if let Some(value) = crate::data::resolve_path(&spec.data, &each.path) {
                    if !value.is_array() {
                        return Err(SpecError::EachPathNotArray {
                            element_id: id.clone(),
                            path: each.path.clone(),
                        });
                    }
                }
            }
        }
        if let Some(cond) = &el.if_ {
            // Check `path` exists in spec.data if non-null.
            if !spec.data.is_null() && crate::data::resolve_path(&spec.data, &cond.path).is_none() {
                return Err(SpecError::IfPathMissing {
                    element_id: id.clone(),
                    path: cond.path.clone(),
                });
            }
        }
    }
    Ok(())
}
```

## Open Questions for planner

1. **`equals` vs `eq` operator name.** CONTEXT D-03 example uses `"operator": "equals"`. Existing `VisibilityOperator::Eq` serializes as `"eq"`. Recommendation: align to existing `eq`. The planner must confirm and update CONTEXT or accept the alignment.

2. **`$if` accepts full `Visibility` enum vs just `VisibilityCondition`.** Recommendation: full enum for symmetry; no extra work since `Visibility` is already `#[serde(untagged)]`.

3. **Nested `$each` behavior.** Three options: (a) reject at validation time (`NestedEach`), (b) silent no-op, (c) recursive expansion. Recommend (a) — explicit error is debugging-friendly; defer (c) to a follow-up phase if a real use case emerges.

4. **Correlated child indexes for `$each`.** When a templated parent's child is also `$each` over the same path, should the child IDs be correlated by index? Recommendation: YES (see worked example). Planner confirms and writes the matching-rule.

5. **`$each.path` strict vs lenient at validation time.** If `spec.data` is null (no embedded sample), the validator cannot check that the path resolves to an array. Recommendation: best-effort validation when `spec.data` is non-null; runtime evaluation produces zero clones if path resolves to non-array; document both behaviors.

6. **Action handler templating for per-row URLs.** Should `resolve_expressions` extend to walk `action.handler` / `action.url`? Recommendation: NO for Phase 163 — out of scope. Controller pre-resolves per-row URLs into `spec.data`. Document as known limitation.

7. **Codemod scope.** Should the codemod attempt to detect `$each`-applicable patterns (homogeneous iteration in v1 source via `for item in items { vec.push(make_node(...)) }`) and emit `$each` directives, or always emit flat element entries? Recommendation: always emit flat entries in Phase 163 (the simpler transformation); add `$each` emission in a follow-up. The codemod's value is mechanical migration, not optimization.

8. **`SpecBuilder` ergonomic API exact surface.** Sketched in §Per-decision map D-06. Planner picks the final method names (`element_nested` vs `element_with_children` vs other), and whether `NestedElement` is a new type or `ElementBuilder` gains `.nest(child)` methods.

9. **Order of pass execution if `$each` AND `$if` are on the same element.** Recommendation: `$if` first (if false, skip `$each` entirely). Planner confirms.

10. **`docs/src/json-ui/expressions.md` extension.** Phase 162 owns the v2 expressions doc; Phase 163 should add sections for `$each` and `$if`. Coordinate with Phase 162's plan layout to avoid merge conflicts.
