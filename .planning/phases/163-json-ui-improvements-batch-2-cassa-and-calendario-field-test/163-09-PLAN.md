**Append two new top-level sections to the END of `docs/src/json-ui/expressions.md`.**

First section: `## $each` — element-level iteration directive. Content must include:

1. One-sentence summary: "`$each` instantiates one element per row in a data array."
2. Wire-format example:
   ```json
   "order_card": {
     "type": "Card",
     "$each": {"path": "/orders", "as": "order"},
     "props": {"title": {"$data": "/order/order_number"}}
   }
   ```
3. Subsection `### Fields`:
   - `path` — slash-separated path to a JSON array in `spec.data`.
   - `as` — loop variable name. Paths starting with `/{as}/...` in the templated element's props resolve to the current row.
4. Subsection `### Expansion`:
   - State that ferro replaces the templated element by N clones with IDs `{element_id}-0`, `{element_id}-1`, ...
   - State that parent elements' `children` lists are rewritten to reference the new clone IDs.
   - State that the resolve order is: `$if` first (Plan 03), then `$each`, then `resolve_actions`, then `resolve_expressions`.
5. Subsection `### Validation` — list these errors emitted at `Spec::from_json` time:
   - `EachPathNotArray` — best-effort check when `spec.data` is non-null.
   - `EachAsReservedName` — `as` collides with `data`, `root`, `_root`, `_each`, `this`, `self`.
   - `NestedEach` — a `$each`-templated element's transitive descendant (deeper than direct children) is also `$each`-templated.
   - `MismatchedEach` — a `$each`-templated element's direct child is `$each` over a different `{path, as}`.
6. Subsection `### Correlated children` — explain: sibling templates with the SAME `{path, as}` produce per-row groupings. Concrete example from RESEARCH §"Auto-suffix rule".
7. Subsection `### Limitations` — list:
   - Phase 163 does not synthesize per-row `action.url` from row data; controller pre-resolves URLs into `spec.data` and the templated element references them via `{"$data": "/order/advance_url"}`.
   - Nested `$each` is rejected. If a use case emerges, file an issue.

Second section: `## $if` — element-level conditional emission directive. Content must include:

1. One-sentence summary: "`$if` removes an element from the spec when its predicate evaluates false."
2. Wire-format example:
   ```json
   "btn_advance": {
     "type": "Button",
     "$if": {"path": "/can_advance", "operator": "eq", "value": true},
     "props": {"label": "Advance"}
   }
   ```
3. Subsection `### Distinction from \`visible\``:
   - `$if` (resolve-time): falsy → element removed from spec; no DOM at all.
   - `visible` (render-time): falsy → element renders with hidden semantics; DOM present.
4. Subsection `### Predicate syntax` — reuses the `Visibility` enum:
   - Flat condition: `{"path": "/p", "operator": "eq", "value": x}`.
   - Compound: `{"and": [...]}`, `{"or": [...]}`, `{"not": {...}}`.
   - Operator names (snake_case): `exists`, `not_exists`, `eq`, `not_eq`, `gt`, `lt`, `gte`, `lte`, `contains`, `not_empty`, `empty`. **The canonical name is `eq`, not `equals`.**
5. Subsection `### Validation`:
   - `IfPathMissing` — when `spec.data` is non-null and the predicate path resolves to `None`. Distinct from a present-but-null value.
6. Subsection `### Interaction with `$each`` — when both are on the same element, `$if` evaluates first; falsy → element removed before `$each` expansion.
7. Subsection `### Missing-children behavior` — when a parent's `children` list references an ID that was removed by `$if`, the render layer silently skips it (this is the existing render-layer comment behavior).
