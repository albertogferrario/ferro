```rust
/// Run migrations during server boot without success logging.
///
/// "Silent" refers only to the success path (no `println!("Running migrations…")`

async fn run_migrations_silent<Migrator: MigratorTrait>() {
    let db = Self::get_database_connection().await;
    if let Err(e) = Migrator::up(&db, None).await {
        eprintln!("Migration failed: {e}");
        std::process::exit(1);
    }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migrator → server boot | A failed migration is a server precondition violation; runtime must refuse to serve |
| stderr → operator | The eprintln message is the operator's signal that boot failed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-157-04-01 | Denial of Service | Process exits on migration failure; service unavailable | mitigate (intentional) | This IS the mitigation. Serving traffic with a stale schema is a higher-severity outcome (data corruption / silent failures) than refusing to serve. The PRE_DEPLOY gate from Plan 02 prevents this from reaching production. Local-dev migration failures are expected to abort and be fixed. |
| T-157-04-02 | Repudiation | A migration failure logged only to stderr may be lost in container logs | accept | DO App Platform captures stderr by default. Self-hosted operators are responsible for log capture. Out of scope for ferro. |
| T-157-04-03 | Information Disclosure | The error message printed to stderr could leak DB schema details | accept | The operator IS the audience. The same level of disclosure is in `run_seeders` and `DB::init` (existing precedent). Not a new exposure. |
</threat_model>
