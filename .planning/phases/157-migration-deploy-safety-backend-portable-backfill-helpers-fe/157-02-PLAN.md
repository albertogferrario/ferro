```rust
fn render_jobs_block(web_bin: &str, repo: &str, branch: &str) -> String {
    format!(
        "jobs:\n  \
         - name: migrate\n    \
           kind: PRE_DEPLOY\n    \
           dockerfile_path: Dockerfile\n    \
           source_dir: /\n    \
           github:\n      \
             repo: {repo}\n      \
             branch: {branch}\n      \
             deploy_on_push: false\n    \
           run_command: /usr/local/bin/{web_bin} db:migrate\n    \
           instance_size_slug: apps-s-1vcpu-0.5gb\n    \
           instance_count: 1\n"
    )
}
```

Format/indentation note: the inline `\ ` continuation pattern keeps the function body compact. Confirm the rendered output (when printed) matches the YAML shape in 157-RESEARCH.md §Pattern 2 — two-space indent under `jobs:`, four-space indent under `-`, six-space for `github` children.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-157-02-01 | Tampering | repo/branch strings interpolated into YAML | accept | Values come from `git remote get-url origin` and `git config init.defaultBranch`, both developer-controlled. Same trust level as `services[0].github.repo` which already interpolates the same values. |
| T-157-02-02 | Information Disclosure | run_command path discloses binary name | accept | Binary names are visible in published Cargo manifests and Docker images anyway. No secret content. |
| T-157-02-03 | Elevation of Privilege | The PRE_DEPLOY job runs `db:migrate` with DB write privileges | mitigate | Migrate command uses the same DATABASE_URL env binding that the web service uses — no escalation. The job runs in the same DO app context as the service. Documented in CLAUDE.md migration docs (no change required in this plan). |
