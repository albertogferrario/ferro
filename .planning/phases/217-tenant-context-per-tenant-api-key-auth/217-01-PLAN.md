<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Raw `ferro_` token → `validate_api_key` | Untrusted high-entropy secret; only its SHA-256 hash is compared against stored hashes |
| `mcp_api_keys` row → principal | tenant_id/scope read from the trusted DB row, never from the token payload |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-217-02 | Information Disclosure (at rest) | `mcp_api_keys` schema + generate_mcp_api_key | mitigate | Schema stores `key_hash` (SHA-256 hex) only; plaintext returned once by `generate_mcp_api_key` and never persisted (D-03). Verified: `migration.rs` has no plaintext column; `validate.rs` only ever hashes the inbound token. |
| T-217-03 | Spoofing | `validate_api_key` lookup | mitigate | Unknown/revoked/DB-error all → `BearerCheck::Invalid` (fail closed). Hash-indexed lookup on a 256-bit-entropy secret; `subtle` available if a direct digest compare is later introduced. RED→GREEN tests `unknown_api_key_returns_invalid`, `revoked_api_key_returns_invalid` lock this. |
| T-217-04 | Elevation | scope column on key record | mitigate | `scope` is on the key record from the first migration (D-06) and returned in the principal — not retrofittable. `wrong_expected_tenant_returns_forbidden` + the principal `scope` assertion lock it. |
| T-217-01 | Information Disclosure (cross-tenant) | tenant_id from row | mitigate | tenant_id resolved purely from the matched row, never from caller input. Cross-tenant integration assertion lives in Plan 02 (SC#5). |
</threat_model>
