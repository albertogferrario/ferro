```rust
// Author marks a #[service] trait method #[offload]; the macro derives a Job whose
// struct name is <Trait><Method>Job. The trait method itself stays -> T in-process.
#[service(impl = ReportBuilder)]
#[async_trait]
pub trait Reports: Send + Sync {
    #[offload]
    async fn build_monthly(&self, tenant_id: i64, month: Month) -> Report;  // in-process
}

// The derived Job gains a typed enqueue entrypoint:
let handle: ferro::queue::OffloadHandle<Report> =
    ReportsBuildMonthlyJob { tenant_id, month }.offload().await?;
let key = handle.key();  // inert in this phase — no resolve/subscribe yet
```
- `.offload()` returns `Result<OffloadHandle<T>, Error>`; `T` is the method's SUCCESS type
  (for `Result<T, E>` the handle is `OffloadHandle<T>`; `E` is stringified on failure, not required Serialize).
- A parameter or return type that is not `Serialize + DeserializeOwned` fails to COMPILE with a
  diagnostic naming the offending type (the `OffloadSerializable` boundary).

**1. Authoring surface (D-01).** Marking a `#[service]` trait method `#[offload]` derives a
`ferro-queue` Job from the method signature — no hand-written Job struct, no manual enqueue. The
trait method itself keeps its in-process signature (`-> T`); `#[offload]` layers an enqueue
entrypoint on top. Show the call-site example from the `<interfaces>` block (the `Reports` trait
+ the `.offload().await?` line). State the derived Job name convention (`<Trait><Method>Job`,
confirmed in 245-02-SUMMARY.md).

**2. The typed handle (D-02, D-08).** `.offload()` returns `Result<OffloadHandle<T>, Error>`.
`OffloadHandle<T>` identifies where the result will eventually land — a typed handle carrying the
success type. State plainly that in this phase the handle is **inert**: it exposes a read-only key
(`.key()` / `.id()`) but no resolve or subscribe surface. Frame that resolve/subscribe (reading
the result back, streaming it to a client) is future work in the result-path phases — do NOT name
internal phase numbers or unreleased features by codename; describe them as "a later result-path
capability" (neutral-voice rule; the handle key "is where a subscriber will later attach").

**3. The success-type contract (D-09).** `T` is the method's SUCCESS type. For `-> Report`,
the handle is `OffloadHandle<Report>`. For `-> Result<Report, E>`, the handle is still
`OffloadHandle<Report>`; the error `E` is recorded as a job failure (stringified) and is not
required to be serializable. For `-> ()` or no return, the handle is `OffloadHandle<()>`.

**4. The serializable contract as the module-isolation guarantee (SC#3 — the load-bearing
point).** This is the core of the section. Frame it as the anchor spec does:
   - Every parameter and every return (success) type crossing the offload boundary must be
     `Serialize + DeserializeOwned`. This is enforced at compile time.
   - Present this as a guarantee, not a restriction: because the payload must serialize, the work
     is fully described by data that can travel to another process — the module is *sealed* across
     the boundary. A method that cannot serialize its inputs or output cannot be offloaded, and the
     compiler says so before the code runs. The serializable contract *is* the isolation boundary.
   - Show the compile-time diagnostic: a non-serializable parameter or return type fails to build
     with a message that names the offending type. Quote the actual branded message text verbatim

     #[offload] isolation boundary and must be Serialize + DeserializeOwned` line). Do NOT
