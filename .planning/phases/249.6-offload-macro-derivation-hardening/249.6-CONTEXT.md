# Phase 249.6: Offload macro derivation hardening - Context

**Gathered:** 2026-08-16 (--auto mode)

<domain>
## Phase Boundary

Repair the five latent macro/handle defects recorded in the 244 and 245 REVIEW.md files, all
on the `#[offload]` write-boundary path, **without altering the derivation's external contract**.
The surface must fail loudly (spanned diagnostic, `Err` instead of panic) and constrain correctly
(no over-broad generic bounds, no double-registration). HARDENING only — OFFLOAD-01 and OFFLOAD-02
remain satisfied and are **not reopened**.

In scope — exactly these five defects:
- **244 WR-01** — `owned_type` emits `T` verbatim for `&&T` / `&Ref<'a>` with no spanned diagnostic.
- **244 WR-02** — `JOB_REGISTRARS` not cleared after `apply_registrars`; a second `from_registry` re-runs every registrar.
- **244 WR-03** — generated `handle()` panics via `.expect(...)` instead of returning `Err`.
- **245 WR-01** — `OffloadHandle<T>`'s std-derives inject `T: Clone + Debug + PartialEq + Eq` bounds beyond `OffloadSerializable`.
- **245 IN-01** — the `ferro-queue` re-export doc comment mislabels the offload surface.

Out of scope: any behavior/signature change to the public derivation surface; the 244 INFO items
(IN-01/02/03) and 245 WR-02 (key linkage, closed by Phase 246) and 245 IN-02/03 — see Deferred Ideas.
</domain>

<decisions>
## Implementation Decisions

### WR-01 — Reject unsupported receiver forms in `owned_type` (SC#1)
- **D-01:** In `owned_type` (`ferro-macros/src/offload.rs:80-101`), the `other` arm of the
  `Type::Reference` match (line 96) currently emits `#other` verbatim. Before emitting, guard with
  `matches!(other, Type::Reference(_))` and return a spanned `syn::Error::new_spanned(ty, ...)` whose
  message names the double-reference / `&Ref<'a>` constraint ("the job payload must be fully owned").
  The error must surface **at the `#[offload]` annotation**, not at a downstream use site.
- **D-02:** Scope the check **narrowly to inner references** (the exact reported form). Do NOT attempt
  general ownability/lifetime analysis of arbitrary inner types — that is a larger design change and
  out of scope for a hardening phase. `&str` and `&[T]` arms are unchanged.
- **D-03:** Add a trybuild compile-fail fixture (`ferro-macros/tests/ui/offload/fail/double_ref_param.rs`
  + `.stderr`) mirroring the existing `mut_ref_param.rs` pattern; the `.stderr` pins the spanned message.

### WR-02 — No double-registration across successive `from_registry` (SC#2)
- **D-04:** Lock the **invariant**: two successive `WorkerLoop::from_registry` calls register each job
  exactly once, asserted by a test. The invariant is fixed; the **mechanism is left to planning** (Claude's
  discretion within the constraint below).
- **D-05 (discrepancy — do NOT blindly apply the review snippet):** The 244 review proposes
  `registrars.clear()` inside `apply_registrars` (`ferro-queue/src/db.rs:111-115`). That Vec is **also read
  by** `has_registered_jobs()` (`db.rs:79-85`) and `registered_queue_names()` (`db.rs:91-106`) via
  `JOB_REGISTRARS.lock().is_empty()`. A destructive `clear()` makes the manual-registration Vec one-shot
  and empties the signal those two consumers depend on. The planner/researcher MUST first establish
  (a) what "exactly once" is counted over — per-`WorkerLoop` handler map vs. process-global — and (b) the
  `serve` boot call ordering of `has_registered_jobs`/`registered_queue_names` relative to `from_registry`,
  before choosing between: **(preferred)** non-destructive per-loop idempotency (registering the same job
  key twice into one loop is asserted-once / a no-op), or clear-after-drain only if ordering analysis proves
  no observable regression on the two consumers. Note each `from_registry` already builds a **fresh**
  `WorkerLoop` with a fresh `HashMap`, and `HashMap::insert` is idempotent per key — so the observable
  double-registration surface today is narrow; the fix is primarily defensive and must not regress the
  two consumer signals.

### WR-03 — Panic → `Err` on missing service binding (SC#3)
- **D-06:** Replace `.expect(#expect_msg)` with fallible resolution returning `Err` so a missing binding
  is recorded as a failed job (visible in introspection), not a caught panic that exhausts retries.
- **D-07 (discrepancy — TWO sites, review recorded one):** The 244 review cited a single `.expect()`
  in `handle()`. Phase 246 added `handle_with_value()`, so there are now **two** sites —
  `ferro-macros/src/offload.rs:383-384` (`handle()`) and `:400-401` (`handle_with_value()`). **Both** must
  be converted.
- **D-08:** Use `::ferro::App::make::<dyn #trait_ident>().ok_or_else(|| ::ferro::queue::Error::job_failed(#job_ident_str, #expect_msg))?`.
  `Error::job_failed(job, message)` is confirmed to exist at `ferro-queue/src/error.rs:82`. Both method
  bodies already return `Result<_, ::ferro::queue::Error>`, so `?` composes. Emit only `::ferro::*` paths
  (macro path convention). The `#expect_msg` value is reused as the failure message.

### 245-WR-01 — Drop over-broad generic bounds on `OffloadHandle<T>` (SC#4)
- **D-09:** At `ferro-queue/src/offload.rs:71`, remove `Debug, Clone, PartialEq, Eq` from the
  `#[derive(...)]`; keep `#[derive(Serialize, Deserialize)]` (the phantom is `#[serde(skip)]`, already
  free of `T` bounds). Hand-write `impl<T> Clone`, `impl<T> std::fmt::Debug`, `impl<T> PartialEq`,
  `impl<T> Eq` for `OffloadHandle<T>` that **bound nothing on `T`** and delegate to `self.key`
  (the phantom is `PhantomData<fn() -> T>`, so no `T` is touched).
- **D-10:** Prefer **hand-written impls over a new dependency** (`derive_more`/`educe`) — four trivial
  impls do not justify a dep, consistent with the framework's minimal-dependency posture.
- **D-11:** Add a regression test (extend/sibling `ferro-macros/tests/ui/offload/pass/offload_handle.rs`)
  using a success type that is `Serialize + DeserializeOwned` but **not** `Clone + Debug + Eq`, asserting
  the resulting `OffloadHandle<T>` clones, debugs, and compares.

### 245-IN-01 — Correct the mislabeled re-export doc comment (SC#5)
- **D-12:** At `ferro-queue/src/lib.rs:72`, the `/// Re-export async_trait for convenience` comment above
  `pub use offload::{HandleKey, OffloadHandle, OffloadSerializable, Offloadable};` is a copy-paste of the
  genuine `async_trait` comment below it. Replace with an accurate label, e.g.
  `/// Typed offload handle and serializable-contract primitives.` Trivial doc fix.

### Cross-cutting
- **D-13:** **External contract unchanged.** No signature or runtime-behavior change to the derivation's
  public surface. OFFLOAD-01/02 stay satisfied; this phase only tightens internal correctness/diagnostics.
- **D-14:** **Gate discipline (macro-emission blindspot).** Macro-emission changes require the trybuild UI
  gate **plus** the full changed-crates test run — per-crate `cargo` runs miss broken macro output because
  only the fixtures expand the attribute. Emit only `::ferro::*` paths. Run CI's exact clippy command
  (`cargo clippy --all --all-targets -- -D warnings`); CI also runs Docs (`cargo doc -Dwarnings`) and
  cargo-deny. `cargo test --all-features` can ENOSPC — check `df` and clean `target/` before the full gate.
- **D-15:** **No new dependencies.**

### Claude's Discretion
- WR-02 fix **mechanism** (per-loop idempotency vs. guarded clear) — locked to the D-04 invariant and the
  D-05 constraint, but the concrete implementation is the planner's call after the required call-ordering
  analysis.
- Exact `.stderr` fixture wording for the WR-01 spanned error (must name the double-reference constraint).
- Precise phrasing of the corrected D-12 doc comment.

### Established Patterns
- Macro emits fully-qualified `::ferro::*` paths throughout (path-convention; keep it).
- `#[offload]` derives onto `ferro-queue` (Job/worker), no second mechanism — the hardening must not introduce one.
- `OffloadHandle` phantom is `PhantomData<fn() -> T>` so the handle is `Send + Sync` and serde-skips `T` — the hand-written impls exploit the same property to avoid `T` bounds.

### Integration Points
- `WorkerLoop::from_registry` (`ferro-queue/src/worker.rs`) drives `apply_registrars` (Vec path) + inventory drain (WR-02 blast radius).
- `serve` boot path calls `has_registered_jobs` / `registered_queue_names` to decide worker spawn — the WR-02 fix must preserve those signals (D-05).
