## Summary

Phase 249.6 closes five latent defects in the `#[offload]` macro/handle path — all are
internal correctness gaps with no external contract changes. The research reads every
relevant source file directly and answers the five implementation-knowledge gaps the
CONTEXT.md left for the planner.

The overarching finding is that two of the five fixes are simpler than their review
descriptions suggest: WR-02's double-registration surface is already very narrow
because `from_registry` builds a fresh `HashMap` per call and `HashMap::insert` is
per-key idempotent; WR-03's "serialization failure" wording in SC#3 is a misnomer —
the `.expect()` is on `App::make` (missing binding), not on serialization — so the
fix and test target a missing-service scenario, not a JSON error.

**Primary recommendation:** implement the five fixes in strict order of test surface
(WR-01 compile-fail first, 245-WR-01 compile-pass second, WR-02 runtime invariant
third, WR-03 runtime missing-binding fourth, IN-01 doc grep last) to catch regressions
at the earliest possible stage.

## WR-01: `owned_type` — spanned error for double-reference / `&Ref<'a>` forms

### Current code (verified at `ferro-macros/src/offload.rs:80-101`)

```rust
pub(crate) fn owned_type(ty: &Type) -> syn::Result<TokenStream2> {
    match ty {
        Type::Reference(r) => {
            if r.mutability.is_some() { /* returns Err — already handled */ }
            match r.elem.as_ref() {
                Type::Path(p) if p.path.is_ident("str") => Ok(quote! { String }),
                Type::Slice(s) => { /* -> Vec<T> */ }
                other => Ok(quote! { #other }),  // ← BUG: emits T verbatim, no diagnostic
            }
        }
        other => Ok(quote! { #other }),
    }
}
```

The `other` arm of the inner `match r.elem.as_ref()` emits `#other` (the inner type)
without checking whether `other` is itself a `Type::Reference`. For `&&T` the inner type is
`&T` (a `Type::Reference`), and for `&Ref<'a, T>` it is a `Type::Path` that expands to a
reference guard. Both pass silently, producing a derived struct field with a borrowed type
that cannot implement `Serialize`.

### Fix

Replace the `other =>` arm with:

```rust
other => {
    if matches!(other, Type::Reference(_)) {
        return Err(syn::Error::new_spanned(
            ty,
            "#[offload] parameters must be fully owned — \
             double references (&&T) and reference-wrapping types (&Ref<'a>) \
             are not supported as job payload fields",
        ));
    }
    Ok(quote! { #other })
}
```

`syn::Error::new_spanned(ty, …)` uses `ty` — the outer `&T` token — as the span so the
diagnostic points at the full parameter type in source, matching the `mut_ref_param.rs`
pattern exactly.

### Trybuild fixture authoring (VERIFIED)

**Runner:** `ferro-macros/tests/offload_macro.rs` — a single `#[test]` named
`offload_macro_ui` that calls:
```rust
let t = trybuild::TestCases::new();
t.pass("tests/ui/offload/pass/*.rs");
t.compile_fail("tests/ui/offload/fail/*.rs");
```
All `fail/*.rs` files are picked up via glob; adding `double_ref_param.rs` to
`tests/ui/offload/fail/` is sufficient.

**Fixture structure:** A compile-fail fixture needs only `#[service(Svc)]` + `#[async_trait]`
+ the `#[offload]` method — exactly the shape of `mut_ref_param.rs`. It does NOT need a
concrete `impl`, a running `App`, or any DB wiring. The `Svc` impl is omitted (the
compilation fails before it matters).

**Example new fixture** (`double_ref_param.rs`):
```rust
//! Compile-fail: #[offload] param is &&T (double reference) — no spanned diagnostic before fix.
#![allow(unused_imports, dead_code)]

extern crate ferro_rs as ferro;
extern crate serde;

use ferro::{async_trait, service};
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Inner;

#[derive(Default)]
pub struct Svc;

#[service(Svc)]
#[async_trait]
pub trait MyService {
    #[offload]
    async fn process(&self, data: &&Inner);
}

fn main() {}
```

**Generating `.stderr`:** Run with `TRYBUILD=overwrite` after implementing the fix:
```bash
TRYBUILD=overwrite cargo test -p ferro-macros --test offload_macro
```
This writes the `.stderr` snapshot automatically. The executor must run this command,
inspect the generated file, and verify the message contains the expected wording before
committing.

**Key observation:** The `mut_ref_param.rs` `.stderr` format is a single compact
`error:` block with the span pointing at the parameter type (not at the `#[service]` macro
span). The WR-01 error, emitted from `owned_type` via `syn::Error::new_spanned`, will
propagate as a `compile_error!` call at the site of the `#[service]` macro — the exact
form depends on how `service_impl` converts `syn::Result` to `compile_error!`.
The `.stderr` must therefore be generated (not hand-crafted) using `TRYBUILD=overwrite`.

## WR-02: Double-registration invariant

### Source structure (VERIFIED)

**`ferro-queue/src/db.rs`** contains:
- `JOB_REGISTRARS: std::sync::Mutex<Vec<RegisterFn>>` (line 25) — the runtime Vec.
- `Queue::register::<J>()` (line 65-73) — pushes a closure into the Vec.
- `Queue::apply_registrars(&mut w)` (line 111-115) — iterates the Vec calling each closure.
- `Queue::has_registered_jobs()` (line 79-85) — reads `!JOB_REGISTRARS.lock().is_empty() || inventory has entries`.
- `Queue::registered_queue_names()` (line 91-106) — reads `JOB_REGISTRARS.lock().is_empty()` to decide whether to insert `"default"`.

**`ferro-queue/src/worker.rs:215-224`** — `WorkerLoop::from_registry`:
```rust
pub fn from_registry(config: WorkerConfig) -> Self {
    let mut w = Self::new(config);                     // fresh HashMap
    crate::db::Queue::apply_registrars(&mut w);        // runtime Vec path
    for entry in inventory::iter::<crate::db::JobRegistrarEntry> {
        (entry.register)(&mut w);                      // inventory path
    }
    w
}
```

**`WorkerLoop::register::<J>()`** (line 180-205): inserts into `self.handlers: HashMap<String, JobHandler>` keyed by `std::any::type_name::<J>()`. `HashMap::insert` is idempotent per key — inserting the same key twice overwrites with an identical handler, leaving the count at 1.

**`WorkerLoop::registered_job_count()`** (line 232-234): returns `self.handlers.len()`. This is a `#[doc(hidden)]` test-support accessor already present in the tree. No new accessor needed for the WR-02 test.

### Call ordering analysis (VERIFIED from `framework/src/app.rs`)

In **both** the `serve` path and the `run_worker` path:

1. `has_registered_jobs()` is called **before** `from_registry`.
2. `registered_queue_names()` is called **before** `from_registry`.
3. `from_registry` is called once per boot path.

In `spawn_in_process_worker()` (serve path, line 488-520):
```
has_registered_jobs()          ← line 488: gate check
registered_queue_names()       ← line 513: build config
WorkerLoop::from_registry(...)  ← line 515
```

In `run_worker()` (worker path, line 532-560):
```
registered_queue_names()        ← line 535: effective_queues
registered_queue_names()        ← line 545: known (warning check)
WorkerLoop::from_registry(...)  ← line 556
```

Conclusion: `has_registered_jobs` and `registered_queue_names` are called before
`from_registry`, not after. A destructive `clear()` of `JOB_REGISTRARS` inside
`apply_registrars` would therefore not affect these pre-calls. However, D-05 notes
correctly that a second `from_registry` (e.g. in tests) after a first has cleared the Vec
would find it empty — the `has_registered_jobs` signal is permanently destroyed. This is
the deeper concern.

### Recommended mechanism: per-loop idempotency (no `clear()`)

`HashMap::insert` is already idempotent per key. The only observable double-registration
today is on the inventory path (each `from_registry` call re-iterates `inventory::iter` —
a static collection that cannot be drained). The runtime Vec path (`apply_registrars`)
is equally re-applied on each `from_registry`. Since each `from_registry` builds a
**fresh** `WorkerLoop` with a **fresh** `HashMap`, re-running the registrars only
overwrites map entries with identical values — the resulting `handlers.len()` is still 1
per distinct job type.

The invariant (SC#2) is therefore **already satisfied by construction** for the inventory
path. For the runtime Vec path it is also satisfied because `HashMap::insert` is idempotent
and each `from_registry` starts with an empty map. The gap is that there is no test
asserting this property.

**Recommended fix:** Add a test in `ferro-queue/tests/offload_round_trip.rs` (or a new
file `ferro-queue/tests/registration_idempotency.rs`) that calls `from_registry` twice and
asserts `registered_job_count()` is the same after each call. No source change to
`apply_registrars` or `JOB_REGISTRARS` is needed — the invariant already holds.

**If the planner judges a defensive source hardening desirable** (belt-and-suspenders,
not required by correctness): add a `seen` `HashSet` inside `apply_registrars` or inside
`from_registry` itself that skips entries already in the handlers map by key. This is the
"per-loop idempotency" mechanism and is safe because it reads the map rather than
destroying the Vec.

### Test shape (VERIFIED: existing accessor is usable)

```rust
// Two calls to from_registry — each job registers exactly once.
inventory::submit! {
    JobRegistrarEntry {
        register: |w: &mut WorkerLoop| { w.register::<InventoryJob>(); },
        name: "InventoryJob",
        queue: None,
    }
}

let w1 = WorkerLoop::from_registry(WorkerConfig::default());
let count1 = w1.registered_job_count();

let w2 = WorkerLoop::from_registry(WorkerConfig::default());
let count2 = w2.registered_job_count();

assert_eq!(count1, count2, "second from_registry must not double-register");
assert!(count1 >= 1, "at least InventoryJob registered");
```

The `InventoryJob` in `offload_round_trip.rs` is already submitted to inventory — the new
test can reuse it (same binary, same inventory collection).

## WR-03: Panic → `Err` at both generated handle sites

### Exact emission (VERIFIED at `ferro-macros/src/offload.rs:376-404`)

Two sites both currently use `.expect(#expect_msg)`:

**Site 1 — `handle()`** (lines 382-386):
```rust
async fn handle(&self) -> ::std::result::Result<(), ::ferro::queue::Error> {
    let svc = ::ferro::App::make::<dyn #trait_ident>()
        .expect(#expect_msg);
    #call_expr
}
```

**Site 2 — `handle_with_value()`** (lines 394-403):
```rust
async fn handle_with_value(
    &self,
) -> ::std::result::Result<
    ::std::option::Option<::ferro::serde_json::Value>,
    ::ferro::queue::Error,
> {
    let svc = ::ferro::App::make::<dyn #trait_ident>()
        .expect(#expect_msg);
    #value_capture_expr
}
```

Both return `Result<_, ::ferro::queue::Error>`, so `?` composes directly.

### Variables in scope at both sites (VERIFIED)

At the point where these `quote!` blocks are built (inside `emit_job_items`), the
following are in scope:
- `#job_ident_str` — the derived job struct name as a string literal (line 237)
- `#expect_msg` — the human-readable message (line 316-319)
- `#trait_ident` — the trait identifier
- `#call_expr` / `#value_capture_expr` — already-built token streams

The replacement:
```rust
let svc = ::ferro::App::make::<dyn #trait_ident>()
    .ok_or_else(|| ::ferro::queue::Error::job_failed(#job_ident_str, #expect_msg))?;
```
compiles at both sites without any additional bindings. `Error::job_failed` is confirmed
at `ferro-queue/src/error.rs:82` with signature `fn job_failed(job: impl Into<String>, message: impl Into<String>) -> Self`.

### SC#3 semantic clarification (IMPORTANT)

SC#3 says "returns `Err` on serialization failure" but the `.expect()` is on
`App::make` — a **service resolution** failure (missing binding in the container), not a
JSON serialization failure. Serialization failure in `handle_with_value` is already handled
gracefully: `::ferro::serde_json::to_value(&v).ok()` yields `None` on error (no panic,
no `Err` — it is intentionally fallible-but-silent per the Phase 246 design comment at
line 286).

The correct restatement: SC#3 means "a missing service binding is recorded as a failed job
(returning `Err`) rather than panicking (which would be caught by the panic-isolation
wrapper, exhausting retries without a useful error record)."

### Test approach

The existing `offload_round_trip.rs` tests use sync mode with `QUEUE_CONNECTION=sync`.
The missing-binding scenario requires `App::make` to return `None` — which means no
concrete service was registered in the container. In a test that never calls
`App::singleton(Svc)`, `App::make::<dyn MyService>()` returns `None`.

The test shape: dispatch a derived offload job in sync mode with no concrete service
registered; assert the dispatch returns `Err` (not a panic). Because the panic-isolation
wrapper in the worker catches panics and converts them to `Err`, the distinction between
"panic turned into Err" and "proper Err from .ok_or_else" is not observable at the
dispatch level in sync mode (sync mode calls `handle()` directly via `dispatch_immediately`
which does not wrap in `catch_unwind`). A test can verify the `Err` surface either
directly (if the test fixture arranges a missing binding) or by asserting no panic via
`std::panic::catch_unwind`.

**Simpler approach:** add a compile-pass trybuild fixture that exercises the generated code
path with a type that has a correct container binding, and a separate unit test in
`ferro-queue` that constructs the `Error::job_failed` variant and confirms its `Display`.
The SC#3 behavioral assertion (Err, not panic) is best documented as a code-level property
verified by inspection: the `?` operator cannot panic.

**If a runtime behavioral test is required:** the fixture must use the actual `ferro::App`
container, which requires a `tokio::test` and calling `App::singleton(Svc {})` to
optionally register (or not register) the service. This is feasible in
`ferro-queue/tests/` if the test file adds a `use ferro` dependency — but that couples
`ferro-queue` to `framework`, which is currently a one-direction dependency. Check
`ferro-queue/Cargo.toml` before adding this test; it may need to live in
`framework/tests/` instead.

## 245-WR-01: `OffloadHandle<T>` — remove over-broad derives

### Current code (VERIFIED at `ferro-queue/src/offload.rs:71-96`)

```rust
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct OffloadHandle<T> {
    key: HandleKey,
    #[serde(skip)]
    _phantom: PhantomData<fn() -> T>,
}
```

The `#[derive(...)]` macro injects `T: Debug + Clone + PartialEq + Eq` bounds into the
generated impls. These bounds exceed `OffloadSerializable` (which requires only
`Serialize + DeserializeOwned`).

### HandleKey traits (VERIFIED at `ferro-queue/src/offload.rs:40-53`)

`HandleKey` derives `Debug, Clone, Serialize, Deserialize, PartialEq, Eq`. All four
traits needed by the hand-written impls are available on `HandleKey` without any `T` bound.

### Phantom bound (VERIFIED)

`PhantomData<fn() -> T>` carries no `T` in its data; the function-pointer form makes the
phantom `Send + Sync` regardless of `T`. None of `Clone`, `Debug`, `PartialEq`, or `Eq`
require a bound on `T` for this phantom — `PhantomData<fn() -> T>` is `Copy`, `Clone`,
`Debug`, `PartialEq`, and `Eq` unconditionally (they are all implemented for
`PhantomData<T>` for any `T` in std).

### Exact hand-written impls

```rust
// Remove Debug, Clone, PartialEq, Eq from #[derive(...)]; keep Serialize, Deserialize.
#[derive(Serialize, Deserialize)]
pub struct OffloadHandle<T> {
    key: HandleKey,
    #[serde(skip)]
    _phantom: PhantomData<fn() -> T>,
}

impl<T> Clone for OffloadHandle<T> {
    fn clone(&self) -> Self {
        Self {
            key: self.key.clone(),
            _phantom: PhantomData,
        }
    }
}

impl<T> std::fmt::Debug for OffloadHandle<T> {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("OffloadHandle")
            .field("key", &self.key)
            .finish()
    }
}

impl<T> PartialEq for OffloadHandle<T> {
    fn eq(&self, other: &Self) -> bool {
        self.key == other.key
    }
}

impl<T> Eq for OffloadHandle<T> {}
```

None of these bounds `T`. `PhantomData<fn() -> T>` is not touched in any impl body
(always reconstructed as `PhantomData` or ignored), so no `T` bound is needed.

### SC#4 test fixture location (VERIFIED)

The existing `ferro-macros/tests/ui/offload/pass/offload_handle.rs` tests
`Offloadable<Output = Report>` where `Report` derives `Debug, Clone, Serialize,
Deserialize`. To prove SC#4, add a second test (or extend the same fixture) with a
success type that is `Serialize + DeserializeOwned` but not `Clone + Debug + Eq`:

```rust
//! In offload_handle.rs or a new pass/offload_handle_serde_only.rs

// A type with only the OffloadSerializable contract — no Clone, no Debug, no Eq.
#[derive(Serialize, Deserialize)]
pub struct SerdeOnly {
    pub x: i32,
}

// Structural proof: OffloadHandle<SerdeOnly> supports Clone, Debug, PartialEq
// even though SerdeOnly does not.
fn _check(h: OffloadHandle<SerdeOnly>) {
    let _ = h.clone();
    let _ = format!("{:?}", h);
    let h2 = h.clone();
    let _ = h == h2;
}
```

Adding this directly to the existing `offload_handle.rs` fixture is the cleanest option.
The file already has `fn main()` with structural proof patterns; the new `_check` function
extends it.

## Common Pitfalls

### Pitfall 1: TRYBUILD=overwrite before the fix is implemented

Running `TRYBUILD=overwrite` with the existing (unfixed) `owned_type` will overwrite the
`.stderr` snapshot with an empty or wrong error. Always implement the fix first, then
bless the snapshot.

**Prevention:** Implement `owned_type` change → build → run the overwrite command.

### Pitfall 2: Confusing the two `PhantomData` variance forms

`PhantomData<T>` and `PhantomData<fn() -> T>` both allow unconditional `Clone`/`Debug`/
`PartialEq`/`Eq` in the hand-written impls, but `PhantomData<T>` adds a drop-check
obligation and restricts `Send`/`Sync`. The existing phantom is `fn() -> T` — do not
change it to `PhantomData<T>` as part of this fix.

**Prevention:** Copy the phantom variant from the existing struct definition verbatim.

### Pitfall 3: Forgetting the second `.expect()` site (WR-03)

The review cited one `.expect()`. Phase 246 added `handle_with_value()`, giving a second
site at line 400. Both must be converted in the same commit or the second site will panic
in production while the first returns `Err`.

**Prevention:** Search `ferro-macros/src/offload.rs` for `.expect(#expect_msg)` after the
fix and confirm zero matches remain.

### Pitfall 4: Confusing the `TestCases` glob pickup

`t.compile_fail("tests/ui/offload/fail/*.rs")` uses `glob` — the new fixture file must be
in exactly `tests/ui/offload/fail/` (not a subdirectory) and must end in `.rs`. The
`.stderr` file must have the same base name.

### Pitfall 5: `cargo test --all-features` ENOSPC

Per project memory, `cargo test --all-features` recurrently fills disk. Check `df -h`
before running the full gate; clean `target/` if needed.
