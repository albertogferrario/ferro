  <action>
**In `ferro-json-ui/src/view.rs`:**

1. Add a `data` field to `JsonUiView`:
   ```
   #[serde(default, skip_serializing_if = "serde_json::Value::is_null")]
   pub data: serde_json::Value,
   ```
   Place it after `title` and before `components`. Default to `Value::Null` in `new()`.

2. Add a builder method:
   ```
   pub fn data(mut self, data: serde_json::Value) -> Self {
       self.data = data;
       self
   }
   ```

3. Update existing tests that construct JsonUiView to include `data: serde_json::Value::Null` where struct literals are used (not builder calls — builder calls use `new()` which sets the default). Add tests:
   - View with data serializes data field
   - View without data omits data field (skip_serializing_if is_null)
   - Round-trip with data preserves nested structures
   - Builder `.data()` method works

**In `framework/src/json_ui/mod.rs`:**

1. Update `JsonUi::render()` signature: Keep the existing `render(view: &JsonUiView, data: &serde_json::Value)` signature for backwards compatibility, but merge the explicit data parameter into the view's embedded data before rendering. If the view already has data AND the explicit data is also non-null, merge them (explicit data takes precedence via `serde_json::Value` merge). If either is null, use the other.

   Actually, simpler: Change the approach. The `data` parameter in render() IS the data. Set it on the view JSON output directly. The view's own `.data` field is for when users build views with embedded data. When both exist, the explicit parameter wins (it's the "live" data from the handler).

   Implementation: In the render body, when building the HTML, serialize the data parameter as `data-props` (already done). No change needed for the HTML scaffold — it already embeds data in `data-props`. The view's `.data` field will be included in `data-view` attribute's JSON naturally since it's part of JsonUiView.

   Actually, looking at the current code more carefully: `render()` takes `data` separately and embeds it as `data-props`. The view JSON goes into `data-view`. So the view's `.data` field ends up in `data-view` while the render parameter ends up in `data-props`. This is fine — the Phase 28 renderer will use `data-props` for resolution. The view's `.data` field is there for `render_json()` and API consumers who want a self-contained view.

   Keep the render() and render_with_config() signatures unchanged. Update render_json() to merge the view's embedded data with the explicit data parameter: if explicit data is non-null use it, else use view.data.

2. Update `render_json()` to prefer explicit data over embedded:
   ```rust
   pub fn render_json(view: &JsonUiView, data: &serde_json::Value) -> Response {
       let effective_data = if data.is_null() { &view.data } else { data };
       let payload = serde_json::json!({
           "view": view,
           "data": effective_data,
       });
       Ok(HttpResponse::json(payload))
   }
   ```

3. Update the `sample_view()` test helper to work with the new data field (it uses `new()` builder so it should already work if default is Null).

4. Add a test that verifies render_json uses explicit data when provided, falls back to view.data when explicit data is null.
