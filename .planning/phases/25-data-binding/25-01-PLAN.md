<task type="auto">
  <name>Task 1: Create data path resolver module</name>
  <files>ferro-json-ui/src/data.rs, ferro-json-ui/src/lib.rs</files>
  <action>
Create `ferro-json-ui/src/data.rs` with:

1. A `resolve_path(data: &serde_json::Value, path: &str) -> Option<&serde_json::Value>` function that resolves a slash-separated path against a JSON value. Path format: `/segment/segment/...` where segments are object keys or array indices (numeric strings). Leading slash is required. Empty path or "/" returns the root value. Return None if any segment fails to resolve.

2. A `resolve_path_string(data: &serde_json::Value, path: &str) -> Option<String>` convenience function that resolves the path and converts the result to a string representation. For String values return the string directly, for numbers/booleans use `.to_string()`, for null return None, for objects/arrays return the JSON serialization.

3. Unit tests covering:
   - Simple key resolution: `/name` on `{"name": "Alice"}` → Some("Alice")
   - Nested key resolution: `/user/name` on `{"user": {"name": "Bob"}}` → Some("Bob")
   - Array index resolution: `/users/0/name` on `{"users": [{"name": "Carol"}]}` → Some("Carol")
   - Missing key returns None: `/missing` on `{"name": "Alice"}` → None
   - Empty path returns root: `""` returns root value (this is resolve_path behavior, resolve_path_string would serialize it)
   - Root slash "/" returns root value
   - Numeric value resolution: `/count` on `{"count": 42}` → resolves to Value::Number
   - Boolean resolution: `/active` on `{"active": true}` → resolves to Value::Bool
   - Null value: `/deleted_at` on `{"deleted_at": null}` → resolve_path returns Some(&Value::Null), resolve_path_string returns None
   - Deep nesting: `/a/b/c/d` works
   - Path with invalid array index returns None

Do NOT use any external JSONPath library — the path format is intentionally simple (slash-separated segments, not full JSONPath `$.store.book[0].title` syntax). This keeps the implementation trivial and the paths easy to generate.

Add `pub mod data;` to `ferro-json-ui/src/lib.rs` and add `pub use data::{resolve_path, resolve_path_string};` to the re-exports.
  </action>
  <verify>cargo test -p ferro-json-ui -- data:: --nocapture</verify>
  <done>resolve_path and resolve_path_string functions pass all test cases. Module exported from lib.rs.</done>
</task>

<task type="auto">
  <name>Task 2: Add data_path to form field components</name>
  <files>ferro-json-ui/src/component.rs</files>
  <action>
Add an optional `data_path` field to form field component props that support data binding for pre-filling values from handler data. Add the field to:

- `InputProps`: `#[serde(default, skip_serializing_if = "Option::is_none")] pub data_path: Option<String>` — When set, the renderer resolves this path against the view data to pre-fill the input value. This complements `default_value` (static) with dynamic data binding.
- `SelectProps`: Same field — Pre-fills the selected option from data.
- `CheckboxProps`: Same field — Pre-fills checked state from data (expects boolean value at path).
- `SwitchProps`: Same field — Same as Checkbox.

Add doc comments to each field: `/// Data path for pre-filling from handler data (e.g., "/data/user/name").`

Place the `data_path` field after `default_value` for Input/Select, and after `checked` for Checkbox/Switch, to maintain logical field ordering.

Update the existing tests that construct these component props to include `data_path: None` where needed. Add one new test per component type verifying `data_path` serializes and round-trips correctly when set to `Some("/data/user/field_name".to_string())`.

Do NOT add data_path to non-form components (Card, Table, Alert, etc.) — Table already has `data_path` and other components don't pre-fill from data.
  </action>
  <verify>cargo test -p ferro-json-ui --nocapture</verify>
  <done>data_path field present on Input, Select, Checkbox, Switch props. All existing tests pass. New round-trip tests pass for data_path serialization.</done>
</task>
