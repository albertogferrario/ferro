# Phase 163.1: Codemod Multi-Root Handler Fix — Research

**Researched:** 2026-05-17
**Domain:** ferro-cli codemod (`json_ui_migrate_v1.rs`), integration test fixtures
**Confidence:** HIGH — all findings verified by direct source inspection

## Summary

Phase 163.1 closes the WR-01 finding from 163-REVIEW.md. The `ferro json-ui:migrate-v1` codemod in `ferro-cli/src/commands/json_ui_migrate_v1.rs` silently selects only the first top-level node as `root` when a v1 handler passes multiple elements in its top-level `vec![...]`. The remaining elements are inserted into `elements` but are unreachable from `root` — a spec that looks valid but renders nothing beyond the first node.

The fix is Option B from the code review: check `top_ids.len() != 1` immediately after `flatten_nodes` returns, and return `HandlerResult::Unsupported` before any `Spec::builder()` / `spec` Map construction. This routes through the existing TODO-marker path, which the integration tests already validate for the runtime-branch case. No new code paths, no new components, no catalog changes.

Three concrete deliverables: (1) a 4-line change in `try_migrate_handler`, (2) deletion of `out_auth_login_form.json`, (3) a rewrite of `codemod_one_handler_emits_spec_and_rewrites_controller` that (a) asserts TODO marker for the existing `in_auth.rs` multi-root fixture and (b) asserts clean JSON for a new single-root fixture.

**Primary recommendation:** Insert `if top_ids.len() != 1 { return HandlerResult::Unsupported; }` at line 254 (immediately after `let top_ids = flatten_nodes(...)`) — before the spec `Map` is constructed.

## Research Item 1: Exact Insertion Point in `try_migrate_handler`

**File:** `ferro-cli/src/commands/json_ui_migrate_v1.rs`

The function `try_migrate_handler` (line 225) operates in this sequence:

1. **Lines 230-231** — Tokenise the block and gate on `JsonUiView` presence.
2. **Lines 236-241** — Return `Unsupported` for `Spec::builder` patterns and dynamic keys.
3. **Lines 242-244** — Return `Unsupported` for runtime branches via `has_runtime_branch`.
4. **Lines 246-248** — Extract the `ExtractedView` via `extract_view_call`; return `Unsupported` if absent.
5. **Lines 251-253** — Build the flat element map:
   ```rust
   let mut elements = Map::<String, Value>::new();
   let top_ids = flatten_nodes(view.nodes, &mut elements);
   ```
6. **Lines 254-256** — Current code (the bug site):
   ```rust
   let Some(root) = top_ids.first().cloned() else {
       return HandlerResult::Unsupported;
   };
   ```
   This currently returns `Unsupported` only when `top_ids` is empty; it silently accepts `top_ids.len() > 1` and sets `root` to only the first ID.
7. **Lines 258-286** — Constructs the `spec` Map and returns `HandlerResult::Migrated(...)`.

**Insertion point:** Replace lines 254-256 with a two-stage check:

```rust
// Reject zero-root (empty vec) AND multi-root (>1 top-level nodes).
if top_ids.len() != 1 {
    return HandlerResult::Unsupported;
}
let root = top_ids.into_iter().next().expect("checked len == 1");
```

This is the minimal change — it sits between `flatten_nodes` (line 253) and the `spec` Map construction (line 258). No partial spec is built for the multi-root case because the `Map::new()` at line 251 and the `flatten_nodes` call at line 253 happen before the check, but `elements` is a local variable that is simply dropped when the function returns `Unsupported`. The spec `Map` at line 258 is never touched.

**VERIFIED** by reading `ferro-cli/src/commands/json_ui_migrate_v1.rs` lines 225-286.

## Research Item 2: `HandlerResult::Unsupported` Path — Caller Verification

The `MigrationVisitor::visit_item_fn` method (lines 188-205) handles the return value of `try_migrate_handler`:

```rust
match try_migrate_handler(&item.block, &handler_name, &self.controller_path) {
    HandlerResult::Migrated(spec_path, spec_json) => {
        self.specs.push(HandlerMigration { ... });
    }
    HandlerResult::Unsupported => {
        self.todo_handlers.push(handler_name);
    }
    HandlerResult::NotAHandler => {}
}
```

`HandlerResult::Unsupported` pushes the handler name into `self.todo_handlers`. The `finalize` method (lines 156-185) then processes `todo_handlers` first:

```rust
for handler in &self.todo_handlers {
    let marker = "// TODO: ferro json-ui:migrate-v1 could not auto-translate this handler\n";
    rewritten = inject_todo_above_handler(&rewritten, handler, marker);
}
for migration in &self.specs {
    rewritten = rewrite_handler_body(...)?;
}
let specs: Vec<SpecOutput> = self.specs.into_iter().map(|m| SpecOutput { ... }).collect();
```

Critically, `todo_handlers` entries are ONLY processed through `inject_todo_above_handler` — they never appear in `self.specs` and therefore never produce a `SpecOutput`. The `outputs.specs` loop in `run()` (lines 64-74) that calls `std::fs::write(spec_path, json)` will not be entered for unsupported handlers. **No JSON spec file is emitted for `HandlerResult::Unsupported`.** [VERIFIED: direct read of source lines 156-185]

The `inject_todo_above_handler` function (lines 666-679):
- Finds `fn {handler_name}(` via `src.find(&needle)`
- Walks back to the line start with `src[..fn_pos].rfind('\n')`
- Inserts the marker line above the `fn` line
- Does NOT modify the function body — it stays intact

**Conclusion:** Returning `HandlerResult::Unsupported` for multi-root inputs will: (a) insert the TODO marker above `fn login_form(`, (b) leave the original v1 body intact, (c) produce no JSON file. This is the correct behavior for Phase 163.1.

## Research Item 8: Edge Cases

**Empty top-level list (`top_ids.is_empty()`):**

The current code at lines 254-256 already handles the empty case:
```rust
let Some(root) = top_ids.first().cloned() else {
    return HandlerResult::Unsupported;
};
```

The proposed replacement `if top_ids.len() != 1 { return HandlerResult::Unsupported; }` handles BOTH `len() == 0` (empty) AND `len() > 1` (multi-root) under the same check. This is the correct formulation — both cases are structurally invalid for a single-root v2 spec, so both should return `Unsupported`.

**Can `flatten_nodes` produce an empty `top_ids`?** Yes — if `view.nodes` is an empty `Vec`, `flatten_nodes` returns an empty `Vec`. The existing check handles this correctly and the new `!= 1` check maintains that behavior.

**Is `top_ids.is_empty()` already rejected upstream?** No. `extract_view_call` → `parse_node_list` returns `Some(Vec<ExtractedNode>)` regardless of the vec's length (it only fails if parsing fails). An empty `vec![]` in the source would succeed through `parse_node_list` and produce an empty `top_ids`. The `len() != 1` check is the correct single gate. [VERIFIED: reading `parse_node_list` lines 434-444 — no length check]

## Common Pitfalls

### Pitfall 1: `out_auth.rs` fixture left intact when it should also change

**What goes wrong:** `out_auth.rs` currently contains `JsonUi::render_file(...)` — the expected output after a successful migration. After the fix, `in_auth.rs` is Unsupported so the controller is NOT rewritten to `render_file`; instead it gets a TODO marker and the original body. The `out_auth.rs` fixture is only referenced by `codemod_one_handler_emits_spec_and_rewrites_controller` (line 85) and `codemod_idempotent_on_migrated_file` (indirectly — no, actually idempotent test does not compare against `out_auth.rs`). The main test must stop asserting against `out_auth.rs`. But `out_auth.rs` can remain as a fixture for other purposes or be deleted — it is not referenced by any other test.

**Why it happens:** The rewrite of the test removes the `out_auth.rs` comparison; the fixture becomes dead but does not cause a compile error.

**How to avoid:** Either delete `out_auth.rs` alongside `out_auth_login_form.json`, or retain it for documentation. Given "delete old code completely" project convention, delete both `out_auth.rs` and `out_auth_login_form.json`. They are unused after the test rewrite.

### Pitfall 2: `codemod_dry_run_does_not_write` breaks if controller modification is checked

**What goes wrong:** `codemod_dry_run_does_not_write` uses `in_auth.rs`. In dry-run mode, `run()` calls `print_dry_run` and returns without writing anything. After the fix, `in_auth.rs` is Unsupported — the dry-run output will be different (no spec printed, TODO marker printed to stdout), but the FILE assertions (`before == after` for controller, `!spec_path.exists()` for spec) remain correct. The test passes as-is.

**Verification:** Read `run()` lines 59-62: `if dry_run { print_dry_run(&outputs); return Ok(()); }` — dry-run exits before any `std::fs::write`. [VERIFIED]

### Pitfall 3: `codemod_idempotent_on_migrated_file` breaks due to second-run detection

**What goes wrong:** After the fix, first run of `in_auth.rs` inserts the TODO marker into the controller. Second run: `file_already_migrated` checks `raw_src.contains("// TODO: ferro json-ui:migrate-v1 could not auto-translate")` → true → returns `true` → codemod exits 0 with warning, no changes. The idempotent test asserts `after_first == after_second`. This holds because the second run makes no writes. The test passes as-is. [VERIFIED: `file_already_migrated` line 90]
