  <name>Task 1: Fix reconstruct_service_def to parse action details, guards, and transition guards</name>
  <files>ferro-mcp/src/tools/render_projection.rs</files>
  <action>
The current `reconstruct_service_def` function has critical gaps in its regex parsing. Fix these to enable accurate intent derivation through the MCP pipeline.

**Gap 1: Action builder chains (parse_and_add_actions)**
Currently only captures `ActionDef::new("name")`. Fix to also parse:
- `.transition_trigger("event_name")` → `action.transition_trigger = Some("event_name")`
- `.precondition("guard_name")` → `action.preconditions.push("guard_name")` (may appear multiple times)
- `.display_name("name")` → `action.display_name = Some("name")`
- `.input(InputDef::new("name", DataType::X, FieldMeaning::Y))` → `action.inputs.push(input)`

Approach: Instead of a single regex for `ActionDef::new("name")`, capture the full `.action(...)` expression (everything between `.action(` and its matching `)`), then apply sub-regexes within each captured block. Be careful with nested parentheses from InputDef::new calls — use a character-counting approach or match the outermost `.action(` to its closing `)` by tracking parenthesis depth.

Alternative simpler approach: After creating the basic action, scan the remaining content within the action expression for chained method patterns:
- `\.transition_trigger\("([^"]+)"\)` → set transition_trigger
- `\.precondition\("([^"]+)"\)` → add precondition (repeat for each match)
- `\.display_name\("([^"]+)"\)` → set display_name
- `\.input\(InputDef::new\("([^"]+)",\s*DataType::(\w+),\s*FieldMeaning::(\w+)\)\)` → add input

The key challenge is scoping these sub-regexes to the correct action block. A practical approach: extract each `.action(...)` block using parenthesis depth counting, then apply sub-regexes within that block.

**Gap 2: Transition guards (parse_state_machine)**
Currently captures `Transition::new("from", "event", "to")` but not the chained `.guard("name")`.
Fix: Update the transition regex to optionally capture `.guard("guard_name")`:
```
Transition::new\("([^"]+)",\s*"([^"]+)",\s*"([^"]+)"\)(?:\.guard\("([^"]+)"\))?
```
When capture group 4 is present, apply `.guard(cap[4])` to the Transition.

**Gap 3: Guard definitions on ServiceDef**
Currently not parsed at all. Add parsing for:
- `.guard(GuardDef::new("name"))` → `service.guard(GuardDef::new("name"))`
- Optionally: `.guard(GuardDef::new("name").display_name("Display"))` for completeness

Use a regex similar to the action pattern:
```
\.guard\(GuardDef::new\("([^"]+)"\)(?:\.display_name\("([^"]+)"\))?\)
```

**Validation after fix:**
Run existing tests to ensure no regressions: `cargo test -p ferro-mcp --all-features`

**Add unit tests for the new parsing:**
- Test reconstructing a service with transition_trigger on actions
- Test reconstructing a service with preconditions on actions
- Test reconstructing a service with inputs on actions
- Test reconstructing a service with guarded transitions
- Test reconstructing a service with GuardDef definitions
- Test the full order-like service (state machine + guarded transitions + actions with triggers/preconditions) reconstructs correctly and derives Process intent

These tests should use inline source strings (matching the existing test pattern in the file) and verify that the reconstructed ServiceDef has the expected action/guard/transition properties.

**Important:** Do NOT change the derive engine or any ferro-projections code. Only fix the MCP parser to correctly reconstruct what's already in the source files.

Add integration tests that exercise the MCP tools against the REAL projection files in the sample app. These tests prove the full pipeline works end-to-end: source file → regex parse → reconstruct ServiceDef → derive_intents → validate intent.

**Integration test structure:**
Create a test function for each projection that:
1. Reads the actual source file from `app/src/projections/{name}.rs`
2. Calls `reconstruct_service_def` with the file contents
3. Calls `derive_intents` on the reconstructed ServiceDef
4. Asserts the primary intent (index 0) matches the expected intent

Use a helper to locate the project root relative to the test binary. The app directory is at `{workspace_root}/app/`. The test can find the workspace root via `env!("CARGO_MANIFEST_DIR")` which gives the ferro-mcp crate directory, then navigate to `../app/`.

**Expected intent mapping (validate each):**
| Projection | Expected Primary Intent | Key Signals |
|------------|------------------------|-------------|
| user | Focus | EntityName + Email, few domain fields |
| todo | Focus or Browse | EntityName + FreeText (accept either) |
| api_key | Analyze or Track | Multiple DateTime fields (accept either) |
| order | Process | Guarded transitions, branching, transition triggers |
| product | Browse | EntityName + Category + OneToMany relationships |
| revenue_dashboard | Summarize | All read-only, Money/Percentage/Quantity |
| sales_analytics | Analyze | DateTime + numeric, read-only |
| feedback_form | Collect | >50% writable, write_only fields, action inputs |

For model-based projections (user, todo, api_key), accept any reasonable intent — the goal is verifying the pipeline works, not that simple models produce a specific intent. For hand-crafted projections (order, product, revenue_dashboard, sales_analytics, feedback_form), assert the EXACT expected primary intent — these are specifically designed to produce it.

4. As last resort: add IntentHint::Primary to override — but document WHY structural derivation failed

**Also validate:**

- Each reconstructed ServiceDef has the expected number of fields, relationships, actions, and state machine presence
