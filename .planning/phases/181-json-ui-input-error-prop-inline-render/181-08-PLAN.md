    ```markdown
    # Form Validation

    Server-rendered form validation in ferro pairs three primitives: a `ValidationError` value
    built during request handling, the `_flash.old._validation_errors` session key, and the
    JSON-UI form-control prop `error`. This page covers the four authoring patterns supported
    by `JsonUi::render_validation_error`, the per-field `$data` escape hatch, the flash
    round-trip on POST→GET, and the cross-field summary.

    All form-control components (`Input`, `Select`, `Textarea` via `Input { input_type: "textarea" }`,
    `Checkbox`, `CheckboxList`, `Switch`) accept an `error` prop of shape `Option<String>`. When set,
    the renderer emits a destructive-tone class chain (`border-destructive` or `ring-destructive` on
    the control) and an inline error paragraph below the field:

    ```html
    <p id="err-{field}" class="text-sm text-destructive">{error}</p>
    ```

    The paragraph carries `id="err-{field}"` so the control's `aria-describedby="err-{field}"`
    pairing announces the error to assistive technology.

    ## Blessed Path: `JsonUi::render_validation_error`

    Most handlers hand the framework a `ValidationError` value and let it plumb messages onto
    matching fields automatically. Match is by `name` or `field` prop on the element.

    ```rust
    use ferro::{JsonUi, ValidationError};

    #[handler]
    pub async fn show(req: Request) -> Response {
        let spec = build_spec();
        let data = serde_json::json!({});

        let mut ve = ValidationError::new();
        if let Some(stored) = req.session()
            .and_then(|s| s.get::<ValidationError>("_flash.old._validation_errors"))
        {
            ve = stored;
        }

        JsonUi::render_validation_error(&spec, &data, &ve)
    }
    ```

    On a POST handler that detected a validation failure:

    ```rust
    #[handler]
    pub async fn update(req: Request) -> Response {
        let data = req.input().await?;

        if invalid(&data) {
            return ValidationError::new()
                .add("email", "must be a valid email")
                .with_old_input(&data)
                .redirect_back(&req);
        }

        // ...persist and redirect to success path...
    }
    ```

    The redirect persists the `ValidationError` into `_flash.new._validation_errors`. The session
    middleware ages the flash on the next request, making it readable as `_flash.old._validation_errors`
    in the GET handler.

    ## Escape Hatch: Manual `$data` Binding

    When you need to bind an error to a different field name than the form control's `field`/`name`
    prop (e.g., cross-field validation surfaced under a synthetic key, or custom error placement),
    pass the error string through handler data and reference it from the spec via a `$data`
    expression:

    ```rust
    #[handler]
    pub async fn show(req: Request) -> Response {
        let mut data = serde_json::Map::new();
        data.insert(
            "overage_threshold_error".to_string(),
            serde_json::json!(req.validation_error("overage_threshold")),
        );
        let data = serde_json::Value::Object(data);

        let spec = Spec::builder()
            .element(
                "field_overage_threshold",
                Element::new("Input")
                    .prop("field", "overage_threshold")
                    .prop("label", "Soglia sovrapprezzo")
                    .prop("error", serde_json::json!({"$data": "/overage_threshold_error"})),
            )
            .build()?;

        JsonUi::render(&spec, &data)
    }
    ```

    `JsonUi::render` merges the runtime `data` argument into `spec.data` before resolving `$data`
    expressions, so the binding resolves whether the value lives in the spec's embedded data or
    in the handler-supplied data object.

    Use the escape hatch when the blessed path's `field`-keyed match does not fit — for example, a
    composite key like `{form_id}_{field}_error`, or when displaying an error string adjacent to a
    field that doesn't share a name with the validation key.

    ## Flash Round-Trip on POST → GET

    `ValidationError::with_old_input(&data).redirect_back(&req)` stores both the error map and the
    submitted form values into `_flash.new`. On the next request the session middleware promotes
    them to `_flash.old` where they are readable via `req.old("field")` and `req.validation_error("field")`.

    Restore the form values on GET re-render with `default_value`:

    ```rust
    Element::new("Input")
        .prop("field", "email")
        .prop("label", "Email")
        .prop(
            "default_value",
            serde_json::json!(req.old("email").or_else(|| Some(stored.email.clone()))),
        )
    ```

    Per project convention `req.old("field")` takes precedence — it restores what the user typed
    on a failed submission. The DB value is the fallback for the first GET.

    Cross-reference: `req.old(...)` returns `Option<String>`; `req.validation_error(...)` returns
    `Option<String>` (first message for the field). Use `JsonUi::render_validation_error` to plumb
    the full error map onto controls automatically, OR read individual fields with `req.validation_error(...)`
    and pass them through the manual `$data` escape hatch.

    ## Cross-Field Validation Summary

    A top-of-page summary banner is useful when the form has many fields and individual error `<p>`
    elements may not be immediately visible on scroll. Render a summary element conditionally:

    ```rust
    if req.has_validation_errors() {
        builder = builder.element(
            "validation_summary",
            Element::new("Alert")
                .prop("tone", "destructive")
                .prop("message", "Some fields need attention"),
        );
        root_children.push("validation_summary".to_string());
    }
    ```

    `req.has_validation_errors()` and `req.validation_error(field)` both read from the same
    session key (`_flash.old._validation_errors`) — they cannot disagree within a single handler.
    If you observe divergence, audit the handler for a helper that calls `req.session_mut().get_flash(...)`
    (which clears the key after reading) between the two calls.
    ```
