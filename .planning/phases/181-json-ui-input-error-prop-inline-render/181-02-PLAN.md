<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| handler → JsonUi::render | handler-supplied `serde_json::Value` data crosses into the JSON-UI rendering pipeline |
| handler → JsonUi::render_validation_error | handler-supplied `ValidationError` messages flow through `attach_errors` into `<p>` text content |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-181-W1-01 | Tampering | `render_with_config` merge_data | mitigate | Handler-supplied data merges into a CLONE of `spec.data` (per spec.rs:256-272). Original `spec` is not mutated. Handler keys win on collision (existing render_file precedent). No privilege escalation surface — handler already controls the data argument. |
| T-181-W1-02 | Information disclosure | error messages in `<p>` text | mitigate | All error message strings are interpolated via `html_escape` at the renderer layer (form.rs:309-315). Fix B writes the string into `props_obj["error"]` unchanged — escape happens at the consumer (renderer), not at the producer (attach_errors). No double-escape risk; no XSS surface introduced. |
| T-181-W1-03 | Spoofing | `$data` expression resolution | accept | `resolve_expressions` walks JSON paths under handler control; the merge does not grant access to data the handler didn't pass. No new attack surface vs. the pre-existing `render_file` merge pattern. |

**Overall security posture:** No new attack surface. Both fixes operate on data the handler already controls; HTML emission still passes through the locked `html_escape` chain at the renderer layer. Per RESEARCH §Security Domain: ASVS V5 (Input Validation) — already controlled at the renderer; no change needed at the pipeline layer.
</threat_model>
