    ```rust
    /// Render the `LiveFragment` builtin (Phase 260, D-04/D-05).
    ///
    /// `data` IS the pre-resolved snapshot `Value` (the caller resolved it via
    /// `ProjectionRuntime::read`, using `{}` when absent). The child template is
    /// rendered against it through the existing binding engine; the result is
    /// wrapped in a marked container carrying the projection channel so the client
    /// runtime can subscribe and swap `innerHTML` on delta.
    pub(crate) fn render_live_fragment(
        el: &Element,
        _spec: &Spec,
        data: &Value,
        _depth: usize,
    ) -> String {
        let props: LiveFragmentProps = match serde_json::from_value(el.props.clone()) {
            Ok(p) => p,
            Err(e) => {
                return format!(
                    "<!-- ferro-json-ui: failed to decode LiveFragment props: {} -->",
                    html_escape(&e.to_string())
                );
            }
        };

        let child_spec: crate::spec::Spec = match serde_json::from_value(props.template.clone()) {
            Ok(s) => s,
            Err(e) => {
                return format!(
                    "<!-- ferro-json-ui: LiveFragment template parse error: {} -->",
                    html_escape(&e.to_string())
                );
            }
        };

        // D-05: `data` (the snapshot) is the child template's data scope; the
        // existing render_spec_to_html engine performs all expression binding.
        let inner_html = super::render_spec_to_html(&child_spec, data);

        let channel = format!(
            "projection.{}.{}",
            html_escape(&props.projection),
            html_escape(&props.key)
        );

        format!(r#"<div data-live-fragment data-channel="{channel}">{inner_html}</div>"#)
    }
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| snapshot Value → child template render | Snapshot data is interpolated into HTML by the render engine |
| props.projection / props.key → data-channel attribute | Untrusted-shaped strings emitted into an HTML attribute the client parses |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-260-04 | Tampering (XSS) | snapshot values rendered into HTML | mitigate | The child template renders through the SAME `render_spec_to_html` path as every first-paint server render — all snapshot values flow through the existing ferro-json-ui escaping. No `render_live_fragment` code writes snapshot bytes into HTML directly; it delegates entirely to the engine. The delta re-render (Plan 04) reuses the identical path, so the escaping guarantee is single-sourced. |
| T-260-05 | Tampering (attribute injection) | `data-channel` attribute | mitigate | Both `props.projection` and `props.key` pass through `html_escape` before interpolation (Pitfall 3), so `"`, `<`, `&` cannot break out of the attribute and the client `querySelector('[data-channel="…"]')` cannot be subverted. Grep-asserted in acceptance criteria. |
| T-260-06 | Denial of Service | malformed props / template | accept | Decode/parse failures emit an inert HTML comment and return — no panic, no unbounded work. Bounded by child-spec size (application concern). |
</threat_model>
