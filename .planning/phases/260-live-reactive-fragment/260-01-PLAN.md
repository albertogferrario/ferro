<objective>
Add the renderer-agnostic re-render hook seam to `ferro-projection` (D-01, D-02). A new
`fragment_hook` field on `ProjectionRuntime<P>`, a consuming `with_fragment_renderer()`
builder (default `None` in `new`), and a synchronous hook invocation inside `apply_event`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| domain event → projection runtime | Events fold into persisted state; the hook exposes that state to a renderer closure |
| projection runtime → broadcast channel | The (later) fragment payload is broadcast on the public `projection.{name}.{key}` channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-260-01 | Tampering | `apply_event` step 6.5 hook | mitigate | The hook is ADDITIVE-only — it is inserted strictly AFTER the existing step-6 delta broadcast and cannot modify, suppress, or replace it. Regression test `apply_event_without_hook_still_broadcasts_delta_unchanged` pins the base path; the step-6 block is edited by zero lines (grep-asserted `.event(event_name)` still present). |
| T-260-02 | Denial of Service | hook fires inside per-key Mutex | accept | The hook runs sync inside the per-key Mutex; same-key applies already serialize. This plan only records/serializes state — it does no I/O. High-frequency projections throttle at the application layer (documented in the builder rustdoc). The async broadcast is `tokio::spawn`-ed by the app-side closure (Plan 04), not blocking the Mutex holder. |
| T-260-03 | Information Disclosure | serialized snapshot handed to hook | accept | `P::State: Serialize` is already persisted as JSON in `projection_snapshots`; serializing it to `Value` for the hook exposes nothing new. Channel-name derivation from the fragment's own key (in Plan 04) prevents cross-key leakage; broadcast auth is `ferro-broadcast`'s existing subscribe check. |
</threat_model>
