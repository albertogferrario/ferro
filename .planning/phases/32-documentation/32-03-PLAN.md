  <files>docs/src/json-ui/actions.md</files>
  <action>
Create docs/src/json-ui/actions.md documenting the JSON-UI action system.

Read ferro-json-ui/src/action.rs for the Action struct, builder methods, ActionOutcome, and confirmation types.

Page structure:

1. **H1: Actions** — One sentence: Actions connect UI elements to Ferro routes for navigation, form submission, and destructive operations.

2. **How Actions Work** — Conceptual overview:
   - Actions reference named routes (e.g., "users.store")
   - Framework resolves route names to URLs at render time
   - GET actions render as links, non-GET actions render as form submissions
   - Actions can have confirmations and success outcomes

3. **Creating Actions** — Builder API:
   ```rust
   // Navigation (GET)
   Action::get("users.index")

   // Form submission (POST - default)
   Action::new("users.store")

   // Explicit methods
   Action::put("users.update")
   Action::delete("users.destroy")
   ```

4. **Route Parameters** — How to pass parameters:
   ```rust
   Action::get("users.show").params(json!({"user": user_id}))
   ```

5. **Confirmations** — Three types:
   - `confirm("Are you sure?")` — simple confirm dialog
   - `confirm_danger("Delete this user?")` — destructive confirmation
   - Document the ConfirmDialog struct if relevant

6. **Success Outcomes** — What happens after action completes:
   - `ActionOutcome::Redirect { url }` — navigate to URL
   - `ActionOutcome::Refresh` — reload current page
   - `ActionOutcome::Notify { message, variant }` — show notification
   - Show example: `action.on_success(ActionOutcome::Redirect { url: "/users".to_string() })`

7. **Actions on Components** — How actions attach to components:
   - Via ComponentNode's `action` field (for clickable elements)
   - Via FormProps `action` field (for form submission)
   - Via TableRow `actions` (for row-level buttons)

8. **URL Resolution** — Brief: framework automatically resolves route names to URLs during render. Missing routes produce `url: None`.

<task type="auto">
  <name>Task 2: Create data-binding.md documenting data paths and visibility rules</name>
  <files>docs/src/json-ui/data-binding.md</files>
  <action>
Create docs/src/json-ui/data-binding.md covering both data binding and visibility rules.

Read ferro-json-ui/src/data.rs for data path resolution and ferro-json-ui/src/visibility.rs for visibility conditions.

Page structure:

1. **H1: Data Binding & Visibility** — One sentence: Pre-fill form fields from handler data and conditionally show/hide components based on data state.

2. **Handler Data** — How data flows:
   - `JsonUi::render(&view, &data)` — second argument is handler data
   - Data is a `serde_json::Value` (typically a JSON object)
   - Components reference data via paths

3. **Data Paths** — Path syntax:
   - Simple slash-separated paths: `/data/user/name`
   - Used in `data_path` field on form components (Input, Select, Textarea, Checkbox, Switch)
   - Resolves at render time to pre-fill form fields
   - Example: Input with `data_path: Some("/data/user/email".to_string())` pre-fills from handler data

4. **View Data** — Two sources:
   - `JsonUiView::data(value)` — embedded in the view (for self-contained views)
   - `JsonUi::render(&view, &data)` — explicit handler data (takes priority)
   - When both exist, explicit data wins ("live" data override)

5. **Visibility Rules** — Conditional rendering:
   - Attach via ComponentNode's `visibility` field
   - Simple condition:
     ```rust
     JsonUiVisibility::Condition(VisibilityCondition {
         path: "/data/users".to_string(),
         operator: "not_empty".to_string(),
         value: None,
     })
     ```
   - Operators: eq, neq, gt, gte, lt, lte, not_empty, empty, contains, not_contains

6. **Compound Visibility** — Logical operators:
   - `JsonUiVisibility::And(vec![...])` — all conditions must be true
   - `JsonUiVisibility::Or(vec![...])` — any condition must be true
   - `JsonUiVisibility::Not(Box::new(...))` — negate a condition
   - Show JSON equivalents for each (the untagged serde format: `{"and": [...]}`))

7. **Validation Errors** — How errors bind:
   - `JsonUi::render_with_errors()` / `JsonUi::render_validation_error()` methods
   - Framework resolves validation errors to matching form field `error` props
   - Field name matching: error key "email" → Input with `field: "email"`
   - View-level errors available via `view.errors` for global display

Target length: ~150-200 lines.

Page structure:

1. **H1: Layouts** — One sentence: Layouts wrap JSON-UI pages with consistent navigation, headers, and page structure.

2. **How Layouts Work** — Conceptual overview:
   - Views specify a layout name via `JsonUiView::layout("app")`
   - Layouts are registered in a LayoutRegistry
   - At render time, the layout wraps the rendered component HTML
   - Default layouts included: AppLayout, AuthLayout, BlankLayout

3. **Using a Layout** — Basic usage:
   ```rust
   let view = JsonUiView::new()
       .title("Dashboard")
       .layout("app");  // Uses AppLayout
   ```

4. **Default Layouts** — What's included:
   - `app` — Full page with sidebar navigation, header, user menu
   - `auth` — Centered card layout for login/register pages
   - `blank` — No chrome, just the content

5. **Creating Custom Layouts** — Implement the Layout trait:
   - Show the trait signature
   - Show a minimal implementation
   - Explain LayoutContext fields (title, nav_items, user, content)
   - Register in LayoutRegistry

6. **Layout Context** — Available data:
   - `title` — from JsonUiView
   - `nav_items` — navigation links (NavItem struct)
   - `content` — rendered HTML of the component tree
   - How to pass custom nav items

7. **Render Configuration** — JsonUiConfig:
   - Route resolver callback
   - Layout registry
   - Custom configuration via `JsonUi::render_with_config()`
