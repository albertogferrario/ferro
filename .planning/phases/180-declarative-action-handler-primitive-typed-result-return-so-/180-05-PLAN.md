    ```markdown
    # Action Handlers

    The `#[action]` attribute is the POST-and-redirect counterpart to `#[handler]`. Use it
    on handlers that mutate state and must redirect the browser on every outcome —
    success or failure — without rendering an error page at the POST URL.

    `#[handler]` stays the right choice for GET requests, JSON / Inertia API endpoints,
    and anything that does not need a 303 redirect on error.

    ## When to use `#[action]`

    - The endpoint accepts a POST (or PATCH / DELETE — see [Attribute reference](#attribute-reference)).
    - The endpoint mutates persistent state.
    - The browser is doing a full-page form submit, so a 5xx response would strand the
      user at the POST URL.
    - You want bare `?` over fallible steps without writing `match` ladders or per-handler
      `*_redirect` helpers.

    Use `#[handler]` instead for:

    - GET endpoints (rendering pages, returning JSON).
    - Fetch / XHR / Inertia endpoints where the client handles errors in JavaScript.
    - Long-running handlers that don't need a redirect on completion.

    ## The shape

    ```rust
    use ferro::{action, ActionError, ActionResult, Request};

    #[action(redirect_to = "/dashboard/pages")]
    pub async fn publish_by_id(req: Request) -> ActionResult {
        let id: i64 = req.param("id")?.parse()
            .map_err(|_| ActionError::msg("ID non valido"))?;
        let page = Page::find_by_id(id).await?
            .ok_or(ActionError::not_found("Page not found"))?;
        publish_page(page).await?;
        Ok(())  // → 303 /dashboard/pages?success=1
    }
    ```

    On `Ok(())`, the framework returns a 303 redirect to the URL configured in
    `redirect_to`, writes a structured flash payload to the session under the `_action`
    key, and appends `?success=1` to the redirect URL for back-compat with templates
    that have not yet been updated to read session flash.

    On any `Err(ActionError)`, the framework returns a 303 to the same URL, writes
    `{variant: "error", message: "<text>"}` to the `_action` flash slot, appends
    `?error=<kind>&msg=<percent-encoded text>` to the URL, and emits a `tracing::error!`
    record with the handler name and message.

    ## Compared to `#[handler]`

    Before — `#[handler]` with manual error wrapping:

    ```rust
    #[handler]
    pub async fn publish_by_id(req: Request) -> Response {
        let business = resolve_tenant().await
            .map_err(|e| error_response(500, &format!("Errore: {e}")))?;
        let id: i64 = req.param("id")
            .map_err(|_| error_response(400, "ID non valido"))
            .and_then(|s| s.parse().map_err(|_| error_response(400, "ID non valido")))?;
        let page = Page::find_by_id(id).await
            .map_err(|e| error_response(500, &format!("Errore: {e}")))?
            .ok_or_else(|| error_response(404, "Page not found"))?;
        if page.tenant_id != business.id {
            return Err(error_response(403, "Not authorized"));
        }
        match publish_page(page).await {
            Ok(()) => Redirect::to("/dashboard/pages?success=published").into(),
            Err(msg) => Redirect::to(
                format!("/dashboard/pages?error=publish&msg={}", percent_encode(&msg))
            ).into(),
        }
    }
    ```

    After — `#[action]` with bare `?`:

    ```rust
    #[action(redirect_to = "/dashboard/pages")]
    pub async fn publish_by_id(req: Request) -> ActionResult {
        let business = resolve_tenant().await?;
        let id: i64 = req.param("id")?.parse()
            .map_err(|_| ActionError::msg("ID non valido"))?;
        let page = Page::find_by_id(id).await?
            .ok_or(ActionError::not_found("Page not found"))?;
        if page.tenant_id != business.id {
            return Err(ActionError::forbidden("Not authorized"));
        }
        publish_page(page).await?;
        Ok(())
    }
    ```

    Same observable behavior. Fewer load-bearing characters. No per-handler redirect helper.

    ## Attribute reference

    | Key | Required | Default | Purpose |
    |-----|----------|---------|---------|
    | `redirect_to` | yes | — | The 303 target URL for both success and error. Must be a string literal. |
    | `method` | no | `"POST"` | Informational HTTP method. Reserved for future per-method dispatch wiring; currently has no runtime effect. |

    Missing `redirect_to`, an unknown key, or a non-string-literal value produces a
    compile error pointing at the attribute site.

    ## `ActionResult`, `ActionOk`, `ActionError`

    `ActionResult` is a type alias:

    ```rust
    pub type ActionResult = Result<ActionOk, ActionError>;
    ```

    The common success case is `Ok(())` — the framework converts via `From<()> for
    ActionOk`. Override the success flash key or redirect target with the `ActionOk`
    constructors:

    ```rust
    Ok(ActionOk::flash("created"))                  // ?success=created
    Ok(ActionOk::redirect_to("/dashboard/x/42"))    // → /dashboard/x/42?success=1
    ```

    `ActionError` carries four fields:

    ```rust
    pub struct ActionError {
        pub message: String,
        pub kind: ActionKind,             // Generic | NotFound | Forbidden | Unauthorized
        pub flash_variant: FlashVariant,  // Error | Warning | Info
        pub redirect_override: Option<String>,
    }
    ```

    Constructors:

    ```rust
    ActionError::msg("something failed")
    ActionError::not_found("Page not found")
    ActionError::forbidden("Not authorized")
    ActionError::unauthorized("Sign in to continue")
    ```

    Builder methods (consuming `mut self`):

    ```rust
    ActionError::msg("retry later").with_flash(FlashVariant::Warning)
    ActionError::unauthorized("Sign in to continue").redirect_to("/login")
    ```

    ### Using `?` on arbitrary errors — `IntoActionError`

    Bare `?` works out of the box on these four types because the framework provides
    concrete `From` impls:

    - `FrameworkError`
    - `String`
    - `&'static str`
    - `sea_orm::DbErr`

    For any other type implementing `Display`, use the `IntoActionError` shim:

    ```rust
    use ferro::IntoActionError;

    let id: i64 = "not-a-number".parse()
        .map_err(IntoActionError::into_action_error)?;
    ```

    A blanket `impl<E: Display> IntoActionError for E` covers everything that prints
    a message. The shim is required (instead of a blanket `From`) because a blanket
    `From<T: IntoActionError> for ActionError` would conflict with the four concrete
    `From` impls under Rust's coherence rules.

    ## Auth-failure routing

    `ActionError::unauthorized(...)` does not carry a default redirect target — ferro
    is project-agnostic and has no opinion about your login URL. Configure it per call:

    ```rust
    Err(ActionError::unauthorized("Sign in to continue").redirect_to("/login"))
    ```

    Or share a helper inside your application:

    ```rust
    fn auth_required(msg: &str) -> ActionError {
        ActionError::unauthorized(msg).redirect_to("/login")
    }
    ```

    ## Reading the flash payload

    The `#[action]` macro writes the structured payload to the session flash key
    `_action`:

    ```json
    { "variant": "error", "message": "Page not found" }
    ```

    Consumer templates (or shared Inertia / view props middleware) read it via:

    ```rust
    let action_flash: Option<serde_json::Value> = session.get_flash("_action");
    ```

    `get_flash` ages the value — it survives exactly one request, then is removed.

    The back-compat query string (`?error=<kind>&msg=<text>` or `?success=<key>`) is
    emitted alongside the flash write so templates that have not yet adopted session
    flash continue to work. A future cleanup phase removes the query-string fallback
    once every template reads `_action` directly.

    ## Security

    ### Flash message escaping

    `ActionError::message` is rendered into the session flash payload and the
    back-compat query string verbatim. **Templates that render the message into HTML
    MUST HTML-escape it.** Ferro does not escape at write time because template
    rendering is consumer territory and double-escaping is worse than no escaping.

    Treat `message` as untrusted text:

    - Do NOT interpolate it into raw HTML without escaping.
    - Do NOT pass it to `dangerouslySetInnerHTML` / `v-html` / similar opt-outs.
    - DO render it inside text nodes — the rendering library's default escaping is
      sufficient for `Tera`, `MiniJinja`, `Inertia` (React/Vue), and similar engines.

    ### Same-origin `redirect_override`

    `ActionError::redirect_to(...)` and `ActionOk::redirect_to(...)` are honored only
    when the URL is same-origin — concretely, when it starts with a single `/` and
    not with `//`. Off-origin URLs (`https://attacker.example`),
    scheme-relative URLs (`//attacker.example`), and pseudo-schemes
    (`javascript:`) are silently dropped, a `tracing::warn!` is emitted, and the
    handler's configured `redirect_to` is used as the fallback.

    This mitigates open-redirect attacks where a malicious request could pin the
    redirect target via a user-controlled override. If you need to honor a
    user-supplied next-URL parameter, validate it against an allowlist in your
    handler before calling `.redirect_to(...)`.

    ### Log injection

    Control characters in `ActionError::message` (`\n`, `\r`, `\x00`, etc.) are
    replaced with single ASCII spaces before the message reaches `tracing::error!`.
    Structured-log sinks (JSON, OpenTelemetry) are safe regardless; this guard is
    for plain-text log output where a newline-injected message could forge a log
    entry.

    ## What `#[action]` does NOT do

    - **No CSRF handling.** Apply your existing CSRF middleware before the handler
      runs; `#[action]` does not introduce or bypass it.
    - **No authorization.** Check ownership inside the handler body and return
      `ActionError::forbidden(...)` on failure.
    - **No per-method routing.** The `method` attribute key is informational; you
      still register the route with `post!`, `patch!`, or `delete!` macros.
    - **No HTML rendering.** Errors redirect; they do not render an inline error
      page. Use `#[handler]` for endpoints that render.
