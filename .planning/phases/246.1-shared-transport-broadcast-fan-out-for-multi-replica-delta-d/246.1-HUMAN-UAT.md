## Tests

### 1. Cross-OS-process delivery over real Redis
expected: A WebSocket client subscribed on replica B receives exactly one `ServerMessage::Event` carrying `channel = "orders.1"` and `event = "OrderUpdated"` — no duplicate, no timeout — after replica A publishes it over a shared Redis bus.
steps: |
  1. Start a Redis server (`redis-server`).
  2. Ensure the app bootstrap wires the transport when `config.transport_redis_url` is set —
     i.e. `.with_transport(Arc::new(RedisTransport::connect(&url).await?))` (see WR-01 below;
     wiring lands in Phase 247 / a bootstrap companion step, not this ferro-broadcast-only phase).
  3. Launch two separate OS processes sharing `REDIS_URL=redis://127.0.0.1:6379`
     (e.g. `app serve` on :8080 and :8081).
  4. Subscribe a WebSocket client to `orders.1` on replica B (:8081).
  5. Trigger `broadcast("orders.1", "OrderUpdated", ...)` on replica A (:8080).
  6. Confirm the client on B receives it exactly once within a few seconds.
why_human: |
  CI proves the fan-out logic deterministically via the in-memory bus
  (`sc1_cross_process_delivery`) and proves the Redis transport wires correctly in a
  single-process env-gated test (`redis_integration_cross_process_delivery`). The true
  multi-replica topology — two separately-launched OS processes with independent runtimes
  and separate subscriber loops plus a live Redis server — is not provisioned in CI. This
  is the deployment proof enumerated in VALIDATION.md's Manual-Only row.
