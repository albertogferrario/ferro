### Human Verification Required

#### 1. Cross-OS-process delivery over real Redis

**Test:** Start a Redis server (`redis-server`). Launch two separate application processes (e.g. `cargo run -p app -- serve` on port 8080 and port 8081), both with `REDIS_URL=redis://127.0.0.1:6379` in the environment. Ensure both bootstrap paths call `.with_transport(Arc::new(RedisTransport::connect(&url).await?))` (see WR-01 note below). Subscribe a WebSocket client to channel `orders.1` on replica B (port 8081). Trigger a `broadcast("orders.1", "OrderUpdated", ...)` on replica A (port 8080). Confirm the WebSocket client on B receives it exactly once within a few seconds.

**Expected:** The client on B receives one `ServerMessage::Event` carrying `channel = "orders.1"` and `event = "OrderUpdated"`. No duplicate. No timeout under normal network conditions.

**Why human:** CI proves the fan-out logic deterministically via the in-memory bus (`sc1_cross_process_delivery`) and also proves the Redis transport wires correctly in a single-process test (`redis_integration_cross_process_delivery` with `REDIS_URL` set). The true multi-replica topology — two separately-launched OS processes with independent runtimes and separate subscriber loops — is not provisioned in CI. This is the deployment proof enumerated in VALIDATION.md's Manual-Only row.

**Additional prerequisite note (WR-01):** Before this test can pass, the bootstrap caller (`app/src/bootstrap.rs`) must be updated to call `.with_transport(...)` when `config.transport_redis_url` is set. That wiring is not in this phase's declared scope (it is `ferro-broadcast`-library-only) and is expected in Phase 247 or a bootstrap companion step. The transport capability is fully ready in the library; the wiring gap is in the consumer layer.
