# Phase 246.1: Code Review Report

**Reviewed:** 2026-08-14T00:00:00Z
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

The shared fan-out transport is well-structured and the core design decisions land cleanly. The `BroadcastTransport` trait is object-safe, the `BusEnvelope` reuses the already-serializable `ServerMessage`, and the two background tasks in `with_transport` are wired correctly. The critical safety properties the phase set out to guarantee are, in the main, met and covered by deterministic tests:

- **Echo suppression (D-03)** is correct: local delivery happens synchronously before any fan-out, and bus echoes are dropped by origin-id comparison in the delivery task. `send_to_channel_local_only` correctly omits the `fan_out` call, breaking the recursive-amplification loop. Verified by `sc1_own_echo_suppressed`.
- **The D-04 filter** (`matches!(msg, ServerMessage::Event(_))`) is correct against the `ServerMessage` enum: `MemberAdded`, `MemberRemoved`, and the control variants never reach `publish`. Verified by `presence_stays_per_process`.
- **Error swallowing (D-06)** is bounded to a `warn!` in `fan_out`; the caller always observes `Ok(())`. Verified by `publish_error_does_not_propagate`.
- **Redis `subscribe_loop`** never panics on malformed input: both an unreadable payload and a failed `serde_json::from_str` are logged and skipped. Strict deserialization is respected.
- **Dependency-free default build**: `redis` is `optional = true` and gated behind `redis-transport`; the `Error::Redis` variant, the `redis` module, and both integration-test files are all `#[cfg(feature = "redis-transport")]`. The default build is clean.

Three warnings are worth attention: an unused-config gap where `transport_redis_url` is parsed but never wired to a transport (the feature is currently unreachable from `from_env` alone), an inherent lost-wakeup window between spawning the SUBSCRIBE loop and clients subscribing (documented and partially mitigated in tests via sleeps, but a real ordering hazard in production wiring), and the fact that `with_transport` silently discards clients/channels registered before it is called. None are correctness bugs in the fan-out logic itself; they are integration and lifecycle concerns.

## Warnings

### WR-01: `transport_redis_url` is parsed but never wired — the shared transport is unreachable via config

**File:** `ferro-broadcast/src/config.rs:104-107`, `ferro-broadcast/src/broadcaster.rs:90`
**Issue:** `BroadcastConfig::from_env` reads `BROADCAST_REDIS_URL` / `REDIS_URL` into `transport_redis_url`, and the doc comment states "Absence of both leaves the in-process hub as the only transport" — implying presence enables the shared transport. But nothing consumes this field. `with_transport` is the only way to attach a transport, and it takes an `Arc<dyn BroadcastTransport>` directly; it never inspects `config.transport_redis_url`. The sole construction site (`app/src/bootstrap.rs:186`) calls `Broadcaster::with_config(BroadcastConfig::from_env())` and never calls `.with_transport(...)`. Consequently, setting `REDIS_URL` in a multi-replica deployment has no effect on broadcast fan-out — the config knob is inert, and the multi-replica delta delivery the phase targets does not activate through the documented env-var path. This is the "audit and fix discrepancies" case from project conventions: the config's own documentation promises behaviour the code does not deliver.
**Fix:** Provide a constructor that honours the config field, gated on the feature so the default build stays clean. For example:
```rust
// in broadcaster.rs, behind #[cfg(feature = "redis-transport")]
/// Attach the Redis transport described by `config.transport_redis_url`, if set.
pub async fn with_transport_from_config(self) -> Result<Self, Error> {
    if let Some(url) = self.inner.config.transport_redis_url.clone() {
        let t = crate::transport::redis::RedisTransport::connect(&url).await?;
        return Ok(self.with_transport(std::sync::Arc::new(t)));
    }
    Ok(self)
}
```
Then call it from `app/src/bootstrap.rs`. If wiring is deliberately deferred to a later phase, tighten the `config.rs` doc comment so it does not claim the field activates the transport, and note the field is currently reserved.

### WR-02: Lost-wakeup window between SUBSCRIBE-loop spawn and client subscription

**File:** `ferro-broadcast/src/broadcaster.rs:99-119`, `ferro-broadcast/src/transport/memory.rs:35`, `ferro-broadcast/src/transport/redis.rs:77-79`
**Issue:** `with_transport` spawns the SUBSCRIBE loop as a detached task, but the actual bus subscription happens asynchronously inside it — `rx.subscribe()` for the in-memory bus (memory.rs:35) and `pubsub.subscribe(&self.channel).await` for Redis (redis.rs:78). Both buses only deliver messages sent *after* the subscription is established. There is therefore an unavoidable window between `with_transport` returning and the loop actually attaching, during which any envelope published by another replica is lost. The tests paper over this with `sleep(20ms)` / `sleep(150ms)` (shared_transport.rs:30, redis_integration.rs:55), which confirms the authors know the window exists. In production the risk is not the local subscribe ordering but the startup race: a replica that publishes immediately after `with_transport` — before its own or a peer's loop has attached — will silently drop those early deltas. This is a delivery-gap hazard, not a deadlock. For the in-memory `broadcast::channel`, a slow consumer additionally triggers `Lagged` (handled by a `warn!` and silent drop, memory.rs:43), which is a second, capacity-bound loss path.
**Fix:** Make attachment observable rather than timing-dependent. Option A: have `subscribe_loop` signal readiness — e.g. accept a `tokio::sync::oneshot::Sender<()>` (or a `Notify`) that fires immediately after `rx.subscribe()` / `pubsub.subscribe(...).await` succeeds, and have `with_transport` await it (or expose an `async fn ready()`), so callers can gate first publish on a real attach rather than a sleep. Option B: document the window explicitly as an at-least-once-after-attach guarantee and require callers to establish the transport before accepting traffic. At minimum, remove the reliance on sleeps in a way that could mask a regression — a readiness signal would let the tests assert attachment deterministically.

### WR-03: `with_transport` (and `with_authorizer`) silently discard already-registered clients and channels

**File:** `ferro-broadcast/src/broadcaster.rs:90-120`, `ferro-broadcast/src/broadcaster.rs:67-78`
**Issue:** Both consuming builders construct a brand-new `BroadcasterInner` with fresh, empty `DashMap`s for `clients` and `channels`, copying over only `authorizer`, `config`, `origin_id`, and `transport`. Any client added or channel subscribed on the pre-builder `Broadcaster` is dropped on the floor — the returned instance starts with zero clients and channels. This is safe today only because the established call pattern is `Broadcaster::with_config(..).with_transport(..)` before any client connects (as in the tests and `bootstrap.rs`). But the API shape invites misuse: `with_transport` reads as a mutator that augments an existing broadcaster, and a caller who attaches a transport after clients have connected will silently lose every existing subscription with no error and no log. The `#[derive(Clone)]` on `Broadcaster` compounds this — a cloned handle keeps the *old* inner (old `transport: None`), so clones taken before `with_transport` will not fan out, while the returned handle will. Divergent behaviour across clones of the "same" broadcaster is a latent footgun.
**Fix:** Either (a) preserve state by moving the existing `DashMap`s into the new inner instead of allocating empty ones — but this fights the `Arc<Inner>` sharing, since the old `Arc` may still be cloned elsewhere; or (b) make the transport mutable within a single shared `Inner` (e.g. `transport: parking_lot::RwLock<Option<Arc<dyn BroadcastTransport>>>` or an `ArcSwapOption`) and turn `with_transport` into `&self` that mutates in place and spawns the loop, so every clone observes the transport and no client state is lost. Option (b) also resolves the clone-divergence. If the consuming-builder-before-any-client contract is intended and permanent, document it emphatically on both methods ("must be called before `add_client`; discards existing clients and channels") so the constraint is not left implicit.

## Info

### IN-01: `envelope.clone()` on every in-memory publish is avoidable

**File:** `ferro-broadcast/src/transport/memory.rs:27`
**Issue:** `self.tx.send(envelope.clone())` clones the full `BusEnvelope` (including the `ServerMessage` and its `serde_json::Value` payload) even when there are no receivers. `broadcast::Sender::send` takes the value by move, so the clone is required by the `&BusEnvelope` signature, not a redundant one — but the whole envelope is deep-cloned per publish regardless of subscriber count. Given the trait method takes `&BusEnvelope` this is hard to avoid without changing the trait; flagged only as a note for a future performance pass (explicitly out of v1 review scope, recorded for completeness).
**Fix:** No action for this phase. If a later performance pass touches this, consider `Arc<BusEnvelope>` on the bus to make fan-out clones cheap.

### IN-02: `RedisTransport::new` accepts an empty channel string without applying the documented default

**File:** `ferro-broadcast/src/transport/redis.rs:43-55`
**Issue:** The doc comment states "`channel` defaults to `DEFAULT_CHANNEL` when the empty string is passed", but the body does `let channel = channel.into();` with no empty-string check — an empty string is used verbatim as the pub/sub channel name. Publishing and subscribing on `""` would still work self-consistently, but it contradicts the documented contract and could silently isolate a replica that passed `""` expecting the default. `connect()` is unaffected (it passes `DEFAULT_CHANNEL`).
**Fix:** Either honour the doc — `let channel = { let c = channel.into(); if c.is_empty() { DEFAULT_CHANNEL.to_string() } else { c } };` — or correct the comment to state that the empty string is used as-is and callers should use `connect()` for the default.

### IN-03: In-memory `Lagged` drop is silent data loss beyond the log line

**File:** `ferro-broadcast/src/transport/memory.rs:43-45`
**Issue:** On `RecvError::Lagged(n)`, the loop logs `warn!` and continues, dropping `n` envelopes. For the test/dev substitute this is acceptable, and the doc comment frames it as such, but there is no back-pressure — a burst larger than the `broadcast::channel` capacity silently loses deltas. Worth a one-line doc note on `InMemoryTransport::new` that capacity bounds in-flight envelopes and overflow is dropped, so a test author sizing `capacity` understands the trade-off.
**Fix:** Add to the `new(capacity)` doc: "Capacity bounds in-flight envelopes; a subscriber that lags beyond it drops the overflow (logged, not delivered)."

### IN-04: `BusEnvelope.origin` is an unvalidated opaque string on the deserialization path

**File:** `ferro-broadcast/src/transport/mod.rs:17-25`, `ferro-broadcast/src/transport/redis.rs:90`
**Issue:** `origin` is a free-form `String` deserialized from the bus. Echo suppression compares it against the local `origin_id` (broadcaster.rs:111); a hostile or buggy publisher can set `origin` to any value, including impersonating another replica's origin id to make that replica *suppress* a legitimate delta (a targeted drop), or omitting/randomising it to guarantee delivery. The redis.rs module header (T-246.1-06) already documents that the Redis bus is a trusted, network-isolated boundary with no envelope signing, which is a reasonable v1 stance consistent with `ferro-cache`. This is noted only so the assumption is explicit in the review record: origin-id echo suppression is a correctness mechanism against *self*-echo, not a security control against a compromised bus.
**Fix:** No code change required for v1 given the documented trust boundary. If envelope authenticity ever matters, the existing HMAC signing infrastructure (`sign.rs`, already a dependency) could sign the envelope; track as future work rather than a phase blocker.

### IN-05: SUBSCRIBE-loop error ends fan-out silently with no restart

**File:** `ferro-broadcast/src/broadcaster.rs:103-107`
**Issue:** If `subscribe_loop` returns `Err` (e.g. Redis connection lost in a way `ConnectionManager` does not transparently recover on the pub/sub side, since the dedicated pub/sub connection is *not* the auto-reconnecting manager), the spawned task logs one `warn!` and terminates. The replica then permanently stops receiving cross-process deltas while continuing to publish and serve locally — a silent, one-directional degradation with no retry and no health signal. The Redis PUBLISH path auto-reconnects via `ConnectionManager` (D-07), but the SUBSCRIBE path deliberately uses a separate non-managed connection (D-09) and has no equivalent recovery.
**Fix:** Consider wrapping the loop spawn in a reconnect-with-backoff supervisor for the Redis transport, or at minimum raise the log to `error!` and expose a liveness flag the app can surface in a health check. Acceptable to defer if multi-replica Redis is not yet the shipped path (see WR-01), but worth a tracked follow-up so a dropped SUBSCRIBE connection does not fail open into a partitioned replica.
