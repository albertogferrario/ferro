## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Ship Redis pub/sub as the single real shared transport, behind a `BroadcastTransport` trait. Reuse redis 0.27 + ConnectionManager. Redis dep is **optional** behind a feature flag.
- **D-02:** In-process hub remains the **default**. No-transport-configured behaviour is identical to today (SC2).
- **D-03:** Each `Broadcaster` holds a process-unique origin id (uuid v4). On publish: deliver locally immediately AND publish to bus stamped with `origin`. On bus receipt: deliver locally only if `origin != self` (drop own echo).
- **D-04:** Fan out `ServerMessage::Event` path (`broadcast` / `broadcast_except` / `whisper`). Presence membership stays per-process.
- **D-05:** `MemberAdded` / `MemberRemoved` stays per-process. Documented as a single-node limitation.
- **D-06:** On bus publish error: deliver locally, log, do not fail caller.
- **D-07:** Subscriber side relies on `ConnectionManager` auto-reconnect; dropped bus connection logs and reconnects.
- **D-08:** Single fan-out Redis channel (app-neutral literal, e.g. `ferro:broadcast`). Envelope carries logical channel + origin; each process routes locally.
- **D-09:** Read `REDIS_URL` with `BROADCAST_REDIS_URL` override. Dedicated connection for the SUBSCRIBE loop; PUBLISH via `ConnectionManager`.
- **D-10:** Reuse `ServerMessage` as on-bus payload (already `Serialize + Deserialize`). Wrap with `{ origin, channel, message }`.
- **D-11:** `BroadcastTransport` trait enables an in-memory shared-transport test impl for deterministic SC1 CI testing. Live-Redis test gated behind env/feature.

### Claude's Discretion

- Config env surface: `BROADCAST_TRANSPORT` = `memory` (default) | `redis`, via `BroadcastConfig::from_env`.
- Feature-flag name: `redis-transport` (parallel to `ferro-cache`'s `redis-backend`).
- Exact Redis fan-out channel literal (must be app-neutral).
- Origin-id representation (uuid v4 assumed).

### Deferred Ideas (OUT OF SCOPE)

- Postgres `LISTEN`/`NOTIFY` transport.
- Sharded / per-logical-channel Redis topology.
- Cross-process presence membership.
- Health/metric signal for a partitioned bus.

## Summary

`ferro-broadcast` is today a pure in-process hub: `broadcast()` → `send_to_channel()` → local `mpsc` delivery. Two crates are its only transport dependencies (`tokio` + `tokio-tungstenite`). In a multi-replica deployment a delta published by a worker on replica A is never observed by a client on replica B — which breaks OFFLOAD-04 the moment scale-out is attempted.

This phase adds a `BroadcastTransport` trait and a Redis pub/sub implementation behind a `redis-transport` feature flag, exactly mirroring the `ferro-cache`/`redis-backend` pattern already in the workspace. The default build gains no new deps; the in-process hub remains the default transport. The `Broadcaster` intercepts the `send_to_channel` / `send_to_channel_except` calls, publishes an envelope to the bus, and has a background SUBSCRIBE task that receives bus messages and routes them into local `mpsc` delivery — with echo suppression via a process-unique uuid v4 (already a `ferro-broadcast` dep).

The redis version locked by the workspace is **0.27.6** (`ferro-cache` already pinned it). The pub/sub API at that version is `client.get_async_pubsub().await?` for the SUBSCRIBE connection, with `pubsub.subscribe(channel).await?` and `pubsub.into_on_message()` for the consuming message stream. PUBLISH goes through a cloned `ConnectionManager` via `AsyncCommands::publish`.

**Primary recommendation:** Intercept at `send_to_channel` / `send_to_channel_except`, add `Option<Arc<dyn BroadcastTransport + Send + Sync>>` to `BroadcasterInner`, use `async_trait` (already a direct dep) for the trait, and back the CI test with a `tokio::sync::broadcast` channel shared between two `Broadcaster` instances.

### Pattern 1: BroadcastTransport Trait

The trait must be object-safe so `Broadcaster` can hold `Option<Arc<dyn BroadcastTransport + Send + Sync>>`. `async_trait` (already a dep) is the workspace pattern for object-safe async traits — both `ChannelAuthorizer` (ferro-broadcast) and `CacheStore` (ferro-cache) use it.

```rust
// Source: ferro-broadcast/src/broadcaster.rs (ChannelAuthorizer precedent)
#[async_trait::async_trait]
pub trait ChannelAuthorizer: Send + Sync {
    async fn authorize(&self, data: &AuthData) -> bool;
}
```

Apply the same pattern to `BroadcastTransport`:

```rust
// ferro-broadcast/src/transport/mod.rs
use serde::{Deserialize, Serialize};
use crate::message::ServerMessage;

/// Envelope for cross-process delivery.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct BusEnvelope {
    /// Process-unique origin id (uuid v4) — used for echo suppression.
    pub origin: String,
    /// Logical ferro-broadcast channel name (e.g. "projection.orders.42").
    pub channel: String,
    /// The server-side message payload.
    pub message: ServerMessage,
}

/// Shared fan-out transport.
///
/// Implementations must be `Send + Sync` and object-safe. The `async_trait`
/// macro is used throughout the workspace for this pattern.
#[async_trait::async_trait]
pub trait BroadcastTransport: Send + Sync {
    /// Publish an envelope to the shared bus.
    ///
    /// Must not fail the caller on bus error (D-06); implementations log
    /// and return `Ok(())` on publish failure.
    async fn publish(&self, envelope: &BusEnvelope) -> Result<(), crate::Error>;

    /// Start the background SUBSCRIBE loop. Delivers received envelopes
    /// to `sink` for local routing (origin-filtered by the caller).
    ///
    /// Expected to run as a `tokio::spawn`'d task; returns when the
    /// transport is shut down or encounters a fatal error.
    async fn subscribe_loop(
        &self,
        sink: tokio::sync::mpsc::Sender<BusEnvelope>,
    ) -> Result<(), crate::Error>;
}
```

`[VERIFIED: ferro-broadcast/src/broadcaster.rs, ferro-cache/src/cache.rs]` — workspace async_trait pattern confirmed.

`send_to_channel` becomes the single intercept point:

```rust
async fn send_to_channel(&self, channel_name: &str, msg: &ServerMessage) {
    // 1. Local delivery (always first, D-03)
    if let Some(channel) = self.inner.channels.get(channel_name) {
        for socket_id in channel.subscribers.iter() {
            self.send_to_client(socket_id, msg.clone()).await;
        }
    }
    // 2. Fan out to bus if transport configured (D-01)
    if let Some(transport) = &self.inner.transport {
        if matches!(msg, ServerMessage::Event(_)) {  // D-04
            let envelope = BusEnvelope {
                origin: self.inner.origin_id.clone(),
                channel: channel_name.to_string(),
                message: msg.clone(),
            };
            if let Err(e) = transport.publish(&envelope).await {
                tracing::warn!(error = %e, channel = %channel_name, "bus publish failed");
                // D-06: do not fail the caller
            }
        }
    }
}
```

The background SUBSCRIBE task delivers received envelopes after origin check:

```rust
// spawned in Broadcaster::with_transport(...)
tokio::spawn(async move {
    let mut rx = bus_rx; // mpsc::Receiver<BusEnvelope>
    while let Some(envelope) = rx.recv().await {
        if envelope.origin == broadcaster.inner.origin_id {
            continue; // drop own echo (D-03)
        }
        // deliver to local subscribers on this replica
        broadcaster.send_to_channel_local_only(
            &envelope.channel,
            &envelope.message,
        ).await;
    }
});
```

### Pattern 3: Redis Transport Implementation

```rust
// ferro-broadcast/src/transport/redis.rs
// Source: ferro-cache/src/stores/redis.rs (ConnectionManager pattern)
// Source: docs.rs/redis/0.27.6 (get_async_pubsub + into_on_message)
#[cfg(feature = "redis-transport")]

use redis::{aio::ConnectionManager, AsyncCommands, Client};
use futures_util::StreamExt;

pub struct RedisTransport {
    manager: ConnectionManager,   // for PUBLISH (cloneable, multiplexed)
    client: Client,               // for spawning new SUBSCRIBE connections
    channel: String,              // the single Redis fan-out channel (D-08)
}

impl RedisTransport {
    pub async fn new(url: &str, channel: impl Into<String>) -> Result<Self, crate::Error> {
        let client = Client::open(url)?;
        let manager = ConnectionManager::new(client.clone()).await?;
        Ok(Self { manager, client, channel: channel.into() })
    }
}

#[async_trait::async_trait]
impl BroadcastTransport for RedisTransport {
    async fn publish(&self, envelope: &BusEnvelope) -> Result<(), crate::Error> {
        let payload = serde_json::to_string(envelope)?;
        let mut conn = self.manager.clone();  // ConnectionManager is Clone
        conn.publish::<_, _, ()>(&self.channel, payload).await?;
        Ok(())
    }

    async fn subscribe_loop(
        &self,
        sink: tokio::sync::mpsc::Sender<BusEnvelope>,
    ) -> Result<(), crate::Error> {
        // Dedicated connection — pub/sub cannot share a multiplexed connection (D-09)
        let mut pubsub = self.client.get_async_pubsub().await?;
        pubsub.subscribe(&self.channel).await?;
        // into_on_message consumes the PubSub and returns an owned PubSubStream
        let mut stream = pubsub.into_on_message();
        while let Some(msg) = stream.next().await {
            let payload: String = msg.get_payload()?;
            if let Ok(envelope) = serde_json::from_str::<BusEnvelope>(&payload) {
                if sink.send(envelope).await.is_err() {
                    break; // receiver dropped — shutdown
                }
            }
        }
        Ok(())
    }
}
```

### Pattern 4: In-Memory Test Transport (D-11)

```rust
// ferro-broadcast/src/transport/memory.rs
use tokio::sync::broadcast;

pub struct InMemoryTransport {
    tx: broadcast::Sender<BusEnvelope>,
}

impl InMemoryTransport {
    /// Create a bus with given channel capacity.
    pub fn new(capacity: usize) -> Self {
        let (tx, _) = broadcast::channel(capacity);
        Self { tx }
    }

    /// Subscribe to receive all future messages on this bus.
    /// Two Broadcasters sharing one `InMemoryTransport` each call this.
    pub fn subscribe(&self) -> broadcast::Receiver<BusEnvelope> {
        self.tx.subscribe()
    }
}

#[async_trait::async_trait]
impl BroadcastTransport for InMemoryTransport {
    async fn publish(&self, envelope: &BusEnvelope) -> Result<(), crate::Error> {
        let _ = self.tx.send(envelope.clone()); // ok if no receivers yet
        Ok(())
    }

    async fn subscribe_loop(
        &self,
        sink: tokio::sync::mpsc::Sender<BusEnvelope>,
    ) -> Result<(), crate::Error> {
        let mut rx = self.tx.subscribe();
        loop {
            match rx.recv().await {
                Ok(envelope) => {
                    if sink.send(envelope).await.is_err() {
                        break;
                    }
                }
                Err(broadcast::error::RecvError::Lagged(n)) => {
                    tracing::warn!(dropped = n, "in-memory bus lagged");
                }
                Err(broadcast::error::RecvError::Closed) => break,
            }
        }
        Ok(())
    }
}
```

**Why `tokio::sync::broadcast`:** It is a multi-producer, multi-consumer channel where every receiver sees every message — exactly the fan-out semantics needed. Two `Broadcaster` instances can share one `InMemoryTransport` (via `Arc`) and each get their own `subscribe_loop` receiver. `[VERIFIED: tokio docs — tokio::sync::broadcast is already in ferro-broadcast's tokio dep]`

### Anti-Patterns to Avoid

- **Sharing the pub/sub connection for PUBLISH:** Redis pub/sub connections enter a mode where only pub/sub commands are valid. PUBLISH must go through a separate `ConnectionManager` (D-09). `[CITED: redis docs — multiplexed vs pub/sub connection separation]`
- **Adding `redis-transport` to `[features] default`:** The default build must stay toolchain-only; the feature must be purely opt-in.
- **Gating the in-memory test transport behind `redis-transport`:** The in-memory impl is used in `#[cfg(test)]` blocks unconditionally; it must not require the optional redis dep.
- **Fanning out `MemberAdded` / `MemberRemoved` over the bus:** These depend on local membership state. The filter `matches!(msg, ServerMessage::Event(_))` in the intercept point precisely excludes them (D-04, D-05).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Redis connection auto-reconnect | Custom reconnect loop | `ConnectionManager` | Already implemented with backoff; used by `ferro-cache` |
| Async pub/sub connection | Manual socket code | `client.get_async_pubsub()` | Handles protocol framing, error state |
| Message stream | Manual buffer/poll | `pubsub.into_on_message()` | Returns `PubSubStream: Stream<Item=Msg>` — compose with `StreamExt` |
| Process-unique id | Custom random generator | `uuid::Uuid::new_v4().to_string()` | Already a dep; v4 is cryptographically random |
| Multi-receiver in-memory bus | Manual `Vec<mpsc::Sender>` | `tokio::sync::broadcast` | Built-in fan-out; lag detection included |

### RF-1: redis 0.27 async pub/sub API (verified)

The workspace lock pins `redis = 0.27.6`. The API at that version is:

| Operation | Call | Notes |
|-----------|------|-------|
| Acquire pub/sub connection | `client.get_async_pubsub().await?` | Lives on `redis::Client`; requires `aio` feature (included via `tokio-comp`) |
| Subscribe | `pubsub.subscribe(channel).await?` | `channel: impl ToRedisArgs` |
| Consuming stream | `pubsub.into_on_message()` → `PubSubStream` | Consumes `PubSub`; use with `futures_util::StreamExt` |
| Borrowing stream | `pubsub.on_message()` | Borrows `&mut PubSub`; use when pubsub must be retained |
| Split | `pubsub.split()` → `(PubSubSink, PubSubStream)` | For concurrent subscribe-management + read |
| Publish | `conn.publish::<K, V, RV>(channel, message).await?` | Via `AsyncCommands` on a `ConnectionManager` clone |

**For Phase 246.1:** `into_on_message()` is the right choice — the SUBSCRIBE loop task consumes the `PubSub` and never needs to modify subscriptions at runtime (single static channel `ferro:broadcast`, D-08).

### RF-5: Publish-path intercept points (verified)

Examining `ferro-broadcast/src/broadcaster.rs`, the publish-path call graph is:

```
broadcast()               → send_to_channel()
broadcast_except()        → send_to_channel_except()
whisper()                 → send_to_channel_except()
unsubscribe_internal()    → (MemberRemoved) send_to_channel()   [D-05: do NOT fan out]
```

**Intercept at `send_to_channel` and `send_to_channel_except`.** Both are `async fn` private methods. The `ServerMessage::Event(_)` filter (D-04) applied inside these methods excludes presence membership messages.

Alternative: add a public method `send_to_channel_local_only` for delivering bus-received envelopes without re-publishing to the bus, to avoid the recursive fan-out problem. This is a new private method, not a public API change — SC3 compliance.

**Origin stamping** happens at the intercept point: wrap `msg` in `BusEnvelope { origin: self.inner.origin_id.clone(), channel: channel_name.to_string(), message: msg.clone() }` before calling `transport.publish()`.

**Echo suppression** in the background task: `if envelope.origin == self.inner.origin_id { continue; }`.

Public API (`broadcast`, `broadcast_except`, `whisper`, `Broadcast` builder) is **unchanged** — SC3.

```rust
        Some(bus.clone()),

    let (tx_b, mut rx_b) = mpsc::channel(16);

    broadcaster_b.subscribe("socket_b", "orders.1", None, None).await.unwrap();

    // Replica A publishes (no local subscribers on A for "orders.1")
    Broadcast::new(Arc::new(broadcaster_a))
        .channel("orders.1")
        .event("OrderUpdated")
        .data(serde_json::json!({"id": 1}))
        .send()
        .await
        .unwrap();

    let msg = tokio::time::timeout(
        std::time::Duration::from_millis(100),
        rx_b.recv(),

    match msg {
        ServerMessage::Event(m) => assert_eq!(m.channel, "orders.1"),
        other => panic!("expected Event, got {other:?}"),
    }
}
```

## Common Pitfalls

### Pitfall 1: Sharing the Redis connection for pub/sub and commands

**What goes wrong:** Using the same `ConnectionManager` for both `subscribe` and `publish` causes the connection to enter pub/sub mode, after which only pub/sub commands are valid. PUBLISH commands on the same connection return errors or silently fail.

**Why it happens:** Redis protocol enforces this; it is not a library limitation.

**How to avoid:** `get_async_pubsub()` opens a dedicated connection. PUBLISH uses a separate `ConnectionManager` (cloneable, multiplexed). D-09 codifies this.

**Warning signs:** `ERR only (P|S)SUBSCRIBE / (P|S)UNSUBSCRIBE / PING / RESET / QUIT allowed in this context` errors from the redis crate.

### Pitfall 2: Double delivery on the publishing replica

**What goes wrong:** If the intercept publishes to the bus and the bus echo is not filtered, the publisher's own local subscribers receive the message twice — once from the immediate local delivery and once from the returning bus echo.

**Why it happens:** The bus broadcast reaches all SUBSCRIBEd processes, including the sender.

**How to avoid:** The origin uuid in `BusEnvelope` plus the `if envelope.origin == self.inner.origin_id { continue; }` check in the SUBSCRIBE task. The local delivery path (`send_to_channel_local_only`) must NOT publish to the bus again.

**Warning signs:** Test messages arriving twice in the `rx` channel; the `sc1_own_echo_suppressed` test failing.

### Pitfall 3: Fanning out presence membership messages over the bus

**What goes wrong:** `MemberAdded` / `MemberRemoved` are sent via `send_to_channel` / `send_to_channel_except` from within `subscribe` and `unsubscribe_internal`. Fanning them out would require cross-process presence state coherence — a distributed member registry problem not in scope.

**Why it happens:** The intercept sits at `send_to_channel`, which is called for all message types.

**How to avoid:** Gate the fan-out inside the intercept on `matches!(msg, ServerMessage::Event(_))` (D-04). All other variants (`MemberAdded`, `MemberRemoved`, `Connected`, etc.) pass through local-only.

**Warning signs:** Tests for presence channels failing due to phantom member events arriving from the bus.

### Pitfall 4: `into_on_message()` vs `on_message()` lifetime

**What goes wrong:** Using `on_message(&mut self)` (borrowing stream) while also needing to mutate the `PubSub` (e.g., subscribe to additional channels at runtime) causes a borrow conflict.

**Why it happens:** `on_message` borrows `&mut PubSub`; the borrow is live for the stream lifetime.

**How to avoid:** Since this phase uses a single static channel (`ferro:broadcast`, D-08), no runtime subscribe changes are needed after initialisation. Use `into_on_message()` (consuming) — it transfers ownership and avoids the borrow issue. If dynamic channel subscription were ever needed, use `split()` → `(PubSubSink, PubSubStream)`.

**Warning signs:** Borrow checker errors referencing the `PubSub` lifetime when trying to subscribe after calling `on_message`.

### Pitfall 5: `cargo test --all-features` failing without a live Redis

**What goes wrong:** The `redis-transport` feature activates the Redis integration test, which tries to connect to a Redis server that CI does not have.

**Why it happens:** `--all-features` enables `redis-transport`, activating the test module.

**How to avoid:** Gate the live-Redis test behind both `#![cfg(feature = "redis-transport")]` AND an env var check (`REDIS_URL` must be set and connectable). The in-memory transport test must NOT require `redis-transport`. Mirror the `ferro-queue` pattern exactly.

## Open Questions (RESOLVED)

1. **`BROADCAST_TRANSPORT` env surface — `memory` vs `none` as default label**
   - What we know: D-02 says the default is the in-process hub; the discretion note suggests `memory` as the default value.
   - What is unclear: should the default be `none` (explicit, no env var set = in-process) or `memory` (explicit string required)? The `ferro-queue` pattern uses `DATABASE_URL` absent → SQLite, present → Postgres, with no explicit env mode selector.
   - Recommendation: treat absence of `BROADCAST_TRANSPORT` as "in-process" (no transport); set `BROADCAST_TRANSPORT=redis` to activate Redis. This matches the sparse-env convention the rest of the framework uses.
   - **RESOLVED:** no `BROADCAST_TRANSPORT` discriminator env key; absence of `BROADCAST_REDIS_URL`/`REDIS_URL` = in-process default (D-09). `BroadcastConfig` carries only the transport URL string.

2. **`Broadcaster::with_transport` constructor shape**
   - What we know: `Broadcaster::with_config(BroadcastConfig)` is the existing constructor.
   - What is unclear: should transport be passed separately (`with_transport(impl BroadcastTransport)`) or embedded in `BroadcastConfig`?
   - Recommendation: embed a `transport: Option<Arc<dyn BroadcastTransport + Send + Sync>>` field in `BroadcastConfig`, set via a builder method. This keeps the single-constructor pattern. The `from_env` method on `BroadcastConfig` cannot construct a Redis transport (it is async), so it sets a `transport_url` field; the Redis transport is then constructed separately and injected.
   - **RESOLVED:** `with_transport(Arc<dyn BroadcastTransport + Send + Sync>)` is a separate consuming builder on `Broadcaster`; `BroadcastConfig` stores only the URL string because async `ConnectionManager` construction cannot live in the synchronous `from_env()`.
