# Phase 246.1: Shared-transport broadcast fan-out for multi-replica delta delivery - Context

**Gathered:** 2026-08-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Give `ferro-broadcast` a **configurable shared fan-out transport** so a delta
published in one process reaches subscribers attached to another process. Today
`ferro-broadcast` is an in-process hub (`Broadcaster::broadcast` → `send_to_channel`
→ local `mpsc` delivery; transport deps are only `tokio` + `tokio-tungstenite`), so
at N replicas a client socketed on replica B never receives a delta published by a
worker on replica A. This phase adds the shared transport, selected by
configuration, with the in-process hub retained as the default for single-node and
development.

This is a prerequisite for Phase 247 (read-model delta → broadcast streaming) and
maps to **OFFLOAD-04 (prerequisite)**. It clarifies HOW the fan-out is implemented;
it does not add streaming semantics, worker runtime, or presence replication (those
are other phases).

**Success criteria (from ROADMAP):**
1. A delta published by one process is observed by a subscriber attached to a second
   process, over the configured shared transport.
2. With no shared transport configured, behaviour is unchanged from the current
   in-process hub — single-node/dev need no configuration.
3. Transport selection is configuration-only; publishers and subscribers use one API
   regardless of which transport is active.
</domain>

<decisions>
## Implementation Decisions

### Transport (which fan-out backend ships)
- **D-01:** Ship **Redis pub/sub** as the single real shared transport this phase,
  behind a `BroadcastTransport` trait so Postgres `LISTEN`/`NOTIFY` or another bus
  can be added later with no API change. Reuse the already-vendored `redis 0.27` +
  `ConnectionManager` (precedent: `ferro-cache/src/stores/redis.rs`). The redis
  dependency is **optional, behind a feature flag** (mirrors `ferro-cache`'s
  `redis-backend`); the default build pulls no new deps and no native tooling.
- **D-02:** The in-process hub remains the **default** transport. A build with no
  transport configured behaves exactly as today (SC2).

### Loop prevention & delivery model
- **D-03:** Each `Broadcaster` holds a **process-unique origin id** (uuid v4 minted
  at construction; `uuid` is already a dep). On publish: deliver to local
  subscribers **immediately**, AND publish to the bus stamped with `origin`. On bus
  receipt: deliver to local subscribers **only if `origin != self`** (drop own echo).
  This keeps single-node latency unchanged and makes local delivery independent of
  bus availability. (Rejected: a bus-only uniform path — it adds a round-trip to
  every local delivery and couples local delivery to the bus, at odds with D-04.)

### Fan-out scope (which messages cross the bus)
- **D-04:** Fan out **server `Event`s** — the `broadcast()` / `broadcast_except()`
  path (`ServerMessage::Event`), which is exactly what the projection delta
  (`ferro-projection/src/runtime.rs`) and normal server-driven events use — **and
  whisper** (also a `ServerMessage::Event`; the except-socket exclusion is naturally
  a no-op on remote replicas).
- **D-05:** **Presence membership** (`MemberAdded` / `MemberRemoved`) stays
  **per-process** — it depends on local membership state; cross-process presence is a
  distributed member registry and belongs in its own phase. Document this as a
  single-node limitation of presence channels.

### Failure semantics
- **D-06:** On a bus **publish** error: still deliver to local subscribers, **log**
  the error, and **do not fail the caller**. Consistent with D-21 (broadcast failure
  never rolls back state) and the projection path already treating broadcast as
  best-effort. (Rejected: hard-fail — it propagates bus outages into the
  request/worker path.)
- **D-07:** On the subscriber side, rely on `ConnectionManager` auto-reconnect; a
  dropped bus connection logs and reconnects rather than panicking. (A health/metric
  signal for a partitioned bus was considered and deferred — see Deferred Ideas.)

### Redis channel topology
- **D-08:** Use a **single fan-out Redis channel** (app-neutral literal, e.g.
  `ferro:broadcast`). The envelope carries the **logical channel name + origin**;
  each process SUBSCRIBEs the one Redis channel and routes to its own local
  subscribers. No SUBSCRIBE/UNSUBSCRIBE churn as clients come and go; trivially
  correct. Every process receives every message — acceptable at result-delta volumes;
  sharding can come later if warranted.

### Connection source
- **D-09:** Read `REDIS_URL` (shared with `ferro-cache`) with a `BROADCAST_REDIS_URL`
  **override** for deployments wanting a separate instance. Open a **dedicated
  connection for the blocking SUBSCRIBE loop** (Redis pub/sub cannot share a
  multiplexed command connection); PUBLISH uses a `ConnectionManager`.

### Wire envelope
- **D-10:** Reuse `ServerMessage` as the on-bus payload — it already derives
  `Serialize + Deserialize` (`ferro-broadcast/src/message.rs`), so no new derives are
  needed. Wrap it with `{ origin, channel, message }` for routing + loop suppression.

### Testing strategy
- **D-11:** The `BroadcastTransport` trait enables an **in-memory shared-transport
  test impl** (two `Broadcaster`s sharing one in-memory bus) that proves SC1
  cross-process delivery **deterministically in CI without a live Redis**. A
  Redis-backed integration test is **gated** behind a Redis-available env/feature
  (mirror `ferro-queue`'s `postgres-tests` gating) so `--all-features` CI stays green
  without a running Redis server.

### Claude's Discretion
- Config env surface: proposed `BROADCAST_TRANSPORT` = `memory` (default) | `redis`,
  wired through the existing `from_env` pattern in `ferro-broadcast/src/config.rs`.
- Feature-flag name: proposed `redis-transport` (parallel to `ferro-cache`'s
  `redis-backend`); lives in `ferro-broadcast`, **no new crate**.
- The exact Redis fan-out channel literal (must be app-neutral — no tenant/app
  identity, per the project-agnostic-crates rule).
- Origin-id representation (uuid v4 assumed; planner may pick another
  process-unique token).
</decisions>

## Existing Code Insights

### Reusable Assets
- `redis 0.27` (`tokio-comp`, `connection-manager`) already vendored via `ferro-cache`;
  `ConnectionManager` pattern in `ferro-cache/src/stores/redis.rs`.
- `ServerMessage` / `BroadcastMessage` already `Serialize + Deserialize` — usable as the
  on-bus wire type directly.
- `uuid` (v4) already a `ferro-broadcast` dependency — usable for the origin id.
- `BroadcastConfig::from_env()` established pattern for env-driven config.

### Established Patterns
- Optional backends behind feature flags (`ferro-cache` `redis-backend`); default build
  stays lean and toolchain-only (see CLAUDE.md codec/nasm rule).
- Backend-requiring tests gated by feature (`ferro-queue` `postgres-tests`) so
  `--all-features` CI does not require a live service.
- `ferro-*` crates read framework/`APP_*` env conventions; no hardcoded app identity.

### Integration Points
- Publish interception at `send_to_channel` / `send_to_channel_except` inside
  `Broadcaster`; a shared background SUBSCRIBE task feeds bus-received messages back into
  local delivery (origin-filtered).
- `Broadcaster` gains an `Option<Arc<dyn BroadcastTransport>>` (default `None` = in-process).

### Research Flags (verify during planning)
- redis 0.27 async pub/sub API: acquire a pub/sub connection (e.g. `get_async_pubsub`) +
  message stream for SUBSCRIBE; PUBLISH via `ConnectionManager`. Match the feature set to
  `ferro-cache` (`tokio-comp`, `connection-manager`).
- Ensure the live-Redis integration test is feature/env-gated so `--all-features` CI
  (which builds `redis-transport`) stays green without a Redis server.
- Confirm `ferro-broadcast`'s publish-wave placement in `.github/workflows/publish.yml` is
  unaffected by adding an optional dependency (existing crate; no wave change expected).
</code_context>

<specifics>
## Specific Ideas

- Envelope shape: `{ origin: <process-uuid>, channel: <logical>, message: ServerMessage }`.
- Single Redis fan-out channel, local routing (not per-logical-channel subscribe).
- "Local-first, drop own echo" is the load-bearing correctness rule — a publisher must
  never double-deliver its own message when it returns over the bus.
</specifics>

<deferred>
## Deferred Ideas

- **Postgres `LISTEN`/`NOTIFY` transport** — the `BroadcastTransport` trait makes it an
  additive second impl later; skipped now to avoid the ~8KB NOTIFY payload cap and a
  second test matrix.
- **Sharded / per-logical-channel Redis topology** — only if fan-out volume outgrows the
  single-channel + local-routing model.
- **Cross-process presence membership** (distributed member registry with join/leave
  reconciliation) — its own phase; presence stays single-node here.
- **Health/metric signal for a partitioned bus** — considered during the failure-mode
  discussion; degrade-to-local + log chosen for this phase, observability signal deferred.

None of these are in scope for 246.1.
</deferred>
