    - New crate `ferro-orm` exposing the `GuardedUpdate<E>` builder — compiles to a single `UPDATE … WHERE …` SQL statement, replacing the hand-rolled `read → check → write` pattern wherever a column's value is conditionally mutated. The database engine's per-statement atomicity (SQLite serial writer, Postgres `READ COMMITTED`) is the correctness mechanism; `GuardedUpdate` adds the chainable surface and the rows-affected → `GuardedError` mapping on top.

    - `GuardedUpdate::exec_one(&conn)` — succeeds iff exactly one row matched; `0 → Err(NoRowsAffected)`, `>1 → Err(TooManyRows { affected })`. Default for race-free counter mutations.
    - `GuardedUpdate::exec_at_most_one(&conn)` — `Ok(true)` on 1 row, `Ok(false)` on 0 rows (predicate failure is a normal outcome), `Err(TooManyRows)` on >1 rows. For optimistic updates.
    - `GuardedError` — `NoRowsAffected | TooManyRows { affected } | EmptyUpdate | Db(#[from] DbErr)`. Display prefix `"guarded: …"`.
    - Targeted re-exports of the SeaORM symbols required by the public API (`EntityTrait`, `ColumnTrait`, `ConnectionTrait`, `IntoCondition`, `SimpleExpr`, `Value`, `DbErr`, `Expr`); no blanket `pub use sea_orm::*`.

<threat_model>
This plan touches release infrastructure and the publish process. The first-publish bootstrap is the only security-sensitive moment.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local terminal → crates.io | `cargo publish` carries a personal `publish-new`-scoped token; the token must not be persisted in the repo or piped through CI |
| repo → CI runner | publish.yml is executed by GH Actions with `CARGO_REGISTRY_TOKEN`; after the manual bootstrap, CI uses its `publish-update`-scoped token for subsequent versions |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-152-06-01 | I | `cargo publish` token leakage | mitigate | Bootstrap uses a personal `publish-new`-scoped token, run from the user's local terminal — never persisted in the repo, never piped through CI. The token is supplied on the command line via `--token <PERSONAL_PUBLISH_TOKEN>` and discarded after the command. Subsequent versions auto-publish via the CI token which has only `publish-update` scope (cannot create new crates). |
| T-152-06-02 | E | CI publishes a broken artifact | mitigate | The Task 1 pre-release gate (fmt + clippy + build + test + doc) MUST pass before Task 2 commits the CHANGELOG entry. If the gate fails, the plan aborts before the version-bump-equivalent step (here a no-op since Cargo.toml is not bumped). |
| T-152-06-03 | R | Mismatch between CHANGELOG version and actually-published version | accept | RESEARCH Open Question 1: the CI `check-version` job may auto-bump Cargo.toml on master push if the recorded version is already tagged. The published version may be one higher than the CHANGELOG records. This is acceptable for the initial release — the SUMMARY records the actually-published version and a future cleanup phase can backfill if desired. |
</threat_model>
