# Phase 82 Plan 02: E2E Integration Tests for ferro-api-mcp

**Full pipeline validation: Ferro app serves OpenAPI spec, ferro-api-mcp parses it, MCP tools discovered and CRUD operations executed against live data.**

## Performance

- **Duration:** 25 min
- **Tasks:** 2
- **Files modified:** 6
- **Tests added:** 3

## Accomplishments
- Test infrastructure with reusable helpers: port allocation, TCP polling, binary build caching, TestContext with async cleanup
- `test_openapi_spec_served`: validates OpenAPI JSON is served at /api/openapi.json with correct structure
- `test_mcp_tool_discovery`: connects ferro-api-mcp via TokioChildProcess, verifies at least 4 user-related MCP tools registered
- `test_mcp_crud_operations`: full CRUD cycle through MCP (create user, list users, show user, delete user)
- Fixed OpenAPI spec generation: path parameters now include schema field
- Fixed spec parser to accept OpenAPI 3.1.0 (generated by utoipa 5.x)
- Fixed route parameter naming to match handler variable names

1. **Task 1: Set up test infrastructure** - `1ff5e90` (test)

## Files Modified
- `ferro-api-mcp/Cargo.toml` - Added dev-dependencies (rmcp client, tokio, reqwest, serde_json)
- `ferro-api-mcp/tests/e2e.rs` - Full E2E test suite (3 tests, ~450 lines)
- `ferro-api-mcp/src/spec.rs` - Accept OpenAPI 3.1.x, updated version test
- `framework/src/api/openapi.rs` - Added schema to path parameters in OpenAPI spec generation
- `app/src/api/routes.rs` - Changed route params from :id to :user (match handler variables)
- `Cargo.lock` - Updated for new dev-dependencies

## Decisions Made
- OpenAPI 3.1.0 acceptance: utoipa 5.x only generates 3.1.0, rejecting it would break all generated specs
- Route param naming: Ferro's `#[handler]` macro extracts params by variable name (e.g., `user: users::Model` looks for `:user`), so routes must use `:user` not `:id`
- Schema on path params: openapiv3 crate requires `schema` field on parameters, without it parsing fails with "no variant of enum ParameterSchemaOrContent found"
- Pre-computed API key hash avoids adding sha2 as a dev-dependency

## Deviations from Plan

### Auto-fixed Issues

**1. [Blocking] OpenAPI 3.1.0 rejected by spec parser**
- **Found during:** Task 2 (test_mcp_tool_discovery)
- **Issue:** `parse_spec` required version starting with "3.0" but utoipa generates "3.1.0"
- **Fix:** Changed version check from `starts_with("3.0")` to `starts_with("3.")`
- **Files modified:** `ferro-api-mcp/src/spec.rs`
- **Verification:** Unit test updated, E2E tests pass

**2. [Blocking] Path parameters missing schema in OpenAPI spec**
- **Found during:** Task 2 (test_mcp_tool_discovery)
- **Issue:** openapiv3 requires ParameterSchemaOrContent but framework generated params without schema
- **Fix:** Added `.schema(Some(Object::with_type(Type::String)))` to ParameterBuilder
- **Files modified:** `framework/src/api/openapi.rs`
- **Verification:** Spec parses correctly, MCP tools registered

**3. [Blocking] Route parameters don't match handler variable names**
- **Found during:** Task 2 (test_mcp_crud_operations)
- **Issue:** Routes used `:id` but handler macro generates code that looks for param matching variable name `user`
- **Fix:** Changed routes from `:id` to `:user` in app/src/api/routes.rs
- **Files modified:** `app/src/api/routes.rs`
- **Verification:** Show and Delete operations return correct data
