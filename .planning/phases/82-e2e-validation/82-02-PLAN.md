<task type="auto">
  <name>Task 1: Set up test infrastructure</name>
  <files>ferro-api-mcp/Cargo.toml, ferro-api-mcp/tests/e2e.rs</files>
  <action>
    1. **Add dev-dependencies** to `ferro-api-mcp/Cargo.toml`:
       ```toml
       [dev-dependencies]
       rmcp = { version = "0.12", features = ["client", "transport-child-process"] }
       tokio = { version = "1", features = ["full"] }
       reqwest = { version = "0.12", features = ["json"] }
       serde_json = "1"
       ```
       Note: rmcp needs `client` + `transport-child-process` features for `TokioChildProcess` and `ServiceExt::serve()`. These are DIFFERENT from the `server` + `transport-io` features in the main dependencies.

    2. **Create `ferro-api-mcp/tests/e2e.rs`** with helper infrastructure:

       a. **`get_available_port()`**: Bind `TcpListener` to `127.0.0.1:0`, return the OS-assigned port. Release listener immediately.

       b. **`wait_for_port(port, max_wait)`**: Async function that polls `TcpStream::connect()` every 100ms until success or timeout. Use `tokio::time::timeout()` for the deadline. Return `bool`.

       c. **`ensure_binaries_built()`**: Use `std::sync::Once` to call `cargo build --bin app --bin ferro-api-mcp` exactly once across all tests. Assert build success. This avoids recompilation per test.

       d. **`hash_api_key(raw_key) -> String`**: SHA-256 hash of the raw key, hex-encoded. Use `sha2` crate (already a transitive dep via ferro framework) OR implement inline with `std::process::Command` calling `echo -n {key} | shasum -a 256`. Simpler approach: since the test spawns the app binary which links against ferro, we can compute the hash using the same algorithm. The hash is `hex(sha256(raw_key))`. Use the `sha2` crate as a dev-dependency, or just hardcode a known key/hash pair for the test.

       **Simplest approach for API key seeding:**
       - Use a KNOWN test API key value: `"ferro_test_0123456789abcdef0123456789abcdef"` (>16 chars so prefix extraction works).
       - Pre-compute its SHA-256 hash at compile time or use `sha2` dev-dep.
       - After migrations, INSERT directly into SQLite using `tokio::process::Command::new("sqlite3")`.

       e. **`TestContext` struct**: Holds port, db_path, server child process, and spec_url. Implements `Drop` (or async cleanup) to kill server and remove temp DB.

       f. **`setup_test_app() -> TestContext`**: Orchestrates the full setup:
          - Get available port
          - Create temp DB path (`/tmp/ferro_e2e_{port}.db`)
          - Set required env vars (DATABASE_URL, SERVER_PORT, SERVER_HOST, APP_NAME, APP_KEY, SESSION_DRIVER=cookie, CACHE_DRIVER=memory)
          - Run `target/debug/app db:migrate` with the env vars
          - Insert test API key into SQLite via `sqlite3` command
          - Spawn `target/debug/app serve --no-migrate` with env vars and `kill_on_drop(true)`
          - Wait for port ready (30s timeout)
          - Return TestContext

    **IMPORTANT env vars for the sample app:**
    - `DATABASE_URL=sqlite://{db_path}?mode=rwc`
    - `SERVER_PORT={port}`
    - `SERVER_HOST=127.0.0.1`
    - `APP_NAME=FerroTest`
    - `APP_KEY=test-key-for-e2e-validation-only`
    - `SESSION_DRIVER=cookie` (avoids needing Redis)
    - `CACHE_DRIVER=memory` (avoids needing Redis)

    **IMPORTANT pitfall avoidance (from research):**
    - Build binaries ONCE with `ensure_binaries_built()`, spawn from `target/debug/`
    - Use `kill_on_drop(true)` for automatic cleanup
    - Wait for TCP port, don't sleep
    - Each test gets its own SQLite file and port
  </action>

<task type="auto">
  <name>Task 2: Write E2E test cases</name>
  <files>ferro-api-mcp/tests/e2e.rs</files>
  <action>
    Add integration tests to `ferro-api-mcp/tests/e2e.rs` that validate the full pipeline. All tests use the `setup_test_app()` helper and connect via rmcp's `TokioChildProcess`.

    **Test 1: `test_openapi_spec_served`**
    - Setup test app
    - GET `http://127.0.0.1:{port}/api/openapi.json` with reqwest
    - Assert 200 status
    - Parse response as JSON
    - Assert `openapi` field exists (version string)
    - Assert `paths` object is non-empty
    - Assert at least one path starts with `/api/v1/users`

    **Test 2: `test_mcp_tool_discovery`**
    - Setup test app
    - Connect ferro-api-mcp via `TokioChildProcess`:
      ```rust
      let transport = TokioChildProcess::new(
          tokio::process::Command::new("target/debug/ferro-api-mcp")
              .args(["--spec-url", &spec_url, "--api-key", &test_api_key])
      ).unwrap();
      let service = ().serve(transport).await.unwrap();
      ```
    - Call `service.list_tools(Default::default()).await`
    - Assert tools list is non-empty
    - Assert at least these tool names exist (based on x-mcp-tool-name pattern): tools matching user CRUD operations (list, get/show, create/store, update, delete/destroy)
    - Shut down MCP service

    **Test 3: `test_mcp_crud_operations`**
    - Setup test app
    - Connect ferro-api-mcp
    - **Create**: Call store/create tool with `{"body": {"name": "Test User", "email": "test@example.com", "password": "secret123"}}`. Assert response contains created user data.
    - **List**: Call list/index tool with `{"page": "1"}`. Assert response is not an error. Assert response contains data (may be empty array or contain the created user).
    - **Show**: If create returned an ID, call show tool with the ID. Assert response contains the user data.
    - **Delete**: Call destroy/delete tool with the ID. Assert success response.

    **For each tool call**, use:
    ```rust
    service.call_tool(CallToolRequestParam {
        name: "tool_name".into(),
        arguments: Some(serde_json::json!({...}).as_object().unwrap().clone()),
    }).await
    ```

    **Error handling**: Wrap assertions with descriptive messages. If a tool call returns error content, include the error text in the assertion message for debugging.

    **Test attribute**: Use `#[tokio::test]` with timeout:
    ```rust
    #[tokio::test(flavor = "multi_thread")]
    async fn test_name() { ... }
    ```

    **Cleanup**: Each test cleans up via TestContext's cleanup method (kill server, remove DB file).

    **IMPORTANT**: The exact tool names depend on what x-mcp-tool-name extensions the OpenAPI spec produces. The framework's `mcp_tool_name()` generates names like `list_users`, `get_user`, `create_user`, `update_user`, `delete_user`. If the sample app routes don't have x-mcp extensions, ferro-api-mcp falls back to `operationId` or `method_path` patterns. The test should be resilient — discover tools first, then find tools matching expected patterns.

    **Approach for tool name matching**: After `list_tools()`, search for tools whose names contain "user" (case-insensitive). Group by likely CRUD operation. This avoids hardcoding exact names that might differ based on route naming.
  </action>
