## TL;DR

Phase 127 made `ferro docker:init` / `do:init` work for single-binary projects with no runtime assets. Field-testing the scaffolders against **gestiscilo-it** (a real multi-bin Rust service with a web server, a background worker, runtime themes, and headless Chromium) surfaced a concrete set of gaps that block adoption on any non-trivial project. This document is a ready-to-promote scope for **Phase 131: Project-Aware Scaffolders** that closes those gaps and lets gestiscilo (and other real projects) actually adopt the scaffolder output.

## Proposed phase entry for ROADMAP.md

```markdown
### Phase 131: Project-Aware Scaffolders (multi-bin, copy_dirs, runtime_apt)

**Goal:** Make `ferro docker:init` and `ferro do:init` produce deployable artifacts for real multi-binary projects with runtime resource directories and runtime apt dependencies. Currently the scaffolders only handle the trivial single-bin / no-assets case and silently produce broken output for anything else — documented via the gestiscilo-it Phase 75 field test where the generated Dockerfile had a dead Node.js frontend stage, a single hardcoded binary path with the wrong name, no `COPY themes themes`, and no runtime Chromium. This phase reads `[[bin]]` entries and a new `[package.metadata.ferro.docker]` table (`copy_dirs`, `runtime_apt`) and emits correct multi-bin Dockerfiles and `.do/app.yaml` workers blocks. Also fixes `.do/app.yaml` identity preservation (region/name/repo) and the Phase 127 envs-from-`.env.example` path that silently no-ops in practice.

**Requirements:**
- P131-R1: `bin_detect` returns all `[[bin]]` entries, classified as web (first) or worker (rest); `[package.metadata.ferro.bins.<name>]` can override kind
- P131-R2: Dockerfile template emits one `COPY --from=builder /app/target/release/{bin}` line per detected bin
- P131-R3: `.do/app.yaml` template emits a `workers` entry per non-web bin with correct `run_command`
- P131-R4: `[package.metadata.ferro.docker].copy_dirs = [...]` emits `COPY {dir} {dir}` in runtime stage and whitelists them in `.dockerignore`
- P131-R5: `[package.metadata.ferro.docker].runtime_apt = [...]` emits a runtime-stage `apt-get install --no-install-recommends` layer with list cleanup
- P131-R6: `do:init --force` preserves existing `region`, `name`, and repo binding from the current `.do/app.yaml` instead of overwriting with defaults
- P131-R7: Phase 127's `.env.example` → envs block path actually fires (currently produces an empty envs block on gestiscilo — regression or missed edge case to investigate)
- P131-R8: Unconditional `health_check` block removed; opt-in via metadata OR route detection
- P131-R9: `ferro doctor` drift check re-runs the scaffolder in-memory and diffs against committed files (closes Phase 128 loop)

**Depends on:** Phase 130

**Acceptance test:** Running `ferro docker:init --force` and `ferro do:init --force` against the current gestiscilo-it `master` (commit `6f6d397` or later) produces Dockerfile and `.do/app.yaml` files **byte-identical** to the hand-maintained ones. When this holds, gestiscilo Phase 75 reopens and replaces the "Hand-maintained" warning headers with honest `# Generated by` headers.

**Plans:**
- [ ] 131-01-PLAN.md — Multi-bin detection + Dockerfile multi-COPY + `.do/app.yaml` workers block
- [ ] 131-02-PLAN.md — `[package.metadata.ferro.docker]` copy_dirs + runtime_apt in Dockerfile + `.dockerignore`
- [ ] 131-03-PLAN.md — `.do/app.yaml` identity preservation + envs-from-`.env.example` regression fix + health_check opt-in
- [ ] 131-04-PLAN.md — `ferro doctor` `docker_template_drift` check
- [ ] 131-05-PLAN.md — Field-test against gestiscilo-it byte-identity gate
```

## Concrete pitfalls (learned the hard way)

### 1. The installed binary lags the repo

gestiscilo ran `ferro 0.1.72`, built 2026-02-25. Phases 127 and 130 are checked off in the ferro roadmap but are not in the installed binary the field user is running. **When closing Phase 131, bump the ferro CLI version and cut a release so downstream projects can actually test the fix.** A closed ferro phase that doesn't ship is invisible to field users.

### 2. `--dry-run` doesn't exist in 0.1.72

Phase 127 added `--dry-run` per the roadmap note but the installed binary rejects the flag. This is either a missed build or the flag landed in a later phase. Confirm `--dry-run` actually ships before Phase 131 plans rely on it for drift detection. If it doesn't, add a `--dry-run` requirement to 131-04 explicitly.

### 3. Binary name mismatch bites silently

gestiscilo's `Cargo.toml` declares `[[bin]] name = "gestiscilo"` but the scaffolder emitted `/usr/local/bin/gestiscilo-it` (the *package name with dashes*). The Dockerfile then copied a binary that didn't exist and the container silently started with `CMD ["serve"]` against nothing. **Always read `name` from `[[bin]]`, never derive it from the package name or directory name.**

### 4. The Node.js frontend stage is dead weight for ferro-json-ui projects

The current Dockerfile template includes an unconditional Node.js build stage. Ferro's positioning (per `PROJECT.md`) includes `ferro-json-ui` as a first-class server-rendered UI path — projects that use it have zero JS/TS frontend. The Node stage should be opt-in: detect `frontend/package.json` or check a `[package.metadata.ferro.docker].frontend = "node" | "none"` hint. Default to `none` when there's no `package.json`.

### 5. `.do/app.yaml` identity fields are not scaffolder-owned

`region`, `name`, and the repo binding are **operational** — changing them mid-life breaks running deploys. Treat them as identity, not content. On `--force`, read the current file first and preserve these three fields (or fail loudly if the file is malformed and the user must delete it manually).

### 6. The Phase 127 envs block logic silently no-ops

gestiscilo has a populated `.env.example` with 14 app-level variables. Running `do:init --force` produced an empty `envs:` block instead of the expected SECRET-classified list. Either the parser fails on some `.env.example` syntax the field user's file contains (banner comments? blank lines?) or the code path just doesn't fire. **Reproducer lives in gestiscilo's `.env.example` committed at `6f6d397`** — load it into a 131 test fixture and reproduce before writing the fix.

## Target acceptance protocol

When Phase 131 is ready to verify, run this against the gestiscilo-it repo:

```bash
cd /path/to/gestiscilo-it
git checkout master
git rev-parse HEAD  # expect 6f6d397 or later

# Snapshot the hand-maintained files
cp Dockerfile /tmp/dockerfile.expected
cp .do/app.yaml /tmp/app.yaml.expected
cp .dockerignore /tmp/dockerignore.expected

# Run the new scaffolders
ferro docker:init --force
ferro do:init --force

# Byte-identity gate
diff /tmp/dockerfile.expected Dockerfile && echo "Dockerfile: PASS" || echo "Dockerfile: FAIL"
diff /tmp/app.yaml.expected .do/app.yaml && echo "app.yaml: PASS" || echo "app.yaml: FAIL"
diff /tmp/dockerignore.expected .dockerignore && echo ".dockerignore: PASS" || echo ".dockerignore: FAIL"

# Functional gate
cargo check
docker build .
```

All six checks must pass. Any diff means Phase 131 is incomplete — either the scaffolder is missing an expressivity axis, or gestiscilo's hand-maintained file contains an unjustified hand-edit that should be upstreamed to the template.

## Open questions for the planner

1. **Metadata table naming:** `[package.metadata.ferro.docker]` (TOML-idiomatic) vs `[ferro.docker]` (shorter but squats on the root table). Recommend the former.
2. **Worker classification default:** first `[[bin]]` = web, rest = workers. Safe default, but projects with multiple HTTP services (admin + public) will need the `[package.metadata.ferro.bins.<name>]` override. Should the override ship in 131-01 or defer to a follow-up?
3. **`runtime_apt` image size impact:** adding an apt layer to the runtime stage is the right move but costs image size. Worth a parallel `[package.metadata.ferro.docker].runtime_base = "debian-slim" | "distroless"` knob? Probably defer to a later phase — Phase 131 should stay focused.
4. **gestiscilo `.env.example` parser regression:** is the Phase 127 parser still the one in main, or was it rewritten? If rewritten, the regression may already be fixed and Phase 131 just needs a regression test. Check git log on the relevant module before scoping 131-03.
